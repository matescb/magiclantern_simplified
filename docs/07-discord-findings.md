## Top 10 highest-leverage clues

Ranked by (impact on the Digic-8 boot handoff) × (transfer_confidence). Several are corroborated across multiple channels.

1. **A COMPLETE, WORKING D8 handoff already exists on a sibling (EOS RP), with the exact sequence in its boot log.** RP reserves ML memory, patches `user_mem_size`, rewrites the init_task pointer from Canon `0xE0040225` to the ML-relocated `0x001A7545`, and jumps to relocated startup — verified on **real HW and QEMU**. `Platform_Specific_Development__rp.md:44444`.
   → *Action:* model our `boot-d78` handoff byte-for-byte on this sequence (patch `user_mem_size` in the cstart struct, rewrite the init_task pointer to ML's relocated address, jump). This is the single closest-to-done reference we have.

2. **The handoff hook is a `my_create_init_task` wrap-and-swap, and it must edit the cstart struct or Canon overwrites it.** Wrap Canon `create_init_task`, set `init_task=(uint32_t)my_init_task`, steal memory by bumping `dryos->sys_mem_start`. `Platform_Specific_Development__digic_x.md:7499` (corroborated `Dev_Stuff__ml-developers-general__A.md:77407`, `…__B.md:104412`).
   → *Action:* implement `my_create_init_task` on M50 II, patch the single relative `b.w` to cstart, adjust sys/user mem, chain to the real `create_init_task`. Do the memory reinit **inside** `my_create_init_task`, before Canon's `create_init_task` runs.

3. **The dual-core handshake is the real hazard: cpu1 parks in a WFI sinkhole until cpu0 sends software SGI `0xA` — do NOT force-wake cpu1.** cpu1 wakes on any IRQ but sleeps again unless it's the SW-generated `0xA` SGI; a global flags "cpu1 in wfi" and must not be tampered with. `Dev_Stuff__ml-developers-general__B.md:117090` (corroborated `Dev_Stuff__qemu.md:12170`, `Platform_Specific_Development__m50.md:20597`, `…__200d.md:5527`).
   → *Action:* ensure cpu0 issues SGI `0xA` (via `GICD.ICDSGIR`) and that the `0xA` handler ACKs/EOIs; an unacked `0xA` makes cpu1 spin forever — a hang signature.

4. **The concrete cause of the M50-family lockup: the enlarged autoexec load ERASES a buffer that overlaps the CamIF (three Xtensa cores) init region.** Early CamIF memory init runs in the normal path, but ML's bigger autoexec load+erase clobbers that same memory → lockup. `Platform_Specific_Development__m50.md:20298`.
   → *Action:* make ML's autoexec load/erase and `MARK_UNUSED`/`fixup_boot_memory` avoid the CamIF/fromutil-buffer region near `0x82000000`; this is the specific booby-trap that kills the M50 handoff.

5. **`fixup_boot_memory` == Canon's `reinit_autoexec_memory` / `init_camif`; but calling `Camif_Initialize()` the Digic-X way HARD-LOCKS on Digic 8.** The magic stub re-inits the lime/arima/kutatsu (Xtensa) CamIF regions; on the R (D8) calling it like DX hard-locks, yet without it the Kutatsu/IBIS core dies. `Platform_Specific_Development__digic_x.md:8210` + **critical gotcha** `Platform_Specific_Development__r.md:18146` (corroborated `…__r.md:17715`).
   → *Action:* treat CamIF re-init on M50 II as a two-sided trap — test both calling and not-calling `init_camif`, and watch the boot log for Kutatsu/secondary-core survival. Note M50 II likely has Arima(lens)+Shirahama(mecha) but **no Kutatsu** (no IBIS).

6. **The 200D handoff race is fully diagnosed AND has a working QEMU fix — cpu0 copies the secondary-core code ROM→RAM *after* it wakes cpu1, so cpu1 runs uninitialised code.** Root cause `…__200d.md:5807`; fix = pre-copy `0xe11c11c0→0xdf002800` and delay the cpu1 IPI by 50 ms (1 ms too short) `Platform_Specific_Development__200d.md:5817`.
   → *Action:* replicate on M50 II — pre-copy the secondary-core code region before releasing cpu1 (or delay the IPI); this is the crux of the handoff timing and directly informs both QEMU and real-HW behaviour.

7. **The M50 (mk I) is the direct donor and its exact HIJACK offsets + core boot stubs are already published.** M50 1.1.0: `cstart 0xE00400FC`, `create_init_task 0xE0143CFC`, `init_task 0xE0040224`, `bzero32 0xE0578D64`; HIJACK offsets `HIJACK_FIXBR_CREATE_ITASK 0xE00401AC`, `HIJACK_INSTR_MY_ITASK 0xE00401DC`. `Platform_Specific_Development__m50.md:7778` + `…__m50.md:8037` (near-identical to 200D per `…__rp.md:1572`).
   → *Action:* diff M50 1.1.0 addresses against our M50 II 1.0.1 ROM; HIJACK layout is stable within the family, so pattern-match to find K468 equivalents rather than deriving from scratch.

8. **The missing ARM GIC is the root cause of our QEMU early-hang, and a stock QEMU GICv2 can be dropped straight in.** "digic 8 doesn't go far, stuck in early init task … we don't emulate ARM interrupt controller (GIC) at all and this is needed for d7+." `Dev_Stuff__development_101.md:14142`; GICv2 registers match Cortex-A9 docs so QEMU's GIC can replace the hacks `Dev_Stuff__ml-developers-general__A.md:97827`; reference impl `eos_handle_intengine_gic` at qemu-eos `eos.c#L2629`, signal reg `c100010c` `…__A.md:117120`.
   → *Action:* wire a real GICv2 (or `eos_handle_intengine_gic`) over `0xC1000000–0xC100FFFF` in the M50mk2 model and make the per-CPU IAR return `0xA` for cpu1 — this unblocks cpu1 wake and, per `…__qemu.md:14483`, "solves a lot of D7+ issues right away."

9. **A named dev (bilal_fakhouri) is actively porting the MMU + SGI handlers to the ORIGINAL M50 in QEMU and is stuck at exactly our handoff step; the M50 SGI-handler const is known.** After the `phys_mem` line the missing next step on 200D is "Registered cpu1 wake handler"; needs `#define CONFIG_SGI_HANDLERS` and `DRYOS_SGI_HANDLERS_PTR`, which bilal found `= 0x402c` on M50 (same as 200D, by xref). `Dev_Stuff__qemu.md:16648` + `…__qemu.md:16663`.
   → *Action:* engage bilal_fakhouri (has M50 + M2 + R8 ports on a fork); check whether M50 II also uses `0x402c`, set `CONFIG_SGI_HANDLERS`, and reuse his M50 MMU/SGI work directly.

10. **Second-core start on older-style D8 is a two-word ROM poke, and cpu1 must be routed to `firmware_entry`, not `cstart`.** `MEM(0xBFE01FC8)=MAIN_FIRMWARE_ADDR` (the pointer cpu1 uses to run stage-2), `MEM(0xBFE01FC4)=0x10` magic (optional — R booted without it); in `copy_and_restart` dispatch cpu1 to `ROMBASEADDR+1`. `Platform_Specific_Development__m50.md:20356` + `Dev_Stuff__ml-developers-general__A.md:104412` (corroborated `…__A.md:103594`).
   → *Action:* use the older-style D8 path for M50 II (M50/R/RP/250D/M6II family), verify the `0xBFE01FC8` pointer target by xref, and make our `copy_and_restart` send cpu1 to `firmware_entry` (ROMBASEADDR+1), not `ml_cstart`.
