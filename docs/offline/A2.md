# A2 - EvfDevState state machine (M50 II 1.0.1)

## Question
Decode the EvfDevState matrix (0xE0BBE0F0), decide which (state,input) is the true once-per-frame
"readout done" event and whether our hook on input 6 / state 3 is right; find the EvfDev queue depth,
creator, overflow cause, whether work inside the hook can stall the queue, and the task + priority.

## Summary
1. `*(0x10108)` is **EvfDevState** (LiveViewDrive::EvfDevState.c, 15 inputs x 4 states). It is NOT the object
   M50 mk1 calls EVF_STATE. Input 6 / state 3 = `evfdevUpdateParam`, not a readout-done event.
2. The mk1-equivalent object exists on this ROM: **EvfState** (LiveView::EvfCapState.c), pointer `*(0x8E8C)`,
   matrix 0xE0B5050C, 17 inputs x 8 states. Input 5 = `evfReadOutDoneInterrupt`, input 4 = `evfSetParamInterrupt`,
   both self-transitions in states 3..6 - exactly the 5/5 and 4/5 cells ML generic code expects.
3. 6/3 is a per-frame proxy only: EvfState's `evfSetParamInterrupt` action posts EvfDev event 6. It fires at
   set-param time, in a different task, before readout of that frame.
4. EvfDev task: name "EvfDev", priority 0x0E, stack 0xC00, queue depth 200 (0xC8). EvfCap task (runs EvfState):
   "EvfCap", priority 0x0D (0x13 during init), stack 0xC00, queue 200.
5. Assert EvfDevState.c L:0x174 / L:0x21E = non-blocking TryPostEvent to the EvfDev queue failed. Our hook runs
   inside the EvfDev task, so any blocking work there directly stops queue drain. Static only; not runtime-proven.

## Observed (ROM addresses)

### Generic state-object / TaskClass plumbing
- CreateStateObject 0xE05BB31A(name, auto_seq, matrix, max_inputs, max_states): allocs 0x20; +0x00 magic `*(0xE0A6C4CC)`,
  +0x04 name, +0x08 auto_seq, +0x0C dispatcher 0xE05BB2B3, +0x10 matrix, +0x14 max_inputs, +0x18 max_states, +0x1C current_state.
- Dispatcher 0xE05BB2B2(self, obj, input, a3, a4): cell = matrix + (input*max_states + current_state)*8;
  cell = {next_state, action}. If action==0 returns 0 (no state change). Else writes next_state FIRST, then calls
  action(obj, a3, a4). (0xE05BB2EC..0xE05BB2FA)
- CreateTaskClass 0xE05B9E60(name, prio, stack, queue_len, handler): allocs 0x18; +0 magic `*(0xE0A6C4D0)`, +4 name,
  +8 alive, +0xC task id, +0x10 msg queue (msg_queue_create(name, queue_len)), +0x14 handler; task entry 0xE05B9E21.
- Task loop 0xE05B9E20: receive -> handler(msg[0], msg[1], msg[2], msg[3]) until alive==0.
- Message nodes come from ONE global pool shared by all TaskClass tasks: 0x600 (1536) nodes x 0x10 bytes at 0xBEE18,
  free-list head at 0x39B84, lazily initialised (0xE05B9EA0..0xE05B9EC8). Alloc 0xE05B9EEA, free 0xE05B9DB0.
- TryPostEvent 0xE05B9F9E(taskclass, obj, event, a3, a4): pool alloc; if pool empty prints
  "[TASK ERROR] TryPostEvent MsgQue OverFlow : Name = %s" and asserts System::Task.c L:0xE5; then
  msg_queue_post (non-blocking, 0xE05B55EE); on failure frees node and returns the error.
- PostEvent (blocking) 0xE05B9F10; queue count getter 0xE05BA078; SetPriority wrapper 0xE05BA0A6 -> 0xE05F4262.

### Source / logs
- src/state-object.c:225 hooks `EVF_STATE && input == 6 && old_state == 3` for CONFIG_M50mk2; lines 173, 227, 250 are
  the generic 5/5 (evfReadOutDoneInterrupt) and 4/5 (evfSetParamInterrupt) cells.
- research/bilal_M50_rawvideo/platform/M50.110/include/platform/state-object.h:4: EVF_STATE = `*(0x6cec)`.
- tools/mlserial/run/uart.jsonl: 96 lines "EvfDevState.c L:00000174" and 32 lines "L:0000021E" (ratio 3:1).

## Inferred
- mk1's EVF_STATE (0x6cec) is the EvfState/EvfCapState object, not EvfDevState: ML's hard-coded cell meanings match
  the EvfState matrix here cell for cell and do not exist in EvfDevState. Not verified against a mk1 ROM.
- Steady LV runs EvfState in state 5 and EvfDevState in state 3. Per frame, EvfCap handles Vd (posts EvfDev 8),
  SetParam (posts EvfDev 6) and ReadOutDone; EvfDev additionally gets event 13 from its own sync callback. So about
  3 EvfDev messages per frame, matching the 3:1 assert ratio seen in the UART log.
- With 200 slots and ~3 messages/frame, about 65 frames (~2 s at 30 fps) of EvfDev stall fills the queue. After that
  every post fails: L:0x174 for events from EvfCap, L:0x21E for event 13. That fits the "queue fills -> EvfDevState
  nullptr wedge" seen with the synchronous in-hook copy.
- Because the dispatcher writes next_state before calling the action and the hook wraps the dispatcher, time spent in
  the hook is time the EvfDev task is not receiving. A sleeping/blocking call in the hook is a direct stall.
- EvfCap (0x0D) is higher priority than EvfDev (0x0E); it keeps producing while EvfDev is busy.
- "nullptr" in ML's assert line is just the NULL expression string passed as r0=0 at 0xE069A696 / 0xE069A804.

## Unknown
- Which DryOS error msg_queue_post returned (full vs other); the assert is the same for any failure.
- Whether evfdevUpdateParam (6/3) is exactly once per frame in every video mode; other senders exist (mode change).
- Real interrupt source and phase of EvfState inputs 3/4/5 relative to the raw EDMAC completion on this body.
- What 0xE06F1684 (called by the input-13 action) does; identity of the callback registry 0xE06AFDFE.
- Whether hooking EvfState crashes ("EvfCap crash" history on other D8 bodies).

## Implications for raw video
- The vsync hook is on the wrong object for the generic ML assumptions. Candidate fix: define EVF_STATE as
  `*(struct state_object **)0x8E8C` and drop the M50mk2 special case so the generic 5/5 path is used. The
  `input == 4 && old_state == 5` ISO-override path then also lands on a real evfSetParamInterrupt.
- Whichever object is hooked, the CBR must not block: both tasks have a 200-deep non-blocking queue and Canon asserts
  when it is full. The frame copy/write belongs in a separate task, with the hook only signalling.
- The global TaskClass node pool (1536) is shared; a stuck EvfDev holds up to 200 nodes.

## Next hardware checks
1. `rd 0x8E8C` -> P. `rd P+4` should point to "EvfState" (0xE137558C); `rd P+0x10` = 0xE0B5050C; `rd P+0x14` = 0x11;
   `rd P+0x18` = 8; `rd P+0x1C` in LV: expect 5. Anything else -> the EvfState identification is wrong.
2. `rd 0x10108` -> Q; `rd Q+0x1C` in LV: expect 3; `rd Q+0x10` = 0xE0BBE0F0.
3. Statespy on P for 2 s in LV: expect inputs 3, 4, 5 each ~fps times in state 5. If 5/5 is ~fps, switch the hook.
4. Queue depth live: `rd 0x9B48` -> D; `rd D+8` -> TC; `call 0xE05BA079 TC` returns pending EvfDev messages
   (0 or near 0 when healthy; climbing toward 200 during recording = hook stalling the task). Same for EvfCap:
   `rd 0x554C` -> C; `rd C+8`; call 0xE05BA079.
5. `rd D+0x14` / `rd D+0x18` should read 0x0E; `rd C+0x14` = 0x0D, `rd C+0x18` = 0x13.
6. Pool health: `rd 0x39B84` (free-list head, non-zero when nodes remain).
7. During a failing recording, compare counts of L:0x174 vs L:0x21E; 3:1 confirms the per-frame message model.
