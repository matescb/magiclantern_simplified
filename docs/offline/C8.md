# C8 — mlv_lite on walkback-milestone: what to do with it

Offline analysis, 2026-11-16. No camera attached; nothing here proves behaviour on hardware.

## Recommendation

**Drop `mlv_lite` from `platform/M50mk2.101/modules.included` for now and keep `raw_vidx` as the only recorder.**
Keep a cleaned-up `mlv_lite` in the tree as an A/B candidate, staged by hand, never loaded together with `raw_vidx`.

Reasons:

- **raw_vidx is closer to working on this body.** It has written real sensor data to the card (boot 212, 2026-07-19: 5 sync copies, 13.4 MB, `worker: FIO_WriteFile done`; 3 such lines in `uart.jsonl`, last 2026-07-19 10:56 UTC). Its three body-specific fixes are already module-only and on this branch: source read from `UNCACHEABLE(raw_info.buffer)`, `raw_lv_redirect_edmac` off by default, synchronous in-module copy.
- **mlv_lite on this branch lacks the equivalent fixes and still does the three things known to fail here:**
  - it reads the double buffer the D8 redirect never fills (`mlv_lite.c:1586`), so frames decode to noise and black;
  - it calls `raw_lv_redirect_edmac()` every vsync (`mlv_lite.c:2961`), the call raw_vidx had to disable to stop the MvRawPro/RawPro/LvJob storm;
  - it marks a slot full before the asynchronous copy has finished (`mlv_lite.c:2841`).
- **Its last hardware result is older and weaker.** `uart.jsonl` has 11 `framewrite-ok` lines for `B:/M50TEST.MLV`, the last on 2026-07-18 20:38 UTC, all from uncommitted builds; the project then pivoted to raw_vidx the same day (memory `ml-m50ii-port-status.md`).
- **It still performs diagnostic card writes on every record start** (4 MB of RAM into the output file, a `B:/PROBE2.TXT` file).
- **`m50mk2-port` already made this choice**: its `modules.included` is `bench, file_man, raw_vidx, wifidep`.
- Making mlv_lite primary would mean redoing in a 4800-line module what raw_vidx already has in about 2000 lines.

## Results

### Build and core-symbol check

- Platform build at `e32ef27ea`: rc=0. `magiclantern.zip` built from a clean staging directory contains `bench.mo`, `file_man.mo`, `raw_vidx.mo` only.
- Stripped `mlv_lite.mo`: builds with no warnings (73,692 bytes, md5 `ba62e9fa…`), with the workaround switch at both 1 and 0. Its 174 undefined symbols all resolve against the core `.sym` (0 missing). It no longer imports `m50ii_uart_str`.
- **Core `.sym` versus the main checkout build: identical, but only when the branch name has the same length.**

```
# built on a temporary 18-character branch name (offline/C8-sym-chk, since deleted)
SYM identical to MAIN CHECKOUT build (18-char branch name)
d2f46ba5e091fa02d53a8aae9969442f  wt/C8/.../build/M50mk2_101.sym
d2f46ba5e091fa02d53a8aae9969442f  magiclantern_simplified/.../build/M50mk2_101.sym
```

```
# built on branch offline/C8 (10 characters): pristine a10b16c23 and e32ef27ea give the same .sym,
# but it differs from the main checkout in 53 symbols, each moved by -8 bytes
< 000f357e build_version        > 000f3576 build_version
...
< 000fd658 task_create_zebra_init
```

Cause: `platform/Makefile:610` writes `build_id[] = "<hash> <branch>"` via `build_tools/git_summary.py`. "walkback-milestone" is 18 characters, "offline/C8" is 10, so everything between `build_id` (0xf3561) and `task_create_zebra_init` (0xfd658) moves. Code addresses and `.data`/`.bss` do not move (`handle_module_keys` 0xcd515 and `raw_info` 0x104434 are the same in both).

**This affects every offline worktree in this sprint**: a core built on `offline/<ID>` is not symbol-identical to one built on `walkback-milestone`, even with zero source changes. Given the project's symbol-shift boot-crash history, any build meant for the camera should be made on a branch whose name is 18 characters long, or on `walkback-milestone` itself.

Two other observations on the main checkout build:

- Its `build_id` is `3ccf499dc walkback-milestone`: the binaries in `platform/M50mk2.101/build` were built before commit `a10b16c23` existed.
- Its `raw_vidx.mo` (md5 `0715abdd…`) differs from one built from `a10b16c23` (md5 `051c9d77…`), same size 22,272 bytes. I did not check whether the difference is only embedded metadata.

Not M50 II hacks, but relevant:

- **`hack_liveview()` (`mlv_lite.c:2162`, called at 3633 with 0 and 4118 with 1) is unmodified upstream code.**
  - With `raw.small.hacks` = 1 (the default) it disables Canon's front buffer and calls `aewb_enableaewb`, `lv_ae`, `lv_wb` by name. None of those three names exists as a string in `gang100.bin` or `gang200.bin`, so on this firmware the calls most likely fail to resolve and do nothing.
  - The dialog-refresh-timer patch address is 0 for this body, so that patch is skipped.
  - It was the top suspect for the DAF/EIS storm, then ruled out on hardware by setting `raw.small.hacks` to 0 with the storm unchanged (memory `ml-m50ii-port-status.md`). docs/32:242 also retracts the earlier "writes DIGIC 4/5 registers" claim.
  - `hack_liveview_vsync()` (2102) writes EDMAC registers only when the preview mode is "Hacked" (`raw.preview` = 3, not the default). That path assumes the DIGIC 4/5 register layout and should not be used on this body.
- `mlv_lite.c:4752` (warm-up write from 0x40000000) is upstream and off by default.
- `mlv_lite.c:1576` `printf("No memory suites.")` is upstream; docs/32 records 317 repeats per recording with SRM off. Not addressed.

### Fixes that exist only on m50mk2-port (`fa0834b40`)

`git diff walkback-milestone..m50mk2-port -- modules/raw_video/mlv_lite` is 39 lines, two fixes:

1. **Single buffering** (`setup_buffers`, around line 1586): for uncompressed output, `fullsize_buffers[0] = UNCACHEABLE(raw_info.buffer)` regardless of size. Before, the copy read a separate allocation the redirect never fills; decoded frames went from about 100 active rows to 943 of 1130 (memory note, 2026-07-18).
2. **Copy completion** (`edmac_cbr_w`, `compress_task`, around lines 2700–2865): new `edmac_pending_slot`; `SLOT_FULL` is set in the write-completion callback, not right after starting the copy. `process_frame` refuses a new frame while `edmac_active` is set, so one pending slot is enough.

Both are ported in `e32ef27ea` (the patch applied cleanly). With fix 2, if the core's asynchronous copy never calls back — which is what raw_vidx saw on this body before switching to its own synchronous copy — mlv_lite will write no frames and stop with "EDMAC timeout" on the second frame. Without it, it writes half-copied frames.

Still missing on both branches: mlv_lite calls `raw_lv_redirect_edmac()` unconditionally at line 2961.

### The record-key conflict

Who registers what:

- `mlv_lite.c:4786`: `MODULE_CBR(CBR_KEYPRESS_RAW, raw_rec_keypress_cbr_raw, 0)` → `raw_rec_keypress_cbr()` (4355).
- `raw_vidx/event_pusher.c:499`: `MODULE_CBR(CBR_KEYPRESS, raw_vid_keypress_cbr, 0)` (226).
- Both act on `MODULE_KEY_REC` or `MODULE_KEY_LV` (mlv_lite 4376, raw_vidx 260).

How a press arrives: the physical record button is not bound (`m50ii_rec_keycode = 0xFF`, `src/gui.c:249`). In practice the press is injected over serial as `handle_module_keys(&{param=BGMT_REC})`.

Order: `handle_module_keys()` (`src/module.c:1283`) walks `module_list[]` in index order and returns at the first handler that returns 0. The index order is the order `FIO_FindFirstEx` lists `ML/MODULES/` (`module.c:549`), that is, FAT directory-entry order. It is not alphabetical by rule and changes when a `.mo` is deleted and re-copied. A module is loaded only if `ML/SETTINGS/<name>.en` exists.

What one press does, with both modules loaded:

| Situation | Result |
|---|---|
| raw_vidx listed first | raw_vidx consumes every record press in movie mode (it returns 0 in all states). mlv_lite never sees the key. |
| mlv_lite first, `raw.video.enabled` = 0 (default) | mlv_lite returns 1 at once (4357); raw_vidx starts or stops. mlv_lite is dead weight: 75 KB of module, a vsync callback, a shoot-task callback, a display filter. |
| mlv_lite first, enabled, LiveView display not idle | mlv_lite returns 1 at 4364 (`!liveview_display_idle() && !RECORDING_RAW`); raw_vidx handles the press. On this body `liveview_display_idle()` returned 0 in the injection tests, so this is the common case. |
| mlv_lite first, enabled, LiveView idle | mlv_lite calls `raw_start_stop()` and returns 0; raw_vidx never sees the key. |
| mlv_lite first, enabled, idle state changes between two presses | Press 1 goes to raw_vidx (not idle) and starts it. Press 2 arrives when idle: mlv_lite is not recording, so it starts too, and raw_vidx never gets its stop. Two recorders run at once on the same raw stream and card. |

Independently of the key, with `raw.video.enabled` = 1 mlv_lite keeps raw LiveView requested in movie mode (`raw_lv_request_update`, 1794) and its vsync callback calls `raw_lv_redirect_edmac` while it records; raw_vidx's own vsync callback runs in parallel.

## Limitations

- Nothing was run on the camera or in QEMU. "Builds and links" is the only verified property of the stripped mlv_lite.
- The "still needed?" column rests on docs/32, docs/35 and the memory notes; items 2 and 11 are marked unverified for that reason and left on by default.
- The key-conflict table is from reading the code. The FAT listing order on the real card was not inspected (no mtools installed; the card is not attached).
- Dropping a name from `modules.included` only changes the zip. A `mlv_lite.mo` or `MLV_LITE.EN` already on the card stays there and keeps loading.
- The build does not clean `build/zip`: an incremental build after the change still packed the stale `mlv_lite.mo` until the staging directory was removed.
- `git_summary.py` makes the core layout depend on the branch name (see above).
