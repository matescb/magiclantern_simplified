# G1 - Module-only frame-sync sources and an event-pool watchdog for raw_vidx

Date: 2026-11-16. Offline. No camera attached. **Nothing here has run on the camera.** The host test
proves control flow against fake Canon objects; the ROM facts are static disassembly; whether the two
new sync sources are safe, fire once per frame, or mark a complete frame is open until the hardware
tests in the last section have been run.

## Goal

F1 named two per-frame signals that may be better than the core's vsync hook (state object
`*(0x10108)`, input 6 in state 3) and showed that both can be installed from module code. F4 showed
that the record-time crash family ends in the exhaustion of Canon's event-container pool and asked
for a watchdog. This task turns both into module code (`modules/raw_video/raw_vidx` only), behind
runtime toggles, with a host test, a build that passes the symbol gate, and a staged card directory.

Terms:
- **State object**: Canon structure holding a transition matrix; the word at +0x0C is the dispatch
  function pointer that ML-style hooks replace (F1).
- **EvfState**: the state object at `*(0x8E8C)`; its input 5 is `evfReadOutDoneInterrupt` (A2, F1).
- **Mem1Path slot**: RAM word 0x1029C, the callback Canon calls when the EDMAC channel-3 write of
  the LiveView raw frame completes; its argument is the word at 0x102A0 (A1, F1).
- **Event container**: 16-byte node carrying one posted event; all Canon tasks share one pool of
  1536 (F4).
- **Signal**: one invocation of a hook that the module counts as "a frame happened".

## ROM facts re-checked for this task (observed, static)

- Pool node layout. Init loop 0xE05B9EA0-0xE05B9EC8: head `[0x39B80+4]` = 0xBEE18 (literal at
  0xE05BA0C4), then `str r2,[r0]` with r2 = r0 + 0x10 for 0x5FF rounds and a final `str 0,[r2]`.
  So a free node's word 0 is the address of the next free node, nodes are 0x10 bytes, there are
  0x600 of them (0xBEE18..0xC4E17) and the last link is 0. Pop 0xE05B9EEA: `r0=[0x39B84]; if r0:
  [0x39B84]=[r0]` (0xE05B9EF6-0xE05B9EFC). Push 0xE05B9DB0: `[node]=[0x39B84]; [0x39B84]=node`
  (0xE05B9DBE-0xE05B9DC2). Both call the lock 0xE021B8F0 on 0x39B80 first and restore CPSR after.
  This matches F4 section 3.1.
- EvfState identity words. ROM word 0xE0B50508 (matrix - 4) = 0xE137558C, which is the string
  "EvfState"; literal 0xE06EF038 = 0xE0B5050C (matrix); ROM word 0xE0A6C4CC = 0xE13731D8, which is
  the string "StateObject" - the value Canon's dispatch wrapper 0xE05BB298 compares object +0
  against (F1). Row 5 of the matrix: states 3..6 all hold action 0xE06EF733, states 2 and 7 hold
  0xE06F0355, states 0 and 1 hold NULL (matches F1's table).
- Mem1Path. 0xE0753D9C: `r1=[0x10238+0x64]; if r1: r0=[0x10238+0x68]; bx r1`. 0xE06AD6EE loads
  0xE06AD51B (literal 0xE06AD8B0) and calls the setter 0xE07541A4.

Not re-checked here, taken from the reports: the stock dispatcher value 0xE05BB2B3 and the object
field offsets (F1), the task that runs EvfState (EvfCap, priority 0x0D; F1, A2), the context of the
Mem1Path callback (unknown; F1).

## Toggles

All are `int` globals of the module, set over the serial shell with `wr &<name> <value>` and read
with `rd &<name>` (the shell resolves module symbols; if it does not in a given build, take the
address from the module load log). They are read when a recording starts unless noted.

| Toggle | Default | Default = behaviour of `offline-plan-step1`? | Meaning |
|---|---|---|---|
| `rvx_sync_src` | 0 | yes | 0 = the core's vsync hook drives the recording. 1 = module hook on EvfState input 5. 2 = module chain on the Mem1Path slot. Any other value is refused |
| `rvx_pool_watch` | **1** | **no** (see below) | 0 = off, the pool is never read. 1 = measure, and end the recording when the free level falls below the threshold. 2 = measure only |
| `rvx_pool_stop_below` | 256 | n/a | stop threshold in free containers (F4 section 7, rule 5) |
| `rvx_pool_period` | 8 | n/a | one measurement every N frames handled by the worker (read per frame) |
| `rvx_pool_walk_max` | 1536 | n/a | upper bound of one walk, clamped to the pool size |

Firmware constants live in the struct `rvx_sync_cfg` (`rvx_sync.c`), not in `#define`s, so the host
test can substitute fakes. On the camera a wrong constant can be corrected with `wr` without a
rebuild; nobody should do that casually.

Telemetry (`rd &<name>`; reset at each recording start unless noted):

| Name | Meaning |
|---|---|
| `rvx_sync_active` | source in use by the current recording: 0, 1 or 2. 0 after a refused install |
| `rvx_sync_ticks` | signals counted in Canon's context |
| `rvx_sync_core_ignored` | core vsync callbacks ignored while source 1 or 2 was active. Together with `rvx_sync_ticks` this gives the rate of two sources from one recording |
| `rvx_sync_missed` | signals that arrived before the `rvx_sync` task had handled the previous one |
| `rvx_sync_last_err`, `rvx_sync_last_val` | reason code (`RVX_SYNC_E_*` in `rvx_sync.h`) and the offending value of the last refusal or failed restore |
| `rvx_sync_refused`, `rvx_sync_restore_fail`, `rvx_sync_silent` | counts since boot: refused installs, restores that found a foreign pointer, recordings stopped because the source went silent |
| `rvx_pool_free_start`, `rvx_pool_free_min`, `rvx_pool_free_last` | free containers at start, lowest and latest measurement |
| `rvx_pool_checks` | measurements in this recording |
| `rvx_pool_armed` | 1 = the watchdog may stop this recording |
| `rvx_pool_tripped` | 0, or 1 + the level at which the watchdog stopped the recording |

The stop summary on the UART prints the pool numbers (when `rvx_pool_watch` is not 0) and the sync
numbers (when a source other than 0 was used or an error code is set).

### What changed with every toggle at its default

1. `rvx_pool_watch = 1`. At start one walk of the free list, then one walk every 8 frames from the
   worker task: at most 1536 dependent loads from 24 KiB of RAM, no write, no lock, no interrupt
   masking, no Canon function called. Two UART lines more at start (level) and four at stop. The
   watchdog can end a recording, which the previous build could not do; it arms only if the level
   measured at start is at least twice the threshold (512), so a wrong address or layout (walk
   returns 0 or a small number) cannot stop every recording. I judged this "read-only and cheap"
   as the task required for default-on; `wr &rvx_pool_watch 0` restores the old behaviour exactly.
2. The core's vsync callback now tests one global (`rvx_sync_active`) before doing what it did.
3. Nothing else: with `rvx_sync_src = 0` no semaphore and no task are created, no Canon pointer is
   read or written, and `cli()` is never called (host test `g1_defaults`).

## Design

### Common part of sources 1 and 2

- The hook function in Canon's context does: one increment of `rvx_sync_ticks`, one
  `give_semaphore`, and the call of Canon's original function. No copy, no UART, no allocation, no
  queue post, no wait (`rvx_sync.c`, `rvx_evf_spy`, `rvx_mem1_tramp`).
- A module task `rvx_sync` (priority 0x10, stack 0x1000, created on the first use of source 1 or 2)
  waits on that semaphore and runs `rvx_frame_tick()`, the unchanged body of the former vsync
  callback (take an event slot, fill it, post it to the worker's queue). Priority 0x10 is one
  above the worker (0x11), so events keep being queued or dropped while the worker copies, as they
  are today from the EvfDev task (0x0E). The task does no bulk work; F4 rule 2 allows a task that
  only blocks on a queue to sit above 0x15.
- While `rvx_sync_active` is non-zero the core's vsync callback returns at once, so the recording
  has exactly one source.
- Install is the last step of a start that can no longer fail (`worker.c`, just before
  `recording_state = ACTIVE`), so no start-failure path has a hook to undo. Removal is the first
  step of the stop (`worker.c`, right after `stopping = 1`), before any card I/O and before
  `raw_lv_release()`. Every way a recording ends goes through that stop: REC key, burst complete,
  window does not fit, pool watchdog, silent source.
- Every write of a Canon pointer is a compare-and-store with interrupts masked (`cli()`/`sei()`):
  the word is written only if it still holds the expected stock value, and restored only if it
  still holds the module's function.
- A refused install writes nothing, prints `[RVX] sync: REFUSED, nothing written, using the core
  vsync hook: <reason>` and the value read, sets `rvx_sync_last_err`, and the recording proceeds on
  source 0. I chose fall-back over aborting the start because aborting needs the whole start
  unwound; the price is that an A/B run must check `rvx_sync_active` (or the UART line) to know
  which source really ran.
- If the hook is in place but no signal arrives for 2 s (4 waits of 500 ms), the `rvx_sync` task
  requests a normal stop and reports it. This is the only detection of a Mem1Path slot that Canon
  rewrote during the recording.

### Source 1: EvfState input 5

Validation before anything is written, each with its own error code: `*(0x8E8C)` non-NULL,
word-aligned and inside 0x1000..0x40000000; object +0x00 = 0xE13731D8 ("StateObject"); +0x04 =
0xE137558C ("EvfState"); +0x10 = 0xE0B5050C; +0x14 = 0x11 and +0x18 = 8; +0x1C (current state)
below 8; +0x0C = 0xE05BB2B3. The spy reads the state before calling Canon's dispatcher and signals
after it returned, when `input == 5` and the old state was 3..6 (the four states that share action
0xE06EF733). Nested dispatches inside that action (F1) pass through with other inputs.

Restore: if `*(0x8E8C)` still is the object that was hooked and its +0x0C still is the spy, the
stock dispatcher is written back. Otherwise (the serial `statespy` chained on top, or Canon made a
new object) nothing is written, `rvx_sync_restore_fail` is incremented, and the spy stays behind as
a pass-through that gives no semaphore; the module is never unloaded, so the function stays valid.
A later start finds its own spy at +0x0C and re-uses it.

### Source 2: Mem1Path write-complete chain

Validation: the slot must hold exactly 0xE06AD51B. 0 (raw path not set up; Canon clears the slot at
0xE07541AC) and any other value are refused. The install happens after `raw_lv_request()` and the
raw-job wait, when Canon has programmed the path. Only the callback word is written; the argument
word 0x102A0 is never touched. The trampoline signals first and then calls 0xE06AD51B with the
argument it was given.

Restore: if the slot still holds the trampoline, 0xE06AD51B is written back. If Canon rewrote or
cleared it, it is left as found and reported; a stale callback is never written back.

### Pool watchdog

`rvx_pool_free(limit)` follows the list from the head word 0x39B84 and counts nodes until the limit,
a NULL, or a pointer that is outside 0xBEE18..0xC4E18 or not on a 16-byte node boundary.

Why Canon's lock is not taken: the lock function 0xE021B8F0 masks interrupts and spins on the word
0x39B80. Holding it for a 1536-node walk would keep every `TryPostEvent` in the system, including
those in interrupt handlers on the other core, spinning with interrupts off for the length of the
walk; and calling it from a module adds an unverified call into Canon code. The lock-free walk can
only miscount: every pointer is range-checked before it is followed and the step count is bounded,
so it cannot leave the pool or loop. A node popped during the walk carries event data in word 0,
which normally ends the walk early (reading too low). A low reading is therefore repeated twice and
the highest of the three is used.

The check runs in the worker task, once per `rvx_pool_period` frames, before the frame is copied.
When an armed watchdog reads below the threshold, the frame is not copied, the vsync side is
blocked, and the worker performs its normal stop: sync hook removed, buffers written, header
finalised, file closed, `raw_lv_release()`. The level goes to `rvx_pool_tripped` and to the UART.

## Left out, and why

- No refusal to start on a low pool (F4 suggests 1024). The idle level is unknown (F4 section 6);
  a wrong guess would block every recording. The start level is measured and printed instead.
- No "drop frames below 512" stage, no EvfDev queue-occupancy poll through 0xE05BA078, and the
  logger notify gate `[0x5158]` (F4 rule 6) is not touched. Each needs a hardware number or calls
  Canon code; the task asked for a read-only check.
- The watchdog only runs when the worker handles a frame. If frames stop arriving, or the worker is
  blocked in a long card write, nothing measures the pool.
- The hook hygiene of the core's vsync path is unchanged: with source 0 `rvx_frame_tick()` still
  takes a semaphore and prints in the EvfDev task (C12 "left out"). Sources 1 and 2 are the first
  configuration in which Canon's context does only a count and a semaphore give.
- The sidecar file format (`.RVI`, C12) is unchanged; the new numbers are UART and `rd` only.
- The `rvx_sync` task and its semaphore are never deleted once created.
- Re-checking the Mem1Path slot on a LiveView restart (F1, alternative B step 4) is reduced to the
  2 s silence stop; a recording does not survive a LiveView restart in any case.

## Known weak points (inferred, not tested)

- `cli()` masks interrupts on the calling CPU only. If Canon writes the same word from the other
  core inside the few instructions between compare and store, the compare-and-store is not atomic.
  The Mem1Path setter runs at LiveView start, not per frame, so the window matters only if a mode
  change coincides with REC.
- Source 2 runs `give_semaphore` in whatever context Canon calls the channel-3 callback from. F1
  argues this is legal because Canon's own callback gives a semaphore there (0xE06AD418); the
  context itself is unknown.
- At stop, the `rvx_sync` task may be inside `rvx_frame_tick()` when the hook is removed. It is
  above the worker in priority and does not block except on the event-slot semaphore, so the
  window is small; the core's vsync callback stays gated until the recording is INACTIVE, so the
  two never run the body at the same time unless that window is hit.
- Source 1 adds work to the EvfCap task (priority 0x0D), which older notes associate with a crash
  on other DIGIC 8 bodies (`platform/M50mk2.101/internals.h:38-41`, cited in F1).
- With sources 1 and 2 the per-frame work moves from the EvfDev task (0x0E) to a task at 0x10.
  Frames can therefore be queued slightly later than today; `rvx_sync_missed` counts signals that
  overtook the task.
