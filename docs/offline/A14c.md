# A14c - Porting candidates and unverified constants (M50 II 1.0.1)

## Question
(1) Locate on the M50 II ROM the functions other DIGIC 7/8 ports stub but `platform/M50mk2.101/stubs.S` lacks and that matter for raw video.
(2) Re-derive the constants `platform/M50mk2.101/consts.h` marks as guessed / copied / wrong.

## Summary
- Found with high confidence: debug_assert, dm_set_print_level, dm_set_store_level, DeleteResLockEntry, _LoadCalendarFromRTC (real RTC read, arg order differs from 200D/R), _turn_on_display/_turn_off_display, GUI_ChangeMode (confirms the commented stub).
- NEW DEFECT CANDIDATE: stubs.S `LockEngineResources` = 0xE05BE8A6 is a non-blocking try-lock sibling with zero callers in ROM; the function at the reference-port delta (Create+0x1E8) is 0xE05BE6A6 (105 callers, blocks on contention).
- Constants: LV_OVERLAYS_MODE should be MEM(0x15998) (0x13CC8 is an mk1 value, not present in this ROM); DISPLAY_IS_ON candidate = *(int*)0xAC64; CURRENT_GUI_MODE 0x7EC0 and GMT_NFUNCS 7 confirmed; LVAE_STRUCT 0x75094 and LVAE_ISO_STRUCT 0x8e660 are mk1 values that occur nowhere in this ROM (wrong).
- GUI request modes on this body are composite 32-bit values (class<<12 | id, e.g. 0x2002, 0x4035), so GUIMODE_PLAY=2 / GUIMODE_MENU=3 / 0x63 cannot match CURRENT_GUI_MODE as written.
- Not found statically (no string anchor in this ROM): get_sensor_vsize/accumh, set_rec_mode, get_max_millis_for_mov, dma_memcpy, mem_to_mem_edmac_copy, mpu_send/mpu_recv, HALFSHUTTER_PRESSED, absolute YUV422_LV_BUFFER bases.

## Observed
All addresses ROM0 (gang100.bin), Thumb. Tools: tools/romdis.py, tools/stubfind, plus a scratch ADR/BL reference index (16-bit/32-bit `adr` targets, BL/B.W targets, aligned literal words). "callers" = direct BL/B.W count from that index (indirect calls not counted).

## Inferred
- ML's `LockEngineResources(mem2mem_lock)` in edmac-d8.c:222 currently calls the try-lock sibling. If the engine resources are busy it returns 0xD immediately and the caller (which ignores the result) continues with the lock NOT held, later calling UnLockEngineResources on a non-held entry. The reference ports (bilal M50 mk1, SX740, R, 200D) all stub the Create+0x1E8 blocking function. Whether this contributes to the intermittent MvRawPro storm is not shown by static analysis; docs/32 notes Canon's EIS sees "0xd engine busy", which is the same code this sibling returns.
- `_LoadCalendarFromRTC(tm,0,0,16)` as written for 200D/R would be wrong here even with the right address: tm must be in r3. Calling the thunk 0xE0608794 as `LoadCalendarFromRTC(tm)` (or 0xE0607F62 as `(0,0x10,0,tm)`) is the equivalent. It blocks up to 1 s on a semaphore and asserts on timeout, so task context only, after RTC init ([0x48D0] != 0).
- DISPLAY_IS_ON = `(*(int*)0xAC64)` by analogy with R.180 (0x9fa0) / SX740 (0x9930), which were found with the same string.
- GUIMODE_PLAY is probably 0x2002 (class 2, id 2; SetGUIRequestMode special-cases exactly 0x2002) and menu probably class 3; PLAY_MODE/MENU_MODE macros comparing CURRENT_GUI_MODE with 2/3 are then never true. Unverified.
- LVAE and ISO structs live in the 0x0224xxxx RAM-code module's data and must be re-read from the live handlers.

Candidate neighbourhoods only: 'IMAGER_SetAccumH' @0xE06ACDAC, 'VSizeSetting ...' @0xE06C6DA0, 'RecMode:' @0xE0150B80, '%s%s uiMaxTime MaxOver(%d to 30)' @0xE023FD1C.

- Whether 0xE05BE8A6 has indirect callers (none found as literal).

## Implications for raw video
- Highest value: switch the LockEngineResources stub to 0xE05BE6A6 (module-visible symbol; note the project rule that core rebuilds shift symbols - plan it with the next deliberate core build) or at least log the return value of the current call. A returned 0xD today means mem2mem runs without owning resources 0x100AD/0x100BB.
- DeleteResLockEntry 0xE05BE5A2 allows edmac_memcpy_res_lock() to stop leaking one ResLock entry per recording (it calls CreateResLockEntry on every lock).
- dm_set_store_level / dm_set_print_level give per-class Canon debug-log control over serial (e.g. raise class 0x8B RTC, 0x3C DISP, 0x82 GUI, or the Evf/MvRawPro classes) without a rebuild.
- LV_OVERLAYS_MODE = MEM(0x15998) fixes ML's "is LV clean / which overlay page" logic that mlv_lite/raw_vidx preview code depends on.
- Real RTC read gives correct MLV file timestamps (RTCI block) instead of the 2026-01-01 sentinel.
- LVAE_* constants are stale mk1 values: any ML code touching CONTROL_BV / LVAE_DISP_GAIN (exposure override, ExpSim) writes into unrelated RAM at 0x75094+; keep those features disabled.

## Next hardware checks
Serial-harness style (rd/md = read, call = call function):
1. Lock variant: `call 0xE05BE8A6 <mem2mem_lock>` is what ML does now - instead log r0 of the existing call during a recording start (expect 0 = held, 0xD = contention -> proves unlocked operation). Then A/B: patch the module to call 0xE05BE6A6 and compare storm rate over 10 starts.
2. DeleteResLockEntry: after UnLock, `call 0xE05BE5A2 <entry>` -> expect r0=0 (0xD means still locked, 7 bad signature).
3. dm levels: `call 0xE05D14BE 0xFF 0` then `call 0xE05D14BE 0x82 3` and press PLAY/MENU -> 'SetGUIRequestMode(0x%08x)' lines appear on UART; record the values for PLAY, MENU, LV idle, Q -> gives GUIMODE_PLAY / GUIMODE_MENU / idle. Cross-check with `rd 0x7EC0` (current) and `rd 0x7EC8` (requested) in each state.
4. LV_OVERLAYS_MODE: `rd 0x15998` while cycling INFO in LV -> expect 0,1,2,3.. changing per press (boot log already shows index 3); `rd 0x13CC8` should not track.
5. DISPLAY_IS_ON: `rd 0xAC64` with panel on, after display-off timeout, and with EVF active -> decides polarity/value set. Also `call 0xE05A1EF2` then `rd 0xAC64`, `call 0xE05A1EC8` to restore (confirms _turn_off/_turn_on_display).
6. RTC: from a task (not the serial shell's blocking path if it wedges), `call 0xE0608794 <ptr to 0x28-byte buffer>` then `md <buf> 0x28` -> expect sec,min,hour,mday,mon(0-11),year(-1900); UART should print '[RTC] LoadCalenderFromRTC y/m/d h:m:s' only if class 0 level 1 is enabled.
7. LVAE: `md 0x022491C8 0x60` (lvae_setcontrolaccumh), `md 0x022496C2&~1 0x40` (setdispgain), `md 0x0224925E&~1 0x40` (setmoviemanualcontrol); disassemble as Thumb and take the literal base -> LVAE_STRUCT, verify offsets 0x34 / 0x48 / 0x24. Also `rd 0xA498+0x3C` (=0xA4D4) -> pointer whose first halfword is printed next to the ISO block.
8. YUV buffers: `rd *(0xAB10)+0xB0` (DV_VRAM_PANEL) on several frames -> expect three rotating values 0x3F4800 apart; these are YUV422_LV_BUFFER_1..3.
9. debug_assert handler: `rd 0x4000` -> should hold ML's handler when installed.
