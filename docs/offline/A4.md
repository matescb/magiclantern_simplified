# A4 - PropertyMgr boot crash pc=0xE021B8FC lr=0xE04037A1 dfar=0x46

## Question

Which function sat in the `token_cb` slot of a slave-registration record and tail-called
`_prop_cleanup(0x32, <token>)`? Is it a Canon bug path, a queue/record reuse problem, or ML?
Where does 0x32 come from, and what is the cheapest hardware probe?

## Summary

- NOT identified statically. The culprit is not any Canon ROM0 registration I could resolve: 0 of 118
  `prop_register_slave` call sites pass a `_prop_cleanup` tail-caller as the 5th argument
  (112 resolved, 6 partly unresolved, see Observed 3).
- The crash is NOT tied to `big.1c`: of 29 dumps, the last ML marker was `big.1b` in 21, `post.4` in 7
  and `big.1c` in 1. It fires while `my_big_init_task` is only waiting, i.e. during Canon's own startup
  registrations.
- The frame chain is exact, and in every boot `r1 == r6 ==` the freshly allocated token pointer, always
  exactly 0xF34 above the record. So a *property handler* ran in the token-callback role.
- ML's `global_property_handler` has exactly that shape, but so do 77 Canon handlers; statics cannot
  choose. The record contents were never dumped.
- Cheapest decisive probe: dump 8 words at r8 (the record) in the abort handler of the crashing build.

## Observed

1. Frame chain (ROM + abort dump, uart.jsonl line 640710 onward).
   - `0xE021B8F0` = spinlock acquire; fault at the `ldrex r1,[r2]` (0xE021B8FC), r2 = 0x46 = 0x32+0x14.
   - `0xE0403788(token, prop)`: `add r0,r4,#0x14; bl 0xE021B8F0` -> lr 0xE04037A1. Pushes 6 regs, lr slot
     at sp+0x14 = 0xE05BFD6B (matches dump).
   - `_prop_cleanup` (0xE05BFD48) pushes 6 regs; its lr slot is sp+0x2C = 0xE04034B7 (matches dump). So
     `_prop_cleanup` was entered with lr still = the worker's return address: a tail jump from a function
     whose own frame was already popped (or which never had one).
   - Worker `0xE040347C(obj, record)`: `sub sp,#0x18` + 8-reg push, lr slot at sp+0x64 = 0xE05BB2FD
     (matches). It allocates `0x18 + 12*n`, copies n/handler/priv, then `ldr r1,[r8,#8]; mov r0,r4; blx r1`
     at 0xE04034B4.
   - Registers at the fault: r4=0x32 (token arg), r6=r1=0x00EC46D8 (prop arg), r8=r7=0x00EC37A4 (record),
     r10=0x00809CC4 (manager object), r5=0, r9=r11=0x19980218 (DryOS stack fill pattern).
   - Therefore X(token=0x00EC46D8) executed `_prop_cleanup(0x32, 0x00EC46D8)`: its first argument was
     forwarded as the "property".

2. Record layout and queueing.
   - `prop_register_slave(props, n, handler, priv, token_cb)` (0xE05BF79E) mallocs `0x10+4n`, writes
     `{handler, priv, token_cb, n, props[]}` (strd at 0xE05BF7E8/0xE05BF7EE) and posts event 3 with the
     record pointer via 0xE05C027A -> 0xE05B9F9E (allocate message, `msg_queue_post(obj+0x10)`).
   - The record is passed by pointer and is not copied. Dispatch is 0xE05BB2B2 (state table,
     `blx r3` at 0xE05BB2FA).
   - `_FreeMemory` = 0xE05BEFD8. I did not trace where the worker frees the record (0xE04036CA onward).
   - `0xE05BF802` (only caller 0xE020D8CA) registers every class-0x01000000 property with handler
     0xE05BF79C (`bx lr`) and token_cb = 0, then frees its list. token_cb NULL is skipped by the worker
     (`cbz r1` at 0xE04034B0), so this is not the culprit.

3. Task 1 - Canon tail-callers versus the 5th argument (script over gang100.bin).
   - 77 `b.w 0xE05BFD48` sites and 61 `bl` sites. The only literal 0xE05BFD49 in ROM0 is the stub table
     entry, so `_prop_cleanup` is never itself passed as a callback.
   - 118 `bl prop_register_slave` sites. For 112 the 5th argument resolves to a literal function that
     returns normally. Two were flagged by the classifier and are false positives on manual check:
     0xE007E066 (stores token, tail-calls `_prop_request_change`) and 0xE0778052 (stores token, tail-calls
     DebugMsg).
   - Not fully resolved: 0xE00887DC, 0xE06B1316, 0xE0767756 (token_cb in r5/r4, set earlier in the
     function); 0xE079667C (token_cb 0xE0795C2A, stores token, fine); 0xE0073352 (token_cb = the
     registering state machine 0xE007330E itself, default path stores the argument, fine); 0xE02A25F8
     (table 0xE1022244, 8 entries, token_cbs 0xE02A2885/2AA1/2B1F/2ACB/2AF5/2B49/2B73/2B9D, not
     disassembled).
   - Frameless Canon handlers of the form `f(prop,..) -> _prop_cleanup(*G, prop)` exist (0xE01438A6,
     0xE01E3160), each 6 bytes after or 26 bytes before its own token_cb. They are registered correctly.

4. Task 3 - ML callers (walkback-milestone source; ELF platform/M50mk2.101/build/magiclantern,
   autoexec.bin md5 1df03e45, which is NOT the crashing 1f154452).
   - `src/property.c:179` (`prop_register_handlers`), reached from `prop_init` (INIT_FUNC, run by
     `call_init_funcs` at big.6a, init.c:1100), `prop_update_registration` (module.c:895,
     modules/lua/lua_property.c:136) and `prop_reset_registration`.
   - `src/debug.c:1403` is inside `#if CONFIG_DEBUGMSG`; in the ELF `debug_init` is a 2-byte stub.
   - `src/prop-debug.c:81` is not linked (no symbols in the ELF).
   - ELF: `global_property_handler` at 0xDDD2C pushes r4-r11, and when `actual_num_handlers == 0` goes
     straight to `ldr r0,[global_token]; mov r1,r5; pop; bx 0xE05BFD49`. That reproduces the observed
     frame chain and restores r7. `global_token` = 0x148DBC, `actual_num_properties` = 0x1499C4 (BSS,
     this build only).
   - The compiled call site passes handler in r2 and `global_token_handler` at [sp]: the order is correct.

5. Task 5 - UART history (164 abort dumps in total).
   - 29 dumps with pc=0xE021B8FC / lr=0xE04037A1 / DFAR=0x46, from 2026-07-21 01:10 to 20:40 UTC. The
     28k matching lines are the repeated `[AB]` reprint.
   - The stack chain is identical in all of them (one dump's chain could not be parsed).
   - Last ML marker before the dump: big.1b x21, post.4 x7, big.1c x1 (markers can be lost on the UART).
   - r4 = 0x32 in every dump. The record and token addresses vary per boot (0xEBE750..0xEC37A4), but
     token minus record is 0xF34 in every dump.
   - Other signatures: 0xE02F281A/0xE05BB769 x40, 0xE00436FC/0xE018E213 dfar 0x16 x16, 0xE005DE52 x7,
     0xE05D1ED0/0xE05BF8AF dfar 0xC x7 (lr is inside `_prop_request_change`, a PropertyMgr sibling),
     0xE00A6C44 dfar 0x50/0x53 x4, pc=0 with lr 0xE05D1161 x15.
   - The log lines before the dump show Canon code running from RAM (`Func:0x02268E5E`,
     `Func:0x0225FD08`). That region is not in gang100.bin and was not scanned.

## Inferred

- X is a property handler (signature `f(property, ...)` ending `_prop_cleanup(*token_global, property)`)
  invoked in the token-callback role. The 0x32 is then whatever that handler's token global held: the
  real token callback never ran for it, so the global was never set by registration.
- If the heap placed the token directly after the record (header 0x10, size rounded to 4, from
  0xE05BEFF6 and 0xE05BF016), the record is 0xF24 bytes and n = 964. That is far more than ML's
  256-entry `property_list` and more than any static Canon count I saw (largest 0x4C). If other
  allocations sit between, n is smaller; 964 is an upper bound. The constant gap across 28 boots says
  the same registration faults every time.
- A Canon ROM0 bug path is unlikely: no resolved call site has the slots swapped, and the same ROM
  boots fine with other ML cores.
- Record reuse is not excluded but is a poor fit: random reuse would not give the same handler, the
  same 0x32 and the same 0xF34 gap on every boot.
- Since the fault depends on the ML core build and happens before ML registers, the remaining
  mechanisms are: (a) ML's handler address reaching slot [8] through an ML path I did not find;
  (b) ML's image or BSS overlapping memory Canon uses (the known memory-budget ceiling), corrupting a
  Canon record or a Canon token global; (c) Canon code executing from an MMU-remapped ROM page with a
  bad RAM copy. ML patches 0xE01B8CAC, and two Canon registrations live at 0xE01B27xx and 0xE01B88xx;
  whether they share a remapped page depends on a remap granularity I did not confirm.
  None of these is supported by direct evidence.

## Unknown

- The contents of the record at r8 (handler, priv, token_cb, n). This alone would settle the question.
- Which module owns a token global equal to 0x32, and whether 0x32 is stale data or a real value.
- Whether the RAM-resident Canon code at 0x0225xxxx-0x0226xxxx registers slaves, and with what.
- The eight token callbacks of table 0xE1022244 and the r4/r5 token_cbs at 0xE00887DC, 0xE06B1316,
  0xE0767756.
- Where the worker frees the record, and whether the registrant can free it first.
- The symbol addresses of the crashing build (1f154452); the ELF on disk is a later build.
- Static analysis does not prove runtime behaviour; nothing here was executed.

## Implications for raw video

- This crash belongs to the core-changing "boot-stability" builds, not to raw_vidx. The walkback
  (unchanged core 3ccf499dc + module-only fixes) avoids it, and that remains the safe base for MLV work.
- Do not explain it as "msleep polling at big.1c": 28 of 29 dumps occur before that marker. The card
  mount gate is probably innocent; the empty `normal_code_patches[]`, the changed MMU-patch set and the
  shifted image layout are the better suspects.
- Until the record is dumped, any core rebuild can hit this again, which blocks core-side raw fixes.

## Next hardware checks

1. Decisive, one boot, crashing build fa0834b40 plus about 10 lines in `m50ii_abort_report`: when
   pc == 0xE021B8FC, print 8 words at r8 and 4 words at r6.
   - r8[2] (token_cb) in 0x000C0000-0x00150000: ML code. Resolve it against that build's .sym; if it is
     `global_property_handler`, also print `*global_token` and `actual_num_properties`.
   - r8[2] = 0xE0xxxxxx: look it up in ROM. If it is one of the 77 handlers, the record or the caller's
     argument was corrupted. Compare r8[0] and r8[2] with the literal pair at that module's call site.
   - r8[2] in 0x02xxxxxx: Canon RAM code; dump 0x40 bytes there.
   - r8[3] gives n: 964 confirms the contiguous-heap reading; a small n means something else sits between.
2. Same boot: print `*(uint32_t*)0x4FF4`, then `[mgr+4]` and `[mgr+8]`, to confirm the manager object is
   intact (r10 was 0x00809CC4).
3. On a booting build, over the serial shell: `rd 0xF26C`, `rd 0x8540`, `rd 0x114F0`, `rd 0xA6BC` (Canon
   token globals; expect heap pointers 0x00Exxxxx). Any that reads 0x32 names the module whose token
   callback never ran.
4. MMU-remap test: on the crashing build, `rd 0xE01B87FC 0x20` and `rd 0xE01B2740 0x20` and compare
   with ROM bytes `48 07 04 D0 57 22 00 20` / `48 07 04 D0 6D 22 00 20`. A mismatch means the remapped
   page copy is bad.
5. Bisect without new code: rebuild fa0834b40 with only `mmu_patches.h` reverted to 3ccf499dc. If the
   crash goes, it is the patch set or remap; if it stays, it is image layout or timing.

Evidence:

1. `0xE0403788`: `push.w {r4-r8,lr}` (6 regs), `movs r4,r0; beq 0xE04037BC`, `add.w r0,r4,#0x14; bl 0xE021B8F0`
   (return 0xE04037A0). `_prop_cleanup` 0xE05BFD48: `push {r3-r7,lr}`, `bl 0xE0403788` at 0xE05BFD66.
   Worker 0xE040347C: `push.w {r4-r10,lr}; sub sp,#0x18`, `ldr.w r1,[r8,#8]; cbz r1; mov r0,r4; blx r1` at
   0xE04034B4. Offsets 0x14, 0x18+0x14, 0x30+0x18+0x1C all match the dump at uart.jsonl line 640710.
   Note the `beq` at 0xE0403796: a token of 0 takes a different path (global 0x63B0+0x1C) and would not fault
   at 0x46. So whatever global X read held a non-zero 0x32; a plain zeroed BSS `global_token` would NOT
   produce this crash.
3. My own parse: 164 dumps total, 29 with pc=0xE021B8FC; last marker big.1b 21 / post.4 7 / big.1c 1;
   r4=0x32 in 29/29; r6-r8=0xF34 in 29/29; r7==r8 and r1==r6 in 29/29; first 2026-07-21 01:10:19, last
   20:40:24 UTC. (The report says one dump could not be parsed; all 29 parsed for me.)
4. Counts reproduce exactly (61 `bl`, 77 `b.w`, 118 `bl`, literal 0xE05BFD49 only at 0xE14188B8). But the
   enumeration is incomplete in two ways:
   - `prop_register_slave` is also reachable indirectly: literal 0xE05BF79F at 0xE02D1A68 is loaded at
     0xE02D16B6 and stored to `[table+0x88]` in a function-pointer table (same table gets
     `_prop_request_change` at +0x8C, `prop_deliver` at +0x90, FIO at +0xF4..). Callers through that table
     were not enumerated by either of us.
   - 0xE14188B8 is not a "stub table" of data. 0xE14185E0..0xE14188D0 is a run of 94 ARM veneers
     (`ldr pc,[pc,#-4]` + address) followed by Thumb thunks (`movw ip; movt ip; bx ip`). The thunk at
     0xE14188D4 decodes to 0xE05BFD49 = `_prop_cleanup`. These serve a relocated code blob (see 5), which
     adds **12 more tail calls to `_prop_cleanup`** (`pop {..,lr}; b.w 0xE14188D4`) at 0xE13DFD6C, 0xE13DFDD6,
     0xE13DFDF6, 0xE13DFE16, 0xE13DFE68, 0xE13E8D56, 0xE13E8E32, 0xE13E8EC6, 0xE13E8F7A, 0xE13E9046,
     0xE13E90D0, 0xE13E935E, 2 more `blx` calls (0xE13F42EA, 0xE13FA694), and **10 more
     `prop_register_slave` calls** via veneer 0xE1418930 at 0xE13DF3C0, 0xE13E954A, 0xE13E955C, 0xE13E956E,
     0xE13E9580, 0xE13E9592, 0xE13E95A4, 0xE13E95B6, 0xE13F3550, 0xE13FA666.
5. The RAM code is in ROM0. Scoring all 298 odd 0x0225xxxx-0x0228xxxx literals in 0xE13D0000-0xE1418000
   against "lands on a push" gives one clear relocation delta: ROM = RAM + 0xDF180074 (223 hits, next best
   26). With it, the logged `Func:0x02268E5E` is ROM 0xE13E8ED2 (`push.w {r4-r8,lr}`, a handler) and
   `Func:0x0225FD08` is ROM 0xE13DFD7C, 16 bytes after the tail call at 0xE13DFD6C. Seven of the new
   registrations (0xE13E954A..0xE13E95B6) pass handler = token_cb + 8, e.g. token_cb 0x02268E57 -> ROM
   0xE13E8ECA `ldr r1,=0xA5E0; ldr r1,[r1]; str r0,[r1,#0x14]; bx lr`, handler 0x02268E5F -> 0xE13E8ED2,
   and the handler before it ends `ldr r0,[r5]; mov r1,r4; ldr r0,[r0,#0x18]; pop; b.w _prop_cleanup`.
   So in this blob the tail-calling handler sits physically 4-12 bytes from its own token_cb, and the
   handlers read their token from a heap struct at `*(0xA5E0)` (offsets +8, +0x14, +0x18 seen), not from a
   fixed global. OBSERVED: the seven sites I read pass the pair in the right order. NOT checked: 0xE13DF3C0,
   0xE13F3550 (token_cb 0x02273319, handler 0x0227331F), 0xE13FA666 (n = 0x31, token_cb 0x0227A411).
   INFERRED: these are now the best Canon candidates for X, because (a) they are frameless-at-exit tail
   callers, (b) their token lives in a struct that may be uninitialised or not yet allocated when the
   callback fires, which is a natural source for a junk token such as 0x32, and (c) the code runs from a
   RAM copy at 0x0225xxxx-0x0227xxxx, which an ML image/heap overlap or a late/partial copy could damage
   without touching ROM. None of this is proven.
6. 0xE05BF79E: `strd sl,r5,[r4,#8]` (token_cb = `[sp,#0x28]` after a 10-reg push, n) and
   `strd sb,r8,[r4]` (handler, priv); `mov r3,r4; movs r2,#3; bl 0xE05C027A`. 0xE05C027A forwards to
   0xE05B9F9E. Record pointer is passed as-is. I did not trace the free either.
7. 0xE05BF856: `ldr r2,=0xE05BF79D` (bytes at 0xE05BF79C = `70 47`, `bx lr`), `movs r0,#0; mov r3,r0;
   str r0,[sp]`, then `bl prop_register_slave`, then `_FreeMemory(list)`. Debug string is "## num %d".
8. ELF (md5 1df03e45): 0xDDD2C `push {r0-r2,r4-r11,lr}` (the report says r4-r11; harmless),
   `ldr r3,[r9,#0xC04]` (= 0x1499C0 `actual_num_handlers`), on zero: `ldr r0,[0x148DBC]; mov r1,r5;
   add sp,#12; pop {r4-r11,lr}; bx 0xE05BFD49`. `debug_init` 0xD7944 is 2 bytes. This build is not the
   crashing one, as the report says.
9. The gap arithmetic gives n of about 964-965 only if the token directly follows the record; I could not
   confirm the heap header size. More important: the report compares against static counts only. The
   registration at 0xE05BF802 has a run-time n (the number of class-0x01000000 properties, from
   0xE05CFD00 -> 0xE005D566) and is the only registration found with a potentially very large n. Its
   allocation order (list 4n, record 0x10+4n, list freed, then token 0x18+12n, which cannot fit the freed
   hole) would put the token right after the record, as observed. Its token_cb is 0 in ROM. If the
   faulting record is this one, slot [8] was non-zero at processing time, i.e. the record was overwritten
   between post and processing, or the 5th stack argument was not what the ROM wrote. That contradicts
   the report's "record reuse is a poor fit" only weakly, but it makes "dump r8[0..3]" even more decisive:
   r8[0] == 0xE05BF79D with r8[2] != 0 would prove in-flight corruption of this specific record.
   "## num %d" never appears in uart.jsonl (debug level filtered), so n cannot be read from the log.

Net effect on the report's conclusion: the frame analysis, log statistics and ML-side findings hold. The
statement that no Canon registration could be the source is not supported, because a whole relocated
blob (ROM 0xE13Dxxxx-0xE1418xxx, RAM 0x0225xxxx-0x0229xxxx) with 12 tail-calling handlers and 10
registrations was outside the scan, and so were callers through the table at 0xE02D16B6.

Extra hardware checks this adds (same one-boot abort-handler probe as the report's check 1):
- If r8[2] is in 0x0225xxxx-0x0229xxxx, add 0xDF180074 and look it up in ROM0; compare with the handler
  list above. If r8[2] == r8[0] or r8[2] == r8[0]+/-8, the pair was swapped or shifted.
- Print `*(uint32_t*)0xA5E0` and 8 words at that pointer. A NULL or a struct containing 0x32 at +8/+0x14/+0x18
  names the blob module as X's owner.
- On the crashing build, compare 0x40 bytes at RAM 0x02268E56 and 0x0225FCF8 with ROM 0xE13E8ECA and
  0xE13DFD6C. A mismatch means the RAM copy of the blob is damaged (ML overlap or bad copy).
- If r8[0] == 0xE05BF79D, the record is the class-0x01000000 one and r8[2] must be 0; anything else is
  corruption after `prop_register_slave` returned.
