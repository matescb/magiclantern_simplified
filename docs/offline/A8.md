# A8 — Memory available for frame buffers (M50 Mark II, fw 1.0.1)

Static analysis only (ROM gang100.bin + ML source + docs). Nothing here was run on the camera in this
sprint; every runtime claim is quoted from an earlier doc and marked as such.

## Question

Which allocators can ML use on this camera, what is their real capacity, how many 2096x1164 14-bit
frames (4,269,552 B = 4.07 MiB) or 1792x896 frames (2,809,856 B = 2.68 MiB) can be buffered, where,
with which calls, and which pools are safe to take while LiveView runs.

## Summary

- Only one large pool is wired up today: the shoot-memory suite (RscWrap 0xe0608904/932/960), measured
  earlier at ~63 MB in movie-LV (docs/32:13). That is at most 14 full-res or 22 crop frames.
- The commented-out SRM stubs (0xe056a5c6 / 0xe056da22) are M50 mk1 addresses copied verbatim; on this
  ROM 0xe056a5c6 is not code. The real pair on 1.0.1 is **0xe057b7ba** (alloc) / **0xe057da00** (free).
- Canon's own caller shows the convention: alloc(cbr, ctx), cbr(ctx, buffer) called from RscMgr,
  free(buffer, 0, 0) - identical to what src/exmem.c already expects.
- srmGetShootMemAreaSize (0xe04b3468) holds a 0x2AB1000 (44.8 MB) area with 2 slots; INFERRED to be the
  1stJob raw buffer = SRM_BUFFER_SIZE candidate. Not proven; must be printed from the cbr on hardware.
- docs/32 already correlates "grab all shoot memory" with the AE/Aewb deadline storm, so taking the whole
  shoot pool during LV is NOT safe; SRM is untested on this body and is still disabled on mk1.

## Observed

### ML side (source)
- platform/M50mk2.101/internals.h:29 `CONFIG_MEMORY_SRM_NOT_WORKING`, :45 `CONFIG_MALLOC_STRUCT_V2`.
- platform/M50mk2.101/consts.h:36 `MALLOC_STRUCT_ADDR 0x2d160` (used by src/mem.c:125 for malloc free-space).
- src/mem.c:222-334 allocator table. Active for this build: `malloc` (_malloc 0xE03C5270),
  `AllocateMemory` (_AllocateMemory 0xE05BEE20, DMA variant = C wrapper in function_overrides.c:212),
  `shoot_malloc`. `srm_malloc` is compiled out (mem.c:311). "RscMgr" and "task_mem" are `#if 0`.
- src/mem.c:228-231 / 242-248: malloc and AllocateMemory are only *preferred* up to 512 KB per request
  and must keep 256 KB / 512 KB free - they are not frame-buffer pools by design.
- src/exmem.c:175 `AllocateMemoryResource(size, allocCBR, ctx, 0x50)`, :336
  `AllocateContinuousMemoryResource(size, allocCBR, ctx, 0x50)`, :87 `FreeMemoryResource(hSuite, cbr, 0)`.
  exmem.c:406 probes free space by trying a 32 MB allocation.
- src/exmem.c:441-784 the whole SRM path is under `#ifndef CONFIG_MEMORY_SRM_NOT_WORKING`; it needs
  `SRM_BUFFER_SIZE` (exmem.c:469 asserts it equals the size passed to the cbr). No SRM_BUFFER_SIZE exists
  for M50mk2 or M50; 200D uses 0x2a9c000 (platform/200D.101/consts.h:127).
- function_overrides.c:235-236 stub `srm_malloc_suite` -> NULL, `srm_free_suite` -> no-op.
- stubs.S:266-270: commented SRM stubs 0xe056a5c6 / 0xe056da22 are byte-identical to
  platform/M50.110/stubs.S:211-214 and research/bilal_M50_rawvideo/platform/M50.110/stubs.S:214-217.
  They were never re-resolved for mk2. The working mk1 raw build also has SRM disabled
  (research/bilal_M50_rawvideo/platform/M50.110/internals.h:21).

### ROM: DryOS pool and AllocateMemory
- docs/15 (cstart 0xE0040104): user_mem 0xC78D8 len 0x112E80 (1.07 MB, ML lives here), sys_objs 0xAF80,
  sys_mem 0x1E56D8 len 0xE2200 (0.88 MB). Whole DryOS pool ~2.0 MB.
- cstart also sets MEM(0x4168)=0x80000, MEM(0x416C)=0xA90000, MEM(0x4170)=0xA96000 (docs/13:153-154).
- _AllocateMemory 0xE05BEE20 loads pool handle from RAM 0x51F4 (literal @0xE05BF11C) and on failure calls
  GetMemoryInformation 0xE05BECAA and GetSizeOfMaxRegion 0xE05BEC7E. Pool base/size are not constants in
  that function.

### ROM: RscWrap (the "shoot memory" entry points)
- 0xE0608904 / 0xE0608932 / 0xE0608960 are thunks that tail-call slots 0 / 4 / 8 of a function table in RAM
  at 0x5128 (literal @0xE0608AC4), asserting "System::RscWrap.c" (0xE0608AC8) when a slot is NULL.
- The table is zero in the boot .data image (ROM 0xE1394358 + (0x5128-0x4000) reads all zero) and is filled
  at runtime by 0xE06088D0 (`stm r4,{r0..r3,r5..r8,ip}` + `[r4,#0x24]`), cleared by 0xE06088EA.
- Callers of 0xE06088D0: 0xE0041378 and 0xE0041932 (two init variants). At 0xE004135A-0xE0041378 the ten
  slots are loaded as:
  slot0 = 0xE057CDDF, slot4 = 0xE057CD15, slot8 = 0xE00412B7, slot0xC = 0xE057B849, slot0x10 = 0xE057A80D,
  slot0x14 = 0xE00412A1, slot0x18 = 0xE057F49B, slot0x1C = 0xE0041295, slot0x20 = 0xE057F439,
  slot0x24 = 0xE057F3D5.
- All 0xE057Axxx-0xE0582xxx targets sit in the file that asserts "Resource::RscMgr.c" (0xE057AB10) and use
  the RscMgr object pointer at RAM 0x5280.
- Canon callers: AllocateMemoryResource has 14 BL sites, AllocateContinuousMemoryResource 20,
  FreeMemoryResource 46 (BL scan of ROM0).

### ROM: SRM 1stJob pair
- 0xE00792E8 (Canon code) does, in order: create_named_semaphore -> `ldr r0,=0xE00792DF; r1 = 0xF99C+8;
  bl 0xE057B7BA` (0xE007933E-0xE0079344) -> take_semaphore([0xF99C+4], 5000 ms) -> on timeout
  DryosDebugMsg with the string at 0xE00794C4 "SRM_AllocateMemoryResourceFor1stJob failed [%#x]"
  (adr at 0xE0079362).
- The callback 0xE00792DE is three instructions: `str r1,[r0]` ; load semaphore [0xF99C+4] ;
  `b give_semaphore`. So cbr(ctx = pointer to result slot, r1 = buffer).
- The stored value [0xF99C+8] is then used as a plain memory address: 0xE0079276 walks a memSuite and
  memcpy's each chunk to `r2 + offset` where r2 = [0xF99C+8] (0xE00792A6-0xE00792AE).
- 0xE0079256 releases it: `r0 = [0xF99C+8]; r1 = r2 = 0; bl 0xE057DA00`, then zeroes the slot.
- 0xE057B7BA: AllocateMemory(0x34) message + AllocateMemory(8), asserts RscMgr.c lines 0x30E-0x310,
  msg[0x1C] = arg0 (cbr), msg[0x20] = arg1 (ctx), msg[0x28] = 0xA1, sets [RscMgr+0x28C] = 1, posts
  event 0x2A to the RscMgr state object via 0xE057A7EC.
- 0xE057DA00: same shape (0x34 message + 8), asserts RscMgr.c lines 0xAB1-0xAB3, msg[0x10] = arg0 (buffer),
  msg[0x1C] = arg1, msg[0x20] = arg2. Second caller at 0xE095DF36.
- ROM table 0xE02D19C8 = {0xE057B7BB, 0xE057DA01, 0xE0581295, 0xE0581309, 0xE058137B}: the two functions
  are adjacent in a Canon function table.
- 0xE056A5C6 (the stale stub) disassembles as data (`str r7,[r4,r1]`...), not a function prologue.
- The 0x34 message size matches the stubs.S note "buffer size differs (0x34 vs 0x30)" for D8 vs 200D.

## Inferred

- SRM_AllocateMemoryResourceFor1stJob = 0xE057B7BA and SRM_FreeMemoryResourceFor1stJob = 0xE057DA00.
  Confidence high: Canon's own failure string names the first, the argument order matches ML's prototype,
  and the same result slot is passed to the second with (buf, 0, 0).
- The cbr may receive a size in r2 as ML's `srm_malloc_cbr(dst, buf, size)` assumes, but Canon's own cbr
  ignores r2, so the third argument is not confirmed on this ROM.
- SRM_BUFFER_SIZE is probably 0x2AB1000: it is the only two-slot ~44 MB area, it is close to 200D's
  0x2A9C000 for a sensor of the same pixel count, and 24 MP 14-bit raw needs about that much. Area id and
  the link to the 1stJob message (id 0xA1) were not traced.
- RAM is 1 GB (area addresses reach 0x3F421000; docs/15 MMU map shows 0x00100000-0x3FFFFFFF as main DRAM).
  Canon statically partitions almost all of it into per-feature areas; there is no large unclaimed region.
- 0x2BC61CC8 lies between the area bases 0x29156000 and 0x2F0D7000. It is 0x5ACC8 past
  0x29156000 + 0x2AB1000, so it is not inside a 44.8 MB buffer starting at 0x29156000. Which area owns it
  is not decoded.
- "143 slots" cannot be 143 full frames (143 x 4.07 MiB = 582 MiB > 63 MB). The slot count in that log
  must refer to smaller units; how mlv_lite sized them in that run was not checked.

## Unknown

- Real size and base of the AllocateMemory pool (handle at RAM 0x51F4) and its free space with ML loaded.
- Whether 63 MB is the shoot total in every mode (photo LV, movie LV, 4K crop) and the largest contiguous
  chunk. exmem.c:406 probes only up to 32 MB.
- Whether SRM 1stJob allocation works while LiveView runs on this body, how many buffers it yields
  (inferred 2), and whether the free path works. mem.c:311 says free "seems to not work" on RP/200D/R/M50;
  internals.h:25 says alloc crashed - but that was with the wrong (mk1) address on mk2.
- Full area-id -> address map: the address function uses nested table branches that I did not finish
  decoding (the first TBB at 0xE04B32A4 covers only part of the index range).
- Meaning of the `0x50` type argument to AllocateMemoryResource on D8 and which free list it draws from.
- exmem (AllocateMemoryResource) and "shoot memory" are the same thing here; no separate ExMem API was
  found beyond network-transfer strings (NWCOM ... ExMemory).

## Implications for raw video

Capacity table (upper bounds, ignoring chunk fragmentation and per-slot headers):

| Pool | Calls | Size | 2096x1164 | 1792x896 | LV-safe |
|---|---|---|---|---|---|
| malloc (0x2d160) | _malloc/_free | sub-MB | 0 | 0 | small objects only |
| AllocateMemory | 0xE05BEE20 / 0xE05BEFD8 | unknown, keep 512 KB free | 0 | 0 | small objects only |
| shoot memory | 0xe0608904 / 0xe0608932 / 0xe0608960, type 0x50 | ~63 MB measured | <= 14 | <= 22 | partial grab only |
| SRM 1stJob | 0xE057B7BA / 0xE057DA00 | inferred 2 x 44.8 MB | 10 per buffer (20) | 15 per buffer (31) | untested |
| Canon LV raw buffer 0x6BC61CC8 | none (Canon-owned) | 1 frame | source only | source only | read-only |

- At 24 fps a full shoot pool is ~0.6 s of full-res or ~0.9 s of crop frames; this is a write-smoothing
  buffer, not a recording buffer. Sustained recording depends on card speed, as on mk1.
- Do not take the whole shoot pool. docs/32 ties that to the AE storm. Leave headroom (test 16/32/48 MB).
- SRM is the only route to more than ~63 MB. The two blockers recorded in the source ("alloc crashes",
  "free does not work") were observed with addresses that are wrong for this ROM, so both need a retest.
  Shutter must be locked while SRM buffers are held (exmem.c srm_shutter_lock).
- Any SRM enablement changes the core (stubs.S + consts.h + internals.h). Memory notes say core rebuilds
  shift symbols and have caused boot crashes; plan it as a committed, separately tested core change, or
  call the two addresses directly from a module through function pointers to keep the core unchanged.

## Next hardware checks

1. Confirm the RscWrap table (read-only): `rd 0x5128` 10 words. Expect
   E057CDDF E057CD15 E00412B7 E057B849 E057A80D E00412A1 E057F49B E0041295 E057F439 E057F3D5.
   A different slot 0/4 means the second init variant (0xE0041932) ran - re-read its pool.
2. Read `rd 0x5280` (RscMgr object pointer, must be non-zero) and `rd 0x51F4` (AllocateMemory pool handle).
3. AllocateMemory capacity: from a module task (not the serial shell), call GetMemoryInformation
   0xE05BECAA and GetSizeOfMaxRegion 0xE05BEC7E and print total/free/max. Decides whether any 4 MB DMA
   buffer can come from there (expected: no).
4. Shoot pool size per mode: from a dedicated task, AllocateMemoryResource(size, cbr, ctx, 0x50) with
   size = 16, 32, 48, 64, 80 MB, free after each, in photo-LV and movie-LV. Log the largest success and
   watch UART for "Over the Deadline" lines. Decides the safe grab size. Do not use `call` from the
   shell: docs/32:1141 shows it blocks forever.
5. SRM probe, module-only, LV running, shutter locked: `((void(*)(void*,void*))0xE057B7BB)(cbr, &buf)`
   with a cbr that logs r0, r1, r2 and gives a semaphore; wait 5000 ms like Canon does.
   - cbr fires, r1 non-zero: record r1 and r2. r2 == 0x2AB1000 confirms SRM_BUFFER_SIZE; if r2 is garbage,
     the size argument does not exist on D8 and exmem.c:469 must not assert on it.
   - timeout or assert in RscMgr.c: SRM unavailable in LV; stay with the shoot pool.
   - Repeat until the cbr stops firing to count buffers (expected 2).
6. SRM free: `((void(*)(void*,void*,void*))0xE057DA01)(buf, 0, 0)` in reverse order, then repeat step 5.
   Success on the second round means free works; then take a photo to check for ERR70.
7. While SRM buffers are held, `rd 0xd04202a0` (raw EDMAC address, docs/31:420) and confirm it still
   reads 0x6BC61CC8 and LV keeps running; r1 from step 5 overlapping 0x2BC61CC8 would mean the 1stJob
   buffer and the LV raw buffer share an area and SRM cannot be used during raw LV.

Caveats found while checking:

- Claim 4 signature: in the free function, r1 and r2 are stored at msg+0x1C / msg+0x20, the same two fields
  where the alloc function stores (cbr, ctx). So the two zero arguments are most likely an optional
  completion callback and its context, not "unknown zeros". Canon passes none here; whether free completes
  synchronously without a callback is unknown.
- Claim 2/3: the only caller located is factory code (adjacent strings "FA_RemoteRelease",
  "[FA] MemChunk Buff %lx, Size %ld, Offset %ld"). It bails out with 0x17 when [0xF99C]==0 and with 1 when
  0xE05BE330 returns bit0 set, before ever calling the allocator. Normal shooting code may use a different
  entry of the same family; Ghidra holds no direct xrefs to 0xE057B7BA / 0xE057DA00, so callers reach them
  only via this bl (not a defined function in the project) and the table at 0xE02D19C8.
- Claim 9 arithmetic: 0x2AB1000 is 42.69 MiB (44.77 decimal MB). Per buffer that is 10.48 full-res or 15.93
  crop frames, so 10 and 15 hold. The report's table entry "15 per buffer (31)" for two buffers should read
  30 unless a frame may span buffers. The "14 / 22 frames from 63 MB" figures assume 63 is decimal MB
  (60.1 MiB); if the log meant MiB they would be 15 / 23. docs/32:13 does contain the quoted
  "143 slots from shoot_malloc (63MB shoot, SRM off)" line.
- Claim 10: 143 x 4.07 MiB = 582 MiB, arithmetic correct; slot unit still unchecked.
