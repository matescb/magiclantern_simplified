# A9 - LiveView raw geometry, bit depth, frame timing (M50 II 1.0.1, static)

## Question
Find the sensor/LV mode tables, where LV raw width/height come from, the bit-depth/packing and
digital-gain registers, the frame-timer registers and their clock, and the video-mode property.
State which constants in our tree are wrong.

## Summary
- Frame-timer clock is ~27 MHz, not 32 MHz: ROM timer tables hold the exact mk1 values (0x2D1/0x26F, 0x215/0x1A4, 0x1C5/0x94D). `TG_FREQ_BASE` must be 27000000. High confidence.
- `FPS_REGISTER_CONFIRM_CHANGES 0xD0406190` is a real register in Canon's HEAD tables (written with 1 in 14/14 mode tables). Its "latch" role is inferred, not proven.
- Canon has 14 sensor drive modes (0-5 still, 6-13 LV). The 8 LV raw geometries are in a ROM table at 0xE1359338: 2096x1164, 2096x838, 2096x714, 2096x608, 4368x2201(2), 4288x1202 (two crops), plus 2096x258/146.
- For 2096x1164 Canon's own window is left 92 / top 38 / 2000x1126; our 88/34 matches the 838/714-line modes instead. Medium confidence that 92/38 is the better value.
- Bit-depth (0xD0008094) and SHAD_GAIN (0xD0008030) literals do not exist in either ROM; real replacements NOT found. Packing goes through a RAM handler table at 0x6DC60 (LvComPack.c).

## Observed

### Sensor drive mode ("ImageSequenceStore")
- `ImageSequence::ImageSequenceStore.c` (string 0xE06D0240) state struct at RAM 0x1064C. Field +8 = current drive mode, asserted < 0xE. Setter 0xE06CFE68, getter 0xE06CFE80. Setter is called with `job->[0x4C]->[0x24]` (0xE06C65FE, 0xE06C6816, 0xE06C7DA8, 0xE06C800E) or with 0..4 for stills (0xE06C65F4, 0xE06C6990).
- Map table 0xE0BBFA68, 14 entries per column: +0x00 = [0,1,2,0,3,4,5,5,5,5,5,5,5,5]; +0x38 = [8 x6, 0,1,2,3,4,5,6,7] (LV index, 8 = not LV); +0x70 = [4 x6, 0,1,4,2,4,4,4,3]; +0xA8 = [11,11,11,0..10]; +0xE0 = [0,1,0,2..12]; +0x118 = identity. Getters 0xE06CFFE8, 0xE06D001A, 0xE06D004E, 0xE06D0082, 0xE06D00B8, 0xE06D00EE.

### Packing / gain / property
- `LiveViewCore::LvComPack.c` (0xE071FBC0): FUN_e071fb14(mode<6, arg) dispatches through a RAM table at 0x6DC60 (6 handlers, then 6 args at +0x18). Caller FUN_e07536d6. Registers behind the handlers not traced.
- String `LvRshdGain` at 0xE0785250 has no literal-pool reference; `COLORLV_GetObWbParamAndGain` at 0xE1443E70. Not traced.
- 0x80000039 (our PROP_VIDEO_MODE, src/property.h:461) appears as a literal 25 times in ROM0 (first 0xE04C1F20); 0x80050015 (PROP_LV_DISPSIZE) 19 times. Payload layout not checked.

## Inferred
- **Clock = 27 MHz (high).** Table A mode 7 gives 59.93 fps and mode 8 gives 120.1 fps only with a ~27 MHz base and (reg+1) counts; at 32 MHz they would be 71 and 142 fps. Identical register values to the mk1 port that measured 26.9-27.0 MHz.
- **Table B's 61A4 value is the minimum vertical count per mode (medium-high).** It matches raw heights in all 8 LV modes: binned modes read 2 lines per count (2x(B+1) = 1168, 842, 718, 612, 262, 150 vs heights 1164, 838, 714, 608, 258, 146), full-width modes 1 line per count (2207 vs 2202, 1205 vs 1202). This gives the drive-mode -> geometry map: 6 = 2096x1164 (1080p, 3x3), 7 = 2096x838 (photo LV, 3:2), 8 = 2096x714 (720p HFR), 9 = 2096x608, 10 = 2096x258, 11 = 2096x146, 12 = 4368x2202 (4K, 1:1 crop), 13 = 4288x1202 (1:1 crop: x5/x10 zoom 1208x806 and a 2008x1130 crop).
- Max sensor rates follow: 1080p mode ~64 fps, 720p ~141 fps, 4K ~26.9 fps, zoom/crop ~31 fps (medium).
- Mode names (photo LV, zoom, crop movie) are inferred from aspect ratios only (low-medium). The Pprch key -> Canon video-mode mapping is not established.
- 0xD0406190 = 1 sits next to 0xD0406194 = 1 at the head of every timing table; plausibly an enable/latch, so mk1's "confirm" use is plausible (medium). Not proven that writing it latches A/B.
- Left/top in the geometry records are Canon's processing crop, so they are a safe inner bound of the optical-black border, not necessarily its exact edge (medium).

## Unknown
- The DIGIC 8 raw bit-depth/pack register and its values. 0xD0008094 is not in this firmware; nothing found to replace it.
- The digital-gain (SHAD_GAIN) register. 0xD0008030 is not in this firmware.
- Which drive mode each Canon movie setting (1080p24/30/60, 4K, 720p120, movie crop, x5, x10) selects at runtime, and whether 1080p60 uses the same 2096x1164 mode.
- Whether the 4K raw stream is exposed on the same EDMAC channel (0xD0420200) and at 14 bit.
- Base pointer `*(0x216D0+0x10)` (second HEAD table blob, strides 108/36/32/384) was not located.
- PROP 0x80000039 payload layout on this body.

- Raw width is 2096 only in binned modes. 4K (4368) and zoom/crop (4288) buffers are 2.1x wider and 4K is 2.1x taller: a 4K frame is ~16.8 MB at 14 bit versus 4.27 MB, which matters for the copy-speed/queue-fill problem.
- FPS override limits should come from table B: timer B must stay >= 0x247 in the 1164-line mode.

## Next hardware checks
1. `rd 0xD0406198 4`, `rd 0xD040619C 4`, `rd 0xD04061A4 4` in 1080p24/25/30/60, 720p120, 4K24/25, x5, photo LV. Expect A = 0x2D1/0x215/0x1C5; mk1 predicts B = 0x617/0x5D7/0x4DF/0x26F. fps x (A+1) x (B+1) ~ 27.0e6 confirms the clock.
2. `rd 0x10654 4` (0x1064C+8) in each of those modes: expect 6..13. This gives the Canon mode -> drive mode map and tests the table-B height inference.
3. `rd 0xD0420250 4` in each mode: low 16 bits = bytes/line, high 16 = lines-1. Expect 0x048B0E54 (1080p), 0x02C9xxxx (720p, 714 lines), 0x0899/0x0898 with 7644 bytes/line (4K at 14 bit), 0x04B1 with 7504 (zoom). A bytes/line that is not W*14/8 reveals a different bit depth.
4. `rd 0x6DC60 48`: 6 LvComPack handler pointers + 6 args; disassemble the non-null handlers offline to find the pack/bit-depth registers.
5. `rd 0x216E0 8`: the two HEAD table base pointers (expect second = 0xF0014914); the first locates the remaining sensor tables.
6. FPS confirm test: in 1080p30 write 0xD04061A4 (and 0xD04061B8) = 0x617 without touching 0xD0406190 and watch LV rate; then write 0xD0406190 = 1. Whether the change needs the second write decides the confirm register.
7. Skip check: in a saved 1080p DNG compare mean of columns 88-91 and rows 34-37 with the image area. Dark = use 92/38; image = keep 88/34.

Net: no claim was outright refuted. The weak points are (a) table B has no located code reference, so everything built on it (minimum B per mode, the drive mode -> resolution map, "max fps" figures) is hypothesis; (b) the 27 MHz conclusion depends on mk1 hardware measurements rather than on this ROM; (c) "absent literal = wrong register" is slightly overstated.

Extra static lead: callers of the LvComPack registration function at 0xE071FB42 will give the six pack handlers without needing `rd 0x6DC60`.
