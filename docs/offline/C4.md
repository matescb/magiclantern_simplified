## Results

### Core symbol file

**Built on branch `offline/C4`, `M50mk2_101.sym` is NOT identical to the main checkout's.** This is
true for the untouched baseline too (first build, before any edit), so it is not caused by the
module changes: 53 symbols from `build_version` to `task_create_zebra_init` sit 8 bytes lower.

```
< 000f3576 build_version          (worktree, branch offline/C4)
> 000f357e build_version          (main checkout)
...
< 000fd650 task_create_zebra_init
> 000fd658 task_create_zebra_init
```

Cause: `platform/Makefile` writes `build_id = "<short hash> <branch name>"` into `version.c`.
`"a10b16c23 offline/C4"` is 8 characters shorter than `"3ccf499dc walkback-milestone"`.

Check: with the branch temporarily renamed to the 18-character `offline/C4-symtest` and rebuilt
(HEAD `f8191a47a`, all module fixes in), the result is identical:

```
SYM IDENTICAL with 18-char branch name
d2f46ba5e091fa02d53a8aae9969442f  build/M50mk2_101.sym                     (worktree)
d2f46ba5e091fa02d53a8aae9969442f  .../magiclantern_simplified/platform/M50mk2.101/build/M50mk2_101.sym
```

`autoexec.bin` from that build differs from the main checkout's in 87 bytes, all of them date, hash
and branch strings plus the last 4 bytes of the file. The worktree's `platform/M50mk2.101/build` was
left in this state (its `build_id` reads `offline/C4-symtest`; the branch is named `offline/C4`
again). A plain `make` there on `offline/C4` brings the 8-byte shift back.

Consequence: the core's data layout depends on the length of the branch name. Any core built from a
branch whose name is not 18 characters long differs from the build that was flashed.

### Host test

`worker.c` and `event_pusher.c` are compiled unmodified for 32-bit x86 against stub headers. The
harness models the worker as a coroutine, the write task as inline or lower-priority, and FIO as an
in-memory file system that remembers each file's contents at its last close.

Fixed sources (`hosttest_fixed.log`): 68 checks ok, `failed tests: 0`.

## Limitations

- The host test replaces `mlv_3.c` with a fake block writer, runs single-threaded, and has no
  timing, no priorities beyond "write task runs when the worker blocks", and no Canon behaviour.
- The checkpoint path (`FIO_CloseFile` then `FIO_OpenFile(O_RDWR|O_SYNC)` then seek to end) copies
  the idiom of `FIO_CreateFileOrAppend` in `src/fio-ml.c` but has never run on this camera. Cost per
  16 MB buffer and any effect of `O_SYNC` on write speed are unknown. `wr &rvx_checkpoint 0` turns it off.
- `FIO_Flush` is not called. Its stub is verified but it has only been used after a close in boot
  probes, never on an open file, so I could not justify it.
- On a short card write (card full) the buffer's frames are not counted, but the partial block
  stays in the file, so a strict reader may complain at the tail.
- If a card write is still running 10 s after stop was requested, the buffered frames are dropped,
  the header is left at count 0, and the file is closed anyway (as before).
- A failed start leaves the empty or header-only `tstNN.mlv` on the card (closed, not deleted).
- `worker.c` is now 886 lines, above the 800-line soft ceiling.
- Not changed, but worth knowing: the vsync CBR still calls `fio_malloc` for two LiveView-sized
  capture buffers per session although the default toggles never read them; and the tail write task
  runs at priority 0x1A below the worker (0x11), so it only gets CPU when the worker blocks.
- The main checkout's `raw_vidx.mo` (md5 `0715abdd...`) differs from a fresh build of the same
  commit in the worktree (`98b163a8...`); not investigated.
