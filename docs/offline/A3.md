# A3 - Crash cluster in Canon's debug-message formatter

## Question
Three hardware crash signatures touch Canon's DebugMsg code: (a) pc=0x0 lr=0xE05D1161 during recording, (b) pc=0xE005DFA2 with 0xE05B9FD1 on the stack, (c) boot fault "big.5.3" pc=0xE005DE52 lr=0xE005DE29. What dereferences at each pc, what structure is involved, and do they share one cause?

## Summary
- (a) and (b) are the same fault: CPU0's 4 KB interrupt stack (0xDF000000-0xDF001000) runs off its floor into the MMIO hole below 0xDF000000 while DryosDebugMsg is nested inside TryPostEvent's "MsgQue OverFlow" error path, itself called from DryosDebugMsg.
- The trigger is TryPostEvent's global event-container free list (head at RAM 0x39B84) being empty; DryosDebugMsg's own notify post then fails and logs through DryosDebugMsg again (0xE0 bytes per round).
- The register state of all 24 logged pc=0 dumps matches an epilogue popping zeros at 0xE005D8C0; it does not fit the NULL EDMAC-CBR slot (0x83F24) explanation for this signature.
- (c) is unrelated: Canon's full vsnprintf (0xE005DB9C) handling `%s` with a NULL string pointer, called from ML code on an ML task stack at boot.
- All of this is static analysis plus logged register dumps; recursion depth and who drains the pool are not proven.

## Observed

### Code (ROM0, tools/romdis.py)
- DryosDebugMsg 0xE05D10C4: `push {r0-r3}; push {r4-r11,lr}; sub sp,#0x8c` = 0xC0 bytes of stack per call. Loads context pointer from 0x5154 (literal 0xE05D1338). Exits early if `*0x5154==0`, class==0xFF, `ctx[0xC]==0`, or `ctx[0x38+class*3] > (level&0xF)`.
- 0xE05D10F6 `bl 0xE018E704` returns `[0x1008]`. cstart helper 0xE00401E8 writes the MPIDR cpu id there, so this selects a per-CPU log partition: cpu id >0 uses `ctx[0x14]` (r8=0x12); otherwise `ctx[0x10]` (r8=2), or `ctx[0x18]` for class 0x43 (r8=0x13).
- 0xE05D115C `bl 0xE005D89C(buf=sp+7, size=0x49, fmt, va)`: a mini formatter with a fixed 0x49-byte stack buffer. It copies the format, expands only `%s` (no NULL check, 0xE005D8EA), and for any other `%` stores the raw argument word at the buffer tail (0xE005D8D2). Prologue `push {r4-r7,lr}`, epilogue 0xE005D8C0 `pop {r4-r7,pc}`. Return address into DryosDebugMsg is 0xE05D1161.
- 0xE05D116A `bl 0xE005DF36(logbuf, part, &seq, rec)`: ring-buffer writer. Checks magic 0x4157554B at `[logbuf]`, masks IRQ (0xE05D0BE0) only around the slot/sequence reservation, then outside the critical section `memcpy(slot+8, rec, 0x4C)` (0xE005DF9C) and `str r8,[r4]` at **0xE005DFA2** (r4 = slot address from 0xE005EABC).
- 0xE05D116E-0xE05D1196: if `[0x5158] != 0` and `ctx[0x39+class*3] <= level`, calls 0xE05B9F9E(`ctx[4]`, seq, r8, part); on non-zero return clears `[0x5158]`.
- 0xE05B9F9E (TryPostEvent): `bl 0xE05B9EEA` pops a 16-byte container from a global free list (spinlock 0x39B80, head 0x39B84). If it returns NULL: `DryosDebugMsg(0, 6, "[TASK ERROR] TryPostEvent MsgQue OverFlow : Name = %s", obj[4])` at 0xE05B9FCC (return address 0xE05B9FD1, format at 0xE05BA10C), then assert("System::Task.c", 0xE5) via 0xE0674574, then **falls through** to `str sb,[r4,#0xc]` at 0xE05B9FDA with r4=0.
- EDMAC dispatcher (rival theory): 0xE05B7E70 `pop {r4-r8,sb,sl,lr}` then 0xE05B7E74 `bx r1`. It reloads lr and r9 from the stack before branching.
- cstart 0xE0040104: fills 0xDF000000..0xDF002000 with 0xEEEEEEEE (0xE00401A4) and calls 0xE00401E8(cpu, 0xDF000000, 0x2000, ...), which sets `[0x1014] = 0xDF000000 + 0x1000*(cpu+1)`.
- docs/15-memory-map.md:135-136: 0xC0000000-0xDEFFFFFF is device memory (sparse MMIO); 0xDF000000+ is normal RAM.
- vsnprintf 0xE005DB9C: `%s` handler at 0xE005DE42 loads the pointer from the va_list and reads it at **0xE005DE52** `ldrsb r1,[r0]` with no NULL check.

### ML source

## Inferred
- **(a) is a stack-floor fault, not a NULL callback.** With sp at or below 0xDF000000, 0xE005D89C's `push {r4-r7,lr}` lands in 0xDEFFFFxx (device memory, writes lost), and `pop {r4-r7,pc}` reads zeros. That explains r4-r7=0, pc=0, lr still 0xE05D1161, and r0/r2/r3 holding the formatter's exact exit state. The EDMAC path cannot produce this: it pops lr and r9 from its own frame before `bx r1`, so lr=0xE05D1161 and r9=0x5154 would not survive.
- **(b) is the same event one frame shallower.** DryosDebugMsg's sp was 0xDF000030, so the mini formatter survived; 0xE005DF36's frame reached 0xDF000010 and memcpy's register saves went below 0xDF000000, returning r4=r5=0. r3=0xEEEEEEEE is cstart's stack fill, read from the unwritten tail of the on-stack record.
- The stack is **CPU0's interrupt stack**, 0xDF000000-0xDF001000 (from `[0x1014]`), in SVC mode with IRQ masked. The first visible DryosDebugMsg was entered about 0xE30 bytes deep in a 0x1000-byte stack.
- **Recursion is the likely reason for that depth.** Once the container pool is empty, DryosDebugMsg -> TryPostEvent -> DryosDebugMsg(0,6,...) repeats at 0xE0 bytes per round as long as `ctx[0x39] <= 6`; `[0x5158]` is only cleared after TryPostEvent returns. About 16 rounds fill the stack. The dump's 0x100-byte stack scan shows only one round, so the depth is not confirmed.
- The 57-char output minus 51 literal chars gives a 6-character task name, consistent with the DebugMsg notify task (e.g. "DbgMgr") being the post target.
- DryosDebugMsg is interrupt-safe by design (per-CPU partitions, IRQ-masked reservation, no locks) but not safe against its own notify failing. Its 0xC0-byte frame plus ~0x34 for callees is a real cost on small stacks.
- The earlier "seed 0x83F24 slots, aborts went to 0" result does not contradict this: a later note (m50ii-symbol-shift-boot-crash.md) says the working module uses no seed and storms remained intermittent.
- **(c) has a different cause.** It is the full vsnprintf, on an ML task stack, with a format string in ML's image; an ML caller passed NULL for a `%s`. It shares only the "Canon formatters do not guard NULL" property.
- If ML's non-fatal assert handler returns from the System::Task.c:0xE5 assert, 0xE05B9FDA writes to address 0xC. A data abort at pc=0xE05B9FDA would be the same root cause.

## Unknown
- Which containers exhaust the pool and who holds them. The EIS flood suggests a Canon task not draining its queue while ISRs keep posting, but the pool size and its init are not traced.
- Whether `ctx[0x39]` (class 0 notify threshold) is <= 6, i.e. whether recursion is really unbounded.
- The outermost caller on the interrupt stack (beyond the 0x100 scan window).
- Which ML call produces (c). The three r5 values are format-string cursors in three builds; I did not map them to strings.
- Whether writes below 0xDF000000 are silently dropped or fault on hardware; the dumps imply dropped.
- Whether any ML code logs via DryosDebugMsg from vsync/ISR context in the recording path; the raw_vidx grep was negative but its logging macro was not traced.

## Implications for raw video
- The recording crash is a symptom of event-queue starvation: something in the record path (sync CPU copy, long work with IRQs masked or at high priority) stops Canon tasks from draining events until the global pool at 0x39B84 is empty. Fixing the 0x83F24 slots will not remove it.
- Cheap mitigation to test: zero `[0x5158]` (DebugMsg notify gate) while recording. That removes the recursion, so pool exhaustion becomes a logged error instead of a stack overflow. It does not fix the starvation.
- Lowering DebugMsg volume (class thresholds at `ctx[0x38+class*3]`) reduces container use by the logger itself.
- Any ML logging from ISR context costs at least 0xF4 bytes of the 4 KB interrupt stack per call.
- Guard ML `%s` arguments against NULL; Canon's formatters will fault.

## Next hardware checks
1. Idle, then armed, then recording: `rd 0x39B84` and walk the list (`next = *node`) to count free containers. A count falling toward 0 during recording confirms the trigger; a stable count refutes it.
2. `rd 0x5154` -> ctx; `rd ctx+0x38 0x10` (class 0 bytes at +0x38/+0x39/+0x3A) and `rd 0x5158`. If byte ctx+0x39 <= 6, recursion is unbounded.
3. `rd 0x1008 0x20`: expect `[0x1014]`=0xDF001000 on CPU0, confirming the interrupt stack range.
4. Before a record, write 0 to 0x5158 and record. If pc=0/lr=0xE05D1161 disappears and "[TASK ERROR] TryPostEvent MsgQue OverFlow" lines or a fault at 0xE05B9FDA appear instead, the chain is confirmed.
5. Extend the abort handler's stack scan to 0x1000 bytes when sp is in 0xDEFFxxxx-0xDF001000. Repeating 0xE05B9FD1/0xE05D1193 pairs every 0xE0 bytes prove recursion; the top entries name the ISR that started it.
6. After a record that survived: `rd 0xDF000000 0x100`. Anything other than 0xEEEEEEEE at the floor shows how close the stack came.
7. For (c): in the build that faulted, print the string at the logged r5 (e.g. 0xF6FD6) backwards to its start, or add a NULL guard in ML's snprintf wrapper and log the caller's lr.

5. **CONFIRMED, with extra evidence the report did not use.** 0xE005DF9C is `blx 0xE05D1E6C` (ARM memcpy). For aligned src/dst it reaches 0xE05D0EC0 `push {r4,r5,r6,r7,r8,lr}`. The dump shows exactly r4=r5=0 with r6=0xDF0000B4 (=&seq, sp_dbg+0x84), r8=0xE070 and lr=0xE005DFA1 intact. r2=0xFFFFFFEC = 0x4C-0x60, memcpy's residual count; r1=0xDF000080 = rec+0x4C; r3=0xEEEEEEEE is the last word of the record (0xDF00007C), loaded at 0xE05D0F18.
