## Corrections made relative to the notes

1. The "raw job ready" poll tests two constants (A1, verified); withdrawn.
2. "Redirect off kills the storm" rests on 2 attempts; attempt 44 stormed afterwards.
3. `pc=0 lr=0xE05D1161` is a stack-floor overrun inside DryosDebugMsg via TryPostEvent's
   pool-empty path, not a NULL EDMAC callback slot (A3, verified; C7 finding 4).
4. EvfDevState "nullptr" lines are failed queue posts; the hooked object at 0x10108 is not the
   object generic ML code assumes (A2, verified). A2's "3 messages per frame" figure is not
   repeated (refuted in its verification).
5. A1's "soft assert" explanation of the repeating storm lines is not repeated (refuted).
6. Resource-lock theory withdrawn (A12; not independently verified, stated as such).
7. Movie-format remount theory of docs/32 withdrawn (A6, verified).
8. "Symbol shift crashes boot" withdrawn (C6); the `0xE021B8FC` root cause is stated as unknown.
9. Boot success is 53% over all logged boots of the fast core, not about 90% (C7).
10. `big.5.3` is a NULL `%s` from ML code and predates the fast boot (A3, C7 finding 3).
11. `0xE00436FC` belongs to the big.4a MMU-patch family (C7 finding 2).

## Points where I added a reading of my own (marked Inferred in the docs)

- Reports A1 and A2 speak of a frame "copy in the hook". In the source the copy is in the worker
  task (`worker.c:431-435`); what runs in the hook is `fio_malloc`, a semaphore wait of up to 2 s
  (`event_pusher.c:98`) and UART logging. Doc 42 section 2.3 says so.
- Attempt 45 shows the EvfDevState burst with no card write logged, which the "write priority"
  explanation does not cover. This rests on rate-limited logs.
- C4c attributes a read-only-data shift to build dates; the branch-name length is the more likely
  cause (doc 43 section 6.4).
- The "module state" column of the attempt table in doc 41 comes from the memory notes, not from
  the log.
