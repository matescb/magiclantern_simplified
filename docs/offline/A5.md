# A5 - DIGIC 8 EDMAC on the M50 II (fw 1.0.1): channel map, boomer selector, asserts, API, mem2mem verdict

Static analysis only (gang100.bin, romdis/capstone + Ghidra xrefs, read-only). Nothing here was run on a camera.

## Question
Full EDMAC channel map; meaning of the boomer selector bits (0x26 vs 0x126 vs 0x226); what the two remaining
mem2mem asserts check; real addresses of the SetEDmac / Connect* / Start / Abort / RegisterCBR equivalents;
why mem2mem gave stale frames plus a DAF/EIS storm.

## Summary
1. `edmac_select_boomer` 0xe05b752e and `edmac_reset_boomer_vdkick` 0xe05b7520 are NOT EDMAC functions. They index a
   different table (0xE1087A8C, 56 "Outer" module ports) by port number. Port 13 there is boomer node 0x4E
   (mux reg 0xD0441268), not EDMAC write channel 13 (node 0x0C, mux reg 0xD042327C).
2. The real EDMAC-channel select is 0xe05b802e (Engine::Edmac.c, table 0xE0EC3BD4). It is exactly stop_boomer - 0x94,
   the same delta as M50 mk1 (a3da/a46e) and SX740 (ebbe/ec52). Bilal's unmodified 0x373f0126 passes all its checks for ch13.
3. So the mem2mem copy never routed read ch46 into write ch13, and instead wrote mux value 0x26 into a foreign
   module's input selector and pulsed that module's VdKick. That fits both symptoms (stale destination, Canon-side storm). Inferred, not proven.
4. The 0x226 "fix" only silenced the wrong function's assert. Outer.c:0xCD is an artefact of the same wrong call.
   Edmac.c:0x770 is "channel is not a read channel": 0xe05b9690 is a read-only helper and it overwrites ch13 reg +8 (3 -> 0x11).
5. Channel table: 76 channels, 0-38 write, 39-75 read; ch3 = 0xD0420200, ch13 = 0xD0420C00, ch46 = 0xD0421600.

### Boomer select: two different functions
- 0xe05b802e (Engine::Edmac.c, asserts 0x301/0x304/0x306), args (channel, sel):
  - 0x301: channel must be a write channel and have a boomer id.
  - 0x304: if sel & 0xFF00 is nonzero it must equal table InSelType.
  - 0x306: sel & 0xFFFF0000 must overlap the channel's class bit.
  - then reg +0xB4 = 2 and 0xe0683ca0(node id | (sel & 0xFF)), which writes the low 16 bits to the node's mux register.
- 0xe05b752e (Engine::Outer.c, asserts 0xA0/0xA2/0xCD), args (outer port, sel): same idea on table 0xE1087A8C,
  masks 0xF00 and 0xFFFFF000, plus a comparison of two module state getters (0xCD), then the same 0xe0683ca0.
- Canon call sites (constants recovered): 0xe05b802e is called with EDMAC write channels, e.g. (5 and 6, 0x3F7F0114) at
  0xE077038C/0xE0770396, (0x14, 0x00400401) at 0xE03BEDDE; ch20's table entry is InSelType 0x400, class 0x00400000, matching.
  0xe05b752e is called with ports such as (6, 0x7E123), (9, 0x7F211), (0x25, 0x7FFF508), a different selector layout.
- 0xe0683ca0 asserts BoomerSelector 0x10C when node >= 0xE1, or when the mux register is already nonzero and the new value is nonzero.
- VdKick: 0xe05b7fb6 -> 0xe05b56cc (writes 0), 0xe05b7fde -> 0xe05b56f6 (writes 1), 0xe05b8006 -> 0xe05b5720 (writes 0 then 1);
  all three look up 0xE0EC3BD4 by EDMAC channel. 0xe05b7520 does the 0-then-1 pulse for an Outer port.

### The two remaining asserts
- Engine::Edmac.c 0x770 at 0xE05B96A0, in 0xe05b9690: checks flags bit1 (read channel). It fires for
  StartEDmac_maybe(13) because ch13 is a write channel. The function continues and writes 0x11 to reg +8.
  The prepare function 0xe05b7b42 sets reg +8 = 0x11 for read channels and 3 for write channels, so this call
  replaces ch13's prepared value 3 with the read-channel value.
- Engine::Outer.c 0xCD at 0xE05B757A, in 0xe05b752e: calls the port's two getters (port 13: 0xE05B75D7 and 0xE05B763B)
  and asserts when both are nonzero and differ. It has nothing to do with EDMAC channel 13.

## Inferred
- Selector layout for the EDMAC select: bits 31-16 = one-hot set of write channels (within one EDMAC block) that may
  take this source; bits 15-8 = InSelType, the EDMAC block id (0x100 = 0xD0420000 block, 0x200 = 0xD0440000, ...; 0 skips the check);
  bits 7-0 = mux value written to hardware. 0x373F = write channels 1-6, 8-10, 12, 13 of block 0x100.
- 0x26 is probably "read channel index 6 of this block" (ch46 is the seventh read channel, 0xD0421600): 0x20 | 6.
  Canon's 0x3F7F01xx values use other low bytes for processing-module sources. Not confirmed by any table.
- 0x126 vs 0x226: bilal's 0x126 is correct for the real function. 0x226 was chosen to satisfy Outer port 13 and
  is wrong for EDMAC ch13.
- mk2 homologs: select = 0xe05b802e (high confidence); vdkick = 0xe05b7fb6, "VdKick off" (medium; 0xe05b8006 is the alternative).
- By the -0x3A delta, the reference ports' "ConnectReadEDmac_maybe" may be the plain disable leaf and their "StartEDmac_maybe"
  a direction-neutral function. mk2's Edmac.c is laid out differently after reset_packunpack, so the mk2 Start homolog is not settled.
  No M50 mk1 or SX740 ROM is on disk to compare bodies.
- Verdict on stale data: wrong function pair, not wrong channel pair and not cache. ch13's input mux stayed 0, so the
  write DMA had no source and the destination kept its old contents (the "Overlay\Cropmark" heap strings). At the same
  time, 0x26 went into node 0x4E's mux and node 0x4E's VdKick was pulsed, inside the 0xD0440000 engine block that Canon's
  LiveView pipeline may be using; that is a plausible trigger for the DAF/EIS storm, alongside the resource lock already suspected in docs/32.
- The 0x770 side effect (ch13 +8 = 0x11) may by itself stop the write channel from working even once the mux is right.

## Unknown
- Which Canon module owns boomer node 0x4E / Outer port 13, and whether it is live in LiveView.
- The exact meaning of reg +8 values (0x11, 0x12, 3, 0) and of +0xB4 (0, 1, 2).
- The correct mk2 start sequence for a write channel: whether prepare + enable leaf + boomer select is enough.
- Whether resources 0x100AD / 0x100BB and subchips {0, 7} are right for ch13/ch46 on this body.
- Owners of most channels; only ch3, 5, 6, 20 have evidence.
- Whether the earlier hardware "completion fired" result came from real DMA completions or from the caller invoking cbr_w unconditionally.

## Implications for raw video
- The CPU copy remains the safe default. mem2mem is worth one more attempt, because its failure is explained by two wrong stubs, not by the hardware.
- Candidate module-only change: edmac_select_boomer -> 0xe05b802e, edmac_reset_boomer_vdkick -> 0xe05b7fb6,
  MEM2MEM_BOOMER_SELECTOR back to 0x373f0126, and do not call 0xe05b9690 on ch13.
- Any earlier conclusion drawn from mem2mem behaviour on hardware (storm cause, resource-lock theory) was made with the wrong boomer node and should be re-tested.

## Next hardware checks
Do these in LiveView, photo mode, with the serial harness. `call` needs the odd address. EDMAC MMIO reads can hard-lock
if the sub-chip is asleep; the 0xD042xxxx block is awake in LiveView (ch3 lives there), 0xD044xxxx is not known to be.
1. `rd 0xD0423254` (ch3 mux), `rd 0xD0420204`, `rd 0xD0420208`, `rd 0xD04202B4`: Canon's live values for a working write channel. Tells what +4/+8/+0xB4 look like when running.
2. `rd 0xD042327C` -> expect 0 (ch13 unconnected). `call 0xe05b802f 13 0x373f0126` -> expect no assert; `rd 0xD042327C` -> 0x26 and `rd 0xD0420CB4` -> 2 confirm the real select. `call 0xe05b80c3 13` -> both back to 0.
3. `call 0xe05b802f 13 0x373f0226` -> expect Engine::Edmac.c 0x304. Confirms 0x226 is wrong for the EDMAC select. Follow with `call 0xe05b80c3 13`.
4. Only if step 1 showed the storm is not triggered by reads: `rd 0xD0441268` before and after `call 0xe05b752f 13 0x373f0226`; a change to 0x26 proves the old stub hit node 0x4E. Then `call 0xe0683ca1 0x004E0000` to clear it.
5. `call 0xe05b7b43 13`, `rd 0xD0420C08` -> expect 3; `call 0xe05b9691 13` -> expect 0x770 and `rd 0xD0420C08` -> 0x11. Confirms the clobber.
6. With the three stub/constant changes in a module-only build: one mem2mem copy of a known pattern buffer; compare destination. If still stale, try enable leaf `0xe05b7a6d` on both channels in place of 0xe05b9690.

Corrections and additions:
- Minor error: at 0xE0770390-0xE0770396 channel 6 is called with 0x3F7F0115 (`adds r1, r1, #1`), not 0x3F7F0114.
- The 0x25 in "(0x25, 0x7FFF508)" was not found at the site I checked; 0xE00EECD8 passes port 0x2B. Both rows have InSelType 0x500, so the conclusion is unaffected.
- "One-hot set of write channels" holds for block 0x100 as table data: ch1-6 = bits 16-21, ch7 = bit 22, ch8-10 = bits 24-26, ch11 = bit 27, ch12 = bit 28, ch13 = bit 29. 0x373F therefore covers ch1-6, 8-10, 12, 13 and excludes ch7 and ch11.
- 0xe0683ca0 asserts BoomerSelector 0x10C when the mux register already reads nonzero and the new value is nonzero (0xE0683CAC-0xE0683CB6). A select on ch13 without a prior 0xe05b80c2 disconnect would assert if 0xD042327C is not 0; the proposed probe sequence should read it first (it does).
- Extra support for claim 10: 0xe05b9690 has exactly one direct BL caller in ROM0 (0xE0275D56), against 130 for 0xe05b802e and 139 for 0xe05b7fb6. That is unusual for a general "start" primitive. Indirect calls were not searched.
- Caveat on the proposed fix: the current vdkick stub 0xe05b7520 tail-calls 0xe05b5720 (pulse 0 then 1), while the proposed 0xe05b7fb6 tail-calls 0xe05b56cc (writes 0 only). The pulse variant on the EDMAC table is 0xe05b8006. The report already lists it as the alternative; which one mk1 uses is not decidable here.
