## Findings

### Medium

**M1 - pool watchdog is armed by default and its constants are unproven on hardware**
(rvx_sync.c:38, 360; worker.c:564). The walk is unlocked. A pop during the walk makes it read
low; the code takes the highest of three back-to-back walks. With Canon popping steadily (or on
the second CPU) all three can read low and the recording stops. The stop is the normal clean
one, so the cost is a short clip, not a wedge. For the first clip use `wr &rvx_pool_watch 2`
(measure only) and look at "pool: free at start / minimum".

**M2 - fast copy: Canon's routine invalidates L1 only** (rvx_step1.c:32, 154, 168).
Disassembly of 0xE05D088C: `dsb; r1 = addr + size; bic r0,#0x1f; loop DCIMVAC step 0x20 while
r0 < r1; dsb; write 0 to 0xC1100730; bx lr`. Confirmed: no lock, no interrupt masking, leaf
function, so calling it from the copy task is fine. Range and alignment in `do_copy` are right
(start rounded down to 32, end exclusive, partial last line covered). Open: 0xC1100730 looks
like an outer-cache "sync", not an invalidate; if an outer cache is enabled for RAM, stale lines
survive. A13 says RAM is marked outer-non-cacheable, from the ROM table image only. DCIMVAC also
acts on the calling core only. `rvx_integrity` would show a stale read as "copy differs", but
torn frames set the same flag, so it does not separate the two. Keep `rvx_fast_copy = 0` until
A13 hardware checks 1-3 pass.

**M3 - alias address rests on the plain bit-30 mirror** (rvx_step1.c:154). `CACHEABLE()` clears
0x40000000: 0x6BC61CC8 -> 0x2BC61CC8. A13 confirmed both ranges are identity-mapped with
different cache attributes and that the aliasing happens below the MMU; that 0x2BC61CC8 reaches
the same DRAM as 0x6BC61CC8 is not confirmed. Same gate as M2.

**M4 - install/restore compare-and-store is not atomic against the second CPU**
(rvx_sync.c:194, 227, 272, 296). `cli()` masks interrupts on the calling core only. EvfState's
dispatch word is not rewritten by Canon after creation, so source 1 is low risk. The Mem1Path
slot is rewritten and cleared by Canon (0xE07541A4 / 0xE07541AC); if that runs on the other
core inside the few-instruction window, our store overwrites Canon's new value. Non-default.

**M5 - `rvx_evf_spy` forwards exactly five arguments** (rvx_sync.c:78). I did not check the
stock dispatcher 0xE05BB2B3 for a sixth (stack) argument. If it has one, source 1 corrupts
every EvfState dispatch. Check before `rvx_sync_src = 1`.

**M6 - `rvx_copy_prio != 0` creates a task per frame** (rvx_step1.c:203), 24-60 per second.
Whether DryOS reclaims task slots and stacks fast enough is not known. The worker waits for the
copy task without limit, so a starved copy task (0x1B below the 0x1A writer) stalls recording
and delays the stop; no memory hazard.

### Low

- L1 `rvx_hook_flags &= 4` (event_pusher.c:553): bit 4 is never cleared, so "hook flags" is
  printed at every later stop. `rvx_dropped_nobuf` (event_pusher.c:540) is never reset either.
- L2 Redirect on (`rvx_redirect_edmac = 1`): the worker frees the capture buffers at stop
  (worker.c:1189) while Canon's EDMAC may still point at one (event_pusher.c:626). Present
  before H1 as well. Non-default.
- L3 Allocation failure in `rvx_capture_alloc` can spawn more than one `stop_com` task while
  the hook keeps asking. Non-default.
- L4 `rvx_sync` task runs at 0x10 (rvx_sync.h:66), inside Canon's LiveView band. Its work is
  short and non-blocking, so acceptable. Non-default.
- L5 Sidecar: records stop after 2000 frames (counted in `records_lost`); name buffer is 20
  bytes with a length check (rvx_step1.c:338), so a longer path is refused, not overflowed.

### Checked, no finding

- Hook path (source 0): no semaphore, allocator, task creation, sleep or UART on any branch;
  the harness asserts the same.
- Lock-free pool: one producer at a time holds (core hook returns early while
  `rvx_sync_active`; the sync task ticks only when ACTIVE and outranks the worker). Single-core
  argument only.
- Stop while a copy or write is in flight: the copy is synchronous for the worker; the stop
  takes `write_sem` before writing and closing, unchanged from the reviewed base.
- Burst and pool self-stop: frames still queued are discarded quietly, events released.
- Install validation refuses on any mismatch and writes nothing; restore writes only if the
  word still holds our function; a rewritten Mem1Path slot is left as found and the silent
  source stops the recording after 2 s.
- `msg_queue_post` 0xE05B55EE: calls 0xE05BB71C with third argument 0 and maps -2 to error
  0xD. Consistent with a try-post; I did not read 0xE05BB71C.
