# C5 - Symbol-stability gate (offline sprint)

## Goal

Turn the working rule "keep the ML core layout unchanged, change modules only"
into host-side checks that run before a build reaches a card: compare a new
core `.sym` with the known-booting layout, check module imports, and check that
the `.sym` on a card belongs to the `autoexec.bin` beside it.

Nothing here was run on a camera. The tools only read the main checkout.

## Results

### (b) Current build vs baseline - PASS

```
files are byte-identical
added: 0   removed: 0   moved (ML core): 0   moved (ROM stubs): 0
    anchor raw_lv_redirect_edmac: 0xe5319 OK
    anchor raw_info: 0x104434 OK
    _bss_end           0x14fc00  OK
RESULT: PASS - every pre-existing symbol is at its baseline address
```

This is the baseline compared with its own source, so it only shows the tool
runs. The informative runs are the other agents' worktree builds (read only):

| Build | Result | Detail |
|---|---|---|
| `wt/C6-good` | FAIL, 1 moved | `build_version` 0xf357e -> 0xf357b (-3); passes with `--ignore build_version` |
| `wt/C4` | FAIL, 53 moved | first divergence 0xf357e, -8 on everything after; `.text`/`.rodata` ends -8 |
| `wt/C6-bad` | FAIL, 988 moved, 9 added | first divergence 0xcd121 (`module_load` +4), total shift -1240, `_bss_start` -1216 |

**Finding: the branch name changes the layout.** `version.c` stores
`build_id = "<commit> <branch>"` directly before `build_version`. The baseline
string is 28 characters; `a10b16c23 offline/C6-good` is 25 (the -3 is absorbed
by alignment, one symbol moves), `a10b16c23 offline/C4` is 20 (-8, and 53
symbols plus `.rodata.str*` and the start of `.data` move). So a rebuild of
identical core source on a differently named branch does not reproduce the
booting layout. Functions and `.bss` did not move in either case. Whether a
rodata-only shift matters on the camera is unknown.

### (d) Card check

What is comparable: `autoexec.bin` holds the core image uncompressed behind a
loader stub (blob at file offset 0x158, load address 0xc78e0), so symbol
addresses map to file offsets. There is no embedded hash of the `.sym`, and
`module_load_symbols` (`src/module.c`) does no validation. The check uses the
embedded sym filename, the four `version.c` strings at the addresses the `.sym`
claims, an absolute anchor (load address must map to the core entry branch),
a Thumb-prologue score, optional exact comparison against the ELF, module
imports, and an optional md5 manifest.

| Input | Result |
|---|---|
| `build/zip` + `--elf` | PASS: strings at claimed addresses, prologue 349/775 = 0.45 (shifted control 0.09), `.sym` equals ELF symbol table |
| `sd_mltest.raw` (stale QEMU image, read via 7z) | PASS: self-consistent older pair (1294 symbols, blob at 0x150), 2 modules |
| current autoexec + `.sym` shifted +0x98 from 0xe0000 | FAIL: entry anchor, prologue 0.16, "layout diverges part-way" |
| current autoexec + `.sym` shifted +0x40 uniformly | FAIL on the entry anchor only (prologue score stays 0.45, as expected) |
| manifest write then verify (scratch copy) | PASS, "6 file md5s match" |

```
  [ok]   sym filename matches the name embedded in autoexec.bin: M50mk2_101.sym
  [ok]   address->file delta -0xc7788: load address 0xc78e0 maps to file offset 0x158, which is the core entry branch
  [ok]   version.c strings found exactly at the addresses the .sym claims
```

## Limitations

- The baseline is "the build meant to boot". Its boot status on hardware is
  taken from the task description, not verified here.
- The stability gate compares exported globals only. Static functions and
  `_`-prefixed symbols are not in the `.sym`; a move confined to those is seen
  only through its effect on later globals or on section ends (`--elf`).
- Card check without `--elf` or a manifest is evidence, not proof: a change
  that moves only `.data`/`.bss` symbols, leaving code and the version strings
  in place, is not detected. The uniform-shift case rests on one heuristic
  (an ARM branch at the derived blob start).
- Prologue thresholds (0.30 overall, 0.15 per range) come from two real pairs
  and synthetic shifts.
- "Provided by another module" is a name match on `nm -g --defined-only`; it
  does not check load order or symbol type (e.g. `mlv_set_type` reported as
  provided by `dual_iso.mo` is probably a common symbol, not a real export).
- FAT images are read with `7z`; an image 7z cannot parse gives exit 2.
- The on-camera pairing check is only proposed (README), not implemented,
  because it needs a core change.

## Next hardware checks

1. Before the next flash: run (b) on the build and (d) on the staged card
   directory; boot only if both pass. Record the result next to the boot number.
2. Confirm the baseline really is the booting layout: after a boot, read
   `raw_lv_redirect_edmac` / `raw_info` over the serial shell (`mlresolve`) and
   compare with 0xe5319 / 0x104434.
3. Test whether a rodata-only shift is harmless: boot a build that fails the
   gate only on `build_version` (the `offline/C6-good` case), then one with the
   -8 rodata shift (`offline/C4` case). This separates "any shift crashes" from
   "code/bss shift crashes".
4. `wifidep.mo` against the walkback core: expect a load failure for the 9
   missing socket stubs; check the module load log line on the UART.
5. If a core change must ship, use the gate output (first divergence, shift
   histogram, section-end deltas) as the record of what moved for that boot.
