# A7 - Card write path and achievable speed (M50 Mark II, fw 1.0.1)

## Question
Trace `FIO_WriteFile` down to the SD host driver: chunking, buffer requirements (uncacheable / alignment), max transfer per call, cluster allocation when extending a file, where writes block, which SD bus mode is negotiated, the sustained MB/s ceiling, any Canon benchmark / tuning functions, the stubs `sd_uhs` needs, and the measured throughput in the UART history.

## Summary
- The camera already runs the card at **UHS-I SDR104, 800 mA** (hardware log), and the ROM maps SDR104 to clock index 9, which the clock-name table calls "1.8V 195.0MHz" (index-to-name mapping inferred). Bus ceiling is therefore about 93-97 MB/s.
- Measured on hardware (ML bench, 16 MB buffers, 16 GB card "SD16G"): **write 75.1 / 75.7 MB/s, read 90.4 / 93.9 MB/s**. Read sits at the bus limit; write is below it. Realistic sustained raw budget: about 70-75 MB/s.
- The FSU buffer check rejects a write only when the buffer is **cacheable (< 0x40000000) and not 32-byte aligned**; ROM addresses are also rejected. A rejected write is skipped entirely ("FSUBlockWrite: NotPrepared").
- One block-device call is capped at **0xF800 sectors (31 MiB)**; larger writes loop synchronously in the calling task. All FIO calls on a drive are serialised by a per-drive semaphore.
- There is no "set file size" call. Canon's equivalent is the **Speed Class recording mode** (`CreateSC` / `EntSC` / `RecordStart`, AU = 4 MB, RU = 512 KB on the logged card). Canon's own write-speed test (`DebugSTG_GetSDWriteSpeed`) uses `CreateSC` + `DelayFlush`. There is no SD overclock headroom worth chasing: the stock clock is already 195 MHz.

### Buffer rules (0xE00850F0, disassembly 0xE0085180-0xE00851B8)
- `addr >= 0xE0000000` -> "buf is ROM Addr", return 1.
- Else `FUN_e03f0026(addr)` ("IsUncacheableMemory", returns `addr > 0x3FFFFFFF`). If true -> accepted.
- Else if `(addr & 0x1F) == 0` -> accepted, logged with `a:0`.
- Else -> "Please Designate Uncacheable Addr!!!!!!", return 1.
- Return 1 makes `FSUBlockWrite` log "NotPrepared [W:%s s:%d c:%d" and skip the transfer.
- The function also classifies the buffer against two Canon pools (base pointers at RAM 0x416C and 0x4170, sizes from 0xDC90/0xDC98 and 0xDC94/0xDC9C) and tags it `S`, `L` or `N`. That letter is the `W:S]` seen in logs.
- Hardware history agrees: 5x "Please Designate Uncacheable Addr", 3x "buf is ROM Addr", 7x "NotPrepared" (with `c:1` and `c:63`, so the user buffer goes straight down in sector runs).

### Chunk size
- 0x100D handler (0xE00E5DCC): `FUN_e00df332()`; returns 0 -> max = **0xF800 sectors = 31 MiB**; returns 1 -> max = 0xFFFFFFFF.
- `FUN_e00df332` (0xE00DF332) returns 1 only when `FUN_e01b389a(handle, &x)` yields 2.
- The write loop in 0xE008564E advances `buf += sectorSize * chunk` (sector size at dev+0x30) until done; no yield between chunks other than two hooks (0xE036A72C / 0xE036A81C / 0xE036A854).

### Canon's own timing instrumentation
- After every completed `FSUBlockWrite`, Canon logs class 0x15 level 2: `[W:%s s:%d c:%d T:%dus Ave:%dMB/s` (string 0xE0085978; read twin 0xE008586C). Level 2 is filtered out on our UART.
- The duration in microseconds is stored at **RAM 0x640C** (write) and **0x6408** (read) (base literal 0x63FC at 0xE0085868, offsets +0x10 / +0xC).
- The M50 mk1 Discord dump contains a real line of this form: `[FSU] [W:S] (a:1)0x40aa5200 s:25189 c:1 T:3585us Ave:0MB/s`.

### Byte accounting after each write
- 0xE0084AFC adds `size` to a 64-bit counter at device+0xE8; when it crosses 4 GiB it resets and 0xE0084B2A calls `dev->ioctl(0, 0x100E)` -> 0xE00DF166. The string "SdUHS1TuningSamplingPointPartVDL %d" is referenced at 0xE00DF1AC, just after that entry.

### Bus mode selection (SdEngineWrapper, function starting 0xE00DDF7C)
- 0xE00DE1CE-0xE00DE21A: reads the card's supported access modes (0xE01B553C) and picks the highest: bit1 -> mode 1 / clock 3, bit2 -> mode 2 / clock 5, bit3 -> **mode 3 / clock 9**. The SDR104 branch is guarded by a constant-true `movs r0,#1; nop; cbz`. Bit4 (DDR50) is not tested.
- Mode names in ROM: only "SDR50" and "SDR104" strings exist (0xE137D208, 0xE137D218); no "DDR50".
- Clock-name switch at 0xE011C4E6-0xE011C516 lists, in order: 1.8V 210KHz, 20.0, 24.4, 48.8, 65.0, 97.5, 111.4, 130.0, 156.0, 195.0 MHz, then 3.3V 210KHz, 20.0, 24.4, 48.8 MHz.
- Tuning fallback (0xE00DD770-0xE00DD80C, table at 0xE0B7AA3C): for SDR104 the clock list is 9, 8, 7, 6 then terminator 0xE; for SDR50 it is 5, 4, 0xE. Each step logs "SdUHSTuning TryClkDown->%s", changes clock (0xE01B2F8C) and retunes (0xE01B5942); the terminator logs "SdUHSTuning impossible!!!".
- Hardware log (9 boots): `[SD] SD-UHS1 speed=2 clock=2`, `[UHS1]PowerSupLimit:0x800f`, `[UHS1]current:800mA mode:SDR104 strength:0x800f`, `SCType:USC AUSize:4MB RUSize:512KB SCExecType:0`. No "TryClkDown" line appears anywhere in the history.

## Inferred
- Clock index 9 = 195.0 MHz, 5 = 97.5 MHz, 3 = 48.8 MHz. The name-table order matches SDR104 / SDR50 / SDR25 exactly, but I did not decode the jump table that feeds the name switch.
- SDR104 at 195 MHz carries 97.5 MB/s raw; with CRC and token overhead roughly 93-95 MB/s. The measured 90-94 MB/s read supports both the clock value and "no headroom left".
- Write at 75 MB/s is limited by the card or by busy time, not the bus. Sustained ceiling for raw video: about 70-75 MB/s on a fast UHS-I card, lower once FAT updates and small writes are mixed in. bilal's M50 mk1 note ("~70 MB/s while recording RAW") points the same way.
- The raw_vidx gaps give only a bound of 35-70 MB/s; the timestamp quantisation makes them unusable as a measurement.
- The 0xFFFFFFFF branch of ioctl 0x100D is probably the UHS-II case, which this body cannot use.
- ioctl 0x100E every 4 GiB is probably a periodic sampling-point retune; expect a short stall there.
- `UNCACHEABLE(ptr)` in `fio-ml.c` is sufficient but stricter than needed: a 32-byte aligned cacheable buffer also passes the check. Whether the SD driver then flushes the data cache for an `a:0` buffer is not established, so the current gate plus `sync_caches()` is the safe choice.
- Speed Class mode is how Canon avoids per-cluster FAT churn: it reserves whole 4 MB AUs and writes in 512 KB RUs. `CreateSC` has only debug callers by direct BL in Ghidra, so the movie writer probably reaches it through a pointer or a different wrapper.
- The memcpy figure of ~80 MB/s is suspiciously close to the card rate. A per-frame CPU copy into the write buffer costs as much time as the card write itself.

## Unknown
- Inside the efat library (below 0xE03EF740): cluster allocation policy on extend, when the FAT and directory entry are flushed, and how a large write is split into `FSUBlockWrite` runs when the free space is fragmented.
- Whether `0xE03EF740` can return short in normal operation (the wrapper retries exactly once).
- What `FUN_e01b4362` requires of the buffer beyond the FSU check (DMA alignment, 4-byte or 512-byte boundaries, maximum descriptor count).
- Which task-level primitive `sdconRWWaitInterrupt` blocks on and its timeout value.
- Whether the DebugSTG procedures are registered at runtime, and the exact argument convention of `CreateSC`, `EntSC`, `RecordStart`.
- Behaviour on exFAT cards (the 256 GB "SR256" card mounts as `efat_map_filesys 65536 B: 1 3`); no benchmark was run on it.
- Static analysis does not show how often writes stall on card garbage collection; only a long run will.

## Implications for raw video
- Data-rate budget is about 70 MB/s. Full 2096x1164 at 14-bit is 4.27 MB/frame = 102 MB/s at 24 fps, which cannot be sustained. 10-bit (3.05 MB/frame, 73 MB/s) is marginal; 12-bit needs about 88 MB/s. Sustained 24 fps needs a crop, lower bit depth, or lossless compression.
- SD overclocking is not a lever on this body. Do not port `sd_uhs`.
- Write big, aligned, uncacheable blocks: each `FIO_WriteFile` should be a multiple of 512 KB (RU) and ideally 4 MB (AU), from a 32-byte (better 512-byte) aligned buffer. Writes above 31 MiB are split anyway.
- Remove the per-frame CPU copy. At ~80 MB/s memcpy, copying each frame halves the achievable rate. Write directly from the uncacheable capture buffer or from EDMAC-filled buffers.
- A cacheable, unaligned pointer does not fail loudly: FSU logs a warning and the data is simply not written. Keep the `UNCACHEABLE()` gate for every write path, including header and footer blocks.
- All FIO calls on B: share one semaphore. A log write, config save or screenshot from another task blocks behind a 31 MiB frame write, and vice versa. Keep other card I/O off during recording.
- Pre-allocation: the only native route is Speed Class mode. Worth one experiment (below) before investing; otherwise pre-extend the file by writing once and reuse it.

## Next hardware checks
1. **Free per-write timing.** After any single `FIO_WriteFile` of N bytes: `rd 0x640C` (last write, us) and `rd 0x6408` (last read, us). MB/s = N / value. Decides whether card writes or our copy dominate. Note it holds only the last `FSUBlockWrite` run, so use one large aligned write.
2. **Turn on Canon's own `[W:..] T:..us Ave:..MB/s` lines.** Raise the debug level for class 0x15 (FSU) to 2 or lower, then record. Each line gives start sector, sector count, time. Sector count per line shows how efat splits our writes; gaps in start sector show fragmentation.
3. **Buffer rule.** Write 1 MiB from (a) cacheable 32-byte aligned, (b) cacheable +4, (c) uncacheable +4. Expect (a) OK with `a:0`, (b) "Please Designate Uncacheable Addr" and a short or failed return, (c) OK. Read back and compare (a) to see whether the driver flushes the cache.
4. **Chunk cap.** `call 0xE00DF332` -> expect 0 (cap 0xF800 sectors). A 1 means the cap is off.
5. **Canon benchmark.** With a scratch card: `call 0xE00E6ECB` with a pointer to `{0, 0, 64}` (drive B, plain create, 64 MB), then `{0, 1, 64}` (Speed Class create + DelayFlush). Compare the "Write Time %dus" lines (class 0x17). If the SC variant is clearly faster or steadier, Speed Class mode is worth wiring into the recorder. Risk: writes `B:/DCIM/100CANON/IMG_xxxx.STG`; the directory must exist.
6. **Bus mode per card.** For each card to be used, grep boot log for `mode:SDR104` and for any `TryClkDown`. A clock-down means the card tunes badly and the ceiling drops to 156 / 130 / 111 MHz.
7. **Sustained run.** Bench with 4 MB and 16 MB buffers for at least 8 GiB on the 256 GB exFAT card. Watch for a stall at each 4 GiB boundary (ioctl 0x100E) and for the long-term rate versus the 75 MB/s short-run figure.
8. **Copy cost.** Time `memcpy` of one frame from the raw buffer to the uncacheable write buffer versus the `0x640C` write time for the same frame. If copy is within 2x of write, the zero-copy path is the next piece of work.

Consequences of the two refutations:

- Next-hardware-check 7 ("watch for a stall at each 4 GiB boundary") is likely to show nothing in SDR104; do not read the absence of a stall as evidence about the counter.
- The DebugSTG benchmark does not need a manual registration call. Probe: look up "DebugSTG_GetSDWriteSpeed" through the event-procedure name table (call-by-name) after boot; if found, run it with (drive, 0, small size) first. This gives a Canon-side MB/s figure with no ML copy in the path, to compare against the 75 MB/s ML bench. Risk: it writes a file on the card and blocks the calling task, so run it from a dedicated task, not from the serial shell.
- The 75 MB/s ceiling itself rests on one card and one bench run; the static evidence only establishes 195 MHz SDR104 as the negotiated mode, not the throughput.
