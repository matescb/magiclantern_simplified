## Question

What does the ML Discord say about crop modes and sensor register control on DIGIC 6/7/8 (crop_rec, ADTG/CMOS
registers, engio_write/EngDrvOut on D8, 4K crop, x5 zoom raw, HFR, achieved resolutions/bit depths on
M50 / R / RP / 200D / M6 II, skip offsets, black/white levels, dual ISO), and which raw modes are therefore
realistic on the M50 Mark II?

## Summary

- Hardware-confirmed on M50 mk1 (bilal_fakhouri, Aug-Sep 2025): 14-bit raw at Canon 1080p, 2096x1164 buffer / 2008x1128 active, 23.976 and 60 fps, stable after an mlv_lite realloc fix. Nothing beyond Canon's own 1080p LV raw stream has been recorded on any D8 body.
- Lower bit depth is NOT solved on D7/D8: 10/12-bit gives a good frame only every other frame on 200D and M50; the D5/D7 PACK32_MODE register does not exist as such on D8 (candidate 0xD0413194 was retracted).
- D8 has no shadow memory: EngDrvOut/shamem_read are plain MMIO read/write in 0xDxxxxxxx; `_engio_write` is a bare addr/value loop (max 500 entries). Register poking is mechanically easy; knowing which registers is the gap.
- Sensor register logging works on M50 mk1 (adtglog2 hook on CMOS_write, 200D-style 32-bit words, ISO field identified). That is the only D8 sensor-register evidence; no crop_rec, no x5-zoom raw, no 4K-crop raw, no HFR override exists for any D6/7/8 camera in the dump.
- Dual ISO on D8 is judged "pretty easy" in principle but of little benefit on M50 (mechanical shutter); untested on hardware.

## Inferred

- The M50 II's current result (2096x1164 14-bit, skip 34/88, per project memory) reproduces exactly the M50 mk1 state of 2025-08-18..31; the Discord shows no D8 body ahead of that. Anything further is new ground, not porting.
- Data-rate arithmetic (mine): 2096x1164x14 bit = 4.27 MB/frame = 102 MB/s at 23.976; cropped 2008x1128 = 3.96 MB = 95 MB/s; 12-bit cropped 81 MB/s; 10-bit cropped 68 MB/s. Against bilal's ~70 MB/s UHS-I figure, continuous full-width 1080p24 14-bit is not reachable; only 10-bit (or a reduced window around 1736x976 at 14-bit) fits. This matches the "queue fills -> auto-stop" residual in project memory. Hence bit-depth reduction or in-frame cropping is the gating feature for usable recording, not exotic crop modes.
- Because M50 mk1 60p raw worked with no extra code, Canon's 1080p50/60 (and probably 720p100/120 if the M50 II exposes it as an LV raw source) should "just work" as a different buffer size; skip offsets and black-border geometry must be re-measured per mode (kitor's warning).
- Canon 4K on M50/M50 II is a 1:1 sensor crop, so the LV raw buffer in 4K standby is plausibly an unbinned ~3840-wide stream - a "free" 1:1 crop mode with no sensor-register work, analogous to R's 4032x1289 SAP buffer. Nobody has dumped it; write speed (3840x2160x14 bit = 14.5 MB/frame) would limit it to short bursts or small windows.
- A crop_rec-style module (ML rewriting CMOS/ADTG windowing) is far off: it needs (1) CMOS_write hook on M50 II, (2) decoding of the 200D-style 32-bit register words beyond the ISO field, (3) timing-generator/FPS registers, none of which exist for any D8 body. MMU ROM patching is the prerequisite and the project memory records it as fragile on M50 II (page-pool / memory budget).
- Dual ISO is the cheapest sensor-register feature: one known field (`0b4xxxxx` word on M50 mk1) in a table Canon sends each frame. Feasible only after a CMOS_write hook is located on M50 II fw 1.0.1; benefit on this sensor is doubted by names.
- 10/12-bit: since D8 has no PACK32_MODE register and uses per-channel PackUnpackInfo, bit depth on D8 is probably a property of the EDMAC write channel's pack mode set inside MvRawPro/RawPro, not one global MMIO write. The "every other frame" symptom on 200D and M50 with three different recorders suggests the Canon side alternates/reprograms something per frame (or two buffers alternate and only one path was patched), not an ML recorder race. Unproven.

## Implications for raw video (M50 II)

Realistic now (same mechanism already working): 14-bit, Canon 1080p 24/25/30/50/60 LV raw stream, full buffer or software-cropped window; continuous only if the window/bit depth keeps the rate under roughly 70 MB/s (UHS-I).

Realistic next, no sensor registers needed: (a) smaller centred window via `src_x/src_y` in the D8 EDMAC copy (bilal's fix - check the cacheable/uncacheable handling against this port's `UNCACHEABLE(raw_info.buffer)` recipe rather than copying the mask removal); (b) recording from other Canon video modes (4K 1:1 crop, HFR) after measuring geometry; (c) packed 10/12-bit by CPU repack as a fallback if the hardware pack mode stays unsolved (costly, the sync CPU copy is already the bottleneck).

Research-grade: hardware 10/12-bit (PackUnpack path), dual ISO (needs CMOS_write hook + MMU patch), lossless.

Not realistic in the near term: crop_rec presets, x5-zoom high-res, FPS override, sensor-window 3K/5K modes - zero prior art on D6/7/8.

## Next hardware checks

All are for the serial harness (`rd`/`md`/`call`); addresses must first be resolved on fw 1.0.1 by static work.

1. Mode geometry survey (no new code). In each Canon mode (1080p24, 1080p60, 720p120 if present, 4K24, photo LV, x5, x10), after `lv_set_mm 1` + `lv_save_raw 1`, read `raw_info.buffer`, width/height/pitch as the module reports them and dump the first 64 KiB of the buffer. Decides: which modes deliver a different raw stream (4K = 1:1 crop? x5 = different window or unchanged?). Compare against M50 mk1 1080p 2096x1164 and R 4032x1289.
2. Black/white level and border measurement per mode: from the dumped frame, average the left `skip_left` columns and top `skip_top` rows (expect optical black; SX740 gave 512) and take the max of a deliberately overexposed frame. Decides raw_info.black_level/white_level and confirms 34/88 outside 1080p.
3. Shadow-free MMIO check: `rd 0xD0008094` and `rd 0xD0413194` (also 0xD041318C..0xD0413258 range) in LV idle, with `lv_save_raw` on, and while recording. A stable readable value that changes with raw on/off marks a live pack-related register; all-zero/unchanged supports "wrong register".
4. Pack-mode experiment: if (3) shows 0xD0413194 == 1 with raw active, write 0 / 0x10 / 0x20 via direct MMIO once and dump two consecutive frames; run `bit_printer` on them at 10/12/14/16. Decides whether any single-register write changes packing and whether the alternate-frame effect reproduces here.
5. Alternate-frame diagnosis: log `raw_info.buffer` address and the EDMAC write-channel address for 8 consecutive vsyncs. Two alternating addresses would explain "every other frame good" (only one of two Canon buffers/paths patched).
6. ENGP trace: enable Canon DebugMsg class used by `_engio_write` (its format string is `[%03d](0x%08X),(0x%08X)`) and capture UART across a 1080p -> 4K mode switch and an x1 -> x5 zoom switch. Yields the complete engine register table per mode with no hook - the cheapest route to mode-specific registers.
7. CMOS_write location: find the function whose caller passes a pointer to a 0xffffffff-terminated u32 table (M50 mk1: 0xe0824d02, LR e0834cfd/e0834d0f). Once a candidate exists, `md` the buffer argument region for words of the form `0b4xxxxx` and check it changes with ISO 100 -> 200 -> 400. Decides the ISO field and dual-ISO feasibility before any MMU patch is attempted.
8. LCLK gate: `rd 0xC0400008` once in LV. A data abort/hang means ML's generic `EngDrvOut()` must never run on this body (keep the stub); bit 1 set means the legacy gate is harmless.
9. Write-speed ceiling: benchmark FIO_WriteFile with 4 MiB uncacheable chunks in LV idle versus during raw capture (bilal saw a drop to ~70 MB/s). Decides the largest continuous window for 14-bit 24p.

Static analysis and Discord reports do not prove runtime behaviour on the M50 II; every "confirmed" item above is confirmed on M50 mk1, EOS R, SX740 or 200D only.
