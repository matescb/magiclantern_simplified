# C1 — Host-side MLV lane (mlv_dump, raw_vidx writer replay, mlv_check)

Offline sprint, no camera attached. Nothing here proves behaviour on the camera.
ML tree: `magiclantern_simplified` @ `walkback-milestone` (a10b16c23), not modified
(`git status` unchanged: only the two pre-existing untracked `edmac-d8.{d,o}`).

## Goal

1. Build host `mlv_dump` out of tree.
2. Build and run the `raw_vidx/mlv_3_sample_code` writer test.
3. Produce multi-frame MLVs with the *same* `mlv_3.c` the camera uses, fed with the real
   LiveView frame `tools/mlserial/captures/first_raw_capture.raw`, full frame and the
   raw_vidx crop (1792x896 at x=200,y=100), headers filled as `worker.c` does.
4. Decode with `mlv_dump`, extract DNGs, confirm the image with per-channel statistics.
5. Write `tools/mlvcheck/mlv_check.py` (dependency-free validator, tolerant of a cut-off
   last block) with pytest tests.
6. Report mismatches between what raw_vidx writes and what `mlv_dump` expects.

How to run:

```
tools/mlvcheck/host_writer/build.sh            # [ML_TREE] [OUT_DIR], defaults to the main tree + sim/C1
B=sim/C1/bin; RAW=tools/mlserial/captures/first_raw_capture.raw
$B/rvx_host_mlv -i $RAW -o crop_flush.mlv   -n 8  -s flush               # ideal stop (tail flushed)
$B/rvx_host_mlv -i $RAW -o crop_camstop.mlv -n 8  -s camera              # what worker.c COMMAND_STOP does today
$B/rvx_host_mlv -i $RAW -o crop_crash.mlv   -n 12 -s crash [-c 1000000]  # no close (+ torn tail)
$B/rvx_host_mlv -i $RAW -o full_flush.mlv   -n 5  -s flush -w 2096 -h 1164 -x 0 -y 0
$B/mlv_dump -v file.mlv
$B/mlv_dump --dng --no-fixcp --no-fixfp --no-stripes -o outdir/prefix_ file.mlv
python3 tools/mlvcheck/mlv_check.py file.mlv [-v] [--stats] [--crash-ok] [--strict] [--json] [--extract N out.raw]
python3 tools/mlvcheck/verify_image.py --src $RAW --mlv crop_flush.mlv --dng-glob 'outdir/prefix_*.dng'
cd tools/mlvcheck && python3 -m pytest -q test_mlv_check.py
```

`mlv_check.py` exit status: 0 = consistent, 1 = inconsistencies, 2 = not an MLV / unreadable.
`--crash-ok` downgrades only `TRUNCATED_BLOCK`, `TRUNCATED_HEADER` and
`FRAME_COUNT_UNFINALISED` (count still 0) to warnings, so a crashed recording can be judged
on the part that reached the card. Note that `mlv_dump` writes a `.IDX` next to its input in
some modes; run it on copies, not on the only copy of a card file.

## Results

### 1. mlv_dump build — works out of tree, the in-tree host build is broken on this branch

Two things had to be worked around (both in `build.sh`, nothing changed in the tree):

- `mlv_dump.c` includes `../../module_strings_wrapper.h`, `../../lv_rec/lv_rec.h`,
  `../../../src/raw.h`. These resolve from `modules/mlv_rec/`, but the directory now lives in
  `modules/raw_video/mlv_rec/`. The build mirrors the old layout under `sim/C1/tree`.
- `src/raw.h:217` uses `SIZE_CHECK_STRUCT(raw_info, 0xa0)` without `compiler.h`:
  `error: expected ')' before numeric constant`. Built with `'-DSIZE_CHECK_STRUCT(a,b)='`.

Result: `sim/C1/bin/mlv_dump` (250140 bytes, i386), runs.

### 2. mlv_3_sample_code — the stock Makefile does not build on this branch; fixed out of tree, runs

- `gcc -m32 ... mlv_3.c` fails: `src/property.h:338: #error No PROP_PICSTYLE scheme defined
  for your DIGIC generation!` (needs `-DMODULE`).
- Link fails: `undefined reference to 'm50ii_uart_str'` — `raw_vid.h` now routes
  `SEND_LOG_DATA_STR` to the M50 II UART function, which `function_overrides.c` lacks.

With `-DMODULE` and a one-line stub, `create_mlv` runs (rc 0) and writes a 608-byte `test.mlv`
that `mlv_dump -v` walks to the end (9 blocks, rc 0). `mlv_check` flags sample-only defects:
fps 24/1000 = 0.024, payload 4 bytes for 2x2 @ 14 bpp (should be 7).

## Mismatches found (raw_vidx writer vs mlv_dump / MLV convention)

Camera-side, in `modules/raw_video/raw_vidx`:

- **B1 (real bug, reproduced on host): clean stop loses the frames still in the crop buffer
  and writes a frame count that is too high.** `worker.c` COMMAND_STOP updates the count,
  rewrites the header and closes, but never flushes `crop_buf` (start..cur). With the
  16 MB buffers that is up to 5 crop frames (or 3 full frames); a recording shorter than
  6 crop frames ends as a 572-byte header-only file. `video_frame_count` counts those lost
  frames, so MLVI says 8 while the file has 5. mlv_dump does not notice (it processes the
  5 and exits 0).
- **B2 (convention mismatch): VIDF timestamps are absolute.** `write_video_frame_header()`
  uses `get_us_clock()`; every other block (and mlv_lite's VIDF, `mlv_lite.c:2923`) uses
  time relative to `session_start_timestamp`. mlv_dump shows header blocks at ~0.02 ms and
  the first frame at 60033 ms (uptime). Decode still works; tools that sync audio or derive
  timing from timestamps would be off by the camera uptime.
- **B3 (latent): crop/pan offsets never reach the file.** `start_mlv_session()` does not copy
  `crop_offset_x/y` and `pan_offset_x/y` from the session struct, and worker.c leaves them 0
  anyway. VIDF says `Crop: 0x0 Pan: 0x0` although the crop starts at 200,100. Relevant for
  focus-pixel / bad-pixel maps in post.
- **B4 (code reading, not exercised): possible stale-data frames and over-count on a dropped
  frame.** In IMAGE_DATA the VIDF header is written, `cur` advanced and `video_frame_count`
  incremented *before* `take_semaphore_now(edmac_sem)`; if that fails the code breaks without
  copying, leaving a counted frame whose payload is whatever was in the buffer. With the
  current synchronous copy the semaphore is always free, so this should not trigger now.
- **B5 (code reading, latent): `alloc_crop_bufs()` end pointer overruns the allocation.**
  The block is `INITIAL_CROP_BUF_SIZE + CROP_BUF_ALIGN` bytes, `start` is aligned up by
  k < 0x1000, and `end = start + buf_size`, i.e. k bytes past the block. Not reachable with
  today's frame sizes (5 x 2.81 MB = 14.05 MB of 16 MB), reachable if frames ever pack to
  within 4 KB of the end.
- **B6 (code reading): STOP can race the `raw_write` task.** COMMAND_STOP seeks to 0, rewrites
  the header and closes without waiting for an in-flight `write_buf_to_disk`.
- Not a bug: `v3.0` version string (mlv_dump ignores it), raw_info describing the 2096x1164
  source while frames are 1792x896 (mlv_lite does the same; mlv_dump compensates),
  `file_flags=4`, `fps 29970/1000`, block layouts (RAWI 0xB4, RAWC 0x20, IDNT 0x54, EXPO 0x28,
  LENS 0x60, RTCI 0x2C, WBAL 0x2C, VIDF 0x20 + padding 0x60) all parse correctly.

Host-side:

- **H1: this tree's mlv_dump has no M50 / M50 II entry in `dng/camera_id.h`.** For any WB mode
  other than CUSTOM it computes multipliers from an all-zero matrix and writes
  `AsShotNeutral = 1000000/2147483648, 1, 1000000/2147483648` -> orange renders. Raw pixels
  are unaffected. (The WBAL values in my test files are invented, but the garbage comes from
  the missing table entry, not from them.)
- **H2:** in-tree `mlv_dump` and `mlv_3_sample_code` builds are broken on this branch (see 1, 2).

## Limitations

- All frames are the same single captured frame repeated; no motion, no per-frame differences,
  so frame-order mix-ups inside the image data would not be detected (frame numbers and
  timestamps are checked).
- Host addresses and `aligned_alloc` stand in for `fio_malloc` + `UNCACHEABLE`; padding (0x60)
  matches the camera only because both buffers are 0x1000-aligned, as on the camera.
- Stand-in metadata is assumed, not read from hardware: model id 0x80000453, fps 29970,
  lens/WB/ISO values, RAWC binning. raw_info geometry/levels are the docs/35 values.
- No card, FIO, DMA, cache or timing behaviour is simulated. The `raw_write` task is run
  synchronously, so the buffer-swap race ("After buf swap, buf was in use") and B4/B6 are
  not exercised.
- `mlv_check.py --stats` only handles uncompressed 14-bit frames (row subsample).
  Multi-file (`.M00`) recordings and XREF/IDX are not followed.
- MLV App / ffplay were not tried; only this tree's mlv_dump and darktable.
