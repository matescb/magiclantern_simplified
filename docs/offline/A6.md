# A6 — Canon movie-record state machine and card mount switching (M50 II 1.0.1)

Static analysis only (ROM0 gang100.bin, base 0xE0000000). Nothing here was run on hardware.

## Question
Does Canon run vcmMovieFormatMount @0xe0202328 / fmMountCard @0xe02023c0 at record start and unmount the FAT
(docs/32 ~771-930)? What triggers the movie-record state machine, when can FIO from another task fail while Canon
records, how can ML record raw without Canon starting H.264, what are the real MVR_* constants, and how do bilal's
M50 mk1 port and kitor_raw_draft_v2 handle the record key?

## Summary
- The docs/32 premise is wrong at the address level: 0xe0202328 and 0xe02023c0 are **debug strings**, not functions.
- The real fmMountCard (0xE0202106) / fmUnmountCard (0xE0202612) are FileMgr `FmState.c` state handlers, not part of the
  movie recorder; the `vcmMovieFormatMount` / `vcmMovieFormatUnMount` calls are **compiled out** (constant 0) in this ROM.
- Record start is GUI-driven: `handleMovieButton` 0xE071FE72 (DlgLiveView.c) -> `IsEnableMovieStart` 0xE0547518 ->
  BeginMovieRecSequence -> MovRecState handler `mvrRecStart` 0xE024A8FC. No mount code was found on that path.
- "Not mounted ID=0" is most likely access to drive index 0 (A:), which never exists on this body (SD = Drive 2 = B:).
- MVR object pointer is `*(0x8B94)` (not 0x1ed8); the old 220/212 offsets are junk in bilal's working mk1 port too.

## Observed

### 1. The two "functions" are strings
| Address | Content |
|---|---|
| 0xE0202328 | `"vcmMovieFormatMount(DrvNo=%d) Failed. err=%#x"` |
| 0xE02023C0 | `"fmMountCard"` |
| 0xE02023E0 | `"FileMgr::FmState.c"` |
| 0xE02028B0 | `"fmUnmountCard (ID = %d, Ret = %#x)"` |
| 0xE0202900 | `"vcmMovieFormatUnMount failed [%#x]"` |

`python3 tools/romdis.py e0202328` decodes as nonsense Thumb because it is ASCII.

### 2. vcmMovieFormatMount is stubbed out
The only reference to the 0xE0202328 string is `adr r2` at 0xE0201F66, inside the function that logs
`"fmPrepareShooting (Drive = %d)"` (0xE020226C). The call site is:

```
E0201F56  mov   r0, sl        ; DrvNo argument set up
E0201F58  movs  r0, #0        ; <- where the BL would be: result forced to 0
E0201F5A  nop
E0201F5C  cbz   r0, #0xe0201f6c   ; always taken, "Failed" message unreachable
```

Same pattern in fmUnmountCard (0xE0202612): three sites at 0xE02026AE, 0xE02026B6 (`nop.w`), 0xE02026BC, 0xE02026EE/F4
are `movs r0,#0; nop` or `nop.w` in place of calls; the `"vcmMovieFormatUnMount failed"` print at 0xE02026CA is
guarded by `lsls r0,r0,#0x1f; beq` on that constant 0, so it is unreachable.

### 3. Real fmMountCard / fmUnmountCard
- fmMountCard = 0xE0202106 (`push.w {r0-r2,r4-r8,sb,sl,fp,lr}`, loads the "fmMountCard" string by `adr` at 0xE020210E,
  range-checks `dwDriveNo-1` against the drive count from 0xE05B4210, logs `"%s (ID = %d, Ret = %#x)"`, continues at
  0xE020240C: takes a semaphore (0xE0202438), calls 0xE0201E68 (fmPrepareShooting body), 0xE0201B0C, 0xE02017F0,
  then `_prop_request_change` (0xE02025F6) and gives the semaphore (0xE0202602)).
- fmUnmountCard = 0xE0202612; clears per-drive fields at obj+0x140/0x150/0x154/0x17C (stride 0x68 per drive),
  calls 0xE0458950 and 0xE0766568, then `_prop_request_change` with a card-status property from the table at 0xE0B62F88
  (0x8003000B/C/D).
- Both are referenced only from the FileMgr state table at 0xE0B62F98..0xE0B63120 (pairs of handler,next-state):
  fmMountCard at 0xE0B630A0, fmUnmountCard at 0xE0B630C8, fmInitialized (0xE0202704) at 0xE0B62F98. No literal-pool
  or BL reference from the MovieRecorder code (0xE0249500-0xE024C600, 0xE0729EB4-0xE072EA00) was found.

### 4. Movie record trigger chain
- `handleMovieButton` = 0xE071FE72, in DlgLiveView.c (string `"handleMovieButton RecState(%d),RTime(%d),TftSts(%d)"`
  0xE0720234 loaded at 0xE071FE8A). Neighbouring strings: `BeginMovieRecSequence UILock Failed`,
  `EndMovieRecSequence MVR_StopRecord()`, `handleMovieButton - start anytime movie`.
- Gate: 0xE071FEC8 `bl 0xE0547518` (IsEnableMovieStart); `cmp r0,#1; beq 0xE071FEDA` continues to the begin sequence;
  otherwise it sets `*(0x15ABC+0xC)=1` (0xE053CA0C), calls 0xE069A3F4 and leaves without recording.
- `IsEnableMovieStart` = 0xE0547518 (logs reasons: `!CARD_SAVE`, `!IsEnableMovieRecStart`, `unavailble movie time`,
  `WaitReplyLvDrivingMode`, `IsShowCardFull`, `LvDispBusy`, ...). Called from 0xE0443032, 0xE07090B8
  (handleMovieButtonForTimeLapse, func 0xE070906A) and 0xE071FEC8.
- `IsEnableAnyTimeMovieStart` = 0xE05475DC, single caller 0xE07BEEB8 (func 0xE07BEE98, near
  `BeginAnyTimeMovieRecSequenceReplyLvDrivingMode()`): this is the movie button pressed in a **photo** mode.
- `IsEnableMovieRecStart` = 0xE0547502 (tiny; effectively returns 1).
- Recorder side: state object name `"MovRecState"` (0xE137EF04) in a descriptor at 0xE0BB79BC followed by
  `{1, 0xE024A8FD, 1, 0}`; 0xE024A8FC logs `"mvrRecStart In"`, takes `"MovieRecorder"` (0xE05CC618), later
  `"mvrRecStart : ENCDRWRAP_WaitSlaveReady"`, `"MVR_RQ_RECSTART:%lx"`, `"mvrRecStart : Card Full"`.
  Source file strings: `MovieDS::MovRecState.c`, `MovieDS::MovieRecorder.c`, task name `MovieTSMTask` (0xE024A2D8).
- API entry `"MVR_StartRecord ( FrameType=%d )"` string at 0xE072BC0C (function not resolved in the time box).

### 5. MVR object
- `mvrChangeAckCBR` (0xE0729EB4) loads `r7 = 0x8B90` and `r2 = [r7,#4]`, then uses `r2+0x2000` / `r2+0x237C`.
  0x8B90 appears in 12 literal pools, all inside MovieRecorder.c (0xE072A1D4 .. 0xE072E9C0).
- 0xE0249DD2 (logs `"Usage 0x%x%x W 0x%x N %d"`): 64-bit accumulator at obj+0x2150/+0x2154 incremented by the
  write-size argument; 64-bit limit at obj+0x2180/+0x2184; per-item size at obj+0x2190; "full" flag obj+0x231C.
- `"WriteFrameCount = %d %d"` (0xE024B2BC) is printed at 0xE024AF46 from `[r5,#0x198]`.
- `mvrRecStart` tests obj+0x25C4 (`"mvrRecStart:SetCurState:EXT_REC"`), stores the resource result at obj+0x1C.

### 6. UART history (tools/mlserial/run/uart.jsonl, grep only)
- 0 lines containing fmMountCard, fmUnmountCard, vcmMovieFormat, "Mount Error", handleMovieButton, mvrRecStart.
- 20 lines `[FM] fmPrepareShooting (Drive = 2)`.
- `[FirstEnt] Not mounted ID=0` x862; with ID=1: AcqSize x340, FirstEnt x128, PCtrl x10, DrvName x8.

### 7. ML source
- platform/M50mk2.101/gui.h:49 now defines `BGMT_REC 0x20` (same value as bilal M50.110/gui.h:28 and kitor R.180/gui.h:22).
- src/gui.c:124 `M50II_BYPASS_GUI_OVERRIDE 1`: ML only peeks Canon's event ring and cannot swallow a key.
- mlv_lite.c:4376 / raw_vidx/event_pusher.c:260: record trigger is `MODULE_KEY_LV || MODULE_KEY_REC`, returning 0 to
  consume the key. bilal and kitor rely on the stock gui_main_task override for that consumption.
- research/bilal_M50_rawvideo/platform/M50.110/consts.h:172-186 carries the identical junk MVR block
  (`0x1ed8`, 220, 212, `MVR_BUFFER_USAGE 70`).

## Inferred
- Canon's record start does not remount or unmount the FAT volume on this firmware. The FileMgr mount handlers are
  driven by card insert/remove and init events of the FM state machine, and the movie-format (VCM) layer is absent.
  This matches the later docs/32 bisect (mount bit 0x200000 @0xAAF14 stayed set) and contradicts the 07-14 root cause.
- FileMgr drive numbers are 1-based (`fmPrepareShooting (Drive = 2)` for the SD, `dwDriveNo-1` range check), so FIO
  `ID=0` is drive A:, `ID=1` is B:. The 862 `[FirstEnt] Not mounted ID=0` lines are then directory enumeration on A:
  (which is never mounted), not an SD teardown. `ID=1` errors are the genuine B: not-ready cases (boot race).
- handleMovieButton runs in the GUI task as a dialog event handler (it has no BL callers, so it is reached through a
  dispatch table or a short branch). Not proven statically.
- `MVR_190_STRUCT` equivalent is `(*(void**)0x8B94)`. Candidate fields: bytes written = 64-bit at +0x2150;
  frame count = +0x2198 (assumes r5 = obj+0x2000 in that function, which I did not confirm); capacity = 64-bit at +0x2180.
  These only become meaningful while Canon H.264 records, which the raw path avoids.
- Because bilal's working mk1 port ships the same junk MVR values, they are not needed for raw video; ML only uses
  them for H.264 bitrate/buffer displays.
- Forcing `IsEnableMovieStart` to return 0 would make Canon ignore the movie button in movie mode while ML still sees
  the key through its peek path. `IsEnableAnyTimeMovieStart` is the equivalent gate in photo modes.

## Unknown
- Which task and which event post the mount/unmount events into the FM state machine (table decoded only partly).
- What exactly fails FIO from another task during real H.264 recording. No mount change was found; remaining
  candidates are outside this question (cacheable buffer in FIO_WriteFile, drive-letter selection, memory pressure).
- Who issues the A: FindFirst calls (ML code using a wrong drive letter, or Canon).
- The exact keycode-to-handleMovieButton dispatch and whether a RAM flag (struct at 0x14DD0, `m_fSelfMovieRecEnable`)
  can inhibit recording without a ROM patch.
- Whether offsets +0x2150 / +0x2198 are what ML's MVR_BYTES_WRITTEN / MVR_FRAME_NUMBER expect.
- is_movie_mode / set_rec_mode equivalents in ROM were not identified in the time box.

## Implications for raw video
- Stop designing around a "movie-format remount". No mount-bit polling or remount wait is justified by the ROM.
- The real requirement is the one bilal and kitor satisfy through key consumption: Canon must not start H.264 when
  the record key is used for raw. On M50 II, with the GUI override bypassed, that needs another mechanism:
  1. patch `IsEnableMovieStart` 0xE0547518 to `movs r0,#0; bx lr` (bytes 00 20 70 47) while raw is armed (costs one
     MMU remap page in a region not shared with existing patches; page budget is tight), or
  2. trigger raw from a key Canon does not act on in LiveView, or from the ML menu / serial `call`, or
  3. record in a photo mode and gate `IsEnableAnyTimeMovieStart` 0xE05475DC the same way.
- Replace the MVR block in consts.h with `MVR_190_STRUCT (*(void**)0x8B94)` only after the hardware check below;
  until then keep the code paths that use it disabled, as on mk1.
- Audit ML for paths built with "A:/" on this body; they explain the ID=0 noise and each one costs a DebugMsg.

## Next hardware checks
1. `rd 0x8B94` at idle in movie mode: expect a heap pointer. Then `rd <ptr>+0x2150 8` and `rd <ptr>+0x2198` idle
   (expect 0), start a Canon H.264 clip, read again twice 1 s apart. Monotonic growth confirms bytes/frames fields.
2. During that same Canon clip: `rd 0xAAF14` every 100 ms from before the REC press to 2 s after. Bit 0x200000 staying
   set throughout confirms no unmount. Also grep the UART for `fmMountCard` / `fmUnmountCard (ID` — expect none.
3. While Canon records, from the serial shell create and write a small file on B: with an uncacheable buffer.
   Success means concurrent FIO is fine and the earlier failures were buffer or drive-letter problems.
4. Capture the UART around one REC press and look for `handleMovieButton RecState(`, `mvrRecStart In`,
   `MVR_RQ_RECSTART`. Their presence confirms the chain in section 4 (class 0x82 / MVR class must be enabled).
5. `call 0xE0547519` in movie-mode standby: expect 1 when recording is possible. Then, as a throwaway test, MMU-patch
   0xE0547518 to `00 20 70 47`, press REC: expected result is no H.264 start and no `mvrRecStart In`.
6. Find the A: caller: log `lr` / task name on the next `[FirstEnt] Not mounted ID=0` (the mlserial atomic log already
   tags tasks), or grep ML for hard-coded "A:/" and check `get_card_drive` results on this body.

Net result: the central conclusion (the two docs/32 addresses are strings; the VCM mount/unmount calls return constant 0;
fmMountCard/fmUnmountCard are FM state-table handlers with no direct callers) survives independent checking.
Corrections to carry forward: (1) 0xE024A8FC is a wrapper, the "mvrRecStart In" body is 0xE024A068; (2) 0x8B90 has 13
ROM occurrences, 12 real; (3) handleMovieButton reaches the IsEnableMovieStart gate only under three earlier conditions;
(4) the drive-ID mapping (path[0]-'A') is now observed in code, but "A: never mounted, hence harmless" and the
"not needed for raw" / "patch is safe" statements remain inference until the hardware checks above are run.
