# C6 - Why does relinking the ML core break boot on the M50 II?

Offline analysis only. Nothing here proves behaviour on the camera.

## Goal

Test five hypotheses (H1 stale .sym/.mo on card, H2 hard-coded RAM addresses, H3 memory budget,
H4 alignment-sensitive code, H5 uninitialised statics) for the observation "a core relink that
shifts symbols breaks boot", using two builds and the hardware UART history.

## Short answer

The logs do not support the premise that symbol shift itself breaks boot.

- The `pc=0xE021B8FC` streak (boots 330-359) hit **both** core layouts with an identical
  Canon-side fault, and the "bad" layout had booted to big.8 four times just before (322, 324,
  325, 329). It started at a card touch and ended when the card was re-made.
- The `pc=0xE0729566` "deterministic 3/3" family (boots 197-199) is three boots with three
  different signatures; two of them are the known intermittent crashes that also hit the stable
  build about half the time.
- H3, H4 and H5 are refuted by the build artefacts for the a10b16c23 / fa0834b40 pair.
- H1 and H2 are real, unguarded hazards, but neither can produce a fault ~1 s after `ml_init`
  starts, before any module load and with no host command sent.

The root cause of the 0xE021B8FC streak is **not identified**. Top two candidates: state on the
SD card, versus core content/timing that is independent of layout.

for everything linked before `init.o`.

### 2. The 0xE021B8FC streak is layout-independent

`bootsig.py 322 367`, condensed:

```
322,324,325,329  size=256448 abort=0xE80F1/0xE812B  last=big.8   (329 ran 4059 s)
330-347,350-353  size=256448 abort=0xE80F1/0xE812B  last=big.1b/1c  pc=0xE021B8FC lr=0xE04037A1 dfar=0x46
348              size=256992 abort=0xE81D1/0xE820B  last=big.4a  pc=0xE02F281A (old MMU race)
349              size=256992 abort=0xE81D1/0xE820B  last=big.7   no abort
354-359          size=257696 abort=0xE81D1/0xE820B  pc=0xE021B8FC lr=0xE04037A1 dfar=0x46   (6/6)
360,361          bootloader: "ERROR: efat_openfent(/AUTOEXEC.bin)" -> FROMUTILITY menu
362-366          size=257760 abort=0xE81D1/0xE820B  2 of 5 reach big.8, no 0xE021B8FC
```

- My fa0834b40 build reproduces the 256448 / 0xE80F1 fingerprint exactly, and `FIO_RemoveFile`
  lands at 0xCF4C4, the address the host successfully called in boot 329 (`ret 0`). So boots
  322-347 ran that layout: 4 good boots, then 22 straight crashes, same layout.
- Boots 354-359 ran the **good** layout (0xE81D1, and the same 257696 size as my a10b16c23 build)
  and crashed 6/6 with the same PC, LR, `r4=0x32`, and the same ten ROM return addresses on the
  stack. They predate the a10b16c23 commit (17:41) by under two hours.
- In both layouts the abort comes about 0.8-1.0 s after `post.4: ml_init task created`. In boot
  354 ML was still in the LED blink after `big.0`; in boot 330 it had reached `big.1c`.
- Boots 360/361 show a card with no AUTOEXEC.BIN. The streak does not reappear afterwards.

Warning for the project: the build "meant to boot" has the same size and stub addresses as the
one that crashed 6/6 in boots 354-359. Whether it is the same source cannot be told from logs.

### 3. What the 0xE021B8FC fault is

From the ROM disassembly (`tools/romdis.py`) and the abort dumps:

- `0xE021B8FC` is `ldrex r1,[r2]` in a spinlock acquire; `r2 = r4 + 0x14 = 0x46`, so the object
  pointer is `0x32`.
- The caller `0xE05BFD48` is the address ML's stubs.S names `_prop_cleanup` (comment says
  "matched; verify"). It was entered with `r0=0x32`, `r1=` a heap pointer.
- Its return address is `0xE04034B7`, right after `blx r1` in `0xE040347C`, Canon's
  register-slave worker, which calls the registrant's token callback with the new token.
- Frame arithmetic matches the dump exactly (`sp+0x14`, `sp+0x2C`, `sp+0x64`), so the callback
  itself tail-called or jumped into `0xE05BFD48`.
- The task is a Canon TaskClass loop (`0xE05B9E20`, with `r9=r11=0x19980218` untouched).
- In ML the only code that references `0xE05BFD49` is `global_property_handler`, and the only
  registration site is `prop_register_handlers` (runs at big.6). ML had not registered yet.

So a slave registration processed ~1 s after `ml_init` starts has a token callback that reaches
`0xE05BFD48` with a bogus handle. Who registered it is unknown: the abort handler prints only ROM
addresses, so a RAM callback would not show.

### 4. The 0xE0729566 family (edmac-d8.c shift)

`bootsig.py 186 213`: the shifted build is size 258400, boots 197-199 only.

```
197  last=big.4a2  pc=0xE02F281A   (39 boots total, boots 141-365, all builds)
198  last=big.4a   pc=0xE00A6C44   (5 boots total, boots 173-281)
199  last=big.8    pc=0xE0729566 lr=0x000E8389 dfar=0x4   (only occurrence in 367 boots)
```

- `0xE8388` resolves to `m50ii_nonfatal_assert_handler+0x70` (init.o did not move in that build:
  same 0xE81D1 stubs). Boot 199 is ML's non-fatal assert handler returning into Canon after a
  Canon assert, followed by a NULL+4 read.
- The stable 257760 build in boots 186-213 reached big.8 in roughly half of its boots. Three
  failures in a row is about a 1-in-8 event at that rate.
- No host command was sent in boots 197-200 before the aborts.

"3/3 deterministic 0xE0729566" in the memory note is not what the log shows.

### 5. Hypotheses, ranked

| Rank | Hypothesis | Verdict | Evidence for | Evidence against |
|---|---|---|---|---|
| 1 | Card state (generalised H1) | Open, best fit for 330-359 | Starts at a card touch (329 to 330); same layout booted 4x before; two layouts fail identically; survives a 7 h power-off; ends after the card was re-made | Boots 348/349 (BAK core, presumably same card) passed the crash point 2/2 |
| 2 | Core content/timing, not layout (new) | Open | 256992 and 257760 builds never show it; fault is tied to ~1 s after `ml_init` creation | Same-layout 256448 build booted in 322-329; fast-boot and slow-boot cores both crash |
| 3 | H1 narrow: stale .sym/.mo | Real hazard, cannot explain these crashes | Loader reads `ML/MODULES/M50mk2_101.sym` with no build check; 988/1307 symbols differ; `mlwifi.py` serves only autoexec.bin by default; `flash.sh` stages only mlv_lite.mo | Crashes precede module load by 10-30 s |
| 4 | H2: hard-coded addresses | Real hazard, no logged misuse | In the bad layout 0xCD515 is `module_send_keypress+0x38` and 0xE5318 is `raw_preview_fast_ex+0x94` | `calladdr_audit.py 150 367`: every raw call matched its layout (0xCD515 on 0xE81D1, 0xCD519 on 0xE80F1); no tx before the aborts |
| 5 | H4: alignment | Refuted for this pair | - | MMU space, vector copy, abort stacks all in BSS at identical addresses; .text 2**4, .data 2**3 in both |
| 6 | H5: uninitialised statics | Refuted for this pair | - | `zero_bss()` is inlined in `copy_and_restart`; BSS layout identical, so any garbage would be identical |
| 7 | H3: memory budget | Refuted | - | `_bss_end` = 0x14FC00 in both; the 64 KB-aligned .bss leaves ~42 KB of slack before `_bss_end` can move; bad image is smaller |

## Limitations

- The root cause of the 0xE021B8FC fault is not identified; the registrant of the faulting
  callback is not in the logs.
- Builds are fingerprinted by size and stub addresses, not by hash. The exact binaries flashed
  for boots 322-367 are not available; same-size builds with different content cannot be told
  apart (this matters for 329 vs 330 and for 257696 vs 257760).
- The card image from the crashing period no longer exists.
- Persisted config files were not audited for stored addresses (the crashing card is gone).
- H4 was checked at section/symbol level, not per literal pool.
- No QEMU run was done; QEMU does not reproduce the Canon property/card state involved.
- The deploys table stops at 2026-07-19, so build ids for boots 226-367 in mllog.db are stale.

## Next hardware checks

1. **Deciding experiment (card state vs core content).** On one freshly formatted card, with
   module autoload off and a matching .sym/.mo set for each core, alternate only AUTOEXEC.BIN
   between the a10b16c23 build and the fa0834b40 build, A-B-A-B, at least 5 cold boots each,
   with the passive UART daemon running.
   - fa0834b40 reaches big.8 at the baseline rate: relinking and the boot-fix core are innocent,
     and the streak was card state.
   - 0xE021B8FC follows the fa0834b40 binary on a clean card: it is core content; bisect the
     boot-fix hunks (LED beacons, mount gate, empty patch table).
2. If 0xE021B8FC ever returns, image the card before touching it.
3. Extend `m50ii_abort_report` to print RAM code addresses on the faulting stack and the words at
   `[r8..r8+0x10]`. That names the callback in one boot.
4. Verify the `_prop_cleanup` stub (0xE05BFD48): it inserts `r1` into a list at `token+0xC`,
   which looks like it expects a node pointer, not a property id.
5. Guard H1/H2 regardless: embed a build id in the .sym and refuse a mismatch; make deploy push
   autoexec + .sym + .mo together; resolve every tool address from the .sym instead of literals.
