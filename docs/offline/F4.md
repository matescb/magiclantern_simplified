# F4 - Event-container pool exhaustion: mechanism, observability, and rules for raw_vidx

Status: static analysis of the 1.0.1 ROM (`gang100.bin`, base 0xE0000000) plus a re-read of the logged UART history
(`tools/mlserial/run/uart.jsonl`). No camera was attached. Nothing here is proven on hardware; section 8 lists the
probes that would confirm or refute the model.

## 1. Question

docs/offline/A3.md (verified) showed that the record-time crash signatures `pc=0 / lr=0xE05D1161` and
`pc=0xE005DFA2` are one fault: CPU0's 4 KB interrupt stack overflows while Canon's debug logger (`DryosDebugMsg`,
0xE05D10C4) is nested inside the "MsgQue OverFlow" error path of `TryPostEvent` (0xE05B9F9E), and that the trigger is
an empty event-container free list (head at RAM 0x39B84). This report establishes what that pool is, who fills and
drains it, why the failure is fatal, how to watch the pool level at run time, and what raw_vidx must do about it.

Terms used:
- **TaskClass**: Canon's "task with a message queue" object, created by `CreateTaskClass` 0xE05B9E60. Most Canon
  subsystem tasks (EvfDev, EvfCap, PropMgr, EIS, DAF, FileMgr, ...) are TaskClass tasks.
- **Event container**: a 16-byte node carrying one posted event (four words) from the poster to a TaskClass task.
- **Pool**: the single global array of event containers shared by every TaskClass task.
- **Notify post**: the event `DryosDebugMsg` posts to the debug-manager task ("DbgMgr") for each sufficiently severe
  message, so that DbgMgr prints it on the UART console.

## 2. Summary

- The pool is a fixed array of 1536 containers (0x600 x 16 bytes) at RAM 0xBEE18-0xC4E18. It has no free counter:
  the control block is `{lock @0x39B80, head @0x39B84, init flag @0x39B88}`. Level can only be learned by walking the
  singly linked free list from 0x39B84.
- There are exactly two allocators (`TryPostEvent`, 923 call sites; blocking `PostEvent` 0xE05B9F10, 105 call sites)
  and one releaser in normal operation: the receiving task's own loop. A container is therefore "in use" for exactly
  as long as its event sits unread in some TaskClass queue. Pool level = 1536 minus the sum of all TaskClass queue
  occupancies.
- The declared queue depths add up to at least 27,554 for the 62 creation sites I could decode (19 more are passed in
  registers), 18 times the pool. Canon relies on tasks draining; it does not budget the pool against queue depths.
  Any single queue of depth >= 1536 (MovWriter 4000, FileMgr 2000, two more of 2000/2400) or any combination of
  stalled tasks can empty it.
- Pool exhaustion is always fatal in firmware 1.0.1 with default logger settings. The pool-empty path logs at
  class 0 / level 6; the logger's default notify threshold is 6 for every class (0xE05D106C-0xE05D108A), so the log
  call itself posts a notify event, which finds the pool empty and logs again. The gate that would stop this
  (`[0x5158]`) is cleared only after the nested call returns, so the recursion is unbounded: 0xE0 bytes per round.
  This resolves A3's open question about `ctx[0x39]`.
- The recursion ends in the interrupt stack because an interrupt handler on CPU0 is the one context in which no task
  on that CPU can run and return a container; in task context a preempting receiver can refill the pool and let the
  recursion unwind. Which interrupt handler made the first failing post is not known (the abort handler's stack scan
  covers only 0x100 bytes).
- UART history: 21 of the 26 crashes of this family follow a steady 43-86 s storm of
  `[EIS] ERROR ... TryPostEvent(0xd)` and `[DAF] WARNING` lines (about 76 printed lines per second); 3 follow an
  `EvfDevState.c L:174 / L:21E` assert burst that begins right after the first `FIO_WriteFile`; 2 have almost no
  lead-in. `0xd` is `msg_queue_post`'s "queue full" code, not pool-empty: a Canon task had already stopped draining.
  The string "MsgQue OverFlow" never appears in the log, as expected if the first occurrence is fatal.
- Rules for raw_vidx are in section 7: nothing slow in the state-object hook, no CPU-bound ML task above
  priority 0x15, a pool-level watchdog with a bounded free-list walk, the logger notify gate closed during
  recording, and stop-on-first-distress-sign.

## 3. Observed (ROM)

### 3.1 Pool layout and creation
- `CreateTaskClass` 0xE05B9E60 `(name, prio, stack, queue_len, handler)`: allocates a 0x18-byte object, creates a
  message queue of `queue_len` entries (0xE05B9E8A), then at 0xE05B9EA0 tests the byte at `[0x39B80+8]`. If it is
  zero the pool is built once: `[0x39B80]=0`, `[0x39B84]=0xBEE18` (literal at 0xE05BA0C4), flag set, and a loop
  (0xE05B9EB8-0xE05B9EC4, bound `movw r3,#0x5ff`, step 0x10) links each node to the next; the last node's link is set
  to 0 at 0xE05B9EC8. Result: 0x600 = 1536 nodes of 16 bytes, 0xBEE18..0xC4E17, created lazily by the first
  CreateTaskClass call. There is no second pool and no growth path.
- Control block at 0x39B80: `+0` spinlock word, `+4` free-list head, `+8` init flag byte. Neither the allocator nor
  the releaser touches any other word, so **no free count exists anywhere**.
- Allocator 0xE05B9EEA: takes the lock with 0xE021B8F0 (saves CPSR, `cpsid i`, `ldrex/strex` on the lock word), pops
  the head (`r0=[0x39B84]`; if non-zero `[0x39B84]=[r0]`), releases the lock, restores CPSR, returns the node or 0.
- Releaser 0xE05B9DB0(node): same lock; `[node]=head; head=node`. It does not check `node` for NULL.
- A container holds `[0]=arg1, [4]=arg2, [8]=arg3, [0xC]=arg4` (stores at 0xE05B9FDA-0xE05B9FE4). While free, word
  `[0]` is the link.

### 3.2 Every allocator and releaser
A scan of all Thumb `bl` targets in ROM0 gives:

| Function | Role | Direct call sites |
|---|---|---|
| 0xE05B9EEA | pool pop | 2: 0xE05B9F2E (PostEvent), 0xE05B9FBE (TryPostEvent) |
| 0xE05B9DB0 | pool push | 4: 0xE05B9E18, 0xE05B9F5E, 0xE05B9FF4, 0xE05BA060 |
| 0xE05B9F9E TryPostEvent (non-blocking) | allocates, posts with `msg_queue_post` 0xE05B55EE | 923 |
| 0xE05B9F10 PostEvent (blocking) | allocates, posts with `msg_queue_post_blocking` 0xE05B556C | 105 |
| 0xE05B9DD6 receive | `msg_queue_receive`, copies 4 words out, frees (0xE05B9E18) | 1: the task loop at 0xE05B9E38 |
| 0xE05B9FFC receive variant | queue receive 0xE05B5522, copies out, frees (0xE05BA060) | not counted |

- The four release sites are: the TaskClass task loop after receiving (0xE05B9E18); the receive variant
  (0xE05BA060); and the two post-failure paths (0xE05B9F5E after a failed blocking post, 0xE05B9FF4 after a failed
  non-blocking post).
- The task loop 0xE05B9E20 is `while (obj->alive) { receive; handler(arg1..arg4); }`. The container is freed inside
  the receive, before the handler runs, so a container is held only while its event is queued, not while it is being
  handled.
- Consequence: the only way a container stays allocated is an event waiting in a TaskClass queue. The tasks "that
  free containers" are simply all TaskClass tasks, each for its own queue; the pool empties when receivers stop
  running (blocked, starved, or stuck in their handler) while posters keep posting.

### 3.3 Queue depths versus pool size
Decoding `r3` at the 81 CreateTaskClass call sites (62 immediate, 19 register-passed): the immediate ones sum to
27,554 entries. Largest: MovWriter 4000 (0xE04A76DC), 2400 (0xE04799EE), FileMgr 2000 (0xE0796234), 2000
(0xE0767664), five queues of 1200, DbgMgr 1000 (0xE05D0FB4), two more of 1000, PropMgr 512 (0xE05BF8FC), 512
(0xE02C7EB4). EvfDev and EvfCap are 200 each (0xE065B640, 0xE06CB038; A2.md:16-17). EIS's depth is register-passed
(0xE060B638) and was not resolved.

### 3.4 What a failed post does
- `msg_queue_post` 0xE05B55EE returns 0xD when the kernel reports "would block" (0xE05B5606 `cmn r0,#2`,
  0xE05B5620 `movs r0,#0xd`). `TryPostEvent` then frees the container and returns 0xD (0xE05B9FEE-0xE05B9FF8).
  **Queue-full is recoverable and leaks nothing.** The caller decides what to do; EvfDev's posters assert
  (EvfDevState.c L:0x174 / L:0x21E, A2.md:18), EIS logs `TryPostEvent(%#x)` (strings at 0xE03F3ACC, 0xE03F3B00).
- Pool-empty in `TryPostEvent` (0xE05B9FC2 `movs r4,r0; bne`): `DryosDebugMsg(0, 6, "[TASK ERROR] TryPostEvent
  MsgQue OverFlow : Name = %s", obj->name)` at 0xE05B9FCC, then assert `System::Task.c` line 0xE5 via 0xE0674574,
  then **no branch**: execution continues at 0xE05B9FDA `str sb,[r4,#0xc]` with r4 = 0, i.e. it writes the four
  event words to addresses 0x0-0xF and posts a NULL message pointer to the target queue.
- Pool-empty in blocking `PostEvent` (0xE05B9F2E-0xE05B9F34): there is no NULL check at all; it writes to 0x0-0xF
  and posts NULL without logging.
- A receiver that dequeues a NULL message reads its four arguments from addresses 0x0-0xF (0xE05B9E04-0xE05B9E14)
  and calls 0xE05B9DB0(0), which stores the current head at address 0 and sets the head to 0.

### 3.5 The logger's notify post and its thresholds
- DbgMgr is created at 0xE05D0FB4: `CreateTaskClass(name, prio, stack 0, queue_len 0x3E8, handler 0xE05D0F3D)`;
  priority 0x1F according to A11.md:258. Its object is stored at `ctx+4`, where ctx is the 0x338-byte logger context
  whose pointer lives at 0x5154.
- Default thresholds are written by the loop 0xE05D106C-0xE05D108A for all 256 message classes: `ctx[0x38+3c]=5`
  (store threshold), `ctx[0x39+3c]=6` (notify threshold), `ctx[0x3A+3c]=0`.
- `DryosDebugMsg` 0xE05D116E-0xE05D1196: if `[0x5158] != 0` and `ctx[0x39+3*class] <= (level & 0xF)`, call
  `TryPostEvent(ctx[4] = DbgMgr, ...)`; if that returns non-zero, clear `[0x5158]` (0xE05D1196).
- So every message with `level & 0xF >= 6` costs one container until DbgMgr, the lowest-priority task in the
  system, runs. The pool-empty message is level 6 and therefore qualifies.

### 3.6 Interrupt entry and the stack involved
- IRQ vector handler 0xE03C50FC: on the interrupted mode's SVC stack it saves 0x40 bytes (`srsdb` 8, `push {ip,lr}`
  8, `sub sp,#0x18`, `push {r0-r5}` 0x18); if the nesting counter `[0x100C]` was 0 it switches to
  `sp = [0x1014]` (0xE03C5130) and calls `isr_dispatch` 0xE018E17C. A nested interrupt keeps the current stack
  (0xE03C517C-0xE03C5184), so nested handlers share the same 4 KB.
- `[0x1014]` is 0xDF001000 on CPU0 (cstart 0xE00401E8, A3.md claim 6); the floor is 0xDF000000.
- `isr_dispatch` pushes 10 registers (0x28 bytes, 0xE018E17C) and calls the registered handler with `blx r4`
  (0xE018E210). An interrupt with no registered handler prints `"\n-- Illegal inter 0x%x(%d)[puId %d] --"`
  (format at 0xE018E598) through `uart_printf`.
- Frame sizes on the failing path: `TryPostEvent` 0x20 (`push {r4-r8,sb,sl,lr}`), `DryosDebugMsg` 0xC0 (A3 claim 1),
  mini formatter 0x14, ring writer 0x20 plus memcpy 0x18 (A3 claim 5).

- The printed console lines carry a log index and a millisecond timestamp. In group A the index advances about 177

## 5. Inferred

1. **Who is being starved.** In group A the EIS task's queue is full (code 0xD), so EIS had stopped receiving well
   before the crash while its posters kept running at two posts per frame; DAF and DAFPath report missing frames
   and timeouts at the same time. This is a wedged LiveView pipeline, not a slow one. The pool then empties over
   43-86 s, a net loss of 18-36 containers per second, or roughly one per 40 ms frame. The sink must be one or more
   queues that are deep enough to absorb about 1500 events and whose owner is not running. Candidates by depth are
   in 3.3; which one it is cannot be told from the log. (Confidence: the timing arithmetic is solid; the
   identification of a single per-frame sink is a hypothesis.)
2. **DbgMgr was draining in group A.** The console kept printing notify-level lines up to the abort, and each such
   line is the result of DbgMgr handling one notify event. So the debug storm itself was not the sink there, though
   it adds a standing occupancy equal to DbgMgr's backlog. If DbgMgr is fully starved, 76 notify posts per second
   would fill its 1000-entry queue in 13 s and hold two thirds of the pool.
3. **Group B is a different route to the same end.** The L:174/L:21E pattern is A2's four posts per frame to EvfDev
   failing with queue-full, so EvfDev had already been stalled for at least 200 posts (about 2 s at 25 fps), which
   covers the `cbr_w` period and the 14 MB synchronous write. A full EvfDev queue holds only 200 containers; the
   other ~1300 must have been consumed elsewhere in the same seconds, or the pool was already depleted before the
   recording started (these sessions had long uptimes and earlier attempts), or the head was forced to 0 by the
   NULL-release path of 3.4. The log does not discriminate between these.
4. **Why the interrupt stack.** With the pool empty, `TryPostEvent -> DryosDebugMsg -> TryPostEvent` repeats at
   0x20 + 0xC0 = 0xE0 bytes per round and nothing inside the loop can change the pool state. In task context a
   higher-priority receiver can preempt, free a container and let the recursion unwind (after which the gate is
   closed and one NULL message has been posted per unwound level). In interrupt context on CPU0 no task on that CPU
   runs, so unless a CPU1 task frees a container within the few microseconds the recursion needs, the stack is
   consumed: (0x1000 - 0x28 dispatcher frame - handler frames) / 0xE0 is at most 18 rounds. The observed sp values
   (0xDEFFFFC8-0xDF000010) are the last round crossing the floor. Interrupt handlers post events every frame, so an
   interrupt is also the most probable first context to meet the empty pool.
5. **The failing post originated in an interrupt handler that calls `TryPostEvent` directly or logs at level >= 6.**
   A2 documents two per-frame posters into EvfDev (`evfLvComEvent` 0xE069A670 and the sync callback 0xE069A7E8,
   A2.md:75-82); the EIS "GLOBALVECTOR" posts are a third candidate. None is proven to be the one on the stack.
6. **No back-pressure exists.** Posters get an error only for queue-full. Pool-empty is treated as a fatal
   programming error (assert), and the code after the assert is not written to survive it. With Canon's own assert
   handler the camera stops there; with ML's non-fatal handler returning, execution continues into the NULL writes
   of 3.4. Either way exhaustion is unrecoverable, and with the notify gate open it is a stack overflow before the
   assert is even reached.
7. **`[kern] 0 interrupt occurs!` at record start** (group C and seven other places) shows interrupts being taken
   around the moment raw_vidx arms the raw path; A1.md:83 and B1.md:110 discuss its meaning. It costs interrupt-stack
   depth and UART time but does not use the pool. Its relation to the 3 s crash is not established.

## 6. Unknown

- The idle pool level and the level during normal Canon movie recording. Without it the watchdog thresholds below
  are guesses.
- Which queue absorbs the containers in group A, and why EIS stops receiving.
- Which interrupt handler is at the base of the faulting stack.
- Whether tasks on CPU1 receive TaskClass events (which would make the interrupt-context recursion racy rather than
  deterministic).
- Whether addresses 0x0-0xF are writable and what the NULL-message path does to the receiving handler in practice.
- EIS's queue depth and the 18 other register-passed depths.
- Whether any run-time code changes the notify thresholds from their default of 6.

## 7. Rules for raw_vidx

Each rule states the mechanism it protects against.

1. **The state-object hook does bookkeeping only.** It runs in the EvfDev task (A2.md:18). While it runs, EvfDev
   receives nothing; posters add 3-4 containers per frame to its 200-entry queue (A2.md:122, 216), and after about
   50 frames every post asserts. Allowed in the hook: read the frame address and a timestamp, write one slot of a
   lock-free ring, give a semaphore. Not allowed: frame memcpy, waiting on a semaphore or queue, `msleep`, any file
   I/O, any UART print (the `[RVX] wk.*` dumps seen in group B/C logs are printed per frame), any `DryosDebugMsg`.
   Target: well under 1 ms per invocation.
2. **No CPU-bound ML task numerically below 0x15.** The current worker copies at 0x11 (raw_vid_worker.h:16), which
   starves PropMgr (0x14, queue 512), Imager (0x14, 200), EIS (0x13) and everything below (A11.md:106). Each starved
   TaskClass task converts its incoming events into held containers. Use A11's proposal: copy at 0x15, write at 0x16
   or lower. A task that only blocks on a queue may sit higher.
3. **Never hold a CPU continuously for more than about one frame, at any priority.** DbgMgr runs at 0x1F, below
   every ML task; while it is starved each level >= 6 message holds a container (up to 1000). Yield (`msleep(1)` or
   a blocking wait) at least once per frame in the copy loop and between write chunks.
4. **File I/O only from the low-priority write task**, never from the hook or the copy task, and in chunks small
   enough that rule 3 holds. The group B crashes begin immediately after a single 14 MB `FIO_WriteFile`.
5. **Pool watchdog.** Before starting and then every few frames from the copy task, measure the free level with a
   bounded walk (below). Suggested thresholds until hardware numbers exist: refuse to start below 1024 free; drop
   frames (skip the copy, keep the hook trivial) below 512; stop recording and remove the hook below 256. Also poll
   EvfDev's queue occupancy with Canon's getter 0xE05BA078(taskclass) where taskclass = `*(*(0x9B48) + 8)`
   (A2.md:39-41, 151) and stop if it exceeds about 50.
6. **Close the logger's notify gate while recording**: save `*(uint32_t*)0x5158`, write 0, restore on stop. This
   removes the recursion (3.5) and stops debug messages from consuming containers. It also silences Canon's UART
   console for the duration. It does not make exhaustion survivable (3.4), so it complements rule 5, it does not
   replace it.
7. **Stop on the first distress sign**, not on the crash: any `EvfDevState.c` L:0x174 or L:0x21E assert, or a pool
   level under the stop threshold. ML's non-fatal assert handler should treat `System::Task.c` line 0xE5 as fatal
   (log once over ML's own UART writer and halt) rather than return into the NULL writes.
8. **ML code must not call `DryosDebugMsg` with `level & 0xF >= 6`** from the hook, from interrupt context or in
   per-frame paths; raw_vidx already logs through ML's own UART writer (A3 verification item 11), keep it that way.

Watchdog walk (read-only, safe against a concurrent pop/push because it is bounded and range-checked; it may
under- or over-count by a few nodes when racing, which is acceptable for a threshold test):

```c
#define EVPOOL_HEAD   (*(volatile uint32_t *)0x39B84)
#define EVPOOL_BASE   0x000BEE18u
#define EVPOOL_END    0x000C4E18u      /* base + 0x600 * 0x10 */

/* Returns min(free containers, limit). Cost: at most `limit` loads. */
static int evpool_free_at_least(int limit)
{
    uint32_t p = EVPOOL_HEAD;
    int n = 0;
    while (n < limit && p >= EVPOOL_BASE && p < EVPOOL_END && !(p & 0xF)) {
        p = *(volatile uint32_t *)p;
        n++;
    }
    return n;
}
```

`evpool_free_at_least(512)` costs at most 512 dependent loads (tens of microseconds). A full count for diagnostics
is `evpool_free_at_least(1536)`. To learn who holds the containers, mark the free nodes with a full walk and
histogram word `[0]` (the first event argument, usually the target object) of the remaining nodes.

## 8. Hardware probes

1. Baseline: full free count at idle LiveView, in Canon movie record, and after a clean ML recording stop. Expect a
   value close to 1536 at idle; a value that does not return to baseline after stop means a task is still wedged.
2. During an ML recording, log `evpool_free_at_least(1536)` once per second over ML's UART writer. The model
   predicts a monotonic fall before each crash of this family; a flat level up to the crash refutes it.
3. When the level is falling, run the in-use histogram of section 7 and resolve the dominant `[0]` value to an
   object (e.g. `*(0x9B48)` is EvfDev). This names the stalled receiver directly.
4. `rd 0x5154` -> ctx; `rd ctx+0x38 0x10`: expect bytes 05 06 00 repeating (defaults of 3.5). `rd 0x5158`: non-zero
   while the console is live.
5. With the gate closed (rule 6) and the watchdog disabled, provoke the failure. Prediction: no
   `pc=0 / lr=0xE05D1161`; instead an assert at `System::Task.c` L:0xE5, and afterwards `rd 0x0 0x10` shows event
   words where the vector area was.
6. After any survived run, `rd 0xDF000000 0x200`: the count of words still equal to 0xEEEEEEEE gives the interrupt
   stack's high-water mark (cstart fills it, A3.md).
7. Extend the abort handler's stack scan to the whole range sp..0xDF001000 when sp is within 0xDEFF0000-0xDF001000.
   Pairs of 0xE05B9FD1 / 0xE05D1193 every 0xE0 bytes confirm the recursion; the entries above the last pair name the
   interrupt handler and its poster.
8. A/B at fixed scene and card, ten runs each: (a) current build; (b) hook reduced per rule 1 and priorities per
   rule 2. Compare minimum pool level and EvfDev queue maximum per run.
9. `rd 0x0 4` at idle after a long session: a value inside 0xBEE18-0xC4E18 means the releaser was once called with
   NULL (3.4), i.e. a pool-empty event happened and was survived.
