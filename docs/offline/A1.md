# A1 - LiveView raw job construction and its ready/consume contract

Static analysis of ROM0 1.0.1 (gang100.bin). Nothing here was run on hardware; runtime behaviour is inferred.

## Question

What does Canon do after `lv_save_raw(1)`, what do the `MvRawProDs.c L:125` / `RawPro.c L:1C4` / `LvJob.c L:D5` asserts check, what is the 2-slot ring and who drains it, what is the raw-frame consumer expected to do, and why can reading the buffer from our vsync hook storm even when our "ready" flags say ready?

## Summary

- `lv_save_raw(1)` builds no job. It sets one flag in **Mem1Path** (ctx 0x10238, +0x40; this is `LiveViewDrive::Mem1Path.c`, not "EvfState"). Each frame, `Mem1Path_SetParam` (0xE0754298) re-programs **EDMAC write channel 3** with a buffer the LV core passes in.
- The three asserts are not about lv_save_raw. They are overflow checks in the always-running LV capture pipeline (MvRawProPath -> MvRawProDs -> RawPro, and the 6-slot LvJob pool). They fire when VD kicks continue but Canon's **EDMAC write-complete callbacks stop draining**.
- The 2-slot rings hold "which completions are expected for this VD kick". Only Canon's EDMAC-complete CBR (0xE0760A30) pops them. Anything that replaces that CBR, or stops those channels completing, storms within 3 VDs.
- The flags our module polls (`0x23800+0x30`, `0x292B0+0x30`) are a Create() argument and an EDMAC channel number. They are constant from LV start, so "READY immediately" carried no information.
- No ack/release/CBR is owed by the consumer. The only per-frame "frame done" signal Canon has is the channel-3 complete CBR slot at Mem1Path +0x64. Most likely missing step: sync to that instead of VD, and never touch Canon's EDMAC channels or CBRs.

## Observed

### lv_save_raw / lv_set_mm (flags only)

- `lv_save_raw` handler 0xE06C0D04: stores arg to `[0x19094+4]`; if arg != 0 and `[0x19094+0xc]` and `[+0x10]` are both non-zero it clears them; then tail-calls 0xE075442A, which is `str r0,[0x10238+0x40]; bx lr`.
- `lv_set_mm` handler 0xE0753D86: `[0x10238+0x44]=arg`, `[0x10238+0x6c+0xc] = (arg==0)`. The +0x6c block is later passed to 0xE05B93C4(3, ctx+0x6c) for EDMAC channel 3.
- Both asserts in this module use the string `LiveViewDrive::Mem1Path.c` (0xE07544F4). So ctx 0x10238 is Mem1Path.

### Mem1Path (ctx 0x10238)

- `Mem1Path_Init` 0xE0753DAA: registers eventprocs (lv_af_raw, lv_rshd_raw, lv_set_raw, lv_set_mm handler 0xE0753D87), sets +0x4c=1.
- `Mem1Path_SetPath` 0xE0754236 (called from CapPath 0xE06CFBB6): if `[+0x48] | [+0x50] == 0`: lock engine resources, wake sub-chips, `edmac_reset_channel(3)`, 0xE05B81C8(3,5), `edmac_set_transfer_mode(3,1)`, `RegisterEDmacCompleteCBR(3, 0xE0753D9D, 0)`, then +0x50=1. This does not test the lv_save_raw flag.
- `Mem1Path_SetParam` 0xE0754298(param), tail-called per frame from CapPath 0xE06CFC46:
  - if +0x50 == 0: return.
  - if `[+0x40] != 0` AND `param[8] != 0`: pick width/height into +0x10/+0x14 by raw type `[+0]` (<0x14: +0x18/+0x1c, or +0x20/+0x24 for types 9/0xB/0xF when +0x28 set; >=0x1B with +0x3c set: +0x34/+0x38; else +0x2c/+0x30); line bytes = `width*7/4`; `[+0x58] = param[8]`; on first armed frame `[+0x5c] = param[8]`, `[+0x60] = 1`; then `edmac_set_size(3,..)`, `edmac_set_address(3,[+0x58])`, 0xE05B802E(3,[+0xc]) and four engine calls.
  - otherwise: `edmac_stop_boomer_maybe(3)`.
- Channel-3 complete CBR 0xE0753D9C: calls `[+0x64]([+0x68])` if set. The slot is written by 0xE07541A4, called once from `LiveView::ImagerState.c` at 0xE06AD6F0 with `imagerMem1PathWrDmacCompleteCBR` (0xE06AD51B).
- `imagerMem1PathWrDmacCompleteCBR` 0xE06AD51A: reads ImagerState `[0x93A4+0xc]`: 0 -> nothing; 1 -> give semaphore once (`+0x10` latch); 2 -> count frames against a list at 0x4D810 and give semaphore at the end. Strings next to it: `imagerSaveRaw`, `imagerMultipleSaveRaw`.
- Getters: 0xE0754424 returns +0x58 (current buffer), 0xE0754436 returns +0x5c (first buffer), 0xE0754402 returns `w*h*7/4`.

### CapPath (LiveViewDrive::Path.c, ctx 0x10220)

- Init 0xE06CFB10 calls MvRawProPath init 0xE076FD00, 0xE07AE0E6, 0xE0770302, Mem1Path_Init.
- SetPath (around 0xE06CFBA0): `MvRawProPath_SetCompleteCBR(0xE06CFA71, 1)`, `MvRawProPath_SetPath`, `Mem1Path_SetPath(0)`, ..., `[0x10220+0xc]=1`.
- Start 0xE06CFBF2: `MvRawProPath_Start` 0xE076FDF2, 0xE07AE240, 0xE077050C.
- SetParam 0xE06CFC2C: 0xE07AE264, 0xE077054A, 0xE076FEB8, then `Mem1Path_SetParam`.
- `CapPath_CompleteCBR` 0xE06CFA70: ORs bit into +8, logs `CapPath Complete 0x%x(0x%x)`, when mask == 1 calls `[+0x10]([+0x14])`.

### MvRawProPath / MvRawProDs / RawPro (the asserting chain)

- `MvRawProPath_Start` 0xE076FDF2 (ctx 0x1910C): if `[+0xc]`: call 0xE07B9CB0; if `[+0x10]==0` call 0xE07B9D08.
- `MvRawProDs_Create` 0xE07B9B28(cfg, r1, r2) (ctx 0x23800), called only from MvRawProPath_SetPath at 0xE076FDCA with `r1 = [0x1910C+0x10]`, r2=5: zeroes +0x34, +0x38, +4, +0x18, +0x1c, +0x20, +0x24; **`[+0x30] = r1`**; calls `RawPro_Create` 0xE0760A88 with mode 0x120021 / channel 0x29 (or 0x120017 / 0x4C), registers 0xE07B9AD1 as RawPro's complete CBR (bit 1) and with a second sub-module at 0xE0761B50 (bit 2); sets bits in `[+0x18]`.
- `MvRawProDs_PushFrame` 0xE07B9CB0: if `[+0x18] != 0`: IRQ off; **if `[+4] >= 2`** -> line 0x125 report, then `[+4]=0`; `ring[+0x34 + 4*count] = [+0x18]`; count++; IRQ on. Tail-calls `RawPro_PushFrame`.
- `MvRawProDs_SubCompleteCBR` 0xE07B9AD0(bit): `[+0x20] |= bit`; if equal to `ring[0]`: clear, `ring[0]=ring[1]`, `[+4]--`, call `[+8]([+0xc])` (= MvRawProPath_CompleteCBR 0xE076FCC5).
- 0xE07B9D08: asserts line 0x132 if `[+0x30] != 0`. 0xE07B9D58 / 0xE07B9D7E: assert lines 0x151 / 0x15E if `[+0x30] != 1`. So +0x30 selects a variant; it is not a "created" flag.
- `RawPro_Create` 0xE0760A88 (ctx 0x292B0): zeroes ring +0x64/+0x68, count +0, masks +0x24/+0x28/+0x2c; `[+0x30]=cfg[8]` (EDMAC channel A), `[+0x34]=cfg[4]` (EDMAC channel B), `[+4]=cfg[0]` (mode), `[+8]=cfg[0xc]`. `RegisterEDmacCompleteCBR([+0x30], 0xE0760A31, 2)` at 0xE0760B6C and `RegisterEDmacCompleteCBR([+0x34], 0xE0760A31, 1)` at 0xE0760CBA (skipped for modes 0x120017 / 0x120000).
- `RawPro_PushFrame` 0xE0760E74: mask = bit0 if mode is not 0x120017/0x120000, bit1 if `[+0x60]==1`. If mask != 0: IRQ off; **if `[+0] >= 2`** -> line 0x1C4 report, `[+0]=0`; `ring[+0x64 + 4*count] = mask`; count++.
- `RawPro_EDmacCompleteCBR` 0xE0760A30(bit): `[+0x28] |= bit`; if equal to `ring[0]`: clear, shift ring, `[+0]--`, call `[+0x14]([+0x18])` (= 0xE07B9AD1 with bit 1).
- Both "asserts" first call 0xE06C811E (returns `[0x22D9C+8]`). If non-zero they call `[0x22D9C](file, line)` via 0xE06C8124 instead of the fatal assert 0xE0674574, then reset the count and carry on.

### LvJob (LiveViewCore::LvJob.c, ctx 0x9A04)

- `LvJob_CreateJob` 0xE06AF4B2: scans 6 slots at 0x50AF8, stride 0x188, for `slot[0] != 0` (free). If none: log `LiveView CreateJob BufferOver`, call `[0x9A04+0x28]` if set, re-test slot `[0x9A04+8]`; **still busy -> assert line 0xD5**. Then marks the slot busy (`slot[0]=0`).
- 0xE06AF552 sets `job[0]=1`; it is referenced from stage tables at 0xE099F658..0xE099F70C.

### Our module and the reference

- `modules/raw_video/raw_vidx/worker.c:496-510` polls `*(0x23800+0x30)==1 && *(0x292B0+0x30)!=0` as "raw job READY".
- `research/bilal_M50_rawvideo/src/raw.c:2456-2461` does the same `lv_set_mm(1)` + `lv_save_raw(1)`; its only RegisterEDmacCompleteCBR calls are on its own mem2mem channels (`platform/M50.110/edmac-d8.c:116-117`). Our port's edmac-d8.c uses channels 46 and 13 (`platform/M50mk2.101/edmac-d8.c:83-84,168-169`). `m50ii_seed_edmac_cbrs` no longer exists in the walkback-milestone tree.

## Inferred

- **Sequence after lv_save_raw(1):** nothing is constructed. From the next CapPath_SetParam on, if the LV core supplies a buffer in `param[8]`, channel 3 is pointed at it and the sensor raw (tap chosen by lv_set_raw/raw type, packing by lv_set_mm) is written there every frame, to the same or a core-chosen address. Whether `param[8]` is non-zero in plain LV is not established (see Unknown).
- **What the asserts mean:** L:125 and L:1C4 = "a third VD kick arrived while two earlier kicks still await their EDMAC completions". L:D5 = "all 6 LV jobs still in flight". All three are the same symptom at different depths: the capture pipeline's completion callbacks stopped while VD kept ticking. Because the first two are soft in this mode and reset their counter, they re-fire about every third VD, which is the "storm" shape.
- **Who drains:** only Canon's 0xE0760A30, from the EDMAC completion of the two RawPro channels (`[0x292B0+0x30]`, `[0x292B0+0x34]`, expected 0x29 for B). RegisterEDmacCompleteCBR holds one CBR per channel, so an ML registration on either channel, a redirect that changes that channel's address/size so it never completes, or an abort/reset of it, stops the drain permanently. This matches the two earlier fixes (CBR seed removed, redirect off).
- **Why the READY poll passed and it still stormed:** `0x23800+0x30` is the variant argument stored at Create (LV start) and `0x292B0+0x30` is a channel number. Both are non-zero whenever LV is up. The poll never observed pipeline health.
- **Why a vsync-hook read can still storm:** the ring gives exactly one frame of slack. Candidates, not distinguishable statically: (a) the hook runs inside the EVF state machine, so a multi-millisecond uncacheable copy (2096x1164x14 bit = 4.27 MB) delays the task that programs/starts the next frame's EDMACs while VD-driven pushes continue; (b) our own mem2mem EDMAC use contends for engine resources with channels RawPro waits on; (c) reading at VD rather than at channel-3 completion races the write and is unrelated to the storm. I rank (a) first because the residual storm was intermittent and load-dependent.
- **Consumer contract:** Canon's own consumer (imagerSaveRaw) only waits on a semaphore given by the channel-3 complete CBR. There is no ack, release or buffer return.
- **Most likely missing step:** take the frame at channel-3 write-complete (Mem1Path +0x64 slot, chaining to 0xE06AD51B), do the copy in a task, and gate start-of-recording on the ring counters being < 2 and stable rather than on the +0x30 fields.

## Unknown

- Whether `param[8]` is supplied in normal LV, and by whom. If it is zero, channel 3 is stopped every frame and `raw_info.buffer` content would come from somewhere else.
- Whether `RAW_LV_EDMAC_CHANNEL_ADDR 0xD0420200` is channel 3's register block (not checked against the EDMAC base table).
- The runtime value of `[0x292B0+0x30]` (RawPro channel A, from MvRawProPath cfg[0x10]) and whether `[0x292B0+0x60]` (raw-write bit) is ever 1 in LV.
- Calling context of MvRawProPath_Start (VD ISR vs. EVF task). This decides whether hypothesis (a) is possible.
- The `[kern] N interrupt occurs!` message (string at 0xE05BA4E0, next to SystemIF::KerSys.c) was not analysed; its relation to the ring overflow is unproven.
- What `[0x22D9C]` (soft-assert sink) is and who sets `[0x22D9C+8]`.
- What the 2026-07-22 storm build had enabled; I did not correlate with uart.jsonl.

## Implications for raw video

- Stop treating the MvRawPro asserts as an lv_save_raw race. They indicate ML disturbed, or starved, Canon's per-frame EDMAC completions.
- Hard rule for the module: never RegisterEDmacCompleteCBR, redirect, reset or abort on channel 3, 0x29, 0x4C or whatever `[0x292B0+0x30]` holds.
- Replace the READY poll in worker.c:496-510 with ring-health checks: `[0x23804] < 2` and `[0x292B0] < 2` over several VDs, and all six `0x50AF8 + n*0x188` not simultaneously 0.
- Move the frame copy out of the vsync hook. Signal a task from the channel-3 completion and copy there.
- `[0x10290]` (Mem1Path +0x58) is Canon's own record of the address it programmed this frame. It is a better source for `raw_info.buffer` than reading the MMIO register.

## Next hardware checks

All are read-only `rd` probes unless stated. Do them in LV, photo mode, before loading raw_vidx.

1. Baseline, lv_save_raw never called: `rd 0x10278 0x30` (Mem1Path +0x40..+0x6f). Expect +0x40=0, +0x4c=1, +0x50=1. If +0x50=0, Mem1Path is inactive and lv_save_raw cannot work in this mode (check +0x48).
2. `call lv_set_mm 1`, `call lv_save_raw 1`, wait 200 ms, `rd 0x10278 0x30` and `rd 0x10248 8`. +0x58 (0x10290) non-zero and +0x60=1 means the core supplies `param[8]` and channel 3 is armed; compare 0x10290 with raw_info.buffer (0x6BC61CC8). +0x58 = 0 means no buffer is supplied and the raw data path is not Mem1Path.
3. Identify the channels: `rd 0x292B0 0x70`. Record +4 (mode), +8, +0x30, +0x34, +0x60. Add both channels to the module's forbidden list.
4. Ring health while idle: sample `rd 0x23804 4`, `rd 0x23818 4`, `rd 0x23834 8`, `rd 0x292B0 4`, `rd 0x29314 8` ten times. Healthy = counts 0 or 1. If a count sits at 2 before we record, the pipeline is already degraded and recording will storm.
5. Same samples during a recording attempt with the copy in the hook, then with the copy disabled (`frame` skipped). Counts reaching 2 only with the copy enabled confirms hypothesis (a).
6. LvJob pool: `rd 0x50AF8 4`, `rd 0x50C80 4`, `rd 0x50E08 4`, `rd 0x50F90 4`, `rd 0x51118 4`, `rd 0x512A0 4`. All six zero at once = L:D5 imminent.
7. CBR integrity after module load: `rd 0x1029C 8` must read E06AD51B and its arg; any other value means something replaced Mem1Path's CBR slot.
8. Soft-assert mode: `rd 0x22D9C 12`. +8 non-zero explains non-fatal repeated prints.
9. Sync-point experiment (write, one word): save `[0x1029C]`, write the address of a module function that sets a flag and then calls the saved pointer with `[0x102A0]`. If the flag ticks once per frame after lv_save_raw(1), use it as the frame-ready signal and retire the VD-based read.

### Evidence

1. CONFIRMED. 0xE06C0D04: `ldr r1,=0x19094; ldr r0,[r0]; str r0,[r1,#4]`, then `b.w 0xE075442A`. 0xE075442A is `ldr r1,=0x10238; str r0,[r1,#0x40]; bx lr`. 0xE0753D86 writes `[0x10238+0x44]` and `[0x10238+0x6c+0xc]` (= +0x78) = !arg. Assert string at 0xE07544F4 is `LiveViewDrive::Mem1Path.c`. Omission: when the argument is non-zero and both `[0x19094+0xc]` and `[0x19094+0x10]` are non-zero, the handler also clears those two words (0xE06C0D0A-0xE06C0D18). "Only writes [+4]" is therefore not quite complete; what +0xc/+0x10 are is unknown.

2. CONFIRMED. 0xE0754236 never reads +0x40; guarded by `[+0x48]|[+0x50]==0`; calls edmac_reset_channel(3), 0xE05B8146(3), 0xE05B81C8(3,5), edmac_set_transfer_mode(3,1), RegisterEDmacCompleteCBR(3, 0xE0753D9D, 0), sets `[+0x50]=1`. 0xE0753D9C is a trampoline: `if [+0x64] bx [+0x64]([+0x68])`. 0xE0754298: if `[+0x50]==0` return; if `[+0x40]==0` or `param[8]==0` it calls 0xE05B80C2(3) (stop); else `[+0x58]=param[8]`, latches `[+0x5c]` once via `[+0x60]`, then 0xE05B93C4(3, ctx+0x6c). The two calls after 0xE05B93C4 were not re-checked as being set_size/set_address.

3. CONFIRMED. 0xE07B9CB0: `ldr r0,[0x23800+0x18]; cbz -> skip`; `ldr r0,[+4]; cmp #2; blo`; line 0x125; `str 0,[+4]`; `ring[+0x34 + 4*count] = [+0x18]`; count++; tail-call 0xE0760E74. 0xE0760E74: mask bit0 if mode `[+4]` is neither 0x120017 nor 0x120000, bit1 if `[+0x60]==1`; skip entirely if mask==0; `[+0] >= 2` gives line 0x1C4, reset, `ring[+0x64 + 4*count] = mask`. Fatal-path file strings: 0xE07B9F08 `Engine::MvRawProDs.c`, 0xE0761268 `Engine::RawPro.c`. Note the ring entries are expected-completion bit masks, not frame pointers (the original report says this correctly in section "Observed"; summary finding 3 is looser).

4. Mechanics CONFIRMED. 0xE0760A30(bit): `[+0x28] |= bit`; only if `[+0x28] == ring[0]` does it clear +0x28, copy ring[1] to ring[0], decrement `[+0]`, and call `[+0x14]([+0x18])`. Registrations: 0xE0760B6C `RegisterEDmacCompleteCBR([+0x30], 0xE0760A31, 2)` and 0xE0760CBA `RegisterEDmacCompleteCBR([+0x34], 0xE0760A31, 1)` (second skipped for modes 0x120017/0x120000). 0xE0760A31 has exactly one literal-pool reference (0xE0760E38). 0xE07B9AD0 has the same shape on ctx 0x23800 (+0x20 accumulator, ring +0x34, count +4, calls `[+8]([+0xc])`); 0xE07B9AD1 has one literal reference (0xE07B9EDC), passed to 0xE0760DEC with r1=1; 0xE076FCC5 is passed to 0xE07B9C80 at 0xE076FDCE. UNVERIFIABLE here: that nothing else decrements the counts. Literal 0x292B0 also appears at 0xE0761750 and 0xE076184C and 0x23800 at 0xE07BA224; I did not audit every store through those. The onward link to CapPath_CompleteCBR 0xE06CFA70 was not re-checked.
   Additional observation the report does not state: the pop is an exact-equality test, not a superset test. If a completion bit arrives that is not in ring[0] (stale bit after a mode change, or a completion for a kick whose mask was pushed differently), the accumulator can never equal ring[0] again and is never cleared, so the drain stalls permanently, not for one frame. INFERRED consequence only.

5. CONFIRMED. 0xE06AF4D8-0xE06AF4F2: index*0x188 (`(i + i<<4 + i<<5) << 3` = i*392) into 0x50AF8, loop to 6, non-zero word = free. None free: DebugMsg `LiveView CreateJob BufferOver` (0xE06AF690), optional `blx [0x9A04+0x28]`, re-test slot `[0x9A04+8]`, assert 0xD5 with `LiveViewCore::LvJob.c` (0xE06AF5E8). Then `slot[0]=0`.

6. Code CONFIRMED, inference REFUTED. 0xE06C811E returns `[0x22D9C+8]`; 0xE06C8124 does `ldrd r3,r2,[0x22D9C]; bx r3`. Both ring checks branch to that sink when non-zero and to 0xE0674574 otherwise. But the two paths use different file strings: the soft sink gets `EPM/Capture/MvRawProDs/MvRawProDs.c` (0xE07B9EE4) and `EHD/Capture/RawPro/RawPro.c` (0xE076124C), the fatal path gets `Engine::MvRawProDs.c` and `Engine::RawPro.c`. `tools/mlserial/run/uart.jsonl` contains 12 lines each of `[ML] !!! ASSERT (non-fatal): nullptr @ Engine::MvRawProDs.c L:00000125` and `... Engine::RawPro.c L:000001C4`, 9 of `LiveViewCore::LvJob.c L:000000D5`, and zero occurrences of `EPM/Capture`. So at runtime the fatal path 0xE0674574 was taken, meaning `[0x22D9C+8]` was 0. 0xE0674574 jumps to the handler at `[0x4000]` if set, else prints and spins at 0xE06745AA (`b .`). The lines repeat only because ML installs `m50ii_nonfatal_assert_handler` (src/init.c:1238-1262, M50II_NONFATAL_ASSERTS=1), which returns. On stock firmware the first overflow would hang the camera. Also 0x22D9C has a single literal-pool reference (0xE06C812C), so no writer of +8 was found via that literal.
   Two further corrections: (a) with no drain at all the arithmetic gives a report every second push, not every third (count 2 -> report+reset+push = 1 -> push = 2 -> report); only the first report takes three pushes. (b) The handler caps logging at 32 lines total (init.c `logged < 32`), so UART line counts say nothing about storm rate or duration.

7. CONFIRMED. 0xE07B9B58 `str r1,[0x23800+0x30]`; caller 0xE076FDC6 loads `r1 = [r5+0x10]` with r5 = 0x1910C (literal at 0xE07700B0), r2=5. 0xE07B9D08 asserts line 0x132 if `[+0x30]!=0`; 0xE07B9D58 and 0xE07B9D7E assert 0x151/0x15E if `[+0x30]!=1`. "Passes whenever LV is up" is INFERRED (depends on the runtime value of `[0x1910C+0x10]`), though the two logged READY lines are consistent with it.

Behaviour CONFIRMED. 0xE06AD51A: assert 0x112 if arg==0, DebugMsg `imagerMem1PathWrDmacCompleteCBR`, then on `[0x93A4+0xc]`: 0 returns; 1 calls 0xE06AD418 (`give_semaphore([0x93A4+0x1c])`) once, latched by +0x10; 2 counts `[0x4D810+8]` against `[0x4D810]` and gives the semaphore on equality; other values assert 0x12B. ### Net effect on the report's conclusions

- The structural findings (rings, drain chain, Mem1Path, LvJob pool) hold.
- The "soft assert explains the storm" explanation is wrong. The storm is a fatal Canon assert being survived by ML's own handler; after the first L:125 the capture pipeline is in a state Canon never intended to continue from, so everything after the first line (including L:D5 and possibly the `[kern] N interrupt occurs!` lines) may be secondary damage. Hardware check 8 (`rd 0x22D9C 12`) should be expected to show +8 == 0.
- Hypothesis (a) (long copy in the EVF hook starves EDMAC programming) remains unproven and is not distinguished from the exact-equality stall noted under claim 4. A decisive probe: on the first L:125, read `rd 0x292B0 4`, `rd 0x292D8 4` (accumulator +0x28), `rd 0x29314 8` (ring), and `rd 0x23804 4`, `rd 0x23820 4`, `rd 0x23834 8`. Accumulator non-zero and different from ring[0] means a mask mismatch (wrong/missing completion bit); accumulator zero with count 2 means no completions arrived at all (channel stopped, CBR replaced, or starved).
