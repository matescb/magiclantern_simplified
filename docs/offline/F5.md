# F5 - PropertyMgr boot crash (pc=0xE021B8FC lr=0xE04037A1 dfar=0x46): RAM-blob registrations, ML overlap, timing

Offline static analysis plus UART history. Nothing here was run on the camera. The crash is
**still not identified**; this report removes several candidates, adds one timing fact that
changes where to look, and specifies the probe that names the culprit in one crashing boot.

## Terms

- **Record**: the block `prop_register_slave` (0xE05BF79E) allocates and posts to the PropertyMgr
  task: `{handler, priv, token_cb, n, props[n]}` (0xE05BF7E8/0xE05BF7EE).
- **Token**: the block the worker `FUN_e040347c` allocates per registration, `0x18 + 12*n` bytes.
- **token_cb**: the registrant's callback that receives the token pointer (worker call at 0xE04034B4).
- **Handler**: the registrant's property-change callback `f(prop_id, priv, buf, len)`; it normally
  ends with `_prop_cleanup(token, prop_id)` (0xE05BFD48).
- **X**: the unknown function that ran in the token_cb slot and tail-called
  `_prop_cleanup(0x32, <token pointer>)`.
- **Blob**: Canon code and data copied at boot from ROM 0xE13BB074 to RAM 0x0223B000..0x02319530
  (firmware_entry 0xE0040050..0xE0040062). ROM address = RAM address + 0xDF180074.

## Summary

1. All 14 registrations made from the blob are coded correctly in ROM, and the blob is excluded
   as the home of X on three independent grounds (section 1). The "adjacent handler/token_cb"
   idea from the A4 verifier does not survive: a handler entered in place of its own token_cb
   would read a token field that is still zero, and a zero token does not fault (0xE0403796).
2. ML does not overlap, relocate or patch the blob's RAM. ML does execute the blob *copy loop*
   from its own relocated copy of firmware_entry, with the two cache-maintenance calls rerouted
   through ML wrappers, but this is identical in every boot, good or bad (section 2).
3. New timing fact: the abort lands at the instant the SD card mount completes, and at or after
   Canon log time 3888 ms. In the fast-boot core the abort cuts ML's own print
   `[ML] big.1c: car` (the mount-ready message) in half. In a good boot Canon's file catalogue
   start (`FC_PrepareCatalog`, 4133 ms) and a registration with a run-time property count
   (0xE01DC11E, logged at 4144 ms) fall in exactly this window (sections 4, 5).
4. Canon's early heap layout changed in the middle of the crash streak without an ML build
   change: the PropertyMgr manager object (r10) is 0x00809CC4 in dumps 1-14 and 0x00809FD8 in
   dumps 15-29. Something on the Canon side differed between those boots before PropertyMgr was
   even created (section 5).
5. What 0x32 is remains unknown. It is not a token and not a zeroed global (section 3).
6. Cheapest decisive probe: in the abort handler, when pc == 0xE021B8FC, print 4 words at r8
   and 3 words at r6. `r6[1]` is the registrant's handler (already written at 0xE04034A4 before
   the callback runs) and `r8[2]` is X. That names both the module and the bad slot in one boot
   (section 7).

## 1. Registrations made from the blob (task 1)

Observed, from `tools/romdis.py` on gang100.bin. All calls go through the veneer 0xE1418930 to
`prop_register_slave`. Argument order at every site is r0=props, r1=n, r2=handler, r3=priv,
[sp]=token_cb, which matches the callee (0xE05BF79E reads the 5th argument from the stack).

### 1a. Module with state pointer `*(0xA5E0)` = 0x00058278 (init function ROM 0xE13E9514)

### 1d. Could a small corruption turn a token_cb into its handler?

- Observed: in six of the seven 1a pairs the handler is the instruction after the token_cb's
  `bx lr`. Three pairs differ in exactly one bit (bit 3) of the pointer: 0x02268E57/0x02268E5F,
  0x02268E15/0x02268E1D, 0x02268F93/0x02268F9B. The token_cb literals live in the RAM copy of
  the code's literal pool (for example RAM 0x02269614 = ROM 0xE13E9688), so a damaged RAM copy
  or a lost `bx lr` would produce "handler runs in the token_cb role".
- Inferred, and decisive against it: such a handler would fetch its token from the struct field
  its token_cb never wrote. Those fields are zero (explicitly zeroed, or BSS). `_prop_cleanup`
  with a zero token takes the branch at 0xE0403796 to 0xE04037BC and does not touch address
  0x46. The crash needs a non-zero 0x32.
- For the 1b table, shifting an entry by one word in either direction gives a pointer where n
  belongs (allocation of gigabytes fails with "NOT ENOUGH MEMORY", 0xE0403154), not this crash.
- Observed, from the crashing boot itself (db boot 330, `sim/C6/boot330.txt`): Canon logged
  `NotFoundID:0x02030023,Func:0x02268E5E` (log index 595) and
  `NotFoundID:0x02050066,Func:0x0225FD08` (index 810). That message is emitted by the worker's
  delivery loop (string 0xE0403A98, printed with `token[1] & ~1`), which is only reached after
  the token_cb call at 0xE04034B4 has returned. So the 0x16-property registration of 1a and
  entry 1 of 1b completed their token callbacks normally in a boot that crashed later.
- Size: the largest blob registration has n = 0x39. Record plus token is under 0x400 bytes, far
  from the constant 0xF34 distance between record and token in all 29 dumps.

Conclusion (Inferred): X is not one of the blob's registrations, and the blob's RAM copy was
executing correctly at Canon time 3440 ms in the crashing boots.

## 2. Does ML modify or relocate the blob's RAM? (task 2)

Observed:

- ML's image and BSS occupy 0x000C78D8..0x0014FC00 (C6.md build table; docs/13, docs/15). The
  blob is at 0x0223B000..0x02319530 (firmware_entry literals 0xE00400D8, 0xE00400DC). There is
  no address overlap. The MMU remap pool (`generic_mmu_space` 0x130000) and the abort vector
  copy (0x14F640) are inside ML's BSS.
- The only ROM patch applied in these boots is the GraphicsConvertPosType cluster at
  0xE01B8CAC (`mmu.gcpt` lines in the boot log); `normal_code_patches` is empty in the
  crashing core. Neither touches 0x0223xxxx.
- ML does run the blob copy itself, indirectly: `copy_and_restart` copies 0x800 bytes of
  firmware_entry to a RAM buffer and runs that copy (wt/C6-bad `src/boot-d678.c:1224-1232`,
  `FIRMWARE_ENTRY_LEN` in `platform/M50mk2.101/consts.h:26`). In the copy, the `bl dcache_clean`
  at 0xE0040068 and the `bl icache_invalidate` at 0xE0040072, which follow the blob copy loop,
  are redirected to `my_dcache_clean` / `my_icache_invalidate` (boot-d678.c:1183-1193,
  1242-1245; consts.h:9-12). The wrappers forward to the Canon functions 0xE05D08F4 and
  0xE05D09C8 (stubs.S:38, 40).
- Canon's own code passes a nonsensical length to that icache_invalidate: r1 = 0x2AD1C -
  0x0223B000 (literal 0xE00400E0 reloaded into r3 at 0xE004006E). This is in ROM, not an ML
  effect (also noted in A15.md line 30).
- The branch patch at 0xE00400C0 is known to damage the neighbouring literal at 0xE00400C8;
  ML restores that one word (boot-d678.c:1294-1305). The blob copy literals at
  0xE00400D4..0xE00400DC were not checked on hardware.

Inferred: everything above is the same in every boot of a given core, including the boots that
reach big.8, so it cannot by itself start and stop a streak. Together with the two "NotFound"
lines in section 1d it makes "ML damaged the blob" the least likely explanation.

Unknown: whether the relocated firmware_entry leaves the literals 0xE00400D4..0xE00400DC
intact on hardware (a wrong value there would stop every boot, so they almost certainly are).

## 3. What holds 0x32? (task 3)

Observed:

- `_prop_cleanup` tolerates a zero token (0xE0403796 -> 0xE04037BC uses the default object at
  `[0x63B0+0x1C]`). The fault needs `token + 0x14 = 0x46`, so the first argument was exactly
  0x32.
- All token locations in the blob start as zero: `*(0xA5E0)`, `*(0xA590)`, 0xA68C and 0x10798
  are zero in the boot-time data image; 0x58278 is BSS (`raminit.py`).
- ML's `global_token` (0x148DBC) is in ML's BSS, cleared by `zero_bss()`, and ML has not
  registered at the time of the crash (property.c:179 runs at big.6a).
- At the fault r7 = r8 = record. The dispatcher sets r7 = record (0xE05BB2C2) and neither
  `_prop_cleanup` nor 0xE0403788 changes r7 before the fault, so X either never used r7 or
  saved and restored it. X therefore returned through a normal epilogue or had no frame.

Inferred: X read 0x32 from a location that is not a token variable for this registration: a
counter, an enum or a state byte of some module, or a field of a struct reached through a
pointer that pointed somewhere else than intended. 0x32 is 50 decimal; nothing found here
gives it a meaning.

Unknown: the location, and therefore the owner. No ROM search was done for "tail call to
`_prop_cleanup` whose r0 comes from a non-token field"; with 77 + 12 tail-call sites that is a
feasible follow-up (about one hour) but the hardware probe in section 7 answers it directly.

## 4. Can card contents influence the path? (task 4)

Observed:

- ML's mount gate polls `is_file("B:/AUTOEXEC.BIN")` every 100 ms and prints
  `[ML] big.1c: card mount ready` as soon as it succeeds (wt/C6-bad `src/init.c:962-970`).
- In db boot 330 the UART shows `1264:   3580.11[ML] big.1c: car` immediately followed by the
  `[ABORT]` dump (`sim/C6/boot330.txt`, host time 7.030 s). The ML message was cut after 11
  characters. In the good boot 329 the same message completes at host time 7.220 s.
- In boot 330 the UART had already carried Canon log lines up to index 2122, Canon time
  3888.888 ms (`[FMID] FMID_SequentialProc`), before the abort. The crash is therefore at or
  after 3888 ms of Canon time.
- In good boot 329 the Canon log shows, in that window: `2530: 4133.131 [FC] WARN
  FC_PrepareCatalog[Task:FileMgr]: 0x0328 -> 0x09f0`, then `2596/2597: 4144.29 [PROPAD] ERROR
  GetPropID(0)=0x0E080015 ... [PRP] ERROR NotFoundID:0x0E080015,Func:0xE01DA956`. The UART
  stream only shows warnings and errors, so registrations that log nothing are invisible.
- The registration that produces that line is at ROM 0xE01DC11E: handler 0xE01DA957
  (literal 0xE01DC410), token_cb 0xE01DA871 (literal 0xE01DC40C), priv 0, and **props and n are
  parameters of the enclosing function** 0xE01DC0D2 (r7 = arg 1, r6 = arg 2), whose only
  direct caller is 0xE05C0ABA (props from r11, n from r10). It allocates a 0x1CE0-byte state
  block first (0xE01DC0DA..0xE01DC0E6). The token_cb at 0xE01DA870 has a frame
  (`push {r4,lr}`) and logs through DebugMsg before storing into the struct at 0x54DC.
- In boot 354 (slow-boot core) ML was still in its LED blink after big.0 when the same abort
  came (C6.md section 2). Canon mounts the card on its own schedule regardless of what ML's
  init task is doing.
- ML does not read any setting from the card before big.3 (`config_flag` load) and does not
  call any property function before big.6a.

Inferred:

- The crash is tied to Canon's card-mount completion, not to an ML action. Canon's FileMgr and
  file-catalogue code run at that moment and their inputs are the card's directory contents
  (DCIM folders, file numbering, catalogue files). That is a concrete route by which a card
  change could start the streak and re-making the card could end it.
- The 0xE01DC11E registration is in the right time window and has a caller-supplied n, so it
  is a candidate for the faulting record. It is only a candidate: its ROM token_cb is not a
  `_prop_cleanup` tail-caller, so for it to be X the record or the call's 5th argument would
  have to be wrong at run time.

Unknown: which Canon task posts the faulting registration; the value of n at 0xE05C0ABA;
whether FC_PrepareCatalog or the mount callback registers slaves itself. The crashing card
image no longer exists (C6.md, Limitations).

## 5. Address pattern across the 29 dumps (task 5)

Observed (my own parse of `tools/mlserial/run/uart.jsonl`; all 29 dumps parsed):

- token - record = 0xF34, r4 = 0x32, r7 = r8 in 29 of 29.
- Record address: 0x00EC37A4 in the first dump (2026-07-21 01:10 UTC); 0x00EBE750..0x00EBEEEC
  in the other 28. The spread of those 28 is 0x79C bytes.
- r10 (PropertyMgr manager object): 0x00809CC4 in dumps 1-14, 0x00809FD8 in dumps 15-29. The
  switch is between the dumps at Unix time 1784631489 and 1784632633. By C6's fingerprints the
  first 22 dumps are the 256448-byte core, so the switch does not coincide with the change of
  ML core at dump 23.
- The record sits about 7 MB above the manager object in the same heap, in every dump.

Inferred:

- The faulting registration is the same one in every boot, made at the same point of Canon's
  start-up (address spread under 2 KB after megabytes of earlier allocations).
- A constant 0xF34 gap means that between allocating the record and allocating the token,
  the same allocations happen every time. If the token directly follows the record, n is about
  965 (A4). If the gap also holds the message block and other blocks, n is smaller; the gap
  alone cannot tell. No registration in the blob comes close (section 1d).
- The 0x314-byte move of the manager object means Canon allocated differently *before*
  creating PropertyMgr in dumps 15-29 than in dumps 1-14, with the same ML core size. Either
  the ML binary changed without changing size (C6 cannot exclude this), or Canon's own
  persistent state (settings held in flash property areas, or the mode the camera starts in)
  changed during the streak. The crash persisted across that change.

Unknown: the allocation index of the record; the heap header size on this DryOS build.

## 6. Ranked explanation

1. **A Canon registration made when the card mount completes carries a wrong token_cb, and the
   trigger is Canon-side state (card contents or stored camera state), not ML code layout.**
   For: abort exactly at mount completion (section 4); identical fault on two ML layouts and
   with ML's init task idle (C6); same registration every time (section 5); Canon's early heap
   changed mid-streak. Against: no ROM call site with a swapped pair has been found (A4, this
   report for the blob), so a run-time cause inside Canon is still required and not shown.
2. **A record is overwritten between `prop_register_slave` and the worker**, most plausibly a
   large one (the class-0x01000000 registration at 0xE05BF856 with token_cb 0, or the
   caller-sized one at 0xE01DC11E). For: the large gap; records are passed by pointer and
   processed later. Against: a random overwrite would not give the same X and the same 0x32 in
   29 boots; it would need a deterministic writer.
3. **ML's property handler reached slot [8] by an ML path.** For: `global_property_handler`
   has X's shape (A4). Against: ML had not registered; `global_token` is zero and zero does
   not fault; two ML layouts with different handler addresses fail identically.
4. **Damage to the blob's RAM copy by ML.** Against: no overlap, blob registrations completed
   in the crashing boot, deterministic boot path (sections 1d, 2). Effectively excluded.

## 7. Cheapest hardware probe

The streak ended at db boot 359 and the card that produced it is gone, so no read over the
serial shell can be scheduled against it; the abort handler also hangs the camera, so the
shell is not available after the fault. The probe therefore has to be armed in the abort
handler and wait for a recurrence.

In `m50ii_abort_report` (src/init.c), when `pc == 0xE021B8FC`, print:

- 4 words at r8: `handler, priv, token_cb, n` of the record.
- 3 words at r6: `n, handler, priv` of the new token. These were written by the worker at
  0xE040349E..0xE04034AA before the callback, so they are valid even if the record was
  overwritten afterwards.
- 1 word at 0x58278+0x14 and 1 word at `[0xA590]`+8 (blob token fields), as a cross-check.

Reading the result:

| Result | Meaning |
|---|---|
| `r6[1]` = 0xE01DA957 | the mount-time registration at 0xE01DC11E; compare `r8[2]` with 0xE01DA871 |
| `r6[1]` = 0xE05BF79D and `r8[2]` != 0 | the class-0x01000000 record was overwritten in flight (explanation 2) |
| `r8[2]` in 0x0223B000..0x02319530 | blob code; add 0xDF180074 and look it up in section 1 |
| `r8[2]` in 0x000C78D8..0x0014FC00 | ML code; resolve against that build's .sym (explanation 3) |
| `r8[0] != r6[1]` or `r8[3] != r6[0]` | the record changed after the worker read it |
| `r8[3]` (n) near 965 | the token directly follows the record |

Cost: about 12 lines in one function, one crashing boot. It changes the core, so build it on
an 18-character branch and check layout with tools/symgate. If the crash returns, image the
card before any other action (C6.md check 2); the card image is the only way to test
explanation 1 directly.

Second, zero-risk check on any booting build, over the serial shell after big.8: `rd 0x58278
0x28` and `rd` of 8 words at `[0xA590]`. All token fields should be heap pointers (0x00Exxxxx).
A field equal to 0x32 or otherwise not a pointer would point at a module whose token variable
is being used for something else.

## Limitations

- X, the owner of 0x32 and the registrant are not identified.
- The handler passed in r7 at 0xE13FA666 and the value of n at 0xE05C0ABA were not resolved.
- The property lists at RAM 0x022F4BAC.. were located but not decoded.
- The timing argument rests on UART text whose host timestamps are in 200 ms buckets and whose
  Canon log is delayed and filtered; the cut ML message is direct evidence, the "4133 ms"
  placement is an estimate from a different (good) boot.
- Callers of `prop_register_slave` through the function-pointer table written at 0xE02D16B6
  (A4 verification item 4) were not enumerated.
- Ghidra was used read-only (decompile of 0xE040347C, 0xE05BF79E, 0xE05BF802, 0xE05BFD48,
  0xE0403788).
