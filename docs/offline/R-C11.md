## (a) offline-buildid-fx

### Checked and confirmed

- **Layout independent of branch name.** Clean build on branch `offline-rc11-rev-a`
  (`build_id` = `765760b5d offline-rc11-rev-a`, 28 characters) and a relink on detached HEAD
  (`build_id` = `765760b5d `, 10 characters): both `M50mk2_101.sym` have md5
  `d2f46ba5e091fa02d53a8aae9969442f`, equal to `tools/symgate/baseline/M50mk2_101.sym`.
  `autoexec.bin` is 257696 bytes in both. `magiclantern.bin` differs in 20 bytes between the
  two builds (hash/branch text and build time only).
- **Longer than the field.** `platform/Makefile:636-641` writes `char name[LEN + 1] = "%.LENs"`,
  so a long string is cut to LEN bytes and the array always keeps its terminating NUL. No
  missing-NUL case exists with a byte-counting `printf` (make uses `/bin/sh`). C11's own test
  (51-character branch, 74-character user@host) agrees. Not re-run by me.
- **Consumers on the camera.** `build_id` / `build_date` / `build_user` are used only through
  `%s` or `strlen` (`src/menuhelp.c:60`, `src/debug.c:613`, `src/config.c:198`, `src/init.c:1877`,
  `src/ptp-ml.c:99-102`); `src/version.h` declares them `extern const char x[]`, nobody takes
  `sizeof`. NUL padding is invisible to all of them. The module loader (`src/module.c:1764`)
  shows the module's own "Build date"/"Build user" strings, not the core's; there is no
  core-version comparison that these strings feed.
- **Host commits do not touch the ARM build.** The final HEAD (all six commits) builds to the
  baseline `.sym`; `src/raw.h` only wraps `SIZE_CHECK_STRUCT` in `#ifdef` (defined in the ARM
  build, so the check still runs there). I did not rebuild the host `mlv_dump`.

### Findings

**A1 (medium, tooling) - `tools/symgate/check_card_image.py:183-185` fails on a short `build_id`
or `build_user`.** The contiguity check requires each version string to be followed within 0-3
bytes by the next one. With NUL padding that only holds when the text nearly fills its field.
Reproduced with the detached-HEAD build:

```
[FAIL] version strings not contiguous: 0xf3561+11 != 0xf357e
RESULT: FAIL - 1 problem(s); do NOT boot this card
```

The 18-character-branch build passes. So after adopting C11 the gate rejects a correct card
whenever the branch name is shorter than 15 characters, or user@host is shorter than 36. This
is a false FAIL (safe direction), but it defeats the point of C11 (freedom from the 18-character
rule) until the checker compares against field width (next symbol address) and accepts NUL
padding. C11.md reports `check_card_image: PASS` only for the 18-character build.

**A2 (low) - cut text is silent.** A branch longer than 18 characters is truncated in
`build_id` and in `version.bin` with no build warning, so two branches can show the same
id on the camera. The 9-character hash is always intact, which is enough to identify a build.

**A3 (low) - widths are tied to one machine.** `BUILD_USER_LEN ?= 39` is the length of this
host's user@host. Layout no longer depends on it, but overriding any `BUILD_*_LEN` on the
command line moves the layout once; `tools/symgate` catches that.

**A4 (low, pre-existing) - a `"` in a branch name breaks `version.c`.** git allows it; the
string is pasted into a C literal unescaped. Not introduced by C11.

### Verdict (a)

Ready for a hardware boot test. With default widths the core is the baseline layout; the only
byte differences are version text. Fix A1 in `tools/symgate` before relying on the card gate
with other branch-name lengths.

## (b) offline-abortdump1, variant B (741c021f6)

### Checked and confirmed (from my rebuild)

- `.abx` is `PROGBITS WAX` at 0x105A3C..0x105D24 (0x2E8 bytes), inside the single `RWE` LOAD
  segment; `magiclantern.bin` grows 254300 -> 255044 (+744), `autoexec.bin` 257696 -> 258432. It
  is therefore in the image and copied by the loader's `blob_memcpy` + `sync_caches`
  (`src/reboot.c:319-326`) like the rest of the core.
- `check_symbol_stability.py`: every pre-existing section and anchor OK, `_bss_end` and
  `ml_reserved_mem` unchanged; the gate prints `RESULT: FAIL` only for `_bss_start`
  0x105A40 -> 0x105D40. `_bss_start` is used only by `zero_bss` (`src/boot.h:290`), which now
  starts above `.abx`, so the section is not wiped.
- No collision with `.bss` is possible: the linker places sections in order and `.bss` is
  64 KB aligned (starts 0x110000). Remaining gap after `.abx`: 0xA2DC bytes.
- Pointer validation (`m50ii_abx_ok`): range 0x1000..0x40000000-len, then ATS1CPR/PAR on the
  first and last byte (disassembly at 0x105A4E matches the source). All dumps are at most 0x40
  bytes, so two probes cover every page touched. A zero pointer from `m50ii_abx_word` becomes
  0x30 and is rejected. I found no path where the guard itself faults or loops.
- Bounded: at most 89 words, about 15 lines. A data fault inside the dump re-enters the stub,
  the marker at `m50ii_abort_stack[0]` makes the second pass skip the dump, and the handler
  reaches its hang loop.
- The critic's "28,494 repeats": the repeated string is the `[AB] pc= lr= dfar=` line that
  `m50ii_abort_report` prints forever by design (`src/init.c`, loop after the HANG line). With
  29 register dumps in the same log that is about 980 lines per crashing boot, consistent with
  one handler entry per boot and a loop until power-off. The source gives no reason to think
  the handler re-entered. Not verified against the log itself.

### Findings

**B1 (high) - the whole existing abort report now depends on `.abx`.** The macro
`#define m50ii_uart_str m50ii_abx_uart_str` (init.c, before `m50ii_abort_report`) redirects
*every* print of the report, including the first `"\n[ABORT] type="`, through the wrapper at
0x105C54. In the baseline, code ends at `_text_end` 0xF3328; nothing in the core executes
above 0x100000. `.abx` would be the first core code executed from the 0x100000 megabyte, and
whether Canon's tables allow execution there is unverified (G2.md does not address it). If
that fetch faults, the prefetch abort re-enters the stub, which calls the report, which faults
on its first print again: an endless silent loop with **no `[ABORT]` output at all**. The
re-entry marker cannot help because it lives inside the same section. G2.md's statement that
"nothing that exists today is lost" is wrong for this case. The dump is aimed at a crash that
is currently diagnosable only through this handler, so losing the handler is the worst
outcome.
Fix: apply the redirect to the single `"[ABORT] HANG ..."` call only (define the macro
immediately before that line and `#undef` after it). Same instruction sizes, so the layout
argument is unchanged, and all existing lines are on the wire before any `.abx` code runs.
Independently, check the execute permission of 0x105000 from the ROM's MMU tables or in QEMU.

**B2 (medium) - not strictly one-shot.** `m50ii_abort_xdump` ends with `*mark = 0`. Any later
handler entry (second CPU, or a fault in the hang loop) prints the full dump again. Remove the
clear to make it one-shot per boot.

**B3 (medium) - a fault inside the dump replaces the looping line.** The stub reloads `sp`
from `m50ii_abort_sp`, so a nested abort overwrites the saved context; the `[AB] pc=` line
that repeats forever (the only redundancy on a lossy UART) then shows the nested fault inside
`.abx`, and the original pc/lr/dfar are on the wire exactly once.

**B4 (medium) - no guard against the gap being exceeded.** `src/magiclantern.lds.S` has no
`ASSERT`. If the loaded image plus `.abx` ever passes 0x110000, `.bss` silently jumps by
64 KB, `_bss_end` and `ml_reserved_mem` grow by 64 KB, and Canon loses that memory (a
documented hang cause on this camera). symgate would flag it, the linker would not. Add
`ASSERT(. <= 0x110000, ...)` or equivalent after `.abx`. The gap was only measured on the
walkback-milestone base, not combined with the recording branches (C10/C12/G1).

**B5 (low) - the core is not byte-identical outside `.abx`.** G2.md section 4 reports two
linker veneers swapping places, which retargets four call sites including the entry branch at
0xC78E0. Functionally equivalent, but it is a core change beyond "one literal". Not
re-measured by me.

**B6 (low) - the dump runs for every abort**, not only pc=0xE021B8FC, adding about 15 lines
before the HANG line on unrelated faults. Reads above the fitted RAM size but below 0x40000000
pass the range check and rely on the MMU probe alone.

### Verdict (b)

Fix first: B1 (redirect only the HANG-line call, and establish that 0x105A3C is executable),
then B2 and B4. After that it is a reasonable diagnostic build for a hardware boot test.
