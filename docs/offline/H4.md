## What the change does

`normal_code_patches[]` on the baseline has exactly one entry: an 8-byte code hook at 0xE021E460 (Canon
keypress handler funcs[0]) jumping to `hook_gui_funcs0_exclusivity`. In `src/patch_mmu.c:812`
`apply_normal_patches()` enters the block only if `COUNT(normal_code_patches)` is non-zero; that block calls
`mmu_reclaim_init1_page()` and then `apply_patches()` (ROM remap at big.4a2, cpu0 only). With the table empty
the whole block is compiled out, so no MMU table change happens at big.4a/big.4a2.

## Functionality lost

- The funcs[0] GUI-input-exclusivity hook is no longer installed. On the baseline it is installed but
  transparent: `m50ii_exclusivity_on` defaults to 0, so it replays the original prologue and continues.
  Default behaviour is therefore unchanged by code reading.
- The runtime switch `wr &m50ii_exclusivity_on 1` over serial becomes a no-op. The variable and hook function
  still exist in the image, but nothing jumps to the hook.
- Canon buttons keep leaking to Canon's UI while the ML menu is open - same as the baseline default.
- Side effect to be aware of: the init1-hijack remap page is no longer reclaimed at big.4a2. It stays mapped
  (PTR_INIT1_TASK patch), which is the state the 256448 core ran in.

Not affected, by grep:

- GraphicsConvertPosType NOP (0xE01B8CAC): separate code path in `init_remap_mmu` (`patch_mmu.c` ~973-1062),
  does not go through `normal_code_patches`.
- Raw path: `modules/raw_video/raw_vidx/*.c` and `mlv_lite` have no reference to `apply_normal_patches`,
  `normal_code_patches`, `m50ii_exclusivity_on` or 0xE021E460. `early_code_patches`, `early_data_patches`
  and `normal_data_patches` were already empty.
- Menu input: the working menu uses the read-only ring peek bridge in `gui.c`; `gui.c:384` mentions the hook
  only in a comment.
- `init.c:1055` still calls `apply_normal_patches()`; it now returns 0 after the cpu1 wait loop. The UART line
  "big.4a: calling apply_normal_patches" still prints; "big.4a2: init1 remap page reclaimed" and
  "big.4b1: funcs[0] exclusivity patch applied" no longer print - log parsers keyed on those need to know.

## Evidence for the fix (from docs/43 section 2, C7)

Abort `pc=0xE02F281A lr=0xE05BB769 dfar=0xE0997D80`, always at big.4a/big.4a2, 40 occurrences 07-18..07-22:
19 of 92 boots that reached big.4 on autoexec size 257760, 13 of 27 on 256992, 0 of 70 on 256448 (the core
with the empty table). This is a correlation across builds that differed in other ways too, not an A/B of
this single change. C7 also ties `0xE00436FC` (16 boots) and other big.4a aborts to the same builds; whether
the empty table removes those is not established.

## Hardware test needed before adoption (docs/39)

1. Commit is already made; stage the tip build with `check_card_image.py --write-manifest`.
2. Baseline a10b16c23: 10+ cold boots, record last boot marker and any `[AB]` pc per boot.
3. `offline-mmupatch-0` tip (65f17ec22): same number of cold boots, same card, same mode dial position.
4. Pass: no `pc=0xE02F281A`, no stall at big.4a/big.4a2, big.8 rate not lower than baseline, and the
   known-good EVF stage is reached (the fa0834b40 build crashed at 0xE021B8FC with other changes mixed in -
   this branch must show that crash is absent).
5. With about 20% baseline incidence, 10 clean boots still leaves roughly an 11% chance of a false pass;
   20 boots brings that to about 1%.
6. Then one menu check (FN opens, pad navigation in Photo and Video mode) and one raw_vidx record.

If only the first commit is wanted for testing, expect the full-layout-shift risk the "core unchanged" rule
exists for; the tip is the candidate.
