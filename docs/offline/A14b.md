# A14b - Stub audit, slice 2 (GUI, display, properties, F1-F6, EDMAC/raw, misc)

## Question
Re-verify every active stub in `platform/M50mk2.101/stubs.S` in the GUI/dialog/timer, display, property, F1-F6,
raw-video EDMAC and misc sections that is not tagged `[M50II 1.0.1 OK]`. Give a verdict per stub and a corrected
address where the stub is wrong. `stubs.S` was not edited.

## Summary
- 11 stubs in this slice are wrong or very likely wrong. Six of them sit on the raw-video EDMAC path:
  `edmac_reset_boomer_vdkick`, `edmac_select_boomer`, `StartEDmac_maybe`, `ConnectReadEDmac_maybe`, `LockEngineResources`
  (plus the selector constant `0x373f0226`, which was bent to fit the wrong function).
- New in this report: `LiveViewApp_handler` points at the *StarShootingTime* dialog handler; the real pair is
  handler `0xE0444058` / dialog slot `0xE9F0`. `sd_device` is the wrong global (real `pStgDev` slot is `0x14060`).
  `gui_task_list` real base is `0x11144`. `StartEDmac_maybe` positional homolog is `0xE05B82AE` (267 callers vs 1).
- `dialog_redraw`, `fsuDecodePartitionTable` and `gui_init_end` are wrong with no confirmed replacement; all three are still callable from ML code.
- Everything else checked is confirmed or consistent (GUI queue/event loop, timers, app handlers except LiveView, `_prop_cleanup`, event flags, CBR register pair, set_address/set_size, PwrMng pair).
- All of this is static. Positional matches against M50 mk1 / SX740 stub tables are structural only; no mk1 or SX740 ROM is on disk to compare bodies.

## Method
- `python3 tools/verify_stubs.py`: 153 stubs, REVIEW=4 (dump_file, malloc_info, memmap_info, smemShowFix: all outside this slice), SKIP=3, LEAF=19, OK=109, DATA=17, NULL=1. EDMAC CBR regression guard PASS. The tool only checks entry shape, so OK there does not mean the right function.
- `tools/romdis.py` at every address; a ROM-wide BL/B.W tally (direct callers per target) and a literal-pool scan (private scripts in the scratchpad); ADR/literal xrefs for anchor strings.
- Stub-table deltas against `platform/M50.110`, `platform/SX740.102`, `platform/R.180`, `research/bilal_M50_rawvideo/platform/M50.110/stubs.S`.
- Ghidra was only queried for existing names (none for dialog functions); nothing was changed.

### Stale selector comment (stubs.S ~394)
- The comment says bilal's `0x373f0126` "passes its InSelType(0x100)/InSelEdmacType(0x20000000) checks for ch13/46".
  Those two values are the ch13 row of the **Edmac.c** table at 0xE0EC3BD4: `{0x000C0000, 0x100, 0x20000000}`, which is the table used by 0xE05B802E.
- The stub actually points at 0xE05B752E, which reads the **Outer.c** table at 0xE1087A8C; row 13 there is `{0x004E0000, 0x200, 0x00040000, ...}`.
- `edmac-d8.c:89` now defines `MEM2MEM_BOOMER_SELECTOR 0x373f0226`. Type 0x200 and mask bit 0x40000 satisfy the Outer.c row, so the constant was changed to pass the wrong function's asserts.
- ch46 row in the Edmac.c table is `{0x00E70000, 0, 0}`.

### Canon's own channel bring-up order (one path, 0xE00BEDF6 and 0xE00BF3D6)
`0xE05B7B42` x3 -> `0xE05B7FB6(ch)` -> `0xE05B802E(ch, 0x017F0118)` -> `RegisterEDmacCompleteCBR` x3 -> `0xE05B8146` / `0xE05B8106` ...
then `edmac_set_address` x3 -> `0xE05B82AE` x3 -> `0xE05B7A32` x2 (last one a tail call).
This is the same shape as `mem2mem_emdac_copy_d8()` in `edmac-d8.c:158-187`.

## Inferred
- EDMAC homologs by position (mk1 and SX740 deltas agree with each other in every case):
  vdkick = Unregister+0x4E -> 0xE05B7FB6; select = stop_boomer-0x94 -> 0xE05B802E; Start = set_address-0x1E2 -> 0xE05B82AE (-0x1E0);
  ConnectRead = reset_channel-0x3A -> 0xE05B7B08; Lock = Create+0x1E8 -> 0xE05BE6A6. A5, B5 and A12 reached the boomer and lock results independently; the Start homolog is new here.
- 0xE05B82AE body: disable (reg+4=0), reset pulse on +0x18, then enable (reg+4=1) for a channel without flag bit0, or check 0xE05B995C and set +0xB4=1 for one with it. That is a direction-neutral "restart channel", which fits the reference comment "call twice for each channel".
- With the current stubs, ML configures boomer node 0x4E (Outer port 13) and never connects a source to EDMAC write channel 13. That alone would explain mem2mem never completing on hardware.
- `gui_task_list`: the lock is at +0 as ML expects, but the name string is at +0x1C (EOS R: +0x14) and the dispatcher reads `[base+0xC]`, so `current` is probably at +0x0C here, not +0x08 as in `gui-common.h:116`.
- `LiveViewApp_handler`: ML compares the top dialog's handler against this symbol (`zebra.c:3600`, `liveview.c:69`); with the current value those tests can only be true while the star-shooting-time dialog is up.
- `gui_init_end`: if `gui.c:410` is ever reached with r0 == 0 it calls 0xE06CF730(4), a Canon function with unknown side effects.

## Implications for raw video
- The CPU-copy recipe does not touch any of the wrong stubs, so the current working path is unaffected.
- A module-only mem2mem retry needs four changes together, not one: select -> 0xE05B802E, vdkick -> 0xE05B7FB6, selector back to 0x373f0126, and Start/Connect moved off 0xE05B9690 / 0xE05B95E4 (candidate order from Canon: 0xE05B82AE on both channels, then 0xE05B7A32 on the read channel).
- `LockEngineResources` is a try-lock today, so its return value (0xD = busy) is ignored and the "lock" may never have been held. Earlier conclusions about the resource lock causing the storm were drawn with that stub.
- The GUI findings matter for overlays during recording: any "is LiveView idle / on top" test built on `LiveViewApp_handler`, `LiveViewApp_dialog` or `gui_task_list` is currently reading the wrong objects.
- Do not use the bootflag menu on this body until `sd_device` and `fsuDecodePartitionTable` are fixed: it would call through pointers taken from the wrong struct and then jump to 0xDF00D364.
