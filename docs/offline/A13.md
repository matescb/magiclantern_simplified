# A13 - Why the raw-frame copy is slow, and the fast path

Static analysis only (ROM gang100.bin 1.0.1, ML source, UART history). Nothing here was run on the camera.

## Question

Why does raw_vidx's synchronous per-row memcpy take ~0.4-0.6 s per 2.8 MB frame, what are the MMU/cache
attributes of source and destination, which memcpy is in use, which Canon bulk-copy primitives exist, how
reliable is the measured rate, and what copy strategy reaches the ~64 MB/s needed for 1792x896@24?

## Summary

1. The copy runs in memcpy's **byte loop**: the source row address is 2 mod 4 (crop x=200 -> 350-byte offset), and ML's linked memcpy goes fully byte-wise when src/dst are not both word aligned.
2. Both ends are **uncached**: source 0x6BC61CC8 and destination 0x46331080 both sit in the Normal non-cacheable alias (L1 entries 0x400-0xBFF). So every byte is one uncached read plus one uncached write.
3. Measured rate re-derived: 0.49 s/frame mean over 20 intervals = **about 5.7 MB/s** (range 5.1-6.2). Host timestamps are quantised to 200 ms, so only the multi-frame mean is meaningful.
4. Cheapest fix: make the crop x a multiple of 16 px (word path, est. 15-30 MB/s). Real fix: read the source through the cacheable alias 0x2BC61CC8 after a per-range d-cache invalidate (Canon has one at 0xE05D088C), est. 40-150 MB/s depending on how the destination is written.
5. Canon's ROM memcpy (0xE0329D10) is a plain word loop, no NEON/PLD - not a fast path. XDMAC and Mem2Mem engines exist but their argument semantics are not resolved.

## Observed

### MMU mapping (ROM L1 table image at 0xE0000000, copied to 0xBFF20000 by mmu_table_init_copy 0xE00722BC)

Decoded all 4096 L1 words from gang100.bin offset 0. All RAM entries are 16 MB supersections, identity mapped.

| L1 index (VA) | raw descriptor | attributes |
|---|---|---|
| 0x020-0x3FF (0x02000000-0x3FFFFFFF) | 0x..054406 | Normal, inner WBWA, **outer non-cacheable**, S=1, AP=1, XN=0 |
| 0x400-0xBFF (0x40000000-0xBFFFFFFF) | 0x..054402 | Normal, inner NC, outer NC (uncached), S=1, AP=1, XN=0 |
| 0xC00-0xDEF (sparse) | 0x..050416 | Device-shared, XN=1 |
| 0xDF0-0xDFF | 0xDF054406 | Normal inner WBWA / outer NC |
| 0xE00-0xE7F, 0xF00-0xF7F | 0x..05D406 | Normal inner WBWA / **outer WBWA**, read-only (ROM) |

- Low 32 MB goes through per-core TTBR0 tables (+0x4800: 0x114406... = 1 MB sections, same inner WBWA / outer NC).
- 0x6BC61CC8 (Canon raw buffer, EDMAC ram_addr) -> index 0x6BC -> **uncached**, identity mapped (VA 0x6BC... -> PA 0x6BC...).
- 0x2BC61CC8 (raw_info.buffer) -> index 0x2BC -> **cacheable (inner WBWA)**.
- 0x46331000-0x47332000 (crop_buf, from fio_malloc) -> index 0x463-0x473 -> **uncached**. Cacheable twin would be 0x06331000.
- This agrees with docs/15 section 3; the only refinement is that entries are supersections and that RAM is outer-NC while ROM is outer-WBWA.

### The 0x40000000 alias

- The table does NOT remap 0x4xxxxxxx onto 0x0xxxxxxx; both ranges are identity mapped with different cache attributes. The aliasing of the two onto the same DRAM is therefore done below the MMU (physical address decode).
- ML: `UNCACHEABLE(x) = x | 0x40000000` only when x < 0x40000000 (src/mem_defs.h:16); `fio_malloc` -> `_alloc_dma_memory` = AllocateMemory + UNCACHEABLE (platform/M50mk2.101/function_overrides.c:208-219).

### Cache geometry and Canon cache primitives (ROM, Thumb)

- 0xE05D088C `(addr,size)`: `bic r0,#0x1f`; loop `mcr p15,0,r0,c7,c6,1` (DCIMVAC) step 0x20; then writes 0 to 0xC1100730. = d-cache invalidate by range.
- 0xE05D08F4 (existing stub dcache_clean): same shape with c7,c10,1 (clean by range).
- 0xE05D0958: same shape with c7,c14,1 (clean+invalidate by range).
- 0xE05D08B8 / 0xE05D0920 / 0xE05D0984: set/way loops (c7,c6,2 / c7,c10,2 / c7,c14,2) over set index 0..0x1000 step 0x20 and way in bits 31:30.
- 0xE05D083A: clears SCTLR.C then flushes by set/way.
- Line size used everywhere is 32 bytes. The set/way loop bounds are 128 sets x 4 ways.
- Every routine ends by writing 0 to 0xC1100730; dcache_clean_multicore (stubs.S:39) uses 0xC11007B0.

### Which memcpy

- raw_vidx calls plain `memcpy` (worker.c:432). In the current build `memcpy` = 0x000ECBA8 inside ML (platform/M50mk2.101/build/magiclantern), ARM-mode newlib C memcpy.
- Disassembly 0xECBA8: if `(src|dst)&3 != 0` it falls to 0xECC50, a `ldrb/strb` loop for the **whole length**. It never aligns one pointer and continues word-wise. Aligned path = 4 x ldr/str per 16 bytes.
- Canon ROM memcpy 0xE0329D10 (memcpy_dryos): aligns dst bytewise, then if src is also aligned copies 4 words per iteration with single ldr/str pairs; src offset 2 -> halfword loop; offset 1/3 -> byte loop. No LDM/STM bursts, no PLD, no NEON.
- `memcpy64` exists at 0x000DB105 (src/stdio.c:153); needs 4-byte aligned pointers and n multiple of 8. Source comment (5D3 numbers, not this camera): newlib 75/17 MB/s, diet 19/4, memcpy64 80/32 (cacheable/uncacheable).

### The actual copy geometry

- event_pusher.c:421-424: `x=200, y=100, w=1792, h=896`; src = `UNCACHEABLE(raw_info.buffer)` (line 434).
- worker.c:427-429: `sbase = src + ((x+7)/8*BPP) + (y/2*2)*pitch` = 0x6BC61CC8 + 25*14 (=350) + 100*3668. 350 mod 4 = 2, pitch 3668 mod 4 = 0, so **every source row starts at an address that is 2 mod 4**.
- UART: `wk.dst=0x46331080`, `wk.line_size=0xC40` (3136), `wk.pitch=0xE54`, `wk.h=0x380`; next dst 0x465DF100, 0x4688D180. Destination rows are 32-byte aligned.
- Result: aligned dst + misaligned src -> newlib byte loop -> 2,809,856 uncached byte reads and 2,809,856 uncached byte writes per frame.

### Measured rate (tools/mlserial/run/uart.jsonl)

Only five recording runs with `cbr_w: give sem` exist, 5 frames each:

| run (local time) | span first->last give | mean per frame |
|---|---|---|
| 07-19 06:23:07 | 1.805 s | 0.451 s |
| 07-19 12:50:27 | 1.806 s | 0.451 s |
| 07-19 12:56:39 | 2.008 s | 0.502 s |
| 07-19 15:07:38 | 2.014 s | 0.503 s |
| 07-22 02:58:43 | 2.208 s | 0.552 s |

- Overall 9.84 s / 20 intervals = 0.492 s per 2.81 MB frame = **5.7 MB/s**.
- Reliability: mlserald.py:107 opens the port with `timeout=0.2` and stamps each `read(4096)` batch, so every delta in the log is 0, 0.2, 0.4 or 0.6 s. Individual "0.4 / 0.6 s" frame times are just 2 or 3 poll ticks. Each run's span carries about +-0.2 s, i.e. +-0.05 s per frame -> 5.1-6.2 MB/s.
- The interval also contains whatever else the worker does between frames (7 RVX_HEX log lines on the first three frames, queue receive). The queue was full ("All events are non-empty, stopping"), so the worker was back-to-back.
- Card write of 0xD66280 bytes shows as 0.2-0.4 s, i.e. somewhere between 20 and 70 MB/s; the log cannot resolve it better.
- 171 ns per byte copied is consistent with one uncached read plus one uncached write per byte.

### Canon bulk-copy primitives found

- XDMAC: `Engine::XdmacWrap.c` (string 0xE0619050): open 0xE0618F1C, start variants 0xE0618F8A and 0xE0618FEA `(ch, 2, a, b, c, cbr, arg)`, both ending in `Peripheral::XdmacTransfer.c` 0xE036A0A2. Four channels (mask 1/2/4/8). Callers: 0xE0132A20/0xE0132A50 and 0xE057A542/0xE057A58E.
- Mem2Mem: strings `InitMem2Mem/StartMem2Mem/TermMem2Mem` (0xE0062434.., registered from FUN_e00620ba) and `InitMem2MemPath/StartMem2MemPath(%#x)/TermMem2MemPath` (0xE0089A94..).
- Strings `MEMCPY end!` (0xE03833FC, 0xE03BC478) exist; no code xref found for the first.
- No "dma_memcpy"/"dmaCopy"/"MemCopy" strings. No xdmac stub in platform/M50mk2.101/stubs.S or in the reference repos.

## Inferred

- The slow copy is caused mainly by the byte loop, secondarily by both buffers being uncached. Not proven at runtime; it follows from the addresses in the log plus the memcpy disassembly.
- 0xC1100000 looks like an ARM L2C-310 outer cache controller (0x730 = Cache Sync, 0x7B0 = Clean Line by PA). RAM is marked outer-NC, so the L2 would only serve ROM. This is register-offset pattern matching, not confirmed.
- L1 d-cache = 16 KB, 4-way, 32-byte lines (from the set/way loop bounds), assuming Canon's loop covers exactly the cache.
- Reading the raw buffer through 0x2BC61CC8 is legal if the range is invalidated first: EDMAC writes go straight to DRAM, so the only hazard is stale lines. With a 16 KB cache almost nothing of a 2.8 MB frame survives anyway, but `raw_update_params` reads the buffer through the cacheable address, so stale lines are possible and the invalidate is required for correctness.
- Never use invalidate-ALL (0xE05D08B8) for this: it discards other tasks' dirty lines. Use invalidate by range, or clean+invalidate.
- Expected rates (estimates, scaled from the 5D3 comment and general Cortex-A9 behaviour; none measured here):

| strategy | expected | meets 67 MB/s? |
|---|---|---|
| current (byte loop, uncached both) | 5.7 MB/s measured | no (about 2 fps) |
| A: crop x multiple of 16 px, same memcpy (word loop, uncached both) | 15-30 MB/s | no (5-10 fps) |
| B: A + src via cacheable alias after range invalidate, dst uncached, memcpy64 | 40-80 MB/s | borderline |
| C: B + dst via cacheable alias 0x06331080, then dcache_clean range before FIO write, PLD on src | 80-150 MB/s | probably |
| D: XDMAC or EDMAC mem2mem (hardware copy) | 100+ MB/s | yes, but high risk |

- 1792x896x14bit@24 = 67.4 MB/s (64.3 MiB/s). The copy must also leave CPU for the card write, so C or D is the realistic target; A is a 10-minute sanity check of the diagnosis.

## Unknown

- Whether the physical alias really is plain address-bit-30 wraparound (RAM size, DRAM decode).
- ACTLR.SMP/FW: whether cache maintenance by MVA is broadcast to the other core, and whether DryOS can migrate the worker task between cores mid-frame. If it can, a stale line on the other core is possible.
- Real uncached vs cached read speed on this SoC; all MB/s figures except 5.7 are estimates.
- Whether the Normal-NC destination benefits from store merging; whether a WBWA destination pays a line fill per line.
- XDMAC argument order (which of a/b/c is src, dst, size), channel ownership (who already holds channels 0-3 in movie LV), and whether it needs uncached addresses.
- Whether the copy is being pre-empted by Canon LV tasks (worker task priority), which would also inflate the measured time.
- Tearing: single-buffering means Canon overwrites the buffer every frame; a copy slower than one frame period always mixes frames, regardless of cache path.

## Implications for raw video

- The 0.5 s/frame figure is not a hardware limit; it is an alignment accident. Change `event->x` to 192 or 208 (so `(x+7)/8*14` is a multiple of 4; 192 gives 336, also a multiple of 16) and the same code should be several times faster. Module-only change, no core rebuild.
- For 24 fps the copy has to read through the cacheable alias. Module-only recipe: per row (or per frame) call Canon dcache_invalidate_range on the cacheable source, then memcpy64 from 0x2BC... to the destination.
- If the destination is written through the cacheable alias, it must be cleaned before FIO_WriteFile. fio-ml.c already calls `sync_caches()` when the pointer is cacheable, but that is a whole-cache set/way clean; a range clean with 0xE05D08F4 on the 2.8 MB just written is the targeted alternative.
- mlv_lite's async cpu_copy worker (edmac-d8.c:286-304) has the same exposure: check its row addresses for alignment before blaming the engine.
- Hardware copy (XDMAC/EDMAC) is not needed to hit 24 fps if strategy C delivers; keep it parked given the DAF/EIS storm history.

## Next hardware checks

All are serial-harness probes; `call` addresses are Thumb (odd).

1. Confirm the mapping live: `rd 0xBFF21AF0 1` (L1[0x6BC]) expect 0x6B054402 or similar NC pattern; `rd 0xBFF20AF0 1` (L1[0x2BC]) expect 0x2B054406; `rd 0xBFF2118C 1` (L1[0x463]) expect 0x46054402. If patch_mmu has swapped tables, read TTBR-relative instead.
2. Confirm aliasing: with raw armed, `md 0x2BC61CC8 4` vs `md 0x6BC61CC8 4` twice a second apart. Uncached view changes every frame; cached view changing more slowly or not at all proves stale lines exist.
3. Prove invalidate works: `call 0xE05D088D 0x2BC61CC0 0x40` then `md 0x2BC61CC8 4` and compare with `md 0x6BC61CC8 4`. Equal after invalidate, unequal before = cacheable read path is legal with invalidate. A hang or abort = do not use this primitive from task context.
4. Diagnosis check (module-only rebuild): set `event->x = 192`, rerun the 5-frame recording, compare the first->last `give sem` span. Expect about 0.4-0.8 s total instead of 1.8-2.2 s. No change = the byte-loop theory is wrong; look at task pre-emption.
5. Proper timing: log `get_ms_clock()` (or the DIGIC timer) before and after the row loop into one `@ML>` line per frame, so the result does not depend on the 200 ms host poll.
6. Micro-benchmark in a throwaway module task, 4 MB each, timed on-camera: (a) memcpy unc->unc misaligned src, (b) memcpy unc->unc aligned, (c) memcpy64 unc->unc, (d) invalidate + memcpy64 cached src -> unc dst, (e) invalidate + memcpy64 cached -> cached + `call 0xE05D08F5 dst size`. Pick the first variant above 80 MB/s; if (d) and (e) both stay under 67 MB/s, the CPU path cannot do 24 fps at this size and XDMAC needs RE.
7. Byte-compare after variant (d)/(e): copy one frame both ways with LV paused (or compare only rows far from the EDMAC write position) to check for stale-line corruption.
8. `rd 0xC1100000 1` and `rd 0xC1100100 1` (PL310 cache ID / control) to confirm the outer cache controller guess; informational only.

Caveats that the confirmations do not remove:

- Claim 1 is the ROM image. mmu_table_init_copy (0xE00722BC) copies 0x4900 bytes from 0xE0000000 and rewrites only the two words at +0x4800 and +0x4880, so the copy should carry the same RAM attributes, but the live table address and contents are not observable offline. Hardware check 1 in the report is still needed.
- Claim 4 was checked against the ELF built Jul 21 17:40. Four of the five timed runs are from 07-19, on a different core build; the memcpy source is the same, the address may not be. That 0x2BC61CC8 is the cacheable raw_info.buffer value comes from docs/35:26, not from the UART log (the log only shows the already-UNCACHEABLE 0x6BC61CC8).
- "171 ns per byte matches" (claim 4/6) is a consistency argument, not a measurement. The same 0.49 s also contains the worker's logging and any pre-emption by Canon LV tasks; nothing offline separates these. The x=192 experiment (hardware check 4) is what decides it.
- Strategy rates A-D (claim 9) and the legality argument (claim 10) are estimates/inferences and were not checkable. One point for claim 10: all three range primitives take no lock and do not mask interrupts (only 0xE05D0984 does `cpsid if`), and they act on the calling core only as far as the code shows; whether the other core can hold stale lines for the same range is open.
