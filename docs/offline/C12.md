# C12 - First plan steps as module code (priorities, throttled copy, RAM burst, frame integrity)

Date: 2026-11-16. Offline. No camera attached. **Nothing here has run on the camera; the host test
proves control flow against a model of DryOS, not behaviour on the M50 II.**

## Goal

Turn the earliest steps of `docs/offline/C9-recommended.md` that need no new hardware fact into code,
module-only (`modules/raw_video/raw_vidx`), each behind a runtime toggle whose default is the previous
behaviour: (a) copy / writer task priorities with a throttled copy, (b) capture-to-RAM-then-write,
(c) frame-integrity instrumentation, (d) the faster copy from A13 as an off-by-default toggle.

### Toggles (all `int`, set over serial with `wr &<name> <value>`, read when a recording starts unless noted)

| Toggle | Default | Default = old behaviour? | Meaning |
|---|---|---|---|
| `rvx_write_prio` | 0x1A | yes | priority of the `raw_write` task, read per write. A11 recommends 0x16 |
| `rvx_copy_prio` | 0 | yes | 0 = copy inside the worker (0x11). Non-zero = copy in an `rvx_copy` task at that priority while the worker only waits. A11 recommends 0x15, the plan's step 2 says 0x1B. Read per frame |
| `rvx_copy_chunk_kb` | 0 | yes | N = `msleep(rvx_copy_sleep_ms)` after every N KiB copied. Plan value 256 |
| `rvx_copy_sleep_ms` | 10 | n/a | length of that pause, clamped 1..100 |
| `rvx_burst_frames` | 0 | yes | N = capture at most N frames into RAM, no card write during capture, then stop by itself and write |
| `rvx_burst_release_first` | 0 | yes | burst only: 1 = `raw_lv_release()` before the card write |
| `rvx_integrity` | **1** | **no** | per-frame record in RAM plus a UART summary at stop. No card I/O |
| `rvx_sidecar` | 0 | yes | 1 = write the records to `<clip>.RVI` after the MLV is closed |
| `rvx_drop_torn` | 0 | yes | 1 = do not store a frame whose source changed during the copy |
| `rvx_fast_copy` | 0 | yes | 1 = cacheable source after Canon's range invalidate, `memcpy64` when aligned |
| `rvx_crop_w/h/x/y` | 1792/896/200/100 | yes | the former compile-time window. Plan's first clip: 1280, 720, 192 |

Both priorities go through `rvx_prio_clamp()`: anything below 0x15 becomes 0x15, so no value typed over
serial can put a bulk task into Canon's LiveView band (0x0D-0x14 per A11).

### Behaviour that changed with every toggle at its default (three things)

1. `rvx_integrity = 1`: one `fio_malloc` of 72,128 bytes at start (freed at stop), `get_us_clock()` in
   the vsync hook (the hook already called `get_ms_clock()`, which runs the same clock update), 3 x 512
   bytes of probe reads per frame in the worker, and six extra UART lines at stop. I judged this
   safe enough to be on, because the next hardware session needs the numbers; it is not "strictly
   safer", so turn it off with `wr &rvx_integrity 0` if an A/B against the old behaviour is wanted.
2. The two full-frame capture buffers (2 x 4.27 MB) are no longer allocated from the vsync hook when
   nothing reads them (`rvx_src_from_raw_info = 1` and `rvx_redirect_edmac = 0`, the defaults).
   Strictly safer by A8 (8.5 MB less out of the pool that must not be drained) and by the plan (no
   allocator call in the EvfDev context). They are allocated as before when either toggle is flipped
   before REC.
3. The window is checked: width multiple of 8 and height even at REC, and inside the raw frame on the
   first vsync (the recording stops itself otherwise). The old values pass both checks.

## Per item: implemented, left out, hardware test

### (a) Priorities and throttle

Implemented: `rvx_write_prio`, `rvx_copy_prio`, `rvx_copy_chunk_kb`, `rvx_copy_sleep_ms`, clamp.
The worker stays at 0x11 as queue monitor (A11's "split it" variant) and blocks on a semaphore while
the copy task runs.

Left out, and why:
- The copy task is **created per frame** and exits after one frame. A resident task would be the
  better form; I did not write it because the host harness is a single-threaded coroutine model that
  cannot schedule a second resident task, and I preferred a tested per-frame task to an untested
  resident one. 25 `task_create` calls per second have never run on this camera (the module already
  creates one `raw_write` task per buffer, about 5 per second). If creation fails the frame is copied
  inline and `rvx_copy_task_fail` counts it.
- The worker waits for the copy task without a time limit (it logs after each second, five times). A
  limit would mean freeing a buffer the task is still writing into.
- The plan's hook hygiene (no semaphore, no UART in the vsync hook, `vd_count++` only) is not done:
  `get_empty_event()` still takes `events_sem` with a 2 s timeout in the hook. That is a rewrite of the
  event pool, not a toggle.
- With a throttle the frame rate falls: 1280x720 is 1.6 MB = 6 pauses of at least 10 ms, so at most
  about 10 fps before the copy time itself. That is the plan's intent for burst mode, not a defect.

Hardware test (A11 check 4): movie-mode LV, same card and scene, 10 recordings each of
(1) defaults; (2) `wr &rvx_copy_prio 0x15`, `wr &rvx_write_prio 0x16`;
(3) `wr &rvx_copy_prio 0x1B`, `wr &rvx_write_prio 0x1A`, `wr &rvx_copy_chunk_kb 256`.
Count MvRawPro storms, EvfDevState asserts and `Task.c` asserts per set; read "slowest frame copy, us"
from the stop summary. Pass for (2)/(3) = fewer asserts than (1) and `rd &rvx_copy_task_fail` = 0.
A11 check 5 comes for free: if the copy time at 0x15 is clearly longer than at 0x11, Canon's 0x12-0x14
tasks are preempting the copy.

### (b) Capture to RAM, then write

Implemented: `rvx_burst_frames`. The two existing 16 MiB buffers are the ring (32 MiB, the amount A8
and the plan call proven once, boot 212). During a burst no `raw_write` task is started; when the
target is reached or both buffers are full the worker blocks the vsync hook, runs its normal stop
(write older buffer, newer buffer, header, close) and returns to INACTIVE without a key press. Frames
per burst: 10 at 1792x896, 20 at 1280x720 (host-tested, matches the plan's "32 MiB ring = 20 frames").
`rvx_burst_release_first` selects the order.

Left out, and why:
- Default order is write + close, then `raw_lv_release()` (the plan's "close before `raw_lv_release`").
  The task text asked for "stop raw LV and write"; that is `rvx_burst_release_first = 1`. It is not the
  default because C7 shows `raw_lv_release()` can fault, and with that order a fault costs the whole
  burst (nothing is on the card yet).
- Ring size is not a toggle. 40 and 48 MiB need plan step 1 (allocation hold test) first.
- The MLV header fps still comes from the core (`fps_get_current_x1000()`), which reads about 18.5 %
  high on the walkback core. The measured rate is in the UART summary and the sidecar; rewriting the
  header needs a new function in `mlv_3.c` and was not done.
- No "write after capture" split into a separate low-priority phase beyond what the stop already does:
  the write is two `raw_write` tasks of up to 16 MiB each at `rvx_write_prio`.

Hardware test (plan step 2): `wr &rvx_crop_w 1280`, `wr &rvx_crop_h 720`, `wr &rvx_crop_x 192`,
`wr &rvx_burst_frames 20`, `wr &rvx_copy_chunk_kb 256`, `wr &rvx_copy_prio 0x1B`, `wr &rvx_sidecar 1`,
press REC once, wait for "Recording is inactive". Pass = `mlv_check.py` clean on the clip with 20
frames, `ver` answers 30 s later, `rd 0x39B84` non-zero. Then the same with
`wr &rvx_burst_release_first 1` and compare whether the EvfDevState burst after the write disappears.

### (c) Frame integrity

Implemented:
- vsync hook: `rvx_vsyncs++` and two stores into the event (`vd_seq`, `t_us`). `rvx_vsyncs` counts
  every vsync of the session, so frames that were never copied show as gaps.
- worker, around each copy: FNV-1a hash of 8 probes x 64 bytes of the source window (rows spread from
  the first to the last, read through the uncached address) before and after the copy, the same probe
  positions in the copy, copy start time and duration.
- flags: `TORN` (source changed during the copy), `DST_DIFF` (copy differs from the source read
  afterwards; without `TORN` this means the copy path is wrong), `DROPPED`, `FAST_COPY`.
- counters `rvx_torn`, `rvx_dst_diff`, plus the existing drop counters; UART summary at stop with
  vsync count, torn count, slowest copy, measured fps and the core's fps.
- sidecar `<clip>.RVI` (`rvx_sidecar = 1`): 128-byte header + 36 bytes per frame, written after the
  MLV is closed and before `raw_lv_release()`. Reader: `tools/mlvcheck/rvi_check.py CLIP.RVI
  [--mlv CLIP.MLV] [-v] [--json]`, exit 1 on torn frames, vsync gaps, drops or count mismatches.

Left out, and why:
- No MLV block. `mlv_check.py` warns on unknown block types and `mlv_3.c` is not covered by the host
  test, so a second file was the lower-risk carrier. The MLV is byte-for-byte what it was before.
- At most 2000 records per clip (80 s at 25 fps); later frames are counted in `records_lost`.
- A frame not flagged is not proven whole: a rewrite that leaves all 512 probed bytes unchanged
  (clipped highlights, black) is invisible. With the live buffer and today's copy speed I expect
  nearly every frame to be flagged; that is the measurement, not a malfunction.
- The sidecar is one more create/write/close at stop, on a camera whose stop path has wedged before;
  hence default off.

Hardware test: record 3 s with defaults plus `wr &rvx_sidecar 1`, moving subject. Expect on UART
"frames torn" close to "frames accepted" and "fps x1000 measured" near 0x61A8 (25000); on the host
`rvi_check.py tst00.RVI --mlv tst00.mlv -v`. Cross-check one flagged and (if any) one unflagged frame
by eye after `mlv_check.py --extract`. Plan step 3/4 then gives the decisive check: with
`call lv_save_raw 0` holding the buffer still, a burst must show torn = 0 and dst_diff = 0.

### (d) Faster copy

Implemented: `rvx_fast_copy`. Source rows are read through `CACHEABLE(src)` after Canon's d-cache
invalidate by range (`0xE05D088C`, called as Thumb `0xE05D088D` through the pointer
`rvx_dcache_inval`), in groups of at most 64 rows or one throttle chunk, each group invalidated
immediately before it is read. `memcpy64` is used when source, pitch, destination and line size are
all 4-byte aligned (true for x = 192, not for x = 200, where plain `memcpy` on the cacheable source is
used). The destination stays uncached (A13 variant B, estimated 40-80 MB/s, unmeasured).

Left out, and why:
- Variant C (cacheable destination plus range clean before the write) is not implemented: it adds a
  second ROM routine and the A7 rule that a cacheable unaligned buffer is silently not written.
- Whether DCIMVAC is broadcast to the other core is unknown (A13). If the task migrates, stale lines
  are possible; the `DST_DIFF`-without-`TORN` flag is the detector, and it only works on a still buffer.
- The invalidate start is rounded down to a 32-byte line, so up to 31 bytes before the window (inside
  Canon's raw buffer) are invalidated too. Nothing writes that buffer through the cacheable alias as
  far as A13 found; not verified on hardware.

Hardware test, in this order: A13 check 3 by hand (`call 0xE05D088D 0x2BC61CC0 0x40`, compare `md` of
the cached and uncached address; a hang means never enable the toggle). Then with the buffer frozen
(plan step 3 state) a burst with `wr &rvx_fast_copy 1`, `wr &rvx_crop_x 192`, `wr &rvx_sidecar 1`:
pass = `rvi_check.py` reports 0 torn and 0 "copy differs", and the median copy time is at least 3x
shorter than the same burst with the toggle off.

## Limitations

- No hardware. The harness runs tasks inline in one thread: it cannot show starvation, priority
  effects, real timing, or a copy task that never finishes. "Priority 0x15 observed" means the value
  passed to `task_create`, nothing more.
- The original `tools/raw_vidx_hosttest/run.sh` no longer links against this module (it does not
  compile `rvx_step1.c`). Use the `_c12` copy, which contains the same 10 tests.
- The host test uses `fake_mlv.c`; the real `mlv_3.c` was not changed and not re-run through
  `mlv_check.py` in this task.
- `worker.c` is now about 1190 lines (it was 1088 on the start branch), above the 800-line guideline.
- Plan steps 0, 1 (probe script, bench task) and the rest of patch P1 (hook without semaphore and UART,
  per-second summary line, fps in the MLV header from timestamps) are not in this change.
- The ROM address `0xE05D088C` and the priority table are taken from A13 and A11 as written; I did
  not re-derive them. (Note added by H2 after D7-critic: the Fwrite / MovWriter priority 0x15,
  on which the `rvx_prio_clamp()` floor and the 0x15 / 0x16 recommendation rest, is caller-traced
  in A11, not a constant at the create site. G1 inherits this.)
- The core built in this worktree contains `offline-integrate1`'s core commits. Deploy the `.mo` only,
  never this `autoexec.bin`, unless that core is the one being tested.
