# B1 — Discord dump mined for DIGIC 8 LiveView raw capture

## Question

What does the community dump (`/mnt/data/WORK/eos/ml_discord`, 41 files, 926,702 lines) say about how LiveView raw
capture works on DIGIC 8 (M50, R, RP, SX740, M6 II, 850D/250D): `lv_save_raw`, `lv_set_mm`, MvRawPro / LvJob asserts,
"interrupt occurs", EVF state / vsync hooks, EDMAC channels, mem2mem, Boomer — and what does it imply for the M50 II?

## Summary

1. The D8 enable recipe is hardware-confirmed on EOS R (kitor): `lv_set_mm 1` (YUV->RAW), optional `lv_set_raw_wp 0`, `lv_save_raw 1`. Without `lv_set_mm` the same path delivers YUV.
2. On R, `lv_save_raw` drives write channel 3 (MMIO block `0xd0420200`); `raw_vidx` on the M50 II uses that same address. The channel is Canon-owned and refreshed every frame.
3. `MvRawProDs.c` line 293 (task EvfDev, core 1) is the long-standing "D8 crash": seen on R and RP since 2021 with no raw video at all, usually after `Blanking DeadLine`, and provokable by adding latency. Root cause was never found.
4. The copy-out on working D8 cams (R, SX740, M50) is kitor's reimplemented mem2mem (read 0x3d / write 0x18 on R, plus BoomerSelector); no other channel pair ever worked. Nobody claims to understand Boomer.
5. The dump has no D8-specific EVF state/input numbers and no M50 II raw work. Hooking EVF_STATE crashed RP in 2022; mk1 raw in 2025 just used `CONFIG_EVF_STATE_SYNC`.

Notation: `dev-general` = `Dev_Stuff__ml-developers-general.md`, `m50` = `Platform_Specific_Development__m50.md`,
`r` = `..__r.md`, `rp` = `..__rp.md`, `dev101` = `Dev_Stuff__development_101.md`, `q&c` = `Magic_Lantern_Community__questions-and-chat.md`.
Numbers after the file are line numbers in the dump. Note: `rg` treats several files as binary (embedded NUL); use `rg -a`.

## Inferred

- **MvRawProDs.c:293 is a Canon LV-pipeline deadline/timeout, not something raw video introduces.** It appears on R/RP with no raw code, on core 1 in EvfDev, right after `Blanking DeadLine`, and under injected latency. The stack dumps show `0xFFFFFFFF, 0x00000064` at the top (88101, rp 39352), which looks like a 100-tick wait argument, but nobody decoded line 293. The M50 II "MvRawPro storm" is most likely the same family: something delayed or disturbed Canon's per-frame raw job. This is inference; the ROM assert site should be read.
- **Redirecting Canon's raw channel is the riskiest step.** The channel behind `lv_save_raw` is serviced from interrupt context (names' NULL-redirect spinlock on 200D), and the per-channel status array is updated by ISRs (kitor, R). That fits the project's finding that redirect-off stops the storm. No D8 developer in the dump reports a working redirect on D8; R/SX740/M50 all copy out of Canon's buffer with mem2mem.
- **mem2mem during LV competes with Canon for resources.** On 200D it blocked until LV exited; on R only the exact ROM pair worked. A sync CPU copy (current M50 II recipe) avoids this, at a throughput cost (EDMAC ~600 MB/s vs CPU copy; names' 2096-wide frame <10 ms).
- **`lv_set_raw_wp` is optional** (defaults to SAP::HEAD); other raw types may give partially processed raw with different sizes — unexplored.
- **Stale alternate frames are an mlv_lite race, not a capture problem** (names' raw_vid is clean on 200D at 14-bit). On M50 mk1 they appear only at 10/12-bit.
- **"N interrupt occurs!"** is, per names' QEMU reasoning, the kernel reporting an IRQ entry with nothing valid pending (spurious/unhandled). A storm of it would mean an interrupt source left asserted or acknowledged without a handler — consistent with an EDMAC channel interrupt whose state Canon's code no longer expects. Inference from QEMU behaviour, not from D8 hardware.
- Any stub below `0xE0040000` is bootloader-dependent per unit; this matches the M50 II's own `memcpy_dryos` mis-port.

- Whether `lv_save_raw 1` alone destabilises Canon's movie path over long runs on D8; kitor never ran long enough ("i never used it for that long").

## Implications for raw video

1. Keep the capture side exactly as upstream: `lv_set_mm 1` + `lv_save_raw 1`, no redirect, copy from Canon's buffer. This is the only D8 configuration with hardware evidence (R, SX740, M50).
2. Treat every millisecond in the vsync/EVF path as budget. Logging, `msleep`, or a slow copy in that context reproduces the assert on R. The 50%-intermittent storm is more plausibly timing than a missing seed.
3. If EDMAC copy is revisited, use only the ROM mem2mem pair and BoomerSelector sequence, uncached src/dst without the `0x1FFFFFFF` mask, and a timeout on the completion flag (it never fires on failure).
4. Queue-full then wedge on stop matches the R/M50 "no memory suites" / second-clip freeze; bilal's `realloc_buffers()` fix and checking `setup_buffers` return are the known remedies.
5. Stay at 14-bit; lower depths are unsolved on D8 (no PACK32 register, alternate-frame repeats).
6. Do not call `raw_lv_redirect_edmac` with NULL or an unaligned/cacheable pointer under any path.

## Next hardware checks

1. **Baseline, no ML raw code:** `call lv_set_mm 1`, `call lv_save_raw 1`, then idle 5 min in movie mode with only the UART log. If `MvRawProDs.c` asserts appear, the storm is independent of the module (matches R/RP history). If not, the module's timing is the trigger.
2. **Read channel 3 block before/after:** `rd 0xd0420200 0x100` before and after `lv_save_raw 1`. Expect buffer pointer at `+0xa0` (should equal `0x6BC61CC8` or its uncached alias) and yb_xb at `+0x50`/`+0xf8`. Repeat 5 times one second apart: pointer constant = Canon reuses one buffer (R behaviour); changing = double buffering, which would explain stale frames.
3. **YUV/RAW switch:** `call lv_set_mm 0`, `call lv_save_raw 1`, dump 64 bytes of the buffer; then `lv_set_mm 1`. Different data layout confirms the flag works on M50 II.
4. **Latency sensitivity:** with recording off, add a deliberate 20 ms then 50 ms busy delay in the vsync hook. The delay at which `Blanking DeadLine` / MvRawProDs first appears gives the real budget.
5. **Assert line:** capture the full assert text of one storm event (file + line). Line 293 = same as R/RP; another line = M50 II-specific path.
6. **Per-channel status:** locate the M50 II equivalent of R's `0x73a58` status array (ISR-updated) and read the entry for channel 3 during a storm versus a clean run.
7. **Raw type:** `call lv_set_raw_wp 0` explicitly before `lv_save_raw 1`; if the storm rate changes, the default type on M50 II is not SAP::HEAD.
8. **Stop path:** after auto-stop, check whether `lv_save_raw 0` followed by a 2-frame wait and `lv_save_raw 1` clears the EvfDevState nullptr wedge.
