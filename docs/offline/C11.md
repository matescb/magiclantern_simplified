# C11 — Build-id layout hazard, host mlv_dump build, M50 / M50 II camera_id entries

Offline sprint, no camera attached. Nothing here proves behaviour on the camera.

## Goal

1. Make the ML core layout independent of branch name, date, hash and user@host string lengths.
2. Make the in-tree host builds (`mlv_dump`, `raw_vidx/mlv_3_sample_code`) work from a clean checkout
   without affecting the ARM build.
3. Give `mlv_dump` EOS M50 / M50 Mark II entries so `AsShotNeutral` is no longer garbage.

### 1. Where the variable strings come from

- `platform/Makefile`, rule `$(BUILD_DIR)/version.c` (was lines 608-615) writes
  `build_version` (`$(VERSION)` = `YYYY-mm-dd.MODEL.FW`), `build_id` (output of
  `build_tools/git_summary.py`: `git rev-parse --short HEAD` + space + `git branch --show-current`),
  `build_date` (`date -u '+... %Z'`), `build_user` (`whoami`@`hostname`).
- `version.o` is second in `ML_OBJS` (`platform/Makefile:292`), its 0x73-byte `.rodata` lands inside
  the `.text` output section (`src/magiclantern.lds.S` puts `*(.rodata)` there):
  `build_user` 0xf3521, `build_date` 0xf3549, `build_id` 0xf3561, `build_version` 0xf357e. Everything
  linked after it follows: the rest of `.rodata`, then `.rodata.str1.1`, `.rodata.str1.4`, `.data`,
  `.ARM.exidx`, `_bss_start`.
- Second place, not reported before: rule `$(BUILD_DIR)/version.bin` writes a text block
  (`Commit: <hash> <branch>`, `Built on ... by user@host`) that `src/reboot.c:100` `.incbin`s into the
  autoexec loader *in front of* its code. Its length moves `load_ok`, `blob_start`, `cstart` and the
  rest of the loader (not the core, which is copied to 0xc78e0). Example before the fix: `load_ok`
  0x8000f8 with the baseline strings, 0x8000d4 with user@host `u@h`; `autoexec.bin` 257696 vs 257664
  bytes on a 3-character branch.
- `-DVERSION="..."` in CFLAGS is fixed width for a platform (the date is always 10 characters).

### Fix design

Fixed-size char arrays, default widths equal to the strings of the known-booting build:

```
BUILD_ID_LEN   ?= 28     "3ccf499dc walkback-milestone"
BUILD_DATE_LEN ?= 23     "YYYY-mm-dd HH:MM:SS UTC"
BUILD_USER_LEN ?= 39     user@host of the machine that built the baseline

const char build_id[28 + 1] = "765760b5d offline-buildid-fx";      (printf '%.28s')
```

Shorter text is NUL padded, longer text is cut. `version.bin` uses `%-28.28s` / `%-39.39s`
(space padded). `build_version` is left alone (already length-stable per platform). `version.h`
(`extern const char build_id[];`) needs no change. A linker-script relocation of the strings was
rejected: it only moves the problem to the end of the section (section ends would still vary).

**Does the fix change the layout relative to the known-booting baseline? No.** Because the default
widths equal the baseline string lengths, the `.sym` is byte-identical to
`tools/symgate/baseline/M50mk2_101.sym` and `magiclantern.bin` has the same size (254300). Against
the main-tree `build/magiclantern.bin` 42 bytes differ, all text: build time, hash and branch inside
`build_date`/`build_id`/`build_version` (0xf354e-0xf3587) and the date digits of the `-DVERSION`
string in `.rodata.str1.1` (0xfb222-0xfb226). `autoexec.bin`: 83 differing bytes, the same text in
`version.bin` plus those 42 (and the checksum word). So adoption does not need a layout-motivated
boot test; it is a rebuilt core like any other, so the first card built from it should still get one
normal boot check. Changing any of the three widths later moves the layout once.

## Limitations

- Layout checks compare `.sym`, section ends, loader symbols and binary diffs on the host. No boot.
- The widths are tied to this build machine's 39-character user@host and to 9-character short
  hashes; a longer hash eats into the branch field (still fixed width). On other platforms the widths
  are equally applied but were not built.
- `build_id` on a long branch is cut (`offline/C11-a-very`); the full name is not recoverable from the
  binary.
- The M50 / M50 II colour data is provisional: one D65 matrix used for both illuminants, no forward
  matrices, no focal plane resolution (0/0 as for unlisted cameras). `AsShotNeutral` is derived from
  the matrix and the WBAL Kelvin value, not from Canon's WB gains; colours were not judged visually
  (no render made, WBAL values in the test file are invented).
- What model id the camera actually writes into IDNT was not observed; 0x80000468 is the ROM value.
- `modules/raw_video/mlv_rec/dng2raw.c` still does not compile (wrong include path and missing
  `stdint.h`); it has no Makefile target and was left alone.
- Host builds need a 32-bit multilib gcc (`-m32`), as before.
- The build leaves untracked `platform/M50mk2.101/edmac-d8.{d,o}` in the worktree, as in the main tree.
