# A12 - Engine resource locks (Engine::Ersc.c) on M50 II 1.0.1

## Question
What do resource IDs mean, what does Canon lock for LV raw / movie / DAF / EIS / mem2mem, where is
DeleteResLockEntry, which resources does an ML mem2mem or raw capture need, and should ML hold
`{0x100AD, 0x100BB}` for the whole recording, per frame, or not at all?

## Summary
- `{0x100AD, 0x100BB}` are locked by NO Canon path in this ROM, so the ML lock cannot contend with Canon through the resource manager; the "res-lock starves DAF/EIS" theory (commit 31442ed9a) is not supported by the ROM.
- The stub `LockEngineResources` = 0xE05BE8A6 is the wrong sibling: it is the non-blocking TRY-lock (0 Canon callers). Canon's blocking lock, the one every reference port uses, is 0xE05BE6A6.
- The IDs come from kitor's R.180 `EFsVcopy`; that function and `MemoryToMemoryEsub1` do not exist on M50 II.
- DeleteResLockEntry = 0xE05BE5A2. ML never calls it, so each recording leaks one entry.
- Recommendation: no lock for the CPU-copy path (the current default). Do not "fix" the stub to the blocking variant without the hardware checks below.

## Observed
Addresses are ROM0 (gang100.bin); all code is Thumb.

**Manager (string "Engine::Ersc.c" at 0xE05BE850, RAM state at 0xB0F0)**
- 0xB0F0: +0 node magic, +4 entry magic, +8 bucket array pointer (8 bytes per bucket, indexed by `id >> 16`), +0xC recursive lock, +0x10 waiter list head.
- ID encoding (0xE05BE51A-0xE05BE528, 0xE05BE5F4-0xE05BE5FA): high 16 bits select the bucket; the full 32-bit ID is compared against node+0xC. The low word is never range-checked.
- `CreateResLockEntry(ids, n)` 0xE05BE4BE creates a 0x14-byte node for any ID not already in its bucket (0xE05BE52E-0xE05BE568). Unknown IDs are accepted silently.
- Entry (0x24 bytes): +0 magic, +4 state (1 waiting, 2 locked, 3 unlocked), +8 semaphore, +0xC/+0x10 waiter link, +0x14 ID array, +0x18 count, +0x1C/+0x20 async callback and argument.
- Node: +0 magic, +4/+8 list link, +0xC ID, +0x10 locked flag (0 or 1). There is no owner field.

**ML source**
- `platform/M50mk2.101/edmac-d8.c:219-222` calls Create + "Lock" and ignores the return value; unlock is at :237; there is no Delete.
- `mem2mem_resources {0x100AD, 0x100BB}` is byte-identical in kitor SX740.102, R.180 and bilal M50.110 `edmac-d8.c:82`. The comment there says "Values stolen from R180 EFsVcopy ... DNE on SX740, but config still works".
- bilal `mlv_lite.c:2682` locks once at record start and unlocks at :2698 on stop, only when `OUTPUT_COMPRESSION == 0`. That is a whole-recording hold, using the blocking variant.
- Discord (Dev_Stuff 152893, 152937): ID = (block << 16) | device ID in that block; a block-1 path locks block-1 resources and wakes PwrMng device 0.

## Inferred
- Because Canon never names 0x100AD or 0x100BB, ML's Create makes two private nodes. The try-lock then always succeeds and blocks nobody. As far as the resource manager goes, the lock is inert on this body, for any hold duration.
- Canon code cannot receive 0xd from resource contention: its only lock entry points are the blocking and async ones. A starved Canon path would hang in `take_semaphore`, not log an error. The 0xd in the EIS storm comes from the event-post path, and the match with the try-lock's 0xd is coincidental.
- If `m50ii_edmac_skip_reslock=1` ever changed behaviour on hardware, the cause would be timing or the PwrMng wake/suspend, not the lock.
- The 21 unresolved Create sites build their lists on the stack or in RAM (MovWrapTask, OrcaDS, DirectPrint, GigaCapture). They are movie-wrap, transcode and print paths; I expect no category-1 0xAD/0xBB there, but did not prove it.
- On M50 mk1 the same two IDs are probably just as foreign (same R-derived constants), which would explain why a whole-recording hold "works" there.

## Unknown
- The mapping from EDMAC channel (WR 13, RD 46) to a category-1 resource ID. Channels 3, 5/6 and 2 do not line up with an obvious offset in their paths' lists.
- Whether Canon holds MvRawProPath / SapPath / Mem1Path resources for the whole LV session or per frame. This decides whether a correct blocking lock from ML would deadlock.
- Bucket array size (the bound on `id >> 16`); categories seen are 1-7 and 9.
- Whether mk1's 0xe0558386 is byte-equivalent to 0xE05BE6A6 (no mk1 ROM here; the offset match is structural only).
- Runtime behaviour in general: none of this was executed.

## Implications for raw video
- Stop treating the res-lock as the DAF/EIS storm cause. Look at the EDMAC channel hijack (`raw_lv_redirect_edmac`, already implicated) and PwrMng wake/suspend instead.
- CPU-copy path (`m50ii_edmac_cpu_copy=1`, the working recipe): no engine resource is used, so no lock is correct. `m50ii_edmac_skip_reslock=1` is a safe default and avoids the per-recording leak.
- EDMAC mem2mem path, if revived: the R-derived IDs protect nothing here. A meaningful lock needs the IDs Canon ties to channels 13 and 46; the nearest Canon analogues are InitMem2MemPath `{100A8, 100B0, 10046, 1004E, 1004F, 10062}` and Mem1Path `{10062, 10072, 100B1}`. 0x100B0 is shared with MvRawProPath and 0x10062 with Mem1Path, so a whole-recording hold of those would block Canon's LV raw path forever. Only a short per-copy hold, or no lock, is viable.
- Do not repoint the stub to 0xE05BE6A6 blindly. With the current foreign IDs it changes nothing; with real IDs it can hang the ML task while LV owns them.
- If the lock is kept, add DeleteResLockEntry (0xE05BE5A2) after unlock, or create the entry once.

## Next hardware checks
1. Manager state in LV idle: `rd 0xB0F0 0x20`. Take B = word at +8. Category-1 bucket is at B+8.
2. Walk category 1, idle and again during H.264 recording: `link = [B+8+4]`; while `link != B+8`: ID = `[link+8]`, locked = `[link+0xC]`, `link = [link+4]`.
   - 0x100B0 / 0x10062 / 0x10044 locked in every sample: Canon holds per session, so a correct ML lock would deadlock; use no lock.
   - They toggle: Canon locks per frame; a short per-copy ML lock is possible.
   - No node for 0x100AD / 0x100BB before ML first records: confirms Canon never creates them.
3. After one ML recording with `m50ii_edmac_skip_reslock=0`, repeat the walk. Expect nodes 0x100AD and 0x100BB to exist with locked = 0, and locked = 1 only while recording.
4. Return value of the current stub: `call 0xE05BE4BF <addr of mem2mem_resources> 2` gives entry E; `call 0xE05BE8A7 E` should return 0; a second call should return 1; `call 0xE05BE741 E` 0; `call 0xE05BE5A3 E` 0. A 0xd on the first lock would falsify "nobody else uses these IDs".
5. A/B the storm with `wr &m50ii_edmac_skip_reslock 1`. Prediction: no change in DAF/EIS storm rate. A change points at timing or PwrMng, not the lock.
6. Only with a watchdog or power-cycle path ready: build `{0x100B0}`, Create, then `call 0xE05BE8A7` (try, safe). 0xd in LV means Canon holds it right now. Never use 0xE05BE6A7 from the serial shell; it can block the shell task forever.
