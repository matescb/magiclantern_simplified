## Question

What does the ML community know about card write speed and recording throughput on DIGIC 7/8 bodies
(SD overclock, UHS modes, measured MB/s, bench.mo, FIO_WriteFile behaviour, pre-allocation, exFAT/4 GB,
continuous resolutions, lossless and 10/12-bit on D8), and what does that imply for an M50 II recorder?

## Summary

- M50 (mk1, same UHS-I class as M50 II) already runs the SD bus at ~195 MHz (SDR104) stock; nobody has pushed it higher. "All UHS1 D8 cap about 90 MB/s" in bench, and M50 drops to ~70 MB/s while recording raw in LiveView.
- No one has overclocked SD on any D8 body ("Noone explored overclocking on D8", kitor 2026-04). The 2025 `sd_uhs`/autotune work is D5/D6/D7 (200D) only.
- Lossless (LJ92 / TwoInTwoOut) does not exist on any D7/D8 port. Only strings were located on 200D in 2023; no stubs, no working call.
- 10/12-bit on D8 (M50) is not usable: either every other frame is stale, or (pitch patch) the image is tilted. 14-bit is the only working depth.
- Net for M50 II: budget ~65-70 MB/s sustained, 14-bit uncompressed. Full 2096x1164 at 24p needs ~102 MB/s, so continuous needs a crop of about 1.6 MP (for example 1920x818, the mode that ran 15 minutes on 200D).

### 2. SD clock modes and "overclocking" on D6/D7/D8

- What sd_uhs really is: "IIRC it is not really overclocking. We just put controller into faster modes that it does support but it is not exposed through official firmware." (kitorpl 2023-09-08, 101:11794).
- D6/D7 driver ships SDR104 code but selects SDR50: "on digic 6 at least (and I think at least some 7 too), Canon appears to always select SDR50 even if the card advertises SDR104 support, despite the fact that the firmware has code to support SDR104" ... "just setting the clock up to SDR104 speed without telling the card works fine" (reyalpchdk 2025-08-25, gen:187848-187850).
- D6 clock table from ROM tops out at 195.8 / 202.5 MHz on registers `0xD2090600..0xD2090628` (bilal 2025-08-26, gen:187964-187978); 200D table has 111/130/156/195 MHz rows with `0xD2090604` acting like a multiplier (gen:187990-188015).
- "kinda think 195 / SDR104 is the best digic 6 can do ... the values that change get lower for faster speeds, and I don't think they can go lower than final two entries" (reyalpchdk 2025-08-27, gen:188162). Experiments on a D6 PowerShot: wrong values crash on SD access or reset to non-UHS (gen:188166-188178).
- 200D root cause (static + HW): Canon's init never calls the autotune function on 200D but does on 6D2 (gen:188199-188221); "There was a bug in Canon code. It has an array of speeds to try, with 192 being the first. But it increments the array index at the top of the loop, so it always skips the first entry" and "Made SD faster on 200D, it can now use 192MHz mode" (names_are_hard 2025-08-29, gen:188316-188318). Before the fix: "With autotune, I think 200D will attempt 192, but it always seems to fallback to 156" (gen:188279).
- Shared driver: "sddomChangeClockSpeed and SetSDClkFrequency are nearly identically between 200d and digic 7 p&s" (reyalpchdk 2025-08-11, gen:187134). SD register access is guarded by a semaphore; on 200D 1.0.1 the take function at `e0391204` references "SdcommonAPISemLock" (gen:188664).
- Tuning matters mostly for reads (SD spec quote by reyalpchdk, gen:188142-188146); D5 experience: 240 MHz stable for write, less for read; unstable OC drops the controller to a ~21 MB/s safe mode; OC that is stable outside LV can fail inside LV (bilal 2025-08-31, gen:188628-188636; gen:20758).
- D8 status: "Noone explored overclocking on D8" / "This is likely a brand new controller so who knows." (kitorpl 2026-04-08, qc:195188-195190). The official `sd_uhs` module merged in Sept-Oct 2025 "including fixes for dangerous behaviour on new cams" (gen:191709) - it is not a D8 overclock.
- UHS-II theory quoted for R: "UHS-II: 156 MB/s full-duplex, or 312 MB/s half-duplex" / "clearly we are running half duplex" (kitorpl, r:16003, r:17112-17114).

### 3. FIO_WriteFile, cacheable vs uncacheable, alignment

- M50 screenshot bug (HW): a buffer whose first bytes were non-zero was written as garbage; "so it is FIO_WriteFile problem" -> "Could still be cache/uncache" -> "yes, it is" / "forced pointer to UNCACHEABLE()" (kitorpl + names_are_hard 2022-01-07, m50:16891-16915). kitor then opened the PR "without `UNCACHEABLE()` change" (m50:16933), so the workaround was not upstreamed at that time.
- EOS R (HW, UART): `[FSU] WARN Please Designate Uncacheable AdSdr!!!!!!` followed by `[FSU] WARN FSUBlockWrite: NotPrepared` and `[FIO] ERROR @EvShel Write(ecode=0x1003)` (kitorpl 2021-03-20, r:6477-6479); "fix rom dump task not working (FIO complains about addresses **not** being in uncacheable memory)" (kitorpl 2021-03-31, r:8356). Also R: "`FIO_WriteFile` writes the correct ammount of bytes but returns -1 and file contains garbage" (coon_42 2021-03-21, r:6752-6754).
- Memory model: "M50 has 1 gig of ram so it should work similar to eralier models. On 2 gig models (R,RP, M6II, ???) there's 1 gig that is uncacheable only." (kitorpl 2025-08-31, m50:21065; same in 101:32060).
- DMA rule: "For DMA operations, it's required that you use uncache addresses" / "You also want to align the start of the operation to some number (differs per generation, I think, 0x20 is common, I align higher out of paranoia)" / "DMA operations act on the physical ram directly, and thus ignore the CPU cache" (names_are_hard 2025-08-31, m50:20923-20927). On M50 bilal fixed EDMAC-copy cropping by removing the `& 0x1FFFFFFF` mask (m50:20908-20917); names warns that is not portable to all D8 (m50:20929).
- Canon's own FSU write log format on M50 UART: `[FSU] [W:S] (a:1)0x40aa5200 s:25189 c:1 T:3585us Ave:0MB/s` (m50:15942) - note the buffer address `0x40aa5200` is in the uncacheable mirror.
- No chunk-size or sector-alignment tuning for card writes on D78 is discussed anywhere in the dumps (searched: chunk, align, sector, cluster, dma_alignment). The only hit is a Linux `dma_alignment 511` aside (gen:188026-188029).

M50 II ROM strings (OBSERVED in `gang100.bin` via `strings -t x`; address = file offset + 0xE0000000; code xrefs NOT resolved, the literal-pool xref search returned none):

- `0xE00854C4` "Please Designate Uncacheable Addr!!!!!!", `0xE0085890` "FSUBlockWrite: NotPrepared [W:%s s:%d c:%d"
- `0xE0085978` "[W:%s s:%d c:%d T:%dus Ave:%dMB/s", `0xE008586C` read variant
- `0xE00DE39C` "SD-UHS1 speed=%d clock=%d", `0xE00DDAF0` "SdUHSTuning TryClkDown->%s", `0xE00DDB24` "SdUHSTuning impossible!!!", `0xE00DF45C` "SdUHS1TuningSamplingPointPartVDL %d", `0xE00DE470` "[UHS1]current:%s mode:%s strength:%#04x"
- evproc-style names: `0xE00E86E8` DebugSTG_GetSDWriteSpeed, `0xE00E87C8` DebugSTG_SetSDRMode, `0xE00E89B0` DebugSTG_CacheUnCache, `0xE00E81AC` "DebugSTG_MemorySpeed %d us", `0xE00E876C/0xE00E8788` DebugSTG_StartInfWrite / StopInfWrite, `0xE00E87E0` DebugSTG_SplitPerformance, `0xE00E897C` DebugSTG_GetClusterSize, with `0xE00E810C/0xE00E811C` "Time(Cache) %d" / "Time(UnCache) %d".

- 200D (HW): "on 200D it's only in 12 or 10 bit that it skips frames. 6D2 sucked in all bit depths (with mlv_lite)" (names_are_hard 2025-08-30, m50:20844); users see 10/12-bit as "colored grain" (qc:157686, qc:157840).

## Inferred

- M50 II ceiling. M50 II is the same UHS-I class as M50 (qc:195172). If M50 mk1 is already at 195 MHz stock and D8 UHS-I benches cap near 90 MB/s, then M50 II very likely has the same ~90 MB/s Play-mode ceiling and a lower LiveView/recording figure. The only D8 UHS-I recording figure is bilal's "~70 MB/s ... needs further tests". Treat 65-70 MB/s as the planning number until measured.
- SD overclock is not a near-term lever. On D6/D7 the gain came from enabling SDR104 that Canon left unused; on M50 that mode is already in use. Going past 195 MHz is unexplored on D8 and on D6 looked impossible via the known register pattern. Expected gain for M50 II: zero until someone proves otherwise.
- Throughput arithmetic (mine, MB = 10^6 bytes, 14-bit packed):
  - 2096x1164 at 23.976 fps = 102.4 MB/s; at 25 fps = 106.7 MB/s. Above the bench cap, so never continuous uncompressed.
  - 2008x1128 (active area) at 23.976 = 95.0 MB/s. Still above.
  - 1920x818 at 23.976 = 65.9 MB/s. This matches the 200D "~65 MB/s" limit and its 15-minute result, which is a good sanity check of the model.
  - At 70 MB/s and 23.976 fps the budget is about 1.67 MP per frame (for example 1920x868 or 1736x960).
  - If 12-bit worked: 2008x1128 = 81.5 MB/s; 10-bit = 67.9 MB/s. So 10-bit is the only depth where the full active area would fit, and it does not work yet.
- Buffer source for card writes must be an uncacheable address on D8. Three independent observations agree: the M50 garbage-file fix, the R FSU warning, and the fact that the same warning string exists in the M50 II ROM. This is consistent with the project's own `fio-ml.c` uncacheable gate (project memory, docs/35); the Discord evidence says this is a general D8 FSU requirement, not an M50 II quirk.
- The run-to-run slowdown after repeated benchmarks (r:17103) implies a freshly formatted card is needed for any throughput measurement to be comparable.
- LV load costs card throughput on D8 as on older bodies (R: 112 -> 104; M50: ~90 bench vs ~70 recording). Part of the M50 recording drop may be CPU copy time rather than the bus; the dumps do not separate the two.

- Static analysis and chat reports do not prove M50 II runtime behaviour.

## Implications for raw video

1. Design for 65-70 MB/s sustained, 14-bit uncompressed. Offer a continuous preset near 1.6 MP (1920x818 at 23.976 is the proven 200D point) and treat full 2096x1164 as a burst mode whose length is set by RAM buffer size.
2. Buffering matters more than usual: SRM is broken or disabled on D8 (R limited to <30 MB), so the burst length depends on what shoot-memory/other allocation the port can get. With ~32 MB/s of deficit at full frame, every 100 MB of buffer buys about 3 seconds.
3. Do not spend time on SD overclock for M50 II now. First read the clock the camera actually uses; only if it is below SDR104 (as on 200D) is there an easy win.
4. Keep every buffer passed to FIO_WriteFile in the uncacheable mirror and aligned (>= 0x20, 0x1000 is safe). Write the frame from the uncacheable EDMAC destination directly rather than via a cacheable copy when possible; that also removes one memcpy from the copy+write < frame-period budget the project already hit (queue fills, auto-stop).
5. Do not plan on lossless or on 10/12-bit to fix the bandwidth gap. Both are unsolved on every D7/D8 body; 10/12-bit has a known half-solution (EDMAC pitch) that damages the image.
6. Benchmark method: fresh in-camera format, run in Play and in LV, and compare with a real recording, because all three differ.
7. Canon's FSU already logs per-write `T:%dus Ave:%dMB/s`. If that log level can be enabled over UART, it gives ground-truth per-call write timing without ML instrumentation.

## Next hardware checks

Addresses are M50 II 1.0.1 ROM string addresses observed here. Function addresses must be resolved first (the strings have no literal-pool xrefs; look for `adr`/`movw+movt` users in Ghidra).

1. Bus mode at mount. Capture UART across a cold boot with a UHS-I U3 card and grep for `SD-UHS1 speed=%d clock=%d` (fmt at `0xE00DE39C`), `[UHS1]current:%s mode:%s strength:` (`0xE00DE470`) and `SdUHSTuning TryClkDown->` (`0xE00DDAF0`). Existing history can be checked first: `grep -a -i -E 'UHS1|SdChangeClockSpeed|SdUHSTuning' tools/mlserial/run/uart.jsonl`. Decides: SDR104 already in use (no easy win) versus SDR50 or clocked down (200D-style fix possible).
2. Canon write statistics. During an ML recording, look for `[FSU] [W:` lines with `Ave:%dMB/s` (fmt at `0xE0085978`). If absent, find the DryosDebugMsg class/level used by the function referencing that string and raise it. Decides: is the card call itself at ~70-90 MB/s (bus-limited) or much faster with idle gaps (ML copy/scheduling-limited).
3. Uncacheable gate confirmation. Grep the UART history for `Please Designate Uncacheable` and `FSUBlockWrite: NotPrepared`. One deliberate write of a small cacheable buffer versus `UNCACHEABLE()` of the same buffer, with read-back compare, settles whether FSU rejects, warns or silently corrupts on M50 II.
4. Raw ceiling without LiveView cost. Run bench.mo (or a loop writing a 32 MB uncacheable buffer with FIO_WriteFile, 16 times, timed with get_ms_clock) in Play mode and again in movie LiveView, on a freshly formatted card. Expect roughly 85-90 versus 65-75 MB/s. If Play is far below 85, the bus is not at SDR104.
5. Chunk-size sweep. Same loop with write sizes 512 KB, 1, 2, 4, 8, 16, 32 MB and with the buffer start aligned to 0x20, 0x200 and 0x1000. Decides the writer's chunk size and whether sector/cluster alignment matters on D8 (no community data exists).
6. Copy cost. Time the per-frame copy (EDMAC copy or CPU copy) for 2096x1164 separately from the write. Decides how much of the 14 ms/frame at 70 MB/s is available; if copy > ~10 ms the bottleneck is not the card.
7. Canon storage evprocs (only after resolving that they are registered): `call("DebugSTG_GetSDWriteSpeed")`, `call("DebugSTG_GetClusterSize")`, `call("DebugSTG_CacheUnCache")` and watch UART for `Time(Cache) %d` / `Time(UnCache) %d`. Do not call `DebugSTG_SetSDRMode`, `DebugSTG_RandomWrite`, `DebugSTG_1SectorWrite` or `DebugSTG_StartInfWrite` blind: they plausibly write to the card or change bus mode, and blocking callees wedge the serial shell.
8. Continuous preset proof. Record 1920x818 14-bit at 23.976 for 5 minutes on a formatted U3 card; log queue depth each second. Flat queue confirms the ~66 MB/s point; growing queue gives the real sustained rate from its slope.
