# C2 - Reproducible QEMU harness for the M50 Mark II ML build

Date: 2026-11-16. Offline sprint, no camera attached. Nothing here proves behaviour on hardware.

## Goal

One-command, repeatable way to (a) put the *current* ML build on a QEMU SD image,
(b) launch the known-good `qemu-eos-build` M50mk2 model, (c) smoke-test boot to `big.8`
plus the serial shell - and to record exactly what the current `walkback-milestone`
build (a10b16c23) does in QEMU.

## What was built

All under `/mnt/data/WORK/eos/tools/qemu/` (new directory; nothing existing was touched):

| file | purpose |
|---|---|
| `common.sh` | shared paths (ML build dir, base images, QEMU binary, mtools); all overridable by env |
| `mk_sd_image.sh OUTDIR [NAME]` | copy `m50ii_dumper/qemu_stage/sd_mltest.raw` -> `OUTDIR/sd.raw`, replace `AUTOEXEC.BIN` and the whole `ML/` dir via mtools (no sudo/mount), list the image, md5-verify every written file, write `sd.raw.manifest` |
| `run_m50mk2.sh --sd IMG [...]` | launch QEMU with the documented options; `--log`, `--tcp PORT`, `--gdb PORT`, `--freeze`, `--boot 0/1`, `--timeout`, `--detach`, `--rw`; PID-based cleanup + watchdog |
| `smoke_test.py --sd IMG --outdir DIR` | boot, wait for `big.8`, run `ver` + `help` over the TCP serial shell (20 ms/char), write `summary.txt`/`summary.json`; exit 0/1/2/3 |
| `vendor/mtools/` | mtools 4.0.43 unpacked from the Ubuntu .deb with `dpkg -x` (mtools is NOT installed on this host; `apt-get download mtools`, no sudo). Used automatically when no system `mcopy` exists |

How to run:

```
cd /mnt/data/WORK/eos
tools/qemu/mk_sd_image.sh sim/C2                       # -> sim/C2/sd.raw (+ .manifest)
tools/qemu/run_m50mk2.sh --sd sim/C2/sd.raw --log sim/C2/run1/uart.log --timeout 60
tools/qemu/smoke_test.py --sd sim/C2/sd.raw --outdir sim/C2/smoke1 --port 4487 --boot-timeout 300
# gdb: start frozen, attach (one foreground shell command, see docs/20)
tools/qemu/run_m50mk2.sh --sd sim/C2/sd.raw --log x/uart.log --gdb 1266 --freeze --detach
gdb-multiarch -batch -ex 'target remote :1266' -ex 'hbreak *0x00800000' -ex continue ...
```

Design notes:
- Stale-symbol guard: `mk_sd_image.sh` exits 1 before touching anything if `M50mk2_101.sym`
  is older than `autoexec.bin` (or than the ELF `magiclantern`).
- `ML/` is rebuilt from `build/zip/ML` (fonts, data, scripts, cropmks) but `ML/modules`
  contains ONLY the `.sym` + the modules in `$MODULES` (default `raw_vidx bench file_man`);
  anything else in `ML/modules` fails verification.
- `MODULE_SRC=auto|build|tree` (default `auto`) - see finding 1 below.
- `run_m50mk2.sh` uses `snapshot=on` for SD and CF, so image files are never modified by a
  run (`--rw` opts out for the SD only, refused on the pristine base image). With `--tcp` it
  uses `-chardev socket,...,logfile=` so the UART log is complete even when no client is attached.
- Ports used for C2: serial 4487, gdb 1266.

**Finding:** `platform/M50mk2.101/build/modules/*.mo` and `build/zip/ML/modules/*.mo` (and
therefore `build/magiclantern.zip`) hold module binaries whose embedded "Build date" is
**2026-07-05**, byte-identical to the old `modules/build/*.mo`. Their file mtime (07-21 17:40)
is only the copy time. The real current modules are in `modules/<path>/build/<name>.mo`
(raw_vidx: 22272 bytes with the `rvx_*` symbols, built 07-21 15:40:54 UTC, the same minute as
`autoexec.bin`). The task said to take modules "from the build's modules dir"; doing that
literally would put a 2.5-week-old raw_vidx next to a new `.sym`. The script therefore
defaults to `MODULE_SRC=auto` (pick the later embedded build date, warn loudly);
`MODULE_SRC=build` gives the literal behaviour. The image left in `sim/C2/sd.raw` carries the
per-module (fresh) builds - see `sim/C2/sd.raw.manifest`.

understood, but the *echo* is sometimes mangled (`@1vr` instead of `@1 ver` in run 2) or
split by an async `[FIO]` line (run 1 `help`); the terminator `=ok @N` is reliable.

`sim/C2/smoke2/` (`uart.log`, `uart.log.qemu-stderr`, `summary.txt`, `summary.json`), `sim/C2/gdb1/`.

## Limitations

- The SD card is not mounted by Canon's FIO in QEMU, so the image contents beyond
  `AUTOEXEC.BIN` (modules, `.sym`, fonts) are **never read** by the emulated firmware. The
  harness verifies that the right files are on the image, not that they load. Module loading,
  the stale-`.sym` crash, raw_vidx and MLV writing cannot be exercised with this model as is.
- The lowercase 8.3 names mtools writes (`raw_vidx mo` with NT case bits, LFN only for the
  `.sym`) differ cosmetically from the old image (uppercase + LFN); untested against Canon's
  FAT driver for the reason above.
- Display, PropertyMgr, MPU buttons, CPU1 (`cpu1rdy=0`) are not modelled; the two repeated
  asserts are QEMU-side (KerQueue.c:522 was already classed QEMU-only in the project notes).
- Wall-clock boot time (59-65 s) depends on host load; it is not a camera boot time.
- `smoke_test.py` treats non-fatal asserts as informational: exit code is only about
  `big.8` + shell replies.
- Only two boots were run; no flakiness statistics.
- The "skipping module load" message could not be confirmed either way (see above).

## Next hardware checks

1. Confirm what is on the real card: `raw_vidx.mo` should be the 22272-byte build
   (md5 0715abdd...), not the 14304-byte 2026-07-05 copy that `build/modules`,
   `build/zip` and `magiclantern.zip` contain. If any deploy path copies from
   `platform/M50mk2.101/build/modules` or the zip, it ships stale modules.
2. On camera, after boot: `ver` should print `ML M50mk2 1.0.1 2026-07-21.M50mk2.101`
   (same string QEMU printed) - cheap check that card and QEMU run the same autoexec.
3. On camera the KerQueue.c:522 / GUI.c:894 assert pair should be absent (QEMU-only); if it
   shows up in the hardware UART log it is a real problem.
4. Module load on hardware remains the only way to validate `.sym`/module matching until the
   QEMU SD/FIO mount is fixed (worth a follow-up: why Canon FIO reports `[no sem]` - the FIO
   semaphore is never created because Canon's storage init does not complete in the model).
