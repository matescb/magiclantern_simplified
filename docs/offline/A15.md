# A15 - ROM1 contents and the boot-time RAM images

## Question
(1) What is in gang200.bin (ROM1, 0xF0000000, 16 MB), and is any of it relevant to raw video?
(2) Exact ROM source offsets/lengths of the RAM images Canon copies at boot, a standalone lookup tool,
and the initial values of the RAM pointers raw video depends on.

## Summary
- All seven raw-video pointers (0x10108, 0x4FF4, 0x63B0, 0x83F24, 0x23800, 0x292B0, 0x5154) are **0 at boot**: six sit in the copied `.data` image with a zero initialiser, 0x83F24 is in zero-filled `.bss`. Every one is filled in at run time by Canon init code, so no static image can supply them.
- The three copied images are contiguous in ROM0: file offsets 0x1394358 (len 0x26D1C), 0x13BB074 (len 0xDE530), 0x14995A4 (len 0xBA0). Tool: `docs/offline/tools/raminit.py`.
- ROM1 holds no code. It is four property areas (FIX, an unnamed 16-bit-table area, TUNE, RASEN x2 mirror) plus one 8.7 MB GUI resource container (strings, fonts, images); 43 % is erased 0xFF.
- Canon's own flash-area map is a getter table at ROM0 0xE027C104..0xE027C318; RING and LENS property areas are in ROM0 (0xE1C40000, 0xE1C80000), not ROM1.
- Nothing in ROM1 is needed to get MLV recording going; sensor calibration/defect data most plausibly lives in FIX/TUNE but was not decoded.

## Observed

### RAM images (ROM0, gang100.bin, base 0xE0000000)
Copy code is `firmware_entry` 0xE004003C..0xE00400C6, literals at 0xE00400C8..0xE00400FC (disassembled with tools/romdis.py).

- The three sources are back to back: 0xE1394358+0x26D1C = 0xE13BB074; 0xE13BB074+0xDE530 = 0xE14995A4; image ends 0xE149A144, followed by 0xFF fill. 64 bytes before 0xE1394358 are zero.
- Matches docs/13 and ghidra/memory-map.md exactly; no correction needed.
- Oddity: the icache_invalidate call at 0xE0040072 computes its length as `0x2AD1C - 0x0223B000` (r3 reloaded from literal 0xE00400E0 = 0x2AD1C), i.e. a negative/huge length. Not followed further.
- data image: 39751 words, 19297 non-zero, 5260 point into ROM0, 131 into ramcode, 2 real pointers into ROM1 (RAM 0x21754 = 0xF0880F78, RAM 0x23A88 = 0xF0DA9758, both inside the GUI resource container).
- ramcode image: Thumb code plus 3832 strings; source-file tags are 45 x `AutoExposure::*` (AEWB, APEXMgr, ColorCalc...), 39 x `Fmid::*` (face/tracking), 21 x `Engine::Detect*/Dancing/Messi/Saridon`. No Evf/LiveView/EDMAC/raw file tags.
- blob2 image: starts with SCTLR/cache CP15 sequences (`mrc p15,0,r0,c1,c0,0` ...), contains string `System::SROMInstall.c`.

## Inferred
- The property areas use Canon's nested format: block {size, flags} at area+0x30, then class {size,id}, group {size,id}, then {id,size,data} records. My walker parsed the small groups cleanly but not the large ones (they have a different sub-header), so the per-property listing is incomplete.
- FIX group 0x00030039 (1.25 MB) and TUNE groups 0x0101006F / 0x01040000 are the likely homes of sensor calibration, shading and defect data, based on size only and on the ROM0 factory strings (`FA_LVFACTDEFECT_ConvStlDefDataToLvDefDataForDC`, `FAE_GetSensDefect`). Not confirmed.
- The 0xF01A0000 area is probably a second tuning table set (same reserved size as TUNE, 16-bit gain-like values); its Canon name was not found.
- RASEN = network/WiFi settings with an A/B mirror. It contains device-unique data (name suffix "E1FF1B", certificates); treat gang200.bin as private.
- Since ramcode holds only AE/face/tracking modules, the EVF/LV/EDMAC raw path executes from ROM (XIP), so ROM-address stubs for it are not affected by the RAM overlay. Static reading only.

## Unknown
- Which Canon init function writes each of the seven pointers, and at what boot stage (not traced here; statics only say "0 until written").
- Canon name and consumer of the 0xF01A0000 area; whether any LV crop/mode table sits in ROM1 (none found by string search; LV mode tables are more likely ROM0 const data).
- Exact property IDs inside the large FIX/TUNE groups.
- Why icache_invalidate at 0xE0040072 is passed a wrapped length.

## Implications for raw video
- A NULL at 0x10108 / 0x4FF4 / 0x292B0+0x30 on hardware means "Canon has not initialised this yet", not corruption. Any ML code that dereferences these must gate on non-zero (function_overrides.c already does for 0x4FF4).
- The no-op callback slots (0x23808, 0x23810, 0x292C4, 0x292CC) give a cheap health test: after LV start they should either still hold the `bx lr` stub or a ROM0 Thumb pointer. Anything else indicates memory overlap from ML.
- For QEMU/Ghidra: loading the three images at their RAM addresses is sufficient; ROM1 is only needed for property load (FIX/TUNE/RASEN) and GUI resources, none of which block the raw path.
- ROM1 offers no shortcut for raw video (no sensor mode tables identified); effort is better spent on ROM0.

## Next hardware checks
Serial harness (`rd <addr> <nwords>`), compare against `python3 docs/offline/tools/raminit.py <addr> <n>`:
1. `rd 0x23808 4` and `rd 0x292C4 4` idle in photo mode, then in LV, then while recording. Stub values (0xE07B9C89, 0xE0760DF5) = no client registered; a ROM0 odd pointer = Canon registered a callback; anything else = RAM corruption.
2. `rd 0x10108 1`, `rd 0x4FF4 1`, `rd 0x5154 1`, `rd 0x63B0 1`, `rd 0x83F24 1` right after `big.8`: all must be non-zero RAM pointers. Record at which boot marker each turns non-zero to order ML init safely.
3. `rd 0x292E0 2` in LV: expect the RawPro channel numbers (0x29 / 0x4C per A1). 0 means LV raw path not created yet.
4. Integrity sweep of constants: pick 20 non-zero words that are ROM pointers in the data image (e.g. `raminit.py find` output) and `rd` them; all should be unchanged. A changed const pointer below 0x2AD1C is an ML overlap.
5. `rd 0xF0010058 2` should read ASCII "1.9.0" (0x2E392E31, 0x00000030); `rd 0xF0420058 1` should read 0xBADCAFFE. Confirms ROM1 is mapped where the dump assumes.
