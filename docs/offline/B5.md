# B5 — Line-level comparison: working M50 mk1 raw video vs our M50 II tree

## Question

What exactly differs between the working M50 mk1 raw-video port
(`research/bilal_M50_rawvideo`, HEAD 32dbd9c "M50: added RAW video support, mlv_lite works")
and our tree (`magiclantern_simplified`, branch `walkback-milestone`, HEAD a10b16c23), per file,
and for each difference: adopt mk1, keep ours, or hardware-test? Plus anything in
`research/kitor_raw_draft_v2` / `research/m6ii_raw_video` that neither tree has.

## Summary

1. mk1's whole raw enablement is 9 files / 63 lines; everything else in our diff is base-tree drift (our base is newer: card spanning, 7D2) or M50 II diagnostics.
2. Strongest finding (static, ROM-backed): our `edmac_select_boomer` / `edmac_reset_boomer_vdkick` stubs point at `Engine::Outer.c` functions indexed by a *different ID space*; the `Engine::Edmac.c` per-channel analogs sit at 0xE05B802E / 0xE05B7FB6..0xE05B8006, and mk1's unmodified selector 0x373f0126 passes the 0xE05B802E checks for ch13 exactly. Our mem2mem copy therefore very likely programs boomer node 0x4E instead of ch13's node 0x0C — a candidate root cause of "mem2mem leaves the slot stale".
3. Three source drifts worth reverting to mk1: `raw_lv_request_bpp` early return (ours falls through and can rewrite `raw_info.bits_per_pixel/pitch`), `TG_FREQ_BASE` 27 MHz (ours 32 MHz, fps reads 18.5% high), and a pile of per-recording diagnostics in mlv_lite (4 MB control write, PROBE2.TXT, root filename override).
4. Deliberate and evidence-backed in ours: EVF_STATE 0x10108 + (input 6, state 3) vsync, FIO uncacheable write gate, PICSTYLE off, redirect off / read `raw_info.buffer`.
5. Nothing here is proven at runtime; all ROM claims are static reads of gang100.bin.

## Inferred

- I1 (high confidence, static): 0xE05B802E is the M50 II analog of mk1 `edmac_select_boomer`.
  Evidence: same source file as its neighbours, identical distance to `edmac_stop_boomer_maybe`
  (0x94) as on mk1, same desc+0xB4 field that stop clears, same low-level callee, and mk1's constant
  satisfies its checks for ch13. Our current 0xE05B752E works on the Outer.c table, where index 13 is
  node 0x4E, not EDMAC ch13's node 0x0C — and the 0x0126 -> 0x0226 selector change (docs/32) was made
  to satisfy the wrong function's assert.
- I2 (medium): mk1 `edmac_reset_boomer_vdkick` analog is one of 0xE05B7FB6 (exact positional match,
  anchor+0x4E; clears VdKick) or 0xE05B8006 (same low-level pulse our current stub reaches, but via
  the Edmac.c table). mk1 has 6 more bytes between vdkick and select than mk2, so position alone does
  not fully settle it.
- I3: with I1 wrong on our side, the WR channel's boomer input was never selected, which fits the
  hardware symptom recorded in edmac-d8.c:241-245 (destination slot stale, EDMAC contention storm).
  The CPU-copy workaround may therefore be compensating for a stub error rather than a D8 limitation.
- I4: the removed early return in `raw_lv_request_bpp` is drift, not adaptation: the comment says
  "M50 mk1 does the same", which is false for the fall-through. With BPP=14 it is mostly harmless;
  with any 10/12-bit setting it would change `raw_info.pitch` while the sensor stream stays 14-bit.
- I5: `TG_FREQ_BASE` 32 MHz makes `fps_get_current_x1000()` read ~18.5% high if M50 II timers match
  mk1 (e.g. 23.976 -> ~28.4). That value goes into MLV `sourceFpsNom` and mlv_lite's overflow math.
- I6: with our async CPU copy, mlv_lite marks the slot `SLOT_FULL` before the copy has finished.
  The copy task (0x17) outranks the writer (0x19), but the body is dual-core, so the writer can run
  concurrently; torn frames are possible. mk1's synchronous copy has no such window.
- I7: mk1 keeps `raw_lv_redirect_edmac` double-buffering on and works; our redirect-off choice is
  backed by hardware logs (boots 203/209) and should stay until the EDMAC stubs are re-tested.
- I8: O8 items e, g, h are leftover diagnostics; g alone adds a 4 MB card write to every start.

## Unknown

- Whether the M50 II FPS timers equal mk1's (0x2D1 x 0x617 at 1080p24); TG base not measured.
- Whether 0xD0008094 is a readable register on this body (mk1 never reads it).
- Whether `StartEDmac_maybe` 0xE05B9690 / `ConnectReadEDmac_maybe` 0xE05B95E4 / `edmac_reset_channel`
  0xE05B7B42 are the right analogs: they are Edmac.c functions, but their order relative to the rest
  of the cluster differs from mk1 and I did not verify them.
- Whether Canon's real AllocateUncacheableMemory on this ROM does more than AllocateMemory | 0x40000000.
- Why mk1 needs no FAT-remount wait, no static header buffers and no uncacheable write gate; these
  are M50 II observations with no mk1 counterpart.
- No mk1 ROM is available locally, so mk1 function bodies were not compared, only stub offsets.

## Next hardware checks

1. Read-only table confirmation (decides nothing new, guards against a dump mismatch):
   `rd 0xE0EC3C70 3` expect `000C0000 00000100 20000000`; `rd 0xE1087B90 3` expect
   `004E0000 00000200 00040000`.
2. Boomer stub A/B without rebuilding the core: from a module (or a dedicated task, not serial
   `call` on anything that can block), with `m50ii_edmac_cpu_copy = 0`, replace the two calls in the
   mem2mem setup by direct ROM calls: `0xE05B7FB7(13)` then `0xE05B802F(13, 0x373f0126)`.
   - No assert, `mem2mem_status == 3` within 50 ms, destination differs from its pre-fill pattern
     -> stubs were the root cause; EDMAC copy is usable.
   - Assert `Engine::Edmac.c` line 0x304 or 0x306 -> selector/table reading is wrong; stop.
   - Completes but destination unchanged -> repeat with `0xE05B8007(13)` in place of 0xE05B7FB7.
   - Still stale -> stubs are not the cause; CPU copy stays.
   Pre-fill the destination with a known pattern and compare; watch UART for DAF/EIS storm lines.
3. After a channel has been selected by step 2: `rd (*(0xE0EC37AC + 13*8)) + 0xB4` expect 2; after
   `edmac_stop_boomer_maybe(13)` expect 0.
4. FPS base: in 1080p24 movie LV `rd 0xD0406198` and `rd 0xD04061A4`. If (A+1)x(B+1)x24 is about
   26.9-27.0 MHz adopt 27000000; if about 32 MHz keep ours.
5. `rd 0xD0008094` once in LV. Returns 0x20 -> the fall-through would be a no-op at 14-bit; anything
   else or an abort -> restore mk1's early return regardless.
6. After a take with the `M50TEST.MLV` override removed: file appears under `B:/DCIM/...` and decodes
   -> the earlier "Not mounted ID=0" path failure was the pre-STARTING handle, not the directory.
7. mlv_lite with VERS blocks re-enabled: `[wh]` log shows `ret == bs` for the heap block -> drop the
   skip; `ret=-1` -> keep it.
