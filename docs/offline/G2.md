# G2 - Abort-handler extension that dumps the PropertyMgr registration record and token

Offline work. The code was built and checked with `tools/symgate`; it was **not run**, neither
on the camera nor in QEMU. Every statement about what the dump "will show" is a prediction
from the source and from F5.md, not an observation.

## Summary

- Branch `offline-abortdump1` (18 characters), worktree `/mnt/data/WORK/eos/wt/G2`, started
  from `walkback-milestone` a10b16c23. Two commits: 4e72ae8de (variant A, plain placement,
  kept only as the measured reference) and 741c021f6 (variant B, the one to use).
- Variant B adds 744 bytes of code and strings in a new output section `.abx` at
  0x105A3C..0x105D24, behind `.ARM.exidx` and in front of `.bss`. symgate: **0 pre-existing
  symbols moved**, 1 symbol added (`m50ii_abx_uart_str` 0x105C55), `_bss_start` 0x105A40 ->
  0x105D40. `autoexec.bin` grows from 257696 to 258432 bytes.
- Variant B is not byte-identical to the baseline in the old sections: one literal in
  `m50ii_abort_report` changes (intended), and two linker veneers at the end of `.text` swap
  places, which retargets four call sites including the image entry branch at 0xC78E0
  (not intended, not removed; details in section 4).
- The dump runs for every abort, not only for pc=0xE021B8FC. The decoded "rec/tok" lines are
  printed only for that pc.

## 1. What the existing handler does

Established, from `src/init.c` on a10b16c23:

- `m50ii_install_abort_handler` copies Canon's 16-word vector table to RAM, replaces the
  prefetch-abort and data-abort literals and points VBAR at the copy (init.c:1462-1500 on the
  base commit).
- The Thumb stubs `m50ii_pabort_stub` / `m50ii_dabort_stub` load sp from `m50ii_abort_sp`
  (top of the 1 KB `m50ii_abort_stack`), push r0-r12 and the corrected pc, then push the
  faulting mode's sp and lr, and call `m50ii_abort_report(ctx, spsr, type)`. `ctx` is
  therefore always `m50ii_abort_sp - 64` and holds `[fsp, flr, r0..r12, pc]`.
- `m50ii_abort_report` prints the `[ABORT]` register lines with `m50ii_uart_str` and
  `m50ii_hex`, scans 64 words of the faulting stack for ROM addresses, prints
  `[ABORT] HANG ...` and then repeats a short `[AB] pc= lr= dfar=` line forever.

## 2. What was added (variant B, commit 741c021f6)

Files: `src/init.c` (one block in front of `m50ii_abort_report`, one `#undef` behind it) and
`src/magiclantern.lds.S` (one output section). All of it is inside `#ifdef CONFIG_M50mk2`;
on other cameras the `.abx` section is empty and the linker drops it.

How it hooks in: inside `m50ii_abort_report` the name `m50ii_uart_str` is redirected by a
macro to `m50ii_abx_uart_str`. That wrapper forwards every string to the real
`m50ii_uart_str`; when the string starts with `[ABO` and has `H` at index 8 (only
`"[ABORT] HANG ..."` does) it first calls `m50ii_abort_xdump`. The register values are taken
from the stub frame at `m50ii_abort_sp - 64`. This way no instruction in the existing handler
changes size; only the function-address literal at 0xE9048 changes value.

What `m50ii_abort_xdump` prints, in this order, each line starting with `[ABX] `:

| Lines | Content | Condition |
|---|---|---|
| `r8 @<addr>:` 2 lines of 8 words | 0x40 bytes at r8 | r8 passes the read guard |
| `r6 @<addr>:` 2 lines | 0x40 bytes at r6 | r6 passes the guard |
| `r4 @<addr>:` 1 line | 0x20 bytes at r4 | r4 passes the guard |
| `rec h= priv= tcb= n= props= p0 p1 p2 p3` | first 8 words at r8, labelled | pc == 0xE021B8FC, r8 and r6 readable |
| `tok n= h= priv=` | first 3 words at r6, labelled | same |
| `A5E0><addr>:` 10 words | struct at `*(0xA5E0)` (expected 0x58278); token fields +8..+0x20 (F5 1a) | pointer readable |
| `A590><addr>:` 8 words | struct at `*(0xA590)`, ApexProperty; token fields +8..+0x18 (F5 1b) | pointer readable |
| `A68C @0000A68C:` 2 words | token at +4 (F5 1c, call 0xE13F3550) | always |
| `107B0>+30 @<addr>:` 2 words | `[*(0x107B0) + 0x30]`; the token is the second word, offset +0x34 (F5 1c, call 0xE13FA666) | pointer readable |
| `54DC @000054DC:` 8 words | state struct of the mount-time registration 0xE01DC11E (F5 section 4); the token offset inside it was not determined in F5 | always |
| `63B0 @000063B0:` 8 words | last word (+0x1C) is the default object `_prop_cleanup` uses for a zero token (F5 section 3) | always |

Addresses are rounded down to a multiple of 4. Values are 8 hex digits without `0x`, in
memory order, little-endian words.

Read guard (`m50ii_abx_ok`): the range must lie in 0x1000..0x3FFFFFFF (cacheable RAM; never
MMIO, never ROM), and the first and last byte must translate under the current MMU tables
(ATS1CPR, `mcr p15,0,va,c7,c8,0`, then PAR bit 0). A pointer that fails is skipped silently:
**a missing `r4 @` line means "r4 was not a readable RAM pointer"**, which is the expected
case for this crash (r4 = 0x32).

Re-entry: the function writes the marker 0xAB0D0001 to the lowest word of the abort stack
(`m50ii_abort_sp - 0x400`) while it runs. If one of its reads faults anyway, the abort stub
re-enters, the normal `[ABORT]` lines for the nested fault are printed (pc inside
0x105A3C..0x105C94), the extra dump is skipped and the handler hangs as before. The original
`[ABORT]` lines are already on the wire at that point, so nothing that exists today is lost.

## 3. How to read the dump for pc=0xE021B8FC

Expected shape (addresses from the first recorded dump, db boot 330; values `?` unknown):

```
[ABORT] HANG ... is preceded by:
[ABX] r8 @00EC37A4: <handler> <priv> <token_cb> <n> <prop0> <prop1> <prop2> <prop3>
[ABX] r8 @00EC37C4: <prop4> ...
[ABX] r6 @00EC46D8: <n> <handler> <priv> ? ? ? ? ?
[ABX] r6 @00EC46F8: ...
[ABX] rec h=0x........ priv=0x........ tcb=0x........ n=0x........ props=0x........ 0x........ 0x........ 0x........
[ABX] tok n=0x........ h=0x........ priv=0x........
[ABX] A5E0>00058278: ...
...
```

Field meaning (F5 "Terms"): the record is `{handler, priv, token_cb, n, props[n]}` as posted
by `prop_register_slave` 0xE05BF79E; the token starts `{n, handler, priv}` as written by the
worker at 0xE040349E..0xE04034AA before it calls token_cb at 0xE04034B4.

Decision table (taken from F5 section 7, with the names used in the dump):

| Observation | Meaning |
|---|---|
| `tok h` = 0xE01DA957 | the mount-time registration at 0xE01DC11E; `rec tcb` should then be 0xE01DA871 |
| `tok h` = 0xE05BF79D and `rec tcb` != 0 | the class-0x01000000 record was overwritten in flight (F5 explanation 2) |
| `rec tcb` in 0x0223B000..0x02319530 | code in the RAM blob; add 0xDF180074 for the ROM address and look it up in F5 section 1 |
| `rec tcb` in 0x000C78D8..0x0014FC00 | ML code; resolve with the `.sym` of the build that crashed (F5 explanation 3) |
| `rec h` != `tok h` or `rec n` != `tok n` | the record changed after the worker copied it |
| `rec n` near 965 (0x3C5) | the token directly follows the record (A4) |
| `props=` values | the first four property IDs of the registration; grep them in the ROM property lists to name the registrant even if the handler pointer is damaged |
| any word equal to 0x00000032 in the `A5E0>`, `A590>`, `A68C`, `107B0>`, `54DC` lines | that module's token variable holds the value that faulted; it is the owner of "0x32" (F5 section 3) |

`rec tcb` is the function called X in F5: the callee that reached `_prop_cleanup` with
token 0x32. Disassemble it with `tools/romdis.py` (ROM) or resolve it as above.

Capture advice: the UART drops characters under load (init.c comment at the hang loop). The
extra dump is printed once, not repeated. If a line is damaged, the raw `r8 @` / `r6 @`
lines and the labelled `rec` / `tok` lines carry the same words twice, which is the only
redundancy available. Image the card before anything else if the crash returns (C6.md).

## 4. Layout results

Baseline: `tools/symgate/baseline/M50mk2_101.sym` (md5 d2f46ba5..., 1307 symbols) and the ELF
in the main checkout `platform/M50mk2.101/build/magiclantern`.

### Variant A, commit 4e72ae8de (code and string literals placed normally in init.o)

`check_symbol_stability.py`: FAIL. 340 pre-existing symbols moved, first divergence
`magic_is_off` 0xE8D65. Shift histogram: +188 x6, +492 x3, +496 x238, +512 x13, +640 x37,
+648 x42. `_text_end` +496, `_data_start` +584, `_bss_start` +640, all three anchors
`raw_info`, `edmac_copy_rectangle_cbr_start`, `build_date` moved. `.bss` (0x110000..0x14FC00)
and `_bss_end` did not move. `autoexec.bin` 258336 bytes.

### Variant B, commit 741c021f6 (late-linked `.abx` section)

`check_symbol_stability.py`: 0 moved, 0 removed, 1 added (`m50ii_abx_uart_str` 0x105C55),
all anchors OK, `.text`, `.rodata.str1.1`, `.rodata.str1.4`, `.data`, `.ARM.exidx`, `.bss`,
`_bss_end`, `ml_reserved_mem` unchanged. The gate still prints `RESULT: FAIL` for one reason:
`_bss_start` 0x105A40 -> 0x105D40 (+768). `check_module_syms.py` and `check_card_image.py
build/zip --elf` both PASS. Build products: `autoexec.bin` md5 cb0fbb61dd9775b1b5f1ca04448494d5,
`M50mk2_101.sym` md5 a4a45f5f017c7727d33028c990d2cf4b (both carry today's build date).

Why this works (established from the ELF): `.bss` is aligned to 0x10000 and starts at
0x110000, while the loaded image ended at 0x105A3C. The 0xA5C4-byte gap was unused; `.abx`
takes 0x2E8 bytes of it. `_bss_start` is only used by `zero_bss` (src/boot.h:290), which now
starts clearing at 0x105D40 instead of 0x105A40, so the new code is not wiped. `_bss_end` is
unchanged, so ML's memory reservation is unchanged.

Two traps found on the way, both recorded in comments in the source:

1. A read-only `.abx` output section attracts the orphan sections `.rodata.str1.1` /
   `.rodata.str1.4` (the script only names `*(.rodata)`), which moved all of `.data` by
   -32344..-32384 bytes (79 symbols). The strings of the block are therefore non-const and
   sit in `.abx.data`, which makes `.abx` writable and leaves the orphans behind `.text`.
2. String literals in the new code would go to `.rodata.str1.1` and shift `.data`. The block
   uses named char arrays in `.abx.data` and its own hex formatter instead.

Byte comparison of the old sections against the baseline ELF (objcopy per section, `cmp -l`):

| Section | Differing bytes | Where |
|---|---|---|
| `.data` | 0 | - |
| `.rodata.str1.1` | 4 | not located; consistent with the build date inside `VERSION` (inferred) |
| `.text` | 53 | 3 at 0xE9048 (literal: `m50ii_uart_str` -> `m50ii_abx_uart_str`, intended); 38 at 0xF354E..0xF3587 (`build_date`/`build_id` text); 8 at 0xF331C..0xF3327 and 1 each at 0xC78E0, 0xC8238, 0xC83C8, 0xCF2C1 (veneers, below) |

The veneer difference (established): the linker-generated stubs `__vsnprintf_veneer` and
`__copy_and_restart_from_arm` swap places (baseline 0xF3320 / 0xF3318, G2 0xF3318 / 0xF3320),
and the four branches that use them are retargeted accordingly. The two stubs are identical
in form (`ldr pc,[pc,#-4]` plus target), so the code is equivalent, but the first word of the
image and three other instructions differ from the booting build. Moving the block into the
tail of `.data` instead of its own section gives the same swap (and additionally moves
`__exidx_start`/`__exidx_end` by +747/+744), so the swap is not caused by the extra output
section. Its cause is open; removing it was not attempted.

Reusing an unused function's space was not tried; the gap in front of `.bss` made it
unnecessary.

## 6. Limits and risks

- Not run anywhere. The ATS1CPR/PAR probe is standard ARMv7-A VMSA, but its behaviour on
  this CPU and under Canon's tables is not verified.
- A valid translation does not prove that memory exists behind the address. The upper bound
  0x40000000 follows the existing check at init.c:770; the real RAM size was not checked. A
  read that faults ends in the re-entry path described in section 2.
- The dump adds about 15 lines once per abort before the `[ABORT] HANG` line. It does not
  delay or change the lines that exist today.
- This is a core change. By the project rule it should be flashed only after being
  committed, and the veneer swap in section 4 means it is not "the booting core plus an
  appendix" at byte level.
- The handler passed in r7 at 0xE13FA666 and the token offset in the 0x54DC struct were open
  in F5 and remain open; the `54DC` line is a raw dump for that reason.
