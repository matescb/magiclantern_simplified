# A14a - Stub audit slice 1 (kernel, tasks, memory, FIO, debug)

Static analysis only (gang100.bin, fw 1.0.1). Nothing here is proven at runtime unless a UART log line is cited.

## Question

Re-verify every active stub in `platform/M50mk2.101/stubs.S` in the startup/kernel, tasks/semaphores/queues,
memory, file-I/O and debug sections that is NOT tagged `[M50II 1.0.1 OK]`. Verdict + evidence per stub,
corrected address when wrong.

## Summary

- 9 stubs are WRONG (blind M50.110 copies): `task_max`, `dump_file`, `memmap_info`, `smemShowFix`, `malloc_info`, `sysmem_info`, `_request_RPC`, `clear_RPC_request`, `fsuDecodePartitionTable` (last one already known/intentional). Corrected addresses found for the first 8.
- `_request_RPC` 0xDF002C32 lands in the MIDDLE of a 4-byte `dmb` (ROM source 0xE14999D4). Real entry is +0x18: 0xDF002C4A; `clear_RPC_request` 0xDF002C6A. This is a candidate cause for the "RPC/SGI-to-cpu1 handshake FAULTS on M50 II HW" note in patch_mmu.c:820 (inference, not proven).
- `task_max` must be 0x4108 (get_task_by_id bounds ids by `*0x4108`); 0x40CC is a driver-table struct and reads 1 on hardware (uart.jsonl line 11753).
- The memory-suite accessors (AddMemoryChunk, GetFirstChunkFromSuite, GetNextMemoryChunk, GetMemoryAddressOfMemoryChunk, Create/DeleteMemorySuite, CreateMemoryChunk), recursive locks, take_semaphore_now, msg_queue_count, uart_printf, vsnprintf, send_software_interrupt, change_mmu_tables, memcpy_dryos are CONFIRMED by prologue + argument use + assert strings.
- `tools/verify_stubs.py` has two blind spots: it SKIPs all 0xDF00xxxx stubs (so it missed the RPC pair) and it classed the garbage at `sysmem_info` as LEAF.

### Other observations

- `tools/romdis.py` annotates 0x4108 as `task_dispatch_hook` (stale symbol map); stubs.S has the hook at 0x4144.
- docs/12 and docs/17 contradict each other on task_max; docs/17's "refuted" argument (0x40CC used as `ldrsh [r7,#8]` in 0xE03EF3A0+) describes a struct with a 16-bit count at +8 and 16-char names, i.e. not the word-sized task count that get_task_by_id and the enumerator read at 0x4108.

## Inferred

- `_request_RPC` misalignment explains RPC faults: entering at 0xDF002C32 executes `0x8F5F` (a load via r3), then `str r1,[r0,#8]` (writes the RPC parameter over the function pointer's code+8), then `pop.w {r4-r8,pc}` on an unpushed stack. Any ML path that reaches request_RPC (cpu.c:94/116 -> patch_mmu.c:1136/1187, i.e. runtime ROM patching with cpu1 alive) would crash or corrupt. patch_mmu.c:820 records exactly such a fault on HW and worked around it with CPU0-only application. The causal link is inferred, not demonstrated.
- The corrected RPC entries are inferred from shape (2-arg / 0-arg IRQ-safe wrappers, 0x20 apart, worker with ldrex lock) and from the uniform +0x18 shift relative to mk1; no string anchors exist in that blob.
- With task_max reading 1, tasks.c:231 and gdb.c:1547 loops enumerate at most task id 1, so ML task listings are effectively empty; no crash expected.
- The four memory-info stubs and dump_file are only called from minimal-d78X.c / log-d678.c / io_trace.c / raw.c debug paths, so the wrong addresses are latent crashes, not a cause of current behaviour.
- uart_printf producing no output on HW (boot-d678.c:217 note) is consistent with `*(0x4060)` being NULL at that time rather than with a wrong address.

## Unknown

- The correct `additional_version` RAM address on 1.0.1, and what currently lives at 0xE484.
- Which of the two dump_file twins Canon's own lv_raw_dump uses (either works for ML).
- Exact any/all mode constants in the WaitFor*EventFlag pair (not read).
- Real fsuDecodePartitionTable (inlined on R; not searched).

## Implications for raw video

- None of the WRONG stubs is on the proven raw_vidx recording path (FIO, memory suites, semaphores, queues, event flags used there are CONFIRMED/LIKELY).
- The memory-suite accessors being correct removes them as suspects for mlv_lite buffer handling.
- If any raw-video fix needs a ROM patch applied after cpu1 is running (patch_memory_rom -> request_RPC), it will hit the broken `_request_RPC` stub. Fix the RPC pair before attempting such patches or before re-enabling the cpu1 handshake.
- `dump_file` (corrected) gives a Canon-side way to write a raw buffer to card for debugging: `dump_file("LV.RAW", addr, size)`; note the 0x18-byte path buffer (keep names short).

## Next hardware checks

1. `rd 0x4108` - expect a plausible task count (0xC7 = 199, or 199 + CONFIG_INCREASE_MAX_TASKS). `rd 0x40cc` already returned 1. A count near 199 settles task_max = 0x4108.
2. `md 0xDF002C30 0x50` - expect `bf f3 5f 8f 81 60 bf f3 4f 8f c0 68` at 0xDF002C30 (proves 0xDF002C32 is mid-`dmb`), `70 b5 0d 46 06 46 00 f0 04 e9 04 46` at 0xDF002C4A and `10 b5 00 f0 f6 e8 04 46 ff f7 c0 ff` at 0xDF002C6A. If the bytes match, the RAM blob equals the ROM source and the corrected entries are valid entry points.
3. `call 0xE03CAE31` (malloc_info) and `call 0xE03CAEC9` (sysmem_info) - expect "Malloc Information (... type)" / "System Memory Information" plus 9 value lines on the Canon console (printf 0xE05BBF08). Text appearing = stubs confirmed.
4. `call 0xE039A3D9` (memmap_info, no args needed) - expect "Exception vector", "DRYOS system object", "DRYOS system memory" lines.
5. `call 0xE013D481` (smemShowFix) - needs about 1.7 KB of stack (sub sp 0x694) and prints through DryosDebugMsg class 0x80 level 0x16, so it may only show in the DebugMsg log. Run from a task with a large stack; skip if the shell task stack is small.
6. dump_file: place the string "T.BIN" in RAM with the harness `load`, then `call 0xE065FE59 <strptr> 0x4000 0x100`. Returns 0 and a 256-byte A:/T.BIN on the card = confirmed; return 1 = "Card is not mounted" path.
7. `rd 0x4060` - non-zero means uart_printf output is routed to the console sink; zero explains silent uart_printf.
8. `md 0xE460 0x40` - look for the ASCII firmware version text ("1.0.1" followed by '\n'); the address of that '\n' is the correct additional_version. If no ASCII there, disable CONFIG_ADDITIONAL_VERSION until found.
9. Only after 2 passes and in a build with the corrected stubs: re-test the cpu1 handshake (wait_for_cpu1_busy_wait) that faulted before; a clean return decides whether the misaligned stub was the cause.
