# G3 - Hardware probe pack (`tools/hwprobe`)

**Status: built and unit-tested offline. Nothing in this document has been run on the camera.** The
tool's parser, evaluator and gating are tested against canned replies (25 pytest tests, all passing).
Every "expected" value in the probe table is a static-analysis prediction taken from the cited sprint
report; the first hardware session is what confirms or refutes it.

## What it is

`/mnt/data/WORK/eos/tools/hwprobe/hwprobe.py` is a host-side script (Python standard library only)
that runs the read-only probes the offline sprint asked for through the existing serial harness
(`tools/mlserial`) and writes one timestamped JSON file plus one markdown file per run into
`tools/hwprobe/results/`. The aim is that the first hardware session answers the sprint's open
questions in a few minutes instead of by hand-typed `rd` commands.

Files:

| File | Content |
|---|---|
| `tools/hwprobe/hwprobe.py` | CLI: `plan`, `run` (`--dry-run`, `--replay`), `after` |
| `tools/hwprobe/probes.json` | 35 probe definitions: id, source report, camera state, steps, expected values with the meaning of each outcome, decision unlocked; plus the list of sprint checks that are deliberately not automated |
| `tools/hwprobe/test_hwprobe.py` | pytest tests on replay / dry-run transports |

## How it talks to the camera (established from the sources)

- Transport: `mlserial.cmd(text, timeout)` from `tools/mlserial/mlserial.py:75`, which sends
  `{"op":"cmd",...}` to the `mlserald` daemon and returns `{"status": ok|err|timeout, "body": [...]}`
  (`tools/mlserial/PROTOCOL.md`, "Control socket"). The daemon must already be running.
- Read syntax actually implemented by the camera shell (`magiclantern_simplified/src/serial_shell.c`,
  `cmd_rd`, `cmd_md`, `sh_dump_words`): `rd <addr>` reads **one** word; `md <addr> <nwords>` reads up
  to 0x100 words, four per row, as `0xADDRESS: 0xWORD 0xWORD 0xWORD 0xWORD`. The sprint reports write
  `rd <addr> <len>` with a byte length; the shell ignores a second argument to `rd`. hwprobe therefore
  translates every multi-word read into `md` with a word count.
- `dump <addr> <len>` returns `D <addr> <hex>` rows and `=crc`; hwprobe verifies the CRC.
- `call <addr> [a b c d]` prints `ret 0x........`. Arguments must be numbers: `sh_parse_num` accepts
  only decimal or `0x` hex, so the form `call lv_save_raw 1` shown in `tools/mlserial/TOOLS.md:96-97`
  cannot be parsed by this shell as written (it would answer `=err ... bad addr`). This is read from the
  source, not tried on the camera.
- Replies can be shredded by Canon's console output sharing the UART (TOOLS.md, "@ML> atomic log
  convention"). The parser accepts only complete rows with contiguous addresses and the exact word
  count; a read that fails this is repeated up to two more times. Reads are idempotent; calls are never
  repeated.

## Safety rules built into the tool

1. **Default = plain RAM reads only.** Three flags unlock the rest, and every gated item is printed
   by the plan (which `run` always prints first, and `plan` prints alone):
   - `--allow-risky-read`: MMIO and page-table reads (0xD04xxxxx, 0xC11xxxxx, 0xBFF2xxxx). A5 warns
     that EDMAC MMIO reads can hard-lock when the sub-chip is asleep; use only in LiveView.
   - `--allow-call`: `call` steps. The only shipped one is the queue-depth query 0xE05BA079 (A2.4).
   - `--allow-wr`: `wr` steps. No shipped probe writes; the gate exists so that a later probe cannot
     write by accident.
2. **A blocked `call` wedges the shell** (the callee runs in the shell task; memory note on the WiFi
   work and docs/32:1141 as quoted in A8). A call that times out ends the run at once: nothing more is
   sent, the partial result is written with `aborted` set, exit status 3. A read that times out is
   followed by a `ver` liveness check; a dead shell ends the run the same way.
3. Within a stage, plain-RAM probes run before gated ones, so a hang caused by a risky read loses the
   least data.
4. A probe that follows a pointer first checks that the pointer is non-zero and is reported SKIPPED
   otherwise (A15: these pointers are 0 until Canon's init code has run).
5. ML RAM addresses are never hard-coded: `sym("name")` in `probes.json` is resolved from the `.sym`
   given with `--sym`. Canon RAM / ROM / MMIO addresses exist only in `probes.json`, each with its
   source report. Probe `S0.sym` checks that `ml_started` reads 1 at the address the `.sym` gives; this
   is a weak test that the `.sym` matches the running build (a wrong `.sym` could pass by chance).
6. Rate limit: at least `--min-gap` (0.05 s) between commands, and at least 0.2 s between sampling
   rounds (the daemon polls the port every 200 ms, so faster sampling gains nothing).

## Usage

Run from anywhere; `SYM` must be the `.sym` of the build that is running on the camera (for the
staged C10 card: `wt/C10/platform/M50mk2.101/build/magiclantern.sym`; for the walkback core:
`magiclantern_simplified/platform/M50mk2.101/build/magiclantern.sym`).

```
cd /mnt/data/WORK/eos/tools/hwprobe
python3 ../mlserial/mlserial.py daemon start            # once per session

python3 hwprobe.py plan --sym $SYM --stages 0,1,2,3     # what would run; calls and gated probes listed
python3 hwprobe.py run  --sym $SYM --dry-run --stages 0,1,2,3   # exact command sequence, no camera

# Session order (photo-mode LiveView first, raw never enabled since boot):
python3 hwprobe.py run --sym $SYM --stages 0,1 --label photo-lv
python3 hwprobe.py run --sym $SYM --stages 0,1 --label movie-1080p25 --allow-risky-read
python3 hwprobe.py run --sym $SYM --stages 2   --label movie-1080p25-raw      # asks you to enable raw
python3 hwprobe.py run --sym $SYM --stages 3   --label rec-attempt-1 --duration 20   # asks you to start recording

# After the session, with the card in the reader and the files copied to the host:
python3 hwprobe.py after --result results/hwprobe-<stamp>-rec-attempt-1.json /path/TST00.MLV /path/TST00.RVI
```

- Stage 2 waits for the operator to enable raw (ML menu / module) and press Enter. With
  `--allow-call --enable-raw-by-call` it instead calls ML's `raw_lv_request`, address taken from the
  `.sym`. Whether that function returns promptly when called from the shell task is **open**; prefer
  the operator path in the first session.
- Stage 3 waits for the operator to start the recording, samples for `--duration` seconds, then reads
  the one-shot probes, and counts assert / abort lines that the daemon logged in that time window by a
  read-only pass over `tools/mlserial/run/uart.jsonl` (F1 probe 9, A2 check 7). It does not run
  `mllog.py`.
- `--only A2.1,F4.1` restricts a run to named probes. `--samples` / `--interval` set the stage 1 and 2
  sampling (default 10 rounds, 0.5 s). `--yes` skips the operator prompts.
- In a dry run, an address that depends on a value not yet read is printed symbolically, for example
  `md <P_ptr[0]> 8` after `rd 0x8E8C`; all other commands are printed exactly as they would be sent.
- `--replay FILE` takes canned replies: `{"replies": {"<command text>": [reply, ...]}, "memory":
  {"0xADDR": word-or-list}}`. A reply is a list of body lines or `{"status": "timeout"}`; `rd` / `md` /
  `dump` without a canned reply are synthesised from the sparse `memory` image.
- `after` runs `tools/mlvcheck/mlv_check.py --crash-ok --stats` on every non-`.RVI` file and
  `tools/mlvcheck/rvi_check.py` (with `--mlv` when the sibling `.MLV` exists) on `.RVI` files, and
  appends checker name, exit status and output to the result JSON and markdown.

Exit status of `run`: 0 no FAIL / ERROR, 1 at least one FAIL or ERROR, 3 run aborted.

Verdicts: PASS (all checks as predicted), FAIL (at least one prediction refuted; the "otherwise"
meaning is printed), INFO (values recorded, no prediction), SKIPPED (gated, or the pointer was 0),
ERROR (the camera answered `=err`, or no clean reply after retries). For sampled probes the result
holds per-check pass / fail counts, the distinct values seen and every sample.

## Estimated cost on hardware (inferred, not measured)

With default flags stage 0 is 38 commands (dry-run count) including one 24 KiB `dump` (about 5 s of UART time at 115200 baud).
The harness log shows roughly 0.2-0.4 s per command round trip (daemon poll period), so stage 0 should
take under a minute and ten stage-1 rounds of about 15 commands (plus 8 one-shot commands) about one to two minutes. At that rate one
stage-3 sampling round takes several seconds, so a 20 s recording yields only a handful of samples;
the ring counts are therefore sampled sparsely. A camera-side sampler would be needed for per-frame
resolution.

## Tests

`cd tools/hwprobe && python3 -m pytest -q test_hwprobe.py` gives 25 passed. Covered: row parsing with
echo and log fragments, short / misaddressed rows, dump CRC, call return, expression evaluation and
rejection of non-arithmetic expressions, free-list walk, a full stage 0+1 run on a synthetic "healthy"
memory image (no call, write or MMIO read is sent by default), single-fault images (wrong EvfState
name pointer, ring count 2 in one sample, all LvJob slots busy, depleted event pool, no raw buffer
supplied), retry after a shredded reply, `=err` handling, NULL-pointer skip, call gating and argument
resolution, abort on a call timeout, write gating, the plan and dry-run output, and the `after` helper
with the real `mlv_check.py` on a non-MLV file. The synthetic image encodes the reports' predictions;
passing against it shows that the evaluator implements the table, not that the camera behaves so.

## Limitations and open points

- Open: which words at 0x23818, 0x23834 and 0x29314 are counters. A1 names only `[0x23804]` and
  `[0x292B0]` as the ring counts (A1.md:91); hwprobe checks those two and records the others.
- Open: the event-pool walk (F4.1) is done on a dump taken while the camera runs, so the count can be
  off by a few nodes or the walk can break (reported in `evfree[1]` = 0); F4 accepts this for a
  threshold test (F4.md:242).
- Inferred: the F4.1 pass band (1400 to 1536 free) is this tool's choice; F4 says only "close to 1536".
- The stage-3 assert tally depends on the daemon's host timestamps, which come in 200 ms buckets.
- `tools/hwprobe` is not under version control (`/mnt/data/WORK/eos` is not a git repository; only
  `magiclantern_simplified` is), so there is no commit for this task. No ML source was changed.
