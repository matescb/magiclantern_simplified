# F7 - Corrected stubs and constants outside the EDMAC block

Scope: Magic Lantern (ML) port to the Canon EOS M50 Mark II, firmware 1.0.1. This report covers the
branch `offline-stub-fixes` (worktree `/mnt/data/WORK/eos/wt/F7`, 19 commits on top of
`walkback-milestone` a10b16c23). A "stub" is a line in `platform/M50mk2.101/stubs.S` that gives a
Canon firmware function or RAM variable a name ML can link against. The EDMAC block and
`LockEngineResources` are handled by another agent and are untouched here.

**Nothing in this report was run on a camera.** Every finding is static analysis of the ROM dump
`gang100.bin` (base 0xE0000000) plus two lines of old UART history. The branch was built but not
flashed, not pushed, and not merged.

## Summary

- 13 existing stubs were changed, 9 new stubs added, 1 constant corrected, 2 options added (off by
  default), 1 comment-only change. Each is its own commit with the ROM evidence in the message.
- The build succeeds. The core layout is unchanged: every section start/end and every ML-defined
  symbol is at its baseline address. The only "moved" symbols are the 13 stub values themselves.
- Two commits are expected to change camera behaviour in LiveView and during recording:
  `LV_OVERLAYS_MODE` (b1e413554) and `LiveViewApp_dialog` (ea62b792e, deliberately the last commit
  so it can be dropped alone). Everything else is either not called by any code in this build or
  only reachable from debug menus.
- `dialog_redraw` and `gui_init_end` have no real replacement; both now point at a bare `bx lr`
  (0xE065A4FC), which makes them no-ops without adding code to the core.
- Not applied because not confirmable: `additional_version`, `fsuDecodePartitionTable`, the real
  `LVAE_STRUCT` / `LVAE_ISO_STRUCT`, `GUI_ChangeMode` enablement, the `gui_task_list` field layout.

## Method

For each proposal from A14a, A14b, A14c, A8 and A9 I disassembled the old and the new address with
`tools/romdis.py`, read the referenced strings and literal words from the ROM, and searched ML for
call sites. "Imported by" below means the object file lists the symbol as undefined
(`arm-none-eabi-nm -u` over `platform/M50mk2.101/build/*.o` and the four built modules
`bench.mo`, `file_man.mo`, `mlv_lite.mo`, `raw_vidx.mo`, plus `selftest.mo`, which is not shipped in the zip).
A symbol nobody imports cannot be called, whatever its address.

Risk classes used: **none** (no importer, or build byte-identical), **latent** (only reachable from
a debug or menu action the user must start), **behaviour** (runs during normal LiveView or recording).

## Inferred

- **Interaction between `LiveViewApp_dialog` and `dialog_redraw`.** `liveview_display_idle()`
  (zebra.c:3569) returns `LiveViewApp_dialog`. With the old address the value is probably always 0
  (no code references 0x139B8), which means ML has so far considered LiveView "never idle" and has
  not drawn its LiveView overlays, and `redraw_do()` has always taken the `clrscr()` branch. With
  0xE9F0 the pointer is non-zero in LiveView: overlay drawing starts to run, also during recording,
  and `redraw_do()` calls `dialog_redraw`. Had `dialog_redraw` been left at 0xE054F3CA this would
  execute a literal pool. That is why the no-op stub is committed first. The cost is that stale ML
  graphics are no longer cleared on that path.
- The RPC pair is identified by shape and by the 0x20 spacing it shares with M50.110; there is no string anchor.
- `gui_task_list`: only the base is right. The dispatcher reads `+0xC` where `gui-common.h:116`
  places `current` at `+8`, so `gui_task_list.current` probably still reads the wrong field.
- `LV_OVERLAYS_MODE`: the boot log line "LvInfoToggle_Initialize ToggleIndex:3" (A14c) suggests the
  clean page is 3 as on EOS R, which is what zebra.c:423 assumes.

## Unknown / not applied

- `additional_version` (0xE484): no literal reference in ROM, no replacement. init.c:1892 writes 8
  bytes there on **every boot**. This is the one unverified stub that is exercised at boot.
- `fsuDecodePartitionTable` (0xDF00D365): outside the copied RAM blob, no replacement. The bootflag
  menu (bootflags.c:160) therefore still jumps to an invalid address even with `sd_device` fixed.
- Real `dialog_redraw` (candidate 0xE05A094C from A14b, unverified).
- Real `LVAE_STRUCT` / `LVAE_ISO_STRUCT`.
- `GUI_ChangeMode` 0xE03FF1D8 is confirmed (prologue, stores arg at [0x8264+0x6C]) but left commented
  out: mode values on this body are composite (A14c) and ML callers pass small integers.
- Whether 0x139B8 really reads 0 on hardware; whether 0xAC64 is 1 with the panel on after a normal boot.
- Whether `SRM_BUFFER_SIZE` is right (A8 could not tie the size to this call).

## Implications for raw video

- The proven CPU-copy recording path does not call any changed stub except through the two
  behaviour commits. To keep the first hardware test of this branch comparable with the known
  recipe, flash `HEAD~1` minus b1e413554 first (stub-only, no behaviour change expected), then add
  `LV_OVERLAYS_MODE`, then `LiveViewApp_dialog`.
- With the last commit ML overlays may start drawing during recording. That adds CPU load and
  display traffic to a pipeline that is already throughput-limited, so test it separately.
- `DeleteResLockEntry`, `debug_assert` and the `dm_set_*_level` pair are now linkable from modules.
