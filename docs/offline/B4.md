# B4 — Discord dump mined for the M50 / M50 II raw-video effort (developer history, crashes, memory pools, advice)

## Question

What does `/mnt/data/WORK/eos/ml_discord` (41 files, ~926k lines) record about the M50 / M50 Mark II raw-video
effort and its developers (bilal_fakhouri, kitorpl, names__are__hard, tryinglobster, coon_42, lak132): status
reports, crashes and their fixes, record-button handling, Canon movie-record interference, card "not mounted",
D8 memory pools (SRM / shoot memory), advice to porters — and which concrete techniques have we NOT tried on
the M50 II (checked against docs/29-35, docs/offline/*, the memory notes and the port source)?

## Summary

1. M50 mk1 raw video (bilal, Aug-Oct 2025) is 14-bit only, a straight copy of kitor's `edmac_sx740` code; the only M50-specific fixes were `realloc_buffers()` after stop and dropping the `& 0x1FFFFFFF` mask. Lower bit depths never worked cleanly.
2. The "digic 8 crash" (`Blanking DeadLine` -> `EvfState.c` assert in `EvfCap`/EvfDev variants) has been known on R/RP/M50 since 2022 with no root cause; our EvfDevState wedges are in that family. Do not expect a community fix.
3. New for us: three small SRM allocators that work in video mode on M50 (CaptureWork, 19 x 1.06 MB contiguous), the MOVIE_RECWORK (~256 MB) idea, the `edmaclog` module, and an FS-ready gate instead of a fixed sleep.
4. Community independently confirmed our FIO finding in Dec 2025: `[FSU] WARN Please Designate Uncacheable Addr` -> `fio_malloc` buffers; it is D8-general, not 2 GB-specific.
5. Coverage limit: I read the m50 channel 2025-08-18..31 in full (lines 19321-21122) plus targeted windows of 2021/2023 and of dev-general 2022-2026; the 2020-2021 m50 bulk (lines 1-17350) and the rp/r channels were keyword-scanned only.

Notation: `m50` = `Platform_Specific_Development__m50.md`, `gen` = `Dev_Stuff__ml-developers-general.md`,
`gpu` = `Dev_Stuff__gpu-and-compositor.md`. All quotes are verbatim, trimmed. ROM addresses quoted from Discord
are for M50 mk1 fw 1.1.0, EOS R or 200D — NOT M50 II 1.0.1 — unless stated.

### H. Advice to porters

- EDMAC is not understood: "I'm pretty sure the existing old code only works by accident; people changed channel / connection numbers until it worked" (names, m50:19884); "On D8 it is pure luck for now" (kitor, m50:21115).
- DMA rules (names, m50:20923-20929): "For DMA operations, it's required that you use uncache addresses ... align the start of the operation to some number (differs per generation, I think, 0x20 is common ...) ... you can't simply remove the mask, on some D8 cams, because they do uncache / cache differently". kitor (m50:21065): "M50 has 1 gig of ram so it should work similar to earlier models. On 2 gig models (R, RP, M6II) there's 1 gig that is uncacheable only."
- D8 has no shadow memory: "engdrvout and shamem: they don't exist on D8, everything is directly read/written from registers" (kitor, m50:19582); restrict `shamem_read` to `0xDxxxxxxx` (m50:19587-19600); "on R I saw a ton of reads from 0xc... range that made camera unhappy" (m50:19608).
- Diagnostics recommended: `modules/dev_tools/edmaclog` (names, m50:19831; sample output gen:168587-168600 logs Set Addr / ConnectReadEDMAC / StartEDMAC with LR and channel); `tools/image/bit_printer.py` and `image_buffer_guesser` on raw frame data (m50:19418-19426); `mlv_dump` rather than MLVApp exports; `CONFIG_CRASH_LOG` ("you should be able to swap this line for a define, and it will be useful for you", gen:188850; "should be safe. It won't log all kinds of crashes", gen:168485).
- Use the simple module to bisect: "raw_vid ... has three .c files ... two semaphores, each is only taken in a single place" (gen:187554-187557); 6D2 fails with mlv_lite at any bit depth but works with raw_vid (gen:190213-190217).
- tryinglobster (2023-07, the only prior M50 II porter in the dump): "just under halfway done with the m50_2 stubs" (m50:19261); verifies stubs via `debug_assert` file/line arguments (m50:19263-19265). ## Inferred

- Our `EvfDevState.c` assert floods / wedges and the deterministic `0xE021B8FC` EVF crash are probably members of the community's long-standing "digic 8 crash" family (EvfCap/EvfDev variants after `Blanking DeadLine`). Inference from matching subsystem and symptom only; line numbers and task differ, and nobody in the dump has a root cause.
- Our "auto-stop when the queue fills, then wedge on re-record" matches kitor's R behaviour in Feb 2024 (30-60 frames, "no memory suites", hard lock). On M50 mk1 the re-record lock was cured by `realloc_buffers()`; that fix is mlv_lite-specific, so for `raw_vidx` the equivalent is to make sure all frame buffers are re-armed after stop.
- Our "core rebuild shifts symbols -> boot crash" resembles kitor's unexplained "builds were crashing; switching branches fixed it, clean build didn't". Neither he nor we have a diff of a good vs bad binary; that is the missing experiment. The `udf`-trap explanation is ruled out for our current build.
- Our `FIO_WriteFile` uncacheable gate (`CONFIG_MEM_2GB || CONFIG_M50mk2`) is the same defect the community hit in Dec 2025; their evidence says the condition is "DIGIC 8", not memory size.
- Our 10 s `msleep` in `module_load_task` works around the same FS-not-ready race kitor diagnosed from `[FirstEnt] Not mounted ID=0`; a readiness poll would be the principled form.
- Simultaneous H.264 + raw works on R and M50 mk1, so Canon movie recording is not inherently fatal to the raw path; on those bodies the double-trigger was only a wrong (unpress) key code.
- 14-bit is the only usable depth on D8 today. At ~70-80 MB/s UHS-I, continuous 2096x1164 14-bit 24 fps (~102 MB/s by size arithmetic) cannot be sustained; continuous recording needs a crop or lower resolution, not bigger buffers.

## Implications for raw video

Techniques we have NOT tried on the M50 II (not found in docs/29-37, docs/offline, memory notes or source):

1. **SRM "CaptureWork" allocator as a frame pool** — ~20 MB contiguous on M50 mk1, coexists with H.264 and stills. Would add roughly 7 extra 2.8 MB frames of queue without touching the tiny malloc pool. Stay at or below 19 buffers.
2. **Probe the RscMgr map and borrow MOVIE_RECWORK** (kitor's idea, untested by anyone): allocate a token from the owning pool first so the region can be returned.
3. **`edmaclog` trace of Canon's own per-frame EDMAC calls** in movie LV, with and without `lv_save_raw`. This is the direct way to see what the Canon raw channel does when our MvRawPro storm / redirect conflict happens.
4. **FS-ready gate instead of `msleep(10000)`**: poll a FIO first-entry call (or find Canon's mounted flag) before module load; audit `if (handle)` checks, since handle 0 is valid and errors are -1.
5. **Good-vs-bad binary diff for the symbol-shift crash**: keep `magiclantern.bin` + `objdump` + `.sym` of every build that boots and every one that does not; kitor names this as the experiment he never ran.
6. **REC-key handling**: find the press (not unpress) code for REC in movie mode and consume it in the module, or deliberately let H.264 run as a proxy (works on R and M50 mk1).
7. **`CONFIG_CRASH_LOG`** as a second crash sink next to our abort handler (names says it is safe and catches the usual D8 crash); currently `#undef`.
8. **Core-side cache-sync export for modules** (names: module tasks cannot do cache ops). Relevant to `raw_vidx`'s synchronous CPU copy from an uncacheable source to a buffer later written by DMA.
9. **Pitch reduction on `0xd0420200`** to get clean 10/12-bit — recorded here only as a known dead end (tilted image); not worth trying before 14-bit is stable.

Already done or confirmed (no action): WakeSubChips wrap, no-mask rectangle copy, `lv_set_mm`, shamem guard, WINSYS dirty-bit fake, `-Wnull-dereference`, `struct tm`, no bootloader stubs, `fio_malloc` buffers, uncacheable FIO writes.

Things the community says NOT to do: `SRM_AllocateMemoryResourceFor1stJob` (factory path, returns nothing on D8); `smemFactory2` / `SRM_ChangeMemoryManagementForFactory` (instant lock + Err70); `shoot_malloc` leaks; MMU patches on hardware before QEMU; passing NULL to `raw_lv_redirect_edmac`.
