# A11 - Canon task table vs ML task priorities (M50 II 1.0.1)

## Question
Which Canon tasks matter to raw video (Evf, LiveView, movie recorder, file/storage, PropMgr, GUI, CtrlSrv, MPU, DAF, EIS), with what priority / stack / entry; what priorities do ML and the raw modules use; which ML task can starve which Canon task; what priorities should the raw_vidx copy and write tasks have.

## Summary
- 184 task-creation sites recovered statically (all BLs to `task_create` 0xE05F40BA, `task_create_ex` 0xE05F42D2 and five wrappers), arguments resolved by interprocedural constant propagation; full table in the appendix.
- Canon's LiveView core sits at 0x0D-0x14: EvfCap 0x0D, EvfDev 0x0E, EventMgr 0x0E, Epp 0x0F, ISManager 0x10, DAF 0x11, MovieRecorder 0x11, EIS/AlgsMgr/ImageCodec/DAFPath 0x13, PropMgr/Imager/LVEZM/FileCache 0x14. Canon's own bulk movers (Fwrite, MovWriter) run at 0x15; GuiMainTask 0x17, CtrlSrv 0x18, FileMgr/Fstorage/Fcreate/Fread 0x19, DOSDriver 0x1A.
- raw_vidx `raw_v_worker` (0x11, does the inline 4 MB frame copy) is numerically above PropMgr, Imager, EIS, AlgsMgr, DAFPath, Fwrite, GuiMainTask, CtrlSrv, FileMgr and level with DAF and MovieRecorder; it cannot preempt EvfDev/EvfCap.
- raw_vidx `raw_write` (0x1A) cannot starve any LV/file task; it is itself below ML's `livev_hiprio_task`/`focus_task` (0x18), `clock_task` (0x19) and level with ML `menu_task`/`shoot_task`/`cls_task` and Canon DOSDriver.
- Recommendation (static, needs an A/B on hardware): copy 0x15, write 0x16. Nothing here proves runtime behaviour; plain `task_create` tasks are unpinned on a 2-core SoC, which weakens every starvation argument.

## Inferred
- CtrlSrv priority 0x18: `CtrlSrv` creator 0xE0680C28 takes prio in r0 = `[sp+0x58]` of 0xE018A8B0, i.e. word 2 of an 0x18-byte block; that block is built in create_gui_main_task (0xE021DC70 stores r6 at +8) from stack arg 4, which its only caller 0xE0040648 sets to 0x18. Chain crosses a GUI message hop (0xE021E586), so one indirection is assumed, not followed instruction by instruction.
- Where two values are listed (EvfDev "0xE | arg", PropMgr "0x14 | arg", CSMgrTask 0x1C|0x1E, RTCMgr) there is a second creator entry with no direct BL caller (reached by pointer); the listed constant is the one from the direct boot-time caller.
- Scheduling: DryOS is strict-priority preemptive, so a CPU-bound task at priority P delays every ready task with a larger number on the same core. Tasks made with plain `task_create` are unpinned and may migrate between the two cores (per the scheduler RE recorded in src/init.c:351-359), so one busy ML task does not necessarily stall a lower-priority Canon task. Same-priority behaviour (FIFO vs time slice) is not established.
- What raw_vidx can delay today:
  - `raw_v_worker` 0x11 while running its per-frame memcpy: DAF and MovieRecorder (equal), AFTask, DAFDelivererTask, Gmt, Disp*, RscMgr (0x12), EIS, AlgsMgr, ImageCodec, DAFPath (0x13), PropMgr, Imager, LVEZM, FileCache (0x14), Fwrite, MovWriter (0x15), GuiMainTask (0x17), CtrlSrv (0x18), FileMgr, Fstorage (0x19), DOSDriver (0x1A), and its own `raw_write` (0x1A). It cannot delay EvfCap/EvfDev/EventMgr/Epp/ISManager.
  - `raw_write` 0x1A: only tasks at 0x1B+ (TempSvc, CSMgrTask, HotPlug, PowerMgr, ML console/log/heartbeat/serial shell). The serial shell at 0x1F losing CPU during a long write would look like a harness hang.
  - `raw_write` is delayed by everything at or above 0x1A, including ML's own `livev_hiprio_task` (0x18), `clock_task` (0x19), `shoot_task`/`menu_task`/`cls_task` (0x1A peers) and by `raw_v_worker`'s copy. That fits the "queue fills, copy+write slower than fps" residual: the writer is the lowest-priority party in the pipeline.
  - mlv_lite's `compress_task` at 0x0F outranks ISManager, DAF, MovieRecorder, EIS, PropMgr; `cpu_copy` at 0x17 outranks only GUI/CtrlSrv/file tasks.
- The raw_vid_worker.h comment "Canon LV tasks ~0x0-0x13" is close: the observed band is 0x0D-0x14 (PropMgr, Imager, LVEZM at 0x14). The earlier 0x09 write priority was above EvfCap/EvfDev, consistent with the EvfDevState queue-overflow asserts described there.

## Unknown
- DryOS default stack `[0x5BD8]` and max priority `[0x5BDC]` (runtime values).
- Priorities marked `?` in the appendix (LensCPUComTask, LensDeliverTask, FmCopy, MovPlay, ComMgr, audio tasks, UartLog) - passed through pointers or structures not followed.
- Whether FIO_WriteFile executes entirely in the caller's task or hands work to DOSDriver (0x1A), FileCache (0x14), Fwrite (0x15) or CSMgrTask (0x1C/0x1E). If any stage runs in CSMgrTask, a writer at 0x1A outranks it.
- Actual per-task core placement at runtime, and whether equal-priority tasks time-slice.
- Whether tasks created later at runtime (movie start, LV start) exist that are created through pointers my BL scan cannot see; the scan covers direct BL only, ROM0 only.
- How long the 4 MB uncacheable-source memcpy takes, i.e. how long 0x11 actually holds a core.

## Implications for raw video
- Keeping `raw_write` far below the LV band was the right direction, but 0x1A overshoots: it now sits under ML's own overlay/menu tasks and level with Canon's DOSDriver. Canon runs its own writers (Fwrite, MovWriter) at 0x15, just under the LV band; that is the natural slot.
- The copy runs at 0x11, level with DAF/MovieRecorder and above PropMgr/Imager/EIS/AlgsMgr. If the intermittent MvRawPro storm is a Canon job race, a 0x11 CPU-bound copy delaying PropMgr (0x14) and Imager (0x14) delivery is a plausible contributor. This is a hypothesis, not a finding.
- Recommended starting point: copy task 0x15 (below PropMgr/Imager/LVEZM at 0x14, level with Canon's Fwrite/MovWriter, above GUI), write task 0x16 (below the copy and below Canon's writers, above GuiMainTask 0x17 and all ML overlay tasks). If the queue-monitor role of `raw_v_worker` needs to stay responsive, split it: monitor stays 0x11 (it only blocks on a queue), copy moves to its own 0x15 task. If 0x16 makes the GUI laggy, 0x19 is the fallback (still above ML's 0x1A group).
- Do not go above 0x0F with anything CPU-bound; 0x0D/0x0E is EvfCap/EvfDev/EventMgr.
- Module-only change (raw_vid_worker.h constants), so it respects the "keep core unchanged" rule.

## Next hardware checks
1. `rd 0x5BD8` and `rd 0x5BDC` - default task stack and max priority. Decides what "stack 0" means for PropMgr/FileMgr/EvfDev-class tasks and the legal priority ceiling.
2. Confirm the table at runtime: walk the task list (tskmon, or read task structs from `current_task` 0x1028 / `task_max` 0x4108; this report first said 0x40CC, which is refuted statically, see A14a, F7 and D7-critic section 4 item 1) and print name, priority, cpu_requested/cpu_assigned for EvfDev, EvfCap, PropMgr, MovieRecorder, MovWriter, Fwrite, FileMgr, CtrlSrv, DOSDriver, CSMgrTask. Any mismatch with the table falsifies the static resolution for that row; CtrlSrv (0x18) is the one to check first.
3. During a raw_vidx recording, log which task name is current inside FIO_WriteFile's lowest layer (or sample `current_task` from the heartbeat at 0x1F): tells whether the write runs in `raw_write` or in a Canon task, which decides whether WORKER_WRITE_PRIO matters at all.
4. A/B, module-only, same card and scene, 10 runs each, count MvRawPro storms / EvfDevState asserts / frames before queue-full: (a) current 0x11 copy + 0x1A write; (b) 0x11 monitor, 0x15 copy, 0x16 write; (c) 0x15 copy, 0x19 write. Fewer storms in (b)/(c) supports the PropMgr/Imager-delay hypothesis; no change points back to the lv_save_raw race itself.
5. Time one frame copy (get_ms/us around the memcpy in worker.c) at 0x11 and at 0x15: if the 0x15 copy time grows by more than a few ms, Canon's 0x12-0x14 tasks are preempting it and frame budget becomes the constraint.
