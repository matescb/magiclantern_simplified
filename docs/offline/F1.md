# F1 - Selectable per-frame hook source (EvfDevState 6/3 or EvfState input 5), and the Mem1Path alternative

Offline work only. No camera was attached. Nothing in this report is proven on the camera: the ROM
facts are static disassembly, the code is built and layout-checked but has never run.

## Question

Magic Lantern (ML) needs one callback per LiveView frame (the "vsync hook") to drive raw recording.
On the M50 Mark II the hook currently sits on the state object `*(0x10108)`, input 6 in state 3.
Report A2 says that this is the wrong object. This task: re-verify A2 from the ROM, add a
runtime-selectable alternative hook on the object A2 identified, measure what the core change does
to the symbol layout, describe a third option (the EDMAC channel-3 completion callback in Mem1Path)
that needs no core change, and list the hardware probes that decide between the three.

Terms used below:

- **State object**: a Canon structure of 0x20 bytes holding a transition matrix and a current state.
  Events ("inputs") are fed to its dispatch function, which looks up
  `matrix[input][current_state] = {next_state, action}` and calls `action`.
- **Dispatch pointer**: the word at offset +0x0C of a state object; it points to the dispatch function.
  ML's hook works by overwriting this word in RAM.
- **TaskClass**: Canon's wrapper around a task with a message queue; the task receives events and
  hands each to a handler function.
- **Spy**: ML's replacement dispatch function `stateobj_lv_spy` (src/state-object.c), which calls
  the original dispatcher and then runs ML's per-frame work (`vsync_func`).
- **EDMAC**: Canon's DMA engine that writes image data to memory; "channel 3" is the write channel
  used for the LiveView raw frame (A1).

## Summary

1. A2's identification is confirmed from the ROM. `*(0x8E8C)` is the state object "EvfState",
   matrix 0xE0B5050C, 17 inputs x 8 states; input 5 is `evfReadOutDoneInterrupt` (0xE06EF732), a
   self-transition in states 3, 4, 5 and 6; it is dispatched in the task "EvfCap" (priority 0x0D).
2. Implemented on branch `offline-evfstate-1` (worktree /mnt/data/WORK/eos/wt/F1, commit c444ae918):
   global `m50ii_vsync_src`, default 0 = existing EvfDevState 6/3 hook (behaviour unchanged),
   1 = EvfState input 5. Setting the variable over the serial shell (`wr`) makes the spy move itself
   to the other object on the next event; only one object carries the spy at any time.
3. The change is 52 added lines in two files but it moves 494 of 1307 core symbols (+160 bytes of
   code). The symbol gate (tools/symgate) therefore FAILS by design. Full list:
   /mnt/data/WORK/eos/docs/offline/F1-symgate.txt.
4. Both state-object hooks and the Mem1Path callback can be installed from module code alone (zero
   core symbols moved). That is the lower-risk way to run the first hardware comparison; the core
   branch is the cleaner long-term form.

## Observed (ROM, static)

### State-object layout and dispatch
- The creator function 0xE05BB31A is called at 0xE06EEC48 with r0 = name (`*(matrix-4)`), r1 = 0,
  r2 = 0xE0B5050C (literal at 0xE06EF038), r3 = 0x11, `[sp]` = 8; the result is stored to 0x8E8C
  (0xE06EEC4C..0xE06EEC4E). So the object has 17 inputs and 8 states.
- The word at 0xE0B50508 (matrix-4) is 0xE137558C, which is the string "EvfState".
- The dispatch wrapper 0xE05BB298 checks the magic word at object +0 against `*(0xE0A6C4CC)` and then
  calls the function pointer at object +0x0C (0xE05BB2AC..0xE05BB2AE: `ldr r4,[r0,#0xc]; blx r4`).
  This is the pointer ML replaces. The stock value is 0xE05BB2B3 (function at 0xE05BB2B2). Both
  EvfDevState and EvfState are made by the same creator, so both hold the same stock pointer; that
  is what `stateobj_start_spy` requires (src/state-object.c, "all states use the same transition
  function" check).
- 0x8E8C is also the base of a larger EvfState context: the code reads `[0x8E8C+0x1C]`, `+0x20`,
  `+0x24`, `+0x28`, `+0x34`, `+0x38`, `+0x40` (0xE06EF750..0xE06EF7C6, 0xE06EEC70). Only the word at
  +0 is the state-object pointer.

### Matrix 0xE0B5050C, row for input 5 (raw dump, 8 cells of {next_state, action})
| state | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| next | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| action | NULL | NULL | E06F0355 | E06EF733 | E06EF733 | E06EF733 | E06EF733 | E06F0355 |

- 0xE06EF732 prints the string "evfReadOutDoneInterrupt" (adr at 0xE06EF748 -> 0xE06EFB2C) and
  asserts with line 0x49F if its object argument is NULL (0xE06EF738).
- 0xE06F0354 fills states 2 and 7; A2 names it evfIgnore (not re-checked here).
- Rows 4 and 6 have the same shape with actions 0xE06EF51F and 0xE06EF7E9. The whole 17 x 8 dump
  matches the table in A2.
- Inside the action, two paths call the EvfCap handler 0xE06CAFB8 again (0xE06EF788 with input 3,
  0xE06EF79A with an input read from a table at 0x8E8C+0x5C). So a hook on this object sees
  nested dispatches: a second transition can start before the input-5 transition has returned.

### Which task dispatches it
- EvfState is created from inside the EvfCap object creator: 0xE06CB01A `bl 0xE06EEC38`, result
  stored at owner +0x0C. The same function then calls CreateTaskClass 0xE05B9E60 with name
  `*(0xE099F088)` (A2: "EvfCap"), stack 0xC00, queue length 0xC8 and handler 0xE06CAFB9
  (0xE06CB028..0xE06CB038) and stores the owner at 0x554C (0xE06CB056).
- The only boot caller passes priority 0x0D and init priority 0x13: 0xE0041CDE..0xE0041CE6.
- Handler 0xE06CAFB8 calls the dispatch wrapper on `[*(0x554C)+0xC]` (0xE06CAFC8..0xE06CAFCC). The
  transition, and therefore ML's spy, runs in the EvfCap task.
- Event 5 is posted by 0xE06EEDAC: `TryPostEvent([obj+8], obj, 5, 0, 0)` (0xE06EEDBA..0xE06EEDC0);
  a failed post asserts with line 0x1CE (0xE06EEDCE). TryPostEvent is the non-blocking post
  0xE05B9F9E. The only reference to 0xE06EEDAD is the literal at 0xE06F015C, loaded at 0xE06EFF1E
  and passed with the EvfCap object to the registration function 0xE070747A on the object at
  `[0x8E8C+0x40]`. The posters for inputs 4 and 6 (0xE06EED7E, 0xE06EEDDA) sit next to it.

### Mem1Path completion callback
- 0xE0753D9C: `if ([0x10238+0x64]) tail-call [0x10238+0x64]([0x10238+0x68])`. The slot is RAM
  0x1029C and its argument is RAM 0x102A0.
- 0xE07541A4 writes both words (`strd r0,r1,[0x10238+0x64]`); 0xE07541AC clears both.
- 0xE06AD6EE..0xE06AD6F0 installs 0xE06AD51B (A1: `imagerMem1PathWrDmacCompleteCBR`).

### ML source
- src/state-object.c (baseline a10b16c23): the M50mk2 branch tests
  `self == EVF_STATE && input == 6 && old_state == 3` and calls `vsync_func()` after Canon's
  dispatcher returned. `state_init` waits up to 10 s for `EVF_STATE` to be non-NULL and then calls
  `stateobj_start_spy`, which saves the stock dispatch pointer in the static `StateTransition` and
  writes the spy's address to object +0x0C.
- platform/M50mk2.101/include/platform/state-object.h:7 defines `EVF_STATE` as `*(0x10108)`.
- src/serial_shell.c:465-524 (`statespy`) hooks an arbitrary state object the same way and restores
  the pointer it saved; src/serial_shell.c:554 is the `wr` (memory write) command.

## Inferred

- The poster 0xE06EEDAC is registered as a callback for a hardware event and probably runs in
  interrupt context; the action name says "ReadOutDone". The actual interrupt source and its phase
  relative to the raw EDMAC write were not traced (function 0xE070747A not decoded).
- Steady LiveView keeps EvfState in state 5 (A2). The new hook accepts states 3..6 because the
  matrix has the same action in all four, and because the steady state has not been read on
  hardware. States 3 and 6 are mode-change states (A2), where the raw buffer may be in flux.
- Input 5 fires once per frame. Not provable statically.
- `vsync_func` in the EvfCap task has the same stack budget as today (both tasks have 0xC00 bytes
  of stack per A2), but EvfCap has higher priority (0x0D versus 0x0E) and is the producer of
  EvfDev's messages. Blocking in the hook on EvfCap stalls the EvfCap queue (200 slots, assert
  line 0x1CE on a failed post) instead of the EvfDev queue.

## Unknown

- Whether hooking EvfState's dispatch pointer is harmless on this body (older notes mention an
  "EvfCap crash" on other DIGIC 8 cameras, platform/M50mk2.101/internals.h:38-41).
- Whether any code calls the dispatcher of either object from a task other than its owner.
- Whether the frame in `raw_info.buffer` is complete at input 5, or only at the channel-3 callback.
- In which context (interrupt or task) the Mem1Path callback runs.

## The core change (branch offline-evfstate-1, commit c444ae918)

Files: src/state-object.c (+46/-2), platform/M50mk2.101/include/platform/state-object.h (+6).

- New macro `M50II_EVFCAP_STATE` = `*(struct state_object **)0x8E8C`. `EVF_STATE` is unchanged, so
  every other use of it (src/raw.c:231, src/edmac-memcpy.c:386, the generic
  `input == 4 && old_state == 5` block) behaves exactly as before.
- New global `volatile int m50ii_vsync_src` (requested source; 0 = EvfDevState, non-zero =
  EvfState) and static `m50ii_vsync_src_now` (source whose object carries the spy).
- `m50ii_vsync_src_poll()` runs inside the spy after Canon's dispatcher returned. If the request
  differs from the active source and both objects exist, it restores the stock dispatch pointer on
  the old object first, then writes the spy to the new object. It never blocks and does nothing
  when the request equals the active source (one compare per transition).
- The per-frame test becomes: source 0 -> `self == EVF_STATE && input == 6 && old_state == 3`
  (unchanged); source 1 -> `self == M50II_EVFCAP_STATE && input == 5 && 3 <= old_state <= 6`.
- Boot is unchanged: `state_init` still waits for `EVF_STATE` and hooks only EvfDevState.

Properties and limits:

- Only one object is hooked at a time: the unhook store precedes the hook store, and the function
  is entered only from the spy, that is from the task of the currently hooked object.
- The switch refuses to act (and retries on the next event) if the old object's dispatch pointer is
  not the spy or the new object's is not the stock dispatcher. This prevents corrupting a serial
  `statespy` chained on either object. Consequence: run `statespy off` before switching.
- The switch needs an event on the currently hooked object. Outside LiveView neither object
  receives events, so a `wr` done there takes effect at the first event of the next LiveView start
  (EvfDevState receives inputs 0..5 while LiveView starts, before any frame). Switching back from
  1 to 0 likewise needs an EvfState event.
- Nested dispatches inside input 5 (see Observed) pass through the spy with other inputs; they do
  not trigger `vsync_func`.

Use on hardware (addresses belong to this build only; resolve from the build's `.sym`):

```
wr 0x14C360 1          # m50ii_vsync_src = 1 (EvfState input 5); 0 switches back
rd <*(0x8E8C)>+0xC     # expect 0x000E1991 (stateobj_lv_spy | 1) once switched
rd <*(0x10108)>+0xC    # expect 0xE05BB2B3 (stock dispatcher) once switched
```

## Module-only alternatives (not implemented)

### A. EvfState input 5 from module code
The serial `statespy` command proves the mechanism needs no core support. In raw_vidx: read
`obj = *(0x8E8C)`; if non-NULL and `obj+0xC` holds 0xE05BB2B3, save it and write the address of a
module function `spy(self, x, input, z, t)`. The spy reads `old = *(self+0x1C)`, calls the saved
dispatcher, and if `input == 5 && old in 3..6` runs the same body as `raw_vid_vsync_cbr`
(modules/raw_video/raw_vidx/event_pusher.c:310). On module unload or record stop, restore the
pointer only if it still equals the module spy. While this is active, the module's `CBR_VSYNC`
registration (event_pusher.c:498) must be ignored through a flag, otherwise both sources feed the
module.

### B. Mem1Path +0x64 (EDMAC channel-3 write-complete) from module code
1. Install, with interrupts disabled around the two-word update (`cli()` / `sei(old)`): read
   `orig_cbr = *(0x1029C)` and require it to equal 0xE06AD51B; if it is 0 (LiveView path not set up,
   see 0xE07541AC) or anything else, do not install and report. Write the module trampoline's
   address to 0x1029C. Leave 0x102A0 (the argument) untouched.
2. Trampoline `void rvx_mem1_cbr(void *arg)`: increment a volatile frame counter, store the
   27 MHz timer value if timing is wanted, set a "frame ready" flag or give a semaphore, then
   `orig_cbr(arg)`. Nothing else. Canon's own callback gives a semaphore from this context
   (0xE06AD418 per A1), so `give_semaphore` is the one kernel call known to be legal there.
   Do not post to a message queue, print, or copy from here: A3 attributes earlier crashes to
   interrupt-stack overflow from heavier calls in interrupt context.
3. A module task waits on the semaphore and does what `raw_vid_vsync_cbr` does today (event push,
   then the copy in the worker task).
4. Uninstall: with interrupts disabled, if `*(0x1029C)` equals the trampoline, write `orig_cbr`
   back. Canon rewrites the slot through 0xE07541A4 / clears it through 0xE07541AC (the call at
   0xE06AD6F0 is in LiveView::ImagerState.c per A1), so a LiveView restart or mode change may
   silently drop the chain. The module must re-check the slot whenever LiveView (re)starts and
   whenever its frame counter stops advancing, and must never write a stale `orig_cbr` back after
   Canon changed the slot.
5. The callback only fires while Canon programs channel 3, which requires `lv_save_raw(1)`
   (flag at 0x10238+0x40, A1). Enable raw first, then expect the counter to run.

Cost of A and B: zero core symbols moved; the fixed RAM addresses 0x8E8C, 0x10238 and the ROM
constants 0xE05BB2B3, 0xE06AD51B are firmware 1.0.1 specific and must be checked at install time
as described.

## Hardware probes that decide between the three sync points

All are serial-shell probes on the existing core unless noted. P = `*(0x8E8C)`, Q = `*(0x10108)`.

1. Identity: `rd 0x8E8C` -> P; `rd P+4` -> 0xE137558C; `rd P+0xC` -> 0xE05BB2B3; `rd P+0x10` ->
   0xE0B5050C; `rd P+0x14` -> 0x11; `rd P+0x18` -> 8. Any mismatch stops the EvfState option.
2. Steady state: `rd P+0x1C` several times in LiveView, in photo mode and in each video mode.
   Expect 5. A value of 4 or a value that changes means the 3..6 window must be revisited.
3. Safety and rate of the EvfState hook: `statespy P` for 10 s in LiveView, then `statespy`
   and `statespy off`. Pass: no assert in the UART log, LiveView keeps running, and the count is
   about 3 x fps x 10 if inputs 3, 4 and 5 each fire once per frame. The existing `statespy`
   records only the last input; a per-input count needs a small `exec` payload or the F1 build.
4. Per-source frame rate with the F1 build: read `vsync_counter` growth over 10 s with
   `m50ii_vsync_src` = 0 and then 1 (resolve `vsync_counter` from location.map; it is static).
   The correct source gives fps x 10 within one or two counts in every video mode, including 24p,
   25p, 50p/60p and crop modes, and gives no counts outside LiveView. Report A2 lists other senders
   of EvfDev event 6, so source 0 is expected to over-count around mode changes.
5. Mem1Path slot: `rd 0x1029C 8` in LiveView before and after `lv_save_raw(1)`, and after a
   LiveView restart. Expect 0xE06AD51B plus argument. This tells when the slot is valid.
6. Mem1Path rate: chain a counting trampoline (alternative B, via `load`/`exec` or the module) and
   compare its count over 10 s with probe 4. Equal to fps x 10 only while raw is enabled = usable
   frame-ready signal.
7. Phase / frame completeness, the deciding test: at each sync point record the 27 MHz timer
   (A9) and the first and last few words of `raw_info.buffer`, then copy the frame from a task.
   The right sync point is the one where (a) the copied frame never shows a tear line between two
   exposures under a fast pan or flicker, and (b) the timestamp follows the channel-3 completion,
   not precedes it. Expected order per frame if A1 and A2 are right: EvfDevState 6/3 (set-param,
   before readout) -> Mem1Path callback (channel-3 write complete) and EvfState input 5 (readout
   done); the order of the last two is unknown and is what this probe measures.
8. Queue health while recording with each source: `call 0xE05BA079 <TaskClass>` for EvfDev
   (`*(0x9B48)+8`) and EvfCap (`*(0x554C)+8`), per A2. Pending counts must stay near 0. A count
   climbing toward 200 on the hooked task means the hook body blocks there.
9. Storm comparison: record 30 s with each source and count the assert lines `MvRawProDs.c L:125`,
   `RawPro.c L:1C4`, `LvJob.c L:D5`, `EvfDevState.c L:174/21E` and `EvfCapState.c L:1CE` in the
   UART log. Prefer the source with zero asserts; A1 predicts that syncing to completion instead
   of to set-param removes the first three.
10. Core build only: boot the F1 autoexec.bin with its own `.sym` and modules at least 10 times and
    compare the big.8 success rate with the baseline build, before drawing any conclusion from
    probes 4 and 9 on that build.
