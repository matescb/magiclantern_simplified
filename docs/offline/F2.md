# F2 - Corrected EDMAC stubs for the hardware mem2mem copy (M50 Mark II, fw 1.0.1)

Status: static analysis and a host build only. **Nothing in this report was run on a camera.**
Branch `offline-edmacstubs` (18 characters), commit `3ba436b42`, worktree `/mnt/data/WORK/eos/wt/F2`.
The main checkout and all existing branches are untouched; nothing was pushed or flashed.

## 0. Terms

- **EDMAC**: Canon's DMA engine. A *channel* is one DMA stream; on this body channels 0-38 write to
  memory and 39-75 read from memory (descriptor table 0xE0EC37AC, 8 bytes per channel:
  `{register base, flags}`, flag bit0 = write channel, bit1 = read channel).
- **mem2mem copy**: copying a RAM rectangle by wiring a read channel (46) into a write channel (13),
  instead of a CPU `memcpy`. Implemented in `platform/M50mk2.101/edmac-d8.c:155-203`, a port of
  kitor's SX740 / bilal's M50 mk1 code.
- **Boomer**: Canon's name for the signal router between engine modules. A *node* has an input-select
  register (the "mux") and a "VdKick" start register. `edmac_select_boomer` chooses what feeds a write
  channel; the *selector* is the 32-bit argument that names the source.
- **Stub**: a line in `stubs.S` that gives a ROM address a C name.
- **ResLock**: engine resource lock (`CreateResLockEntry` / `LockEngineResources` / `UnLock...`).
- **mk1**: Canon EOS M50 (firmware 1.1.0), whose port (`research/bilal_M50_rawvideo/platform/M50.110`)
  has working mem2mem. No mk1 ROM is on disk, so mk1 function *bodies* could not be compared; only
  stub addresses (relative offsets between sibling functions) and mk1 C source were available.

The old mk2 stubs break the pattern: `vdkick` sat 0xA48 *before* `UnregisterCBR` and `select` 0xB94
before `stop_boomer`, i.e. in a different source file. Larger distances (for example
`set_address - stop_boomer` = 0x540 on both references, 0x3CC on mk2) differ, so Engine::Edmac.c was
edited between the bodies; only local deltas are meaningful.

## 3. Function-by-function verification

### 3.1 `edmac_select_boomer` -> 0xE05B802E (Observed)

- 0xE05B802E(channel, sel): requires descriptor flag bit0 and a node != -1 in table 0xE0EC3BD4
  (stride 12), else assert `Engine::Edmac.c` 0x301 (0xE05B8054-0xE05B806C). If `sel & 0xFF00` is
  nonzero it must equal row[+4], else 0x304 (0xE05B807A-0xE05B808C). `row[+8] & (sel & 0xFFFF0000)`
  must be nonzero, else 0x306 (0xE05B8090-0xE05B80A4). Then register `+0xB4 := 2` (0xE05B80AC) and a
  tail call to 0xE0683CA0 with `row[0] | (sel & 0xFF)` (0xE05B80B2-0xE05B80BE).
- Row 13 of 0xE0EC3BD4 is `{0x000C0000, 0x100, 0x20000000}`; channel 13 descriptor is
  `{0xD0420C00, flags 5}`. So 0x373F0126 passes: 0x0100 == 0x100, 0x373F0000 & 0x20000000 != 0.
  0x373F0226 would assert 0x304.
- 0xE0683CA0 (`Engine::BoomerSelector.c`) writes the low 16 bits to the mux register of node
  `arg >> 16` (table 0xE1086394; node 0xC -> 0xD042327C) and **asserts line 0x10C when the register is
  already nonzero and the new value is nonzero** (0xE0683CAE-0xE0683CBE).
- The old stub 0xE05B752E uses table 0xE1087A8C (stride 0x14); row 13 there is
  `{0x004E0000, 0x200, 0x00040000, 0xE05B75D7, 0xE05B763B}` = boomer node 0x4E (mux 0xD0441268), a
  different module. Hardware history agrees: `tools/mlserial/run/uart.jsonl` contains 20 x
  `Engine::Outer.c L:000000CD` and 2 x `Engine::Outer.c L:000000A0`, which only this function raises.
- Canon usage: 0xE00BEE3A-0xE00BEE3E loads `(channel [0x1A724+0x10], 0x017F0118)` and calls 0xE05B802E.

### 3.2 `edmac_reset_boomer_vdkick` -> 0xE05B7FB6 (Observed, identity Inferred)

- 0xE05B7FB6, 0xE05B7FDE and 0xE05B8006 are three identical wrappers: look up row[0] of 0xE0EC3BD4 for
  the channel, assert Edmac.c 0x2E7 / 0x2EE / 0x2F5 when it is -1, then tail-call 0xE05B56CC (VdKick
  register := 0), 0xE05B56F6 (:= 1) and 0xE05B5720 (:= 0 then 1) respectively. Those leaves are in
  `Engine::BoomerVdKick.c` and assert 0x141 / 0x14A / 0x153 when table 0xE1086A9C does not mark the node
  as present. Node 0xC is present: row = `{1, 0xD0423124, 0xD0423128}`.
- Why the first one: (a) it is exactly `UnregisterCBR + 0x4E`, the mk1 and SX740 delta; (b) mk1 and
  SX740 both have 0x7E bytes between their `vdkick` and `select` stubs, room for three such wrappers, so
  their stub is the first of the group, as 0xE05B7FB6 is here; (c) Canon calls 0xE05B7FB6 and then
  0xE05B802E on the same channel (0xE00BEE20, 0xE00BEE3E); (d) "reset" fits "write 0".
- Unknown: whether the mk1 group has the same order (off, on, pulse). The old (wrong-table) stub reached
  the *pulse* leaf 0xE05B5720. If the copy does not start, 0xE05B8006 is the first thing to try.

### 3.3 `StartEDmac_maybe` -> 0xE05B82AE (Observed)

- Old 0xE05B9690: `ldrb flags; lsls #0x1e; bmi` - asserts `Engine::Edmac.c` 0x770 unless flag bit1 (read
  channel) is set, then writes 0x11 to register +8 (0xE05B9696-0xE05B96B4). `edmac-d8.c:185` calls it
  on write channel 13 (flags 5), so it asserts on every copy and overwrites the prepared +8 value. The
  UART history has 21 x `Engine::Edmac.c L:00000770`. It has one caller in the whole ROM.
- New 0xE05B82AE: calls 0xE05B7B08 (register +4 := 0), 0xE05B7AA4 (reset pulse 0x80000000 then 0 on
  +0x18), then for a read channel tail-calls 0xE05B7A6C (+4 := 1); for a write channel it sets
  `+0xB4 := 1` if `(+0xC4 & 0x80) == 0` (helper 0xE05B995C). No assert on either direction.
- Canon's sequence at 0xE00BF3FE-0xE00BF454: 0xE05B82AE on the write channel `[0x1A724+0x10]`, then on
  the read channels `[+8]` and `[+0xC]`, then 0xE05B7A32 on the read channels. That is the same shape as
  `edmac-d8.c:185-187` (Start WR, Start RD, ConnectRead RD).
- Inferred: 0xE05B82AE is the mk1 `StartEDmac_maybe` homolog (delta -0x1E0 vs -0x1E2, 267 callers).
  Unknown: `+0xB4` is set to 2 by select and back to 1 here; Canon does the same on its own write
  channel, but what 1 vs 2 means was not established.

### 3.4 `ConnectReadEDmac_maybe` -> 0xE05B7A32 (MEDIUM confidence)

- Old 0xE05B95E4: asserts 0x74D unless read channel, clears 0x300 in +0xC4, kicks 0xC1100730, `+0xB4 := 1`.
  It does not assert on channel 46, but it has two callers and belongs with 0xE05B9690.
- New 0xE05B7A32: asserts Edmac.c 0x3AC unless read channel, `+8 := 0x12`, kick 0xC1100730 := 0,
  `+0xB4 := 1` (0xE05B7A32-0xE05B7A6A). It is what Canon calls after 0xE05B82AE (3.3).
- Conflict, stated plainly: the mk1 delta `reset_channel - 0x3A` lands on 0xE05B7B08, a 12-byte leaf
  that only writes `+4 := 0`. Calling that last on the read channel cannot start a transfer as far as I
  can tell, so I rejected it. Both readings fit the 0x3A gap (0xE05B7A32 is 0x3A bytes long; 0xE05B7B08
  plus the next function 0xE05B7B14 is also 0x3A). Without an mk1 ROM this is not decidable. I changed
  the stub because the pair (0xE05B82AE, 0xE05B7A32) is an observed Canon pairing, while the mixed pair
  (0xE05B82AE, 0xE05B95E4) is observed nowhere. Section 6 step B5 tests this by hand before any
  recording.

### 3.5 Resource lock (Observed)

- 0xE05BE6A6: checks magic against `[0xB0F0+4]` (returns 7), takes the recursive lock, calls
  0xE05BE638; on code 0x1F it queues the entry, creates a semaphore (0xE05CC618), and calls
  `take_semaphore` 0xE05D0DA8 with r1 = 0 (wait without limit); then state := 2. 105 callers.
- 0xE05BE8A6: same prologue, but on 0x1F it releases the recursive lock and returns 0xD at once
  (0xE05BE906-0xE05BE90C). Zero direct callers and zero literal-pool references to 0xE05BE8A7.
- 0xE05BE5A2: magic check (7), returns 0xD if state == 2, else frees `[entry+0x14]` and the entry.

## 5. Why `LockEngineResources` was left on the try-lock

1. Making it selectable at run time needs new code in `edmac-d8.c`, which would move core symbols; the
   project rule is to keep the core layout fixed. Stub-only changes keep it fixed (section 4).
2. The resource IDs `{0x100AD, 0x100BB}` (`edmac-d8.c:82`) are copied from other bodies and are not
   verified for this one (A12). A blocking lock on IDs that LiveView owns would stop the calling ML task
   with no timeout (0xE05BE728); a lock on IDs nobody uses changes nothing.
3. The try-lock cannot hang. Its weakness is that a 0xD result is ignored (`edmac-d8.c:222`).
4. The blocking variant is one stub edit away (swap the two addresses in `stubs.S`; no layout change),
   and both it and `DeleteResLockEntry` can be called by address from the serial shell.

Recommendation: decide after test B6 below shows what the try-lock returns.

## 6. Hardware test sequence

Addresses below are for this build (ML core layout equals the baseline): `m50ii_edmac_cpu_copy`
0x105A20, `m50ii_edmac_skip_reslock` 0x14FA3C, `mem2mem_devices` 0xF5088, `mem2mem_lock` 0x14FA40,
`run_test` 0xD7128. Thumb functions are called at address + 1. Serial commands are
`python3 tools/mlserial/mlserial.py cmd "..."`.

### A. Preparation

1. The source is committed (`3ba436b42`). Put this build's `autoexec.bin`, `.sym` and modules on the
   card; run `check_card_image.py` on the staging directory first.
2. Cold boot until the boot log reaches `big.8`. Photo mode, LiveView idle, not recording.
   Confirm the default: `rd 0x105A20` -> 1. With nothing else touched the camera must behave as before.

### B. Stub probes by hand (no copy yet)

1. `call 0xe06b934f 0xF5088` (wake EDMAC sub-chips 0 and 7). Required before any EDMAC register
   access; kitor's note says access without it hard-locks the camera
   (`research/kitor_edmac_sx740/platform/SX740.102/edmac-d8.c:33-37`).
2. `rd 0xD042327C` -> expect 0. A nonzero value means Canon already uses boomer node 0xC; stop, because
   step 4 would assert `Engine::BoomerSelector.c` 0x10C.
3. `call 0xe05b7b43 13` (prepare), `call 0xe05b7fb7 13` (VdKick off) -> no assert; `rd 0xD0423124` -> 0.
4. `call 0xe05b802f 13 0x373f0126` -> no assert; `rd 0xD042327C` -> 0x26; `rd 0xD0420CB4` -> 2.
5. `call 0xe05b7b43 46`, `call 0xe05b82af 13`, `call 0xe05b82af 46`, `call 0xe05b7a33 46` -> no assert
   (no address or size is set, so no data should move; if the camera reacts badly here, the Start /
   ConnectRead pair is the suspect, not the boomer pair).
6. `call 0xe05b80c3 13` -> `rd 0xD042327C` -> 0 and `rd 0xD0420CB4` -> 0.
   Lock probe: `call 0xe05be4bf 0x105A18 2` (returns an entry pointer E), `call 0xe05be8a7 E` -> 0
   means the try-lock got the resources, 0xD means they are busy, 7 means a bad entry. Then
   `call 0xe05be741 E` and `call 0xe05be5a3 E` -> 0.
7. `call 0xe06b937d 0xF5088` (suspend sub-chips), as the existing code does after a recording.

### C. Small copy: the built-in self-test

`run_test` (`src/debug.c:350-395`) copies a 512 x 8 byte pattern through
`edmac_copy_rectangle_cbr_start` and compares.

1. `wr 0x105A20 0` (select the mem2mem path). Leave `m50ii_edmac_skip_reslock` at 0.
2. Start it from ML menu -> Debug -> "Don't click me", or `call 0xd7129`. The serial `call` blocks the
   shell until `run_test` returns (it also runs `dumpf`, a file write); earlier notes say blocking
   callees can wedge the shell, so prefer the menu.
3. Pass: UART line `[R1] EDMAC mem2mem self-test PASS: N=4096 mism=0 first=-1`, no assert, LiveView
   keeps running. Repeat five times (each run must end with mux 0xD042327C back at 0).
4. `wr 0x105A20 1` to restore. Note that with the default value 1 this self-test is not a valid
   control: the CPU copy is asynchronous and the comparison runs before the worker finishes.

### D. Full frames (only after C passes)

1. `mlv_lite` is the module that calls `edmac_copy_rectangle_cbr_start` per frame; load it instead of
   `raw_vidx`. Movie mode, `wr 0x105A20 0`, record about two seconds, stop.
2. A correct result: `python3 tools/mlvcheck/mlv_check.py file.mlv --stats` reports consistent blocks;
   frames extracted with `mlv_dump` show the scene, with neighbouring rows of the same colour plane
   strongly correlated and values inside the 14-bit black/white range. The known bad result is a frame
   of ML heap contents (ASCII such as "Overlay\Cropmark", row correlation about 0.26; docs/32).
3. Compare against the same scene recorded with `wr 0x105A20 1`.

## 7. Risks

- Nothing here is proven on hardware. A wrong EDMAC call can hard-lock the camera (battery pull).
- The earlier mem2mem attempts wrote mux value 0x26 into boomer node 0x4E and pulsed its VdKick; with
  the corrected stubs that side effect disappears, so earlier conclusions about the storm and about the
  resource lock (docs/32) no longer apply and must be re-measured.
- `ConnectReadEDmac_maybe` is the weakest link (3.4). If it is wrong the expected symptom is a timeout,
  but an unintended read-channel kick could also disturb LiveView.
- `edmac_reset_boomer_vdkick` now leaves VdKick at 0 where the old stub pulsed 0 -> 1 (on the wrong node).
  If channel 13 needs the pulse, the copy times out.
- In step D the copy runs synchronously inside the per-frame callback with a wait of up to 50 ms and
  creates and deletes an event flag per frame (`edmac-d8.c:166-200`). This is the mk1 design, but on a
  timeout it stalls LiveView for 50 ms per frame.
- Resource IDs and sub-chip list `{0, 7}` are unverified for this body; the try-lock result is ignored;
  each `edmac_memcpy_res_lock` call leaks one ResLock entry (no `DeleteResLockEntry` call yet).
- Whether `PwrMng_SuspendSubChips` is reference-counted against Canon's own use is Unknown.
- Modules must be loaded with this build's `.sym`; a stale `.sym` silently routes the four names to the
  old ROM addresses.

## 8. Open questions

1. Which mk2 function is the true mk1 `ConnectReadEDmac_maybe` (0xE05B7A32 by Canon call order,
   0xE05B7B08 by position)? Needs an mk1 ROM or the hardware test.
2. Is the mk1 `vdkick` the "off" or the "pulse" wrapper?
3. Meaning of register +0xB4 values 1 and 2, and of +8 values 0x11 / 0x12.
4. Are `{0x100AD, 0x100BB}` the right resources for channels 13 / 46 here, and does LiveView hold them?
5. Does Canon use boomer node 0xC or channels 13 / 46 in any LiveView or movie mode?
